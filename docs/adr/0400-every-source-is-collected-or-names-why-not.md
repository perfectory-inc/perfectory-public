# ADR 0400: 모든 원천은 받거나, 받지 않는 이유를 카탈로그에 적는다 — 수집 완전성 판정표

- Status: Accepted
- Date: 2026-11-04
- Builds on: ADR-0086(그래프가 모든 데이터셋을 한 번 이름 짓는다), ADR-0176(생성 문서는 항목마다 한 줄),
  ADR-0355(82개 원천 판정), ADR-0348(실거래는 벌크), ADR-0359(토지대장 API 는 받지 않는다)

## Context

사장은 2026-10-30 "나는 모든 데이터 수집을 승인할게", 2026-11-03 "비용은 상관없고, 데이터를 보여 주는 것이 항상
이긴다" 고 했다. 그런데 데이터 지도(`docs/data-pipeline-map.md`)로는 "무엇을 아직 안 받는가" 에 답할 수 없었다.

- 지도의 "수집 이후 아직 연결되지 않은 데이터" 표는 **157개 endpoint 가운데 123개**를 한 목록에 섞었다.
  매일 받는 건축HUB 파일, 중복이라 일부러 끈 API 22개, 사장 신청을 기다리는 주소 전자지도 11개, 수집기가 없는
  기타 일괄 12개가 같은 모양의 줄이었다. 줄마다 `source_acquisition_lane` 하나만 있었다.
- ADR-0355 §6 이 찾은 거짓 신호("승인 후 수집 가능" 인데 수집기가 없음)는 상태 이름을 바꿔 고쳤지만, 같은 일이
  다시 생기지 않게 막는 장치는 없었다. 받지 않는 이유는 ADR 산문에만 있었다.

**측정 (2026-11-04).** 원천 카탈로그 157개를 그래프(`pipeline-graph.v1.json`)와 운영 `catalog.bronze_object`

### 실사례

- **데이터셋마다 상태와 그 이유.** LinkedIn DataHub 의 `Status`·`Deprecation` 측면과 Airbnb Dataportal 의 데이터셋
  상태는 "없는 것" 도 이유와 함께 목록에 둔다. Google 의 데이터 카탈로그(Goods, 2016)는 수집하지 않기로 한
  데이터셋을 지우지 않고 "의도적 제외" 로 표시해, 같은 질문이 반복되지 않게 한다.
- **판정은 정본에, 문서는 생성.** dbt 의 `sources.yml` `freshness`·`meta` 처럼 판정은 원천 선언 옆에 두고
  문서는 그것에서 만든다. 우리 원천 선언은 엔드포인트 카탈로그다.

## Decision

1. **받지 않는 endpoint 는 카탈로그에 이유를 적는다.** 엔드포인트 항목의 `collection_decision`
   (`verdict`, `decision`, `reason_ko`) 이다. `verdict` 는 넷 중 하나다.
   - `api_duplicate_of_bulk` (의도적): 같은 사실을 우리가 받는 전국 파일이 준다. 건축물대장 API 10개(건축HUB 파일),
     실거래가 API 12개(ADR-0348).
   - `file_covers_the_api` (의도적): 필지마다 묻는 API 의 사실을 전국 파일이 준다. 브이월드 토지대장(ADR-0359).
   - `provider_does_not_publish` (의도적): 제공자 목록에 파일이 없다. 건축HUB 연도별 에너지 2개(ADR-0355).
   - `waiting_on_owner_application` (대기): 제공처가 이용 신청·승인 뒤에만 준다. 주소정보 전자지도 11개(ADR-0355 §3).
2. **분류는 두 정본에서만 계산한다**(`scripts/catalog/pipeline_graph.py` `collection_classes`).
   - **수집·서빙**: 살아 있는(implemented·partial) 원천 엣지가 그 endpoint 를 고르고, 거기서 살아 있는 데이터 경로가
     서빙 접점(`serving_surface`)에 닿는다.
   - **수집·미서빙**: 살아 있는 원천 엣지가 고르거나, 매일 원천 확인이 받는 수집 방식(`bulk_file`·`provider_dataset_file`)이다.
   - **의도적 미수집**: `collection_decision` 의 판정이 의도적이다.
   - **미수집**: 그 밖 전부. 대기 판정, 꺼진 원천 엣지, 수집기가 없는 원천이다.
3. **지도는 가족마다 네 수를 한 줄로 보이고**(ADR-0176: 레인 PR 은 제 가족의 줄만 바꾼다), "아직 연결되지 않은 데이터"
   표의 줄마다 판정과 이유를 붙인다(`render-pipeline-map.py`).
4. **이유는 참이어야 한다**(`pipeline-graph-covers-every-dataset.sh` 가 거부한다). ADR-0001: ADR-0355 §6 의 거짓 신호
   — 수집기가 없는데 지도가 "승인 후 수집 가능" 이라 말한 23개 — 가 다시 생기지 않게 한다.
   - 거부 방식(`disabled_api_duplicate`·`provider_inventory_missing`)의 endpoint 는 `collection_decision` 을 반드시 갖는다.
   - `verdict` 는 위 넷 중 하나, `decision` 은 저장소에 있는 `docs/adr/` 파일, `reason_ko` 는 비어 있지 않다.
   - 살아 있는 원천 엣지가 고르는 endpoint 는 `collection_decision` 을 가질 수 없다. 받기 시작한 PR 이 판정을 지운다.
5. **이번 묶음(W8)에서 하지 않는 것과 이유.**
   - 주소정보 전자지도 11개: 사장의 business.juso.go.kr 이용 신청이 먼저다(ADR-0355 §3). 승인 뒤 첫 판을 실측하는 PR 이 수집기를 만든다.
   - KAMCO 국유·공공 부동산(국유지 매각·대부·공실·낙찰가율): 사장이 2026-10-29 "뒤로 미루자" 고 했다. 카탈로그에 넣지 않는다.
     꺼낼 때 카탈로그 항목과 함께 연다.
   - 받는 전국 파일의 API 중복 23개(건축물대장 API 10, 실거래가 API 12, 브이월드 토지대장 1): 위 1의 의도적 판정이다.
6. **기타 공공 일괄 12개**는 ADR-0401 이, **건축HUB "나중 연결" 9개**는 ADR-0402 가 잇는다.

## Consequences

- 이 ADR 의 PR 뒤 main 의 수: 수집·서빙 31 · 수집·미서빙 76 · 미수집 25 · 의도적 미수집 25. 같은 규칙을 이 PR 전의
  카탈로그에 적용하면 의도적 미수집 0, 미수집 50 이다(이유가 어디에도 적혀 있지 않았다).
- 다음 수의 움직임: ADR-0401 의 수집기가 기타 일괄 파일을 받기 시작하면 그 endpoint 가 미수집에서 수집·미서빙으로
  옮겨 간다. 레인이 화면에 닿을 때 수집·서빙으로 옮겨 간다. 건축HUB 레인(ADR-0402)은 이미 받는 파일이므로 수를 바꾸지
  않고, 화면 PR 이 수집·서빙으로 옮긴다.
- 비용 없음(문서·검사만).
