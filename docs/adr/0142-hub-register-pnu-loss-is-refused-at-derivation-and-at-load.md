# ADR 0142: 허브 대장의 PNU 손실은 조립에서 이름으로 거부하고, 적재에서 비율로 거부한다

- Status: Accepted
- Date: 2026-10-04

## Context

2026-09-27 에 `silver.building_register_titles` 가 통째로 덮어써졌다(Iceberg `overwrite`,
8,064,406 행). 그 스냅숏에서 대지구분 `0`(대지) 행의 PNU NULL 은 916,469 행이고, 그중 916,461 행이
통합 시도 12(전남광주통합특별시) 소속이다. 시도 12 의 대지 행은 **전부** PNU 를 잃었다. 직전
스냅숏의 대지 NULL 은 8 행이었다. Gold 재빌드([ADR-0139](./0139-panel-gold-is-rebuilt-when-a-silver-input-changes.md))는 이 입력으로 `gold.building_panel` 이
5,939,794 → 5,268,380 행으로 줄어드는 것을 보고 거부했다 — 그 거부가 이 결함을 드러냈다.

원인은 저장소 main 의 코드가 아니다. 증거는 이렇다.

- 스냅숏 요약에는 `foundation.ingest-write-id` 속성이 있고, 원천 스냅숏 id 가
  `building-register-title-bronze-<bronze_object_id>` 형식이다. 두 표지 모두 main 에는 없다.
  병합되지 않은 코덱스 무결성 체인지셋(로컬 커밋으로만 보존, `remote_lakehouse_job/titles.rs`)에만
  있다.
- 그 트리는 `sigungu_crosswalk.rs` 를 바꿨다. 씨앗 27쌍 전부를 "출처가 선언하지 않은 후보"로
  강등하고, `resolve_sigungu_code_via` 가 강등된 코드에 `None` 을 돌려주게 했다. 그러면 시도 12 의
  모든 시군구 코드에서 PNU 가 사라진다. 경고나 개수는 남지 않는다.
- 노트북 WSL 에서 보존된 그 실행의 핸드오프 JSONL 은 스냅숏과 행 단위로 일치한다. 행 수, NULL 965,150,
  시도 12 NULL 928,891, 시도 12 대지 NULL 916,461 이 모두 같다. 파일의 수정 시각은 Spark 앱 시작
  50초 전이다.
- 같은 트리가 2026-09-30 에 `silver.building_register_units` 도 덮어썼다. 시도 12 대지 행
  1,070,125 개가 전부 NULL 이다. 그 직전(09-26) 스냅숏의 시도 12 대지 NULL 은 0 이었다.

두 가지 구조적 구멍이 이 사고를 가능하게 했다.

1. **조립이 시도 하나를 통째로 조용히 버릴 수 있었다.** main 에서도 크로스워크에 없는 12xxx
   코드는 그대로 통과(identity)했다. 지적도에 12xxx 필지는 없으므로 결과는 고아 PNU 였다. 코덱스
   트리에서는 그 결과가 NULL 이었다. 어느 쪽도 실패로 보이지 않았다.
2. **적재 게이트는 행만 봤다.** `pnu` 는 블록(대지구분 `2`) 때문에 nullable 이다. 그래서 행 단위
   게이트는 전부 통과했다. 대지 NULL 비율이 1e-6 에서 0.116 으로 뛴 것은 아무도 재지 않았다.


## Decision

1. **통합 시도는 크로스워크가 다스린다.** `foundation_shared_kernel::pnu::SigunguCrosswalk` 는
   매핑(`current → superseded`)과 *다스리는 시도*를 함께 가진다. 다스리는 시도의 시군구 코드에
   매핑이 없으면 `UnmappedGovernedSigungu(<코드>)` 로 거부한다. 다스리는 시도로 시작하지만 5자리
   숫자가 아닌 코드도 `MalformedGovernedSigungu(<코드>)` 로 거부한다. 통과나 NULL 은 없다. 두 거부
   문구는 고칠 곳으로 `sigungu-canonical-crosswalk.contract.json` 을 이름으로 댄다. 다스리는 시도
   목록은 그 씨앗 계약의 `sido[].current_code` 에서 읽는다. 따로 적은 목록은 없다. 적재기
   `hub_sigungu_crosswalk` 는 다음 둘도 거부한다. 하나는 다스리는 시도 밖의 매핑이고, 다른 하나는
   대상이 그 시도의 `supersedes` 밖에 있는 매핑이다.
2. **다스리는 것은 선언된 통합 시도뿐이다.** 그 밖의 코드는 그대로 조립된다. 그래서 지적도에 없는
   시도의 코드가 Bronze 에 나타나면, 그 행은 NULL 이 아니라 어느 필지에도 없는 고아 PNU 가 된다.
   NULL 비율 게이트(4)는 그 행을 보지 못한다. 이 구멍은 두 가지로 막는다.
   - **자리표시자.** 허브는 시군구가 없는 행에 정해진 코드를 쓴다. 2026-09 표제부·전유부 Bronze 를
     전수로 읽어 쟀다. 지적도 시도 밖의 코드는 `99999`(표제부 969 행, 전유부 192 행), `99990`(전유부
     15 행), 폭이 틀린 `0`(표제부 1 행), `38022`(표제부 1 행)뿐이었다. 앞의 셋은 씨앗 계약의
     `placeholder_sigungu.codes` 에 한 번만 적는다. 자리표시자는 PNU 를 조립하지 않는다(NULL). 날조한
     고아 PNU 가 아니라 NULL 이므로, 그 행은 NULL 비율에 들어가 보인다. 내보내기 요약
     (`sigungu_sido.placeholder_rows`)에도 센다. `99999` 는 이 저장소가 합성 PNU 용으로 예약한 띠와
     같다. 그 띠의 실물 행이 이제 PNU 를 갖지 않는다. 그래서 합성 PNU 를 조립하는 내보내기 시험은
     정체성 크로스워크를 주입해서 돈다. 전유부·면적 계획의 ADR 0023 불변식(`pnu` 없음 ⟺ 블록)은
     자리표시자 행 하나만 예외로 받는다. 원천 행이 `sigungu_is_placeholder` 를 들고 다니고, 그 행은
     대지구분과 무관하게 `pnu` 가 없어야 한다. 있으면 여전히 거부다.
   - **지적도에 없는 시도의 행 수 상한.** 표제부·전유부·면적 내보내기는 모든 행을 원천 시군구 코드의
     시도별로 센다(`sigungu_crosswalk::SidoTally`). 지적도 시도 집합은 필지 원천 계약
     `vworld-parcel-source-objects.json` 의 `granularity: sido` 객체에서 읽는다. 따로 적은 목록은 없다.
     어떤 시도가 지적도에도 없고 통합 선언에도 없는데, 그 행 수가 씨앗 계약의 `absent_sido_row_bound`
     (10,000)를 넘으면 내보내기를 거부한다. 한계 이하인 시도(`38022` 같은 한두 행)는 통과시키되
     요약(`sigungu_sido.absent_from_cadastre_rows`)에 시도별 행 수로 남긴다. 10,000 의 근거는 이렇다.
     자리표시자를 뺀 이상 코드는 1 행이었다. 가장 작은 실제 시도는 표제부 39,178 행이다. 2026-07 통합
     시도 12 는 928,891 행으로 나타났다. 씨앗이 대체한다고 적은 시도(`supersedes`)가 지적도 집합에
     없으면, 집계기를 만들 때 거부한다. 지적도가 새 코드로 바뀌었는데 짝이 옛 코드를 가리키는 경우다.
3. **조립의 거부는 내보내기의 실패다.** 표제부·전유부·면적 계획의 `_via` 파서와 허브 공통
   내보내기(`hub_register_silver_export`)는 이 거부를 줄 번호와 함께 그대로 올린다. 전유부
   내보내기는 출력을 만들기 전에 Bronze 전체를 한 번 파싱해서 검증한다(`ParentInputs::load`). 그
   사전 검증도 실물 크로스워크와 시도 집계를 쓴다. 그래서 거부가 나면 출력 파일도 요약도 생기지 않는다.
   표제부·면적 내보내기에는 사전 검증이 없다. 크로스워크 거부는 쓰는 도중에, 시도 상한 거부는 다 쓴
   뒤에 난다. 두 경우 모두 0 이 아닌 종료와 요약 없음으로 끝난다.
4. **적재는 대지 PNU NULL 비율의 상한과 상승을 둘 다 거부한다.** 허브 대장 Silver 세 표(표제부·
   전유부·면적)는 계약 품질 게이트 하나로
   `ordinary_land_pnu_null_share <= 0.0005 and increase <= 0.001` 을 선언한다. 이 값의 정본은
   `lakehouse-domain` 의 `ORDINARY_LAND_PNU_NULL_SHARE_GATE` 하나다. `silver_scalar_handoff_to_lakehouse.py`
   는 쓰기 전에 두 비율을 잰다. 하나는 후보의 대지(`register_parcel_key` 11번째 글자 `0`) PNU NULL
   비율이고, 다른 하나는 대상 표의 현재 스냅숏의 같은 비율이다. 둘 중 하나라도 넘으면 아무것도 쓰지
   않고 실패한다(`pnu_null_share_guard.py`). 후보 비율이 상한을 넘거나, 현재 스냅숏보다 상승폭을 넘게
   높으면 거부다. 상한은 기준선 없이도 적용된다. 파일 묶음 적재는 첫 묶음을 쓰기 전에 전체를 판정한다.
   `--validate-only` 에서도 같은 판정을 낸다. 표가 없으면 `no_baseline` 이라는 이름 붙은 결과를
   출력한다.

   상승폭만으로는 부족하다. 지금 표제부의 현재 스냅숏이 바로 09-27 의 나쁜 판(비율 0.115)이다.
   같은 손실을 다시 적재해도 상승은 0 이라서, 상승폭만 보는 게이트는 그 판을 통과시켜 굳힌다.
5. **수치의 근거.** 측정값(카탈로그 읽기, 대지 행 기준)은 이렇다.

   | 판 | 대지 NULL / 대지 행 | 비율 |
   | --- | --- | --- |
   | 표제부 2026-09-03 (정상) | 8 / 7,927,468 | 1.0e-6 |
   | 표제부 2026-09-27 (현재, 결함) | 916,469 / 7,939,750 | 0.115 |
   | 표제부 main 재조립 시험 실행 (자리표시자 전) | 8 / 7,939,750 | 1.0e-6 |
   | 표제부 재조립, 이 결정의 내보내기 (측정: 8 + 958 + 1) | 967 / 7,939,750 | 1.22e-4 |
   | 전유부 2026-09-26 (정상) | 0 / 19,677,721 | 0 |
   | 전유부 재조립, 자리표시자 NULL 반영 (계산: 192 + 15) | 약 207 / 1,968만 | 약 1.1e-5 |
   | 면적 2026-09-11 (현재) | 0 / 112,644,915 | 0 |

   상한 0.0005 는 자리표시자를 반영한 표제부 재조립(1.22e-4)보다 4배 크다. 그 재조립을 09-27 판
   위에 `--validate-only` 로 돌리면 `within_bounds` 다(측정 절). 가장 작은 12xxx 시군구
   하나가 표제부 대지 행에서 차지하는 몫(약 0.2%)보다는 4배 작다. 상승폭 0.001 이면 시도 하나는 물론
   그 시군구 하나만 잃어도 걸린다. 09-27 의 상승폭은 0.116 이었다.

이 게이트가 막는 실제 사고는 2026-09-27 표제부 덮어쓰기와 2026-09-30 전유부 덮어쓰기다. 둘 다
시도 하나의 PNU 를 전부 잃은 Silver 가 정본 표에 들어갔다. 그 판들을 현재 스냅숏으로 둔 채 같은
손실을 다시 적재하는 것도 상한이 막는다.

## Consequences

- 바로잡은 표제부·전유부 Silver 는 main 의 내보내기로 다시 만든다. 쓰기 방식은 운영 결정으로 남긴다.
  `append` 로 쓰면 같은 Bronze 에서 나온 두 파생이 한 스냅숏에 공존한다. 그러면 `gold.building_panel`
  의 단일 `source_snapshot_id` 검사와 `mgm_bldrgst_pk` 유일성 검사가 Gold 를 거부한다. `overwrite`
  는 새 스냅숏을 만들고, 잘못된 스냅숏은 Iceberg 이력에 남는다.
- 다시 만든 판에서는 자리표시자 행(표제부 약 969, 전유부 약 207)의 PNU 가 NULL 이다. 지금 Silver 에
  있는 그 행들은 예약 띠 `99999…` 의 고아 PNU 를 가지고 있다.
- `SigunguCrosswalk` 가 `HashMap` 을 대신하므로 `_via` 파서 셋의 시그니처가 바뀐다. 정체성
  크로스워크는 `SigunguCrosswalk::identity()` 다.
- 새 통합 시도가 생기면 씨앗 계약의 `sido` 와 `sigungu` 를 함께 늘려야 내보내기가 돈다. 시도만
  선언하고 짝을 빠뜨리면 내보내기가 빠진 코드를 대며 멈춘다. 둘 다 빠뜨리면 시도 상한(10,000 행)이
  그 시도를 대며 멈춘다.
- 필지 원천이 새 코드로 다시 수집되면(지적도가 12xxx 로 바뀌면) `vworld-parcel-source-objects.json`
  이 바뀐다. 그때 씨앗의 `supersedes` 가 지적도에 없는 시도를 가리키면 집계기가 거부한다. 짝을 지우거나
  뒤집는 결정이 먼저다.
- **27 쌍은 파생값이다.** 씨앗의 시군구 짝은 모두 `derived:pnu-tail-join:2026-09` 이다. 허브 PNU 꼬리
  (읍면동+본번+부번)를 지적도 필지에 이어서 구했고, 기관이 발행한 값이 아니다. 시도 12 의 존재와
  29·46 폐지만 기관값(`authority:getStanReginCdList`)이다. 각 짝의 `provenance` 가 기관의
  생성·말소 파일(data.go.kr 15092039)과 대조한 출처로 바뀌어야 짝이 기관값이 된다. 그 대조는 스튜어드
  작업으로 남는다.
- `silver.building_register_unit_areas` 는 아직 2026-06 Bronze 그대로라 12xxx 행이 없다. 이 결함은
  없지만 석 달 넘게 낡았다. 다시 적재하면 이 ADR 의 거부들이 처음으로 실물에서 돈다.
- 파일 묶음 적재에서 이 게이트는 입력 전체를 한 번 더 읽는다. 그 비용은 측정 절에 적었다.
- 허브 공통 내보내기(`hub_register_silver_export`, 공동주택가격·전유부 원장)는 자리표시자 NULL 만
  받고 시도 집계는 하지 않는다. 그 표들에는 NULL 비율 게이트도 없다.

## 측정

2026-10-04, ai-server scratch, 이 결정의 코드로. 쓰기 없음(`--validate-only`, Bronze·카탈로그 읽기 전용).

- **표제부 내보내기**(2026-09 Bronze, 8,064,406 행): 150초. 요약의 `sigungu_sido` 는 자리표시자
  `99999` 969 행·`0` 1 행, 지적도에 없는 시도 `38` 1 행(한계 10,000 이하, 통과), 통합 시도 `12`
  928,891 행이다. PNU 가 있는 행은 8,026,012 다.
- **표제부 적재 판정**(`--validate-only`, 현재 스냅숏 = 09-27 판): 후보 967 / 7,939,750(1.22e-4),
  기준 916,469 / 7,939,750, 상한 0.0005, `within_bounds`. 단일 파일 적재라 가드는 8.5초, 전체 231초다.
- **면적 내보내기**(2026-06 Bronze, parquet 456 파일): 1,071초. 자리표시자 `99999` 599 행·`99990` 105 행,
  지적도에 없는 시도 0. 이 Bronze 는 통합 전이라 시도 12 가 없다.
- **면적 적재 판정과 가드 비용**(`--validate-only`, 128 파일 묶음 4개, 현재 스냅숏 2026-09-11 판):
  후보 704 / 112,644,915(6.2e-6), 기준 0, `within_bounds`. 묶음 적재에서 가드는 입력 전체를 한 번 더
  읽는다. 그 가드가 58.3초, 실행 전체가 315초로 18.5% 다. 실제 적재는 쓰기와 되읽기가 더해져 더
