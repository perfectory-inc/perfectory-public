# ADR 0553: main 이나 배포를 고치는 PR 은 큐를 비우지 않고 앞에 서고, 큐가 버린 커밋의 실행은 취소한다

- Status: Accepted
- Date: 2026-11-12
- Builds on: [ADR-0421](./0421-a-run-that-failed-only-because-its-runner-did-is-re-run-once-and-the-merge-queue-keeps-building-two.md)(일정 전용 작업의 `actions: write`),
  ADR-0552(큐는 자기 실행이 초록인 PR 만 병합, #1347)

## Context

2026-11-11 에 고치는 PR 을 먼저 넣으려고 큐를 세 번 비웠다(#1316 OSV 관문, #1337 배포 정지, #1337·#1342 함께). 큐에는
그때 15~19건이 서 있었고, 비울 때마다 돌던 큐 실행 둘이 버려졌으며 나머지는 다시 넣을 때까지 기다렸다. 같은 날 큐에서
손으로 뺀 횟수는 17번이다. `enqueuePullRequest(jump: true)` 는 #1293 에서 한 번 썼는데 "먹지 않았다"고 기록됐다.

### 측정 1 — `jump` 는 먹었다

#1293 의 타임라인과 큐 실행을 대조했다(2026-11-12, `gh api`, 읽기 전용).

| 시각 (11-11 UTC) | 일 |
|---|---|
| 06:16:03 | #1293 준비 완료 |
| 06:16:08 | `jump: true` 로 큐 투입 |
| 06:16:19 | 큐 실행 `pr-1293-a4a0b8d4` 시작. `a4a0b8d4` 는 그때 main 끝이다. 곧 맨 앞에 섰다 |
| 06:16:20 | 뒤로 밀린 #1274 가 #1293 위에서 다시 빌드 시작 |
| 06:16:22 / 06:16:24 | #1293 을 손으로 빼고 다시 넣음. 큐 실행이 06:16:41 에 처음부터 다시 시작 |
| 07:16:16 | 병합. 큐 실행 한 번이 53~60분 걸렸다(러너가 찬 시간대) |

`jump` 는 11초 만에 적용됐다. 권한 문제도 규칙 문제도 아니었다(토큰은 저장소 ADMIN, ruleset 에 우회 actor 없음).
한 시간이 걸린 것은 큐 실행 자체의 시간이고, 14초 뒤에 뺐다 넣은 것이 그 실행을 한 번 더 시작시켰다. 앞에 서도 큐는 필수
검사를 전부 돌리므로, 앞자리의 하한은 큐 실행 한 번이다.

### 측정 2 — 큐가 버린 커밋의 실행은 끝까지 돈다

큐는 항목마다 임시 브랜치(`gh-readonly-queue/main/pr-N-<base>`)에서 빌드한다. 앞 항목이 실패하거나 빠지거나 누가
앞에 서면 큐는 그 브랜치를 지우고 새 브랜치에서 다시 빌드한다. 지워진 커밋의 workflow 실행은 취소되지 않는다.

| 최근 Foundation 큐 실행 200개 (11-08 17:46Z ~ 11-12 00:52Z) | 수 |
|---|---:|
| main 에 들어간 커밋의 실행 | 121 |
| 병합될 수 없게 된 커밋에서 **성공으로 끝난** 실행 | 55 |
| 실패한 실행(main 에 없는 커밋) | 15 |

예: #1293 이 앞에 선 06:16 에 버려진 `pr-1274-a4a0b8d4` 는 06:38 까지 22분 더 돌았다. 같은 시간대에 표준 러너 20칸은
차 있었다(ADR-0552 측정 3: 큐 커밋 하나가 중앙값 88 작업·분).

## Decision

1. **큐에 넣는 길은 `scripts/github/merge_queue_enqueue.py <PR>` 하나다.**
   - 라벨 `hotfix:main-red`(main 의 필수 검사를 고친다) 또는 `hotfix:deploy-stop`(멈춘 배포를 고친다)이 붙은 PR 은
     `jump: true` 로 넣는다. 라벨이 없으면 맨 뒤에 넣는다.
   - **다른 PR 을 큐에서 빼지 않는다.** 라벨이 붙은 PR 이 이미 뒤에 서 있을 때만 그 PR 하나를 빼서 앞에 다시 넣는다.
   - **이미 앞에 선 PR 은 건드리지 않는다**(측정 1 의 06:16:22).
   - 앞에 세우면 PR 에 라벨 이름을 적은 댓글을 남긴다.
   - 우회는 없다. 초안·충돌·필수 검사 미통과는 GitHub 이 거부하고, 큐는 앞에 선 PR 에도 필수 검사를 전부 돌린다.
2. **가드(시험)**: `scripts/github/test_merge_queue_enqueue.py` 가 위 네 경우와 "스크립트의 유일한 제거는 자기 PR"임을
   확인한다. `required/repository` 에서 돈다. 실패가 막는 사고: 고치는 PR 하나를 위해 큐 전체를 비운 일(11-11 세 번).
3. **큐가 버린 커밋의 실행은 취소한다.** `scripts/ci/cancel_superseded_queue_runs.py` 가 다음을 모두 만족하는 실행만
   취소한다.
   - 이벤트가 `merge_group` 이고 대기 중이거나 실행 중이다.
   - 그 실행의 큐 브랜치가 더는 없다(읽지 못하면 "없다"가 아니다. 그대로 둔다).
   - 그 커밋이 main 에 없다. 병합된 항목의 브랜치도 지워지고, 호스트는 큐가 그 커밋에 남긴 검사로 배포를 정하므로
     ([ADR-0167](./0167-the-host-deploys-the-tree-the-merge-queue-passed.md)) main 의 커밋은 절대 건드리지 않는다.
     브랜치를 먼저 묻고 main 을 나중에 묻는다. 병합으로 지워진 브랜치라면 나중 답에 그 병합이 이미 들어 있다.
4. **그 일은 `rerun-runner-failures.yml` 의 같은 작업이 5분마다 한다.** 새 권한은 없다. 그 작업은 ADR-0421 로 이미
   작업 수준 `actions: write` 를 가진 일정·수동 전용 작업이다. 주기를 10분에서 5분으로 줄인다. 큐 실행이 22분쯤이라
   늦게 볼수록 아낄 것이 없다.

## Consequences

- 고치는 PR 이 앞에 서는 데 드는 것은 라벨 하나와 명령 한 번이다. 버려지는 것은 그때 돌던 큐 실행(최대 2개)뿐이고,
  나머지 항목은 자리를 지킨다. 전에는 큐 전체(15~19건)가 다시 들어와야 했다.
- 앞자리의 하한은 큐 실행 한 번이다(한가할 때 22분, 러너가 차면 60분까지). 그보다 빨리 main 에 넣는 길은 만들지 않는다.
  필수 검사를 건너뛰는 길이 되기 때문이다.
- 버려진 실행이 평균 절반쯤 남았을 때 취소된다고 보면, 최근 표본에서 큐 실행 200개 가운데 55개의 남은 시간이 러너로
  돌아온다(계산: 55 × 88 작업·분 × 1/2 ≈ 2,400 작업·분 / 3.3일). 실제 값은 적용 뒤 취소 로그로 잰다.
- 일정 작업이 하루 144번에서 288번 돈다. 각 1분 미만이고 공개 저장소 표준 러너라 비용은 0 이다(계산).
- 라벨은 저장소에 쓸 수 있는 사람이면 붙일 수 있다. 남용은 PR 댓글과 큐 타임라인(`jump`)에 남는다. main 이 깨졌다는
  신호가 기계로 읽히게 되면 `hotfix:main-red` 를 그 신호가 열려 있을 때만 받도록 좁힌다.
- 코디네이터의 keeper 는 `enqueuePullRequest` 를 직접 부르는 대신 이 스크립트를 부른다(저장소 밖 스크립트라 이 PR 이
  바꾸지 못한다).

## Rejected alternatives

- **큐를 비우고 고치는 PR 을 먼저 넣기**: 11-11 에 세 번 한 방식이다. 돌던 실행을 전부 버리고 모든 항목을 다시 넣는다.
- **고치는 PR 을 큐 밖에서 바로 병합(우회 actor)**: main ruleset 에 우회 actor 가 없다는 것이 이 저장소의 전제다.
  main 이 깨진 때일수록 검증 없이 넣은 수정이 두 번째 사고가 된다.
- **`merge_group` 실행에서 스스로 취소**: 큐가 브랜치를 지울 때 workflow 를 깨우는 이벤트가 없고, PR 코드가 도는
  실행에 `actions: write` 를 줄 수 없다(ADR-0421 의 규칙).
