# ADR 0147: 필지·건물 문서는 항목별 묶음 파일로 서빙한다

- Status: Accepted
- Date: 2026-10-04
- Supersedes: [ADR-0096](./0096-parcel-attributes-are-served-from-pre-baked-r2-objects.md), [ADR-0100](./0100-buildings-floors-and-units-are-served-from-pre-baked-r2-objects.md) (필지·건물마다 R2 객체 하나)
- Amends: [ADR-0141](./0141-by-pnu-serving-publishes-changed-documents-as-patch-generations.md) (패치의 단위가 객체에서 묶음으로)

## Context

필지(39,861,511)와 건물(5,945,767)의 상세 문서는 PNU 하나당 R2 객체 하나(`v{n}/{pnu}.json`, 필지 약 2KB)다.
R2 는 객체 하나를 쓸 때마다 요금을 받고, 초당 쓰기 수에도 한계가 있다.

| 일 | 객체 쓰기 | 비용 | 시간 |
|---|---:|---:|---:|
| 필지 전체 다시 굽기 (항목 추가, 공시지가 연간 갱신, 문서 형식 변경) | 39.86M | 약 180달러 | 약 81시간 |
| 건물 전체 다시 굽기 (2026-10-04 `unit_pnu` 추가) | 5.94M | 약 27달러 | 7시간 이상 (진행 중, 429 재시도 발생) |

소유자는 패널에 데이터를 자주 추가할 계획이다. 객체가 하나일 때는 항목을 나눠도 쓰기 수가 줄지 않는다. 항목 하나를
추가해도 4천만 객체를 써야 한다.

같은 문제를 업계는 묶음 파일 + 색인 + 범위 읽기로 푼다. 우리 지도 타일(PMTiles, ADR-0111)이 이미 그렇다.
Overture Maps 의 GeoParquet, Cloud Optimized GeoTIFF 도 같은 원리다.

## Decision

1. **문서는 항목별 묶음 파일에 담는다.**
   - 한 묶음 = 한 항목(예: 용도지역, 공시지가, 토지특성, 임야대장, 토지이동이력, 대지권, 기본 정보) × 한 법정동(PNU
     앞 10자리)의 모든 PNU 문서.
   - 키: `serving/{lane}/packs/{section}/g{generation}/{pnu10}.pack`, create-only.
   - 항목 목록과 묶음 단위(앞자리 길이)는 계약 파일 하나(`config/r2-connections.contract.json`)가 정본이다.
2. **묶음 형식은 머리 + 색인 + 본문이다.**
   - 머리: 형식 버전, 항목, 세대, 원천 Gold 스냅숏, 색인 길이, 본문 sha256.
   - 색인: PNU 오름차순으로 정렬한 (PNU, 시작 위치, 길이, 상태).
     - 상태는 문서 또는 툼스톤이다.
     - Worker 가 이진 탐색한다.
   - 본문: 문서마다 따로 압축한 바이트를 이어 붙인다.
     - 그래서 범위 읽기 한 번으로 문서 하나를 꺼낸다.
     - 압축된 그대로 `Content-Encoding` 으로 돌려준다.
   - 형식은 버전을 가진다. 형식이 바뀌면 새 버전을 함께 굽고 manifest 로 바꾼다.
3. **응답은 지금과 같다.**
   - Worker 가 항목 묶음들에서 그 PNU 의 조각을 동시에 범위 읽기하고, 하나의 문서로 합쳐 돌려준다.
   - 응답 JSON 은 지금과 바이트 단위로 같은 구조다. 웹 코드는 바꾸지 않는다.
   - 묶음 머리·색인은 엣지 캐시에 둔다.
   - 개별 응답의 캐시 키에는 manifest 지문을 넣는다(ADR-0141 §6).
4. **매일 변경은 패치 묶음이다(ADR-0141 을 묶음 단위로).**
   - 바뀐 PNU 만 담은 같은 형식의 묶음을, 바뀐 법정동·항목에 대해서만 쓴다(`g{n}/p{m}/{pnu10}.pack`).
   - 삭제는 색인의 툼스톤으로 표시한다.
   - Worker 는 최신 패치부터 기본 세대까지 찾는다. manifest 가 패치마다 담긴 법정동 목록을 실으므로 해당 없는 패치는 읽지 않는다.
5. **전체 다시 굽기는 항목 단위다.**
   - 새 항목 추가, 한 항목의 연간 갱신, 한 항목의 형식 변경은 그 항목의 묶음만 새 세대로 굽는다.
   - manifest 는 항목마다 세대를 따로 가진다.
6. **전환 관문.** 운영 전환 전에 다음을 모두 통과해야 한다. 통과하지 못하면 지금의 객체 방식이 그대로 서빙한다.
   - (가) 전수 비교: 모든 PNU 에 대해 새 방식 응답의 내용이 지금 객체와 같다. 출처 블록만 다를 수 있다.
   - (나) 응답 시간: 캐시가 없는 첫 조회의 p50·p95 가 지금보다 계약에 적은 값(초기 50ms) 이상 늘지 않는다.
   - (다) 패치 경로: 심은 변경 문서와 툼스톤이 기대대로 보인다.
7. **확인 도구.** PNU 를 넣으면 각 항목 묶음에서 문서를 꺼내 보여 주는 명령을 함께 둔다.
8. **순서.** 건물(규모가 작음)을 먼저 전환하고, 관문 통과 뒤 필지를 전환한다. 옛 객체는 지우지 않는다(append-only).
   옛 객체의 정리 기준은 별도로 정한다.

## Consequences

- 항목 하나를 추가하거나 다시 굽는 비용이 객체 수천 개(1달러 미만)와 몇 시간으로 줄어든다.
  - 법정동 약 2만 개 × 그 항목.
  - 시간은 R2 쓰기 한계가 아니라 계산 시간이 정한다.
- 조회 한 번의 R2 읽기가 항목 수만큼 늘어난다(약 7회, 동시). 읽기 요금은 100만 회당 0.36달러라 비용 영향은 작다.
  - 지연은 관문 (나)로 지킨다.
- Worker 2개, 굽기·발행, 시험을 다시 짠다. 타일 Worker 의 범위 읽기 코드를 재사용한다.
- 사람이 객체를 직접 열어 보는 대신 확인 도구를 쓴다.

## Revision (2026-10-04): 건물 레인 구현에서 정한 것

건물 레인 구현(묶음 형식·굽기·관문·Worker)에서 정정·구체화한 것이다. 결정의 방향은 그대로다.

1. **압축은 문서마다 gzip 한 덩어리다. 여러 항목을 합친 응답은 Worker 가 풀어서 합친다(2·3절).**
   - 2절의 "압축된 그대로 `Content-Encoding` 으로 돌려준다"와 3절의 "조각을 합쳐 하나의 문서로"는 항목이
     둘 이상이면 함께 성립할 수 없다. 건물 문서는 건물 안에 층·호가 들어 있어 gzip 덩어리를 이어 붙여서는
     합칠 수 없다.
   - 그래서 Worker 는 조각을 `DecompressionStream("gzip")` 로 풀어 합치고, 압축하지 않은 JSON 을 낸다.
     클라이언트 쪽 압축은 Cloudflare 엣지가 한다. 합친 응답은 manifest 지문이 든 캐시 키로 엣지에 둔다.
   - gzip 을 고른 이유: Worker 가 기본 기능으로 풀 수 있고, 조각 하나만 읽는 경우에는 그대로
     `Content-Encoding: gzip` 으로 줄 수 있다. 다시 압축하지 않는 경로는 그 경우에만 해당한다.
2. **manifest 는 v2 봉투를 유지하고 `section_packs` 블록(자체 `schema_version` 3)을 더한다(4·5절).**
   - 배포된 읽는 쪽(발행기의 `ServedManifest`, 두 Worker)은 `schema_version` 1·2 외에는 거부하고, 모르는
     필드는 허용한다. 그래서 봉투를 3으로 올리면 운영 중인 Worker 가 모든 요청에 503 을 낸다.
   - v2 필드는 전환 시점의 객체 레인을 그대로 가리킨다. 되돌린 Worker·발행기는 객체를 계속 서빙한다.
     새 Worker 는 블록이 있을 때만 묶음으로 서빙하고, 블록을 믿을 수 없으면 503 이다(객체로 조용히 돌아가지
     않는다). `_capabilities` 는 `[1, 2, 3]` 을 낸다.
   - 객체 발행(전량·패치)은 블록을 그대로 옮긴다. 되돌리기는 객체 패치나 묶음 상태 중 한쪽만 되돌린다.
     묶음 상태를 되돌린다는 것은 묶음의 최신 패치를 떼거나 블록 자체를 떼는 것이다(객체 서빙으로 복귀).
   - 고정 태그(ADR-0146 §2)는 객체 레인과 묶음 레인의 반영 스냅숏을 둘 다 지킨다. 해제는 살아 있는
     manifest 가 적은 태그 중 더 오래된 것보다 오래된 것만 한다.
3. **건물 항목은 넷이다.** 정본은 계약(`building_by_pnu_gateway.section_packs.sections`)이다.

   | 항목 | 담는 것 |
   |---|---|
   | `buildings` (기준 항목) | 문서 식별·`source`·건물 자체 필드. 층·호·미연결 호·가격 자리는 빈 배열 |
   | `floors` | 건물 id 순서대로 그 건물의 층 |
   | `units` | 건물 id 순서대로 그 건물의 호, 그리고 미연결 호. 가격 자리는 빈 배열 |
   | `unit_prices` | 호 id 순서대로 기준일 공시가격 이력 |

   - 기준 항목이 응답 여부(문서·툼스톤·없음)를 정한다. 다른 항목은 같은 판정이어야 하고, id 순서가 기준
     항목과 정확히 같아야 합친다. 어긋나면 일부만 맞춘 문서를 내지 않고 503 이다.
   - 모든 항목이 모든 PNU 를 담는다(조각이 비어 있어도). 그래서 완결성 관문은 "항목마다 문서 수 = Gold
     행 수"다.
   - 합친 문서는 객체가 담던 문서와 내용이 같다. 발행기의 합치기는 바이트까지 같다(시험). Worker 의
     합치기는 정수 값의 실수(`50.0`)를 `50` 으로 쓰는 것만 다르다.
4. **패치 번호는 레인에 하나다.** 패치 `m` 은 각 항목의 자기 세대 아래(`g{n}/p{m}/`)에 쓴다. 항목마다
   `patch_floor`(그 세대에 이미 접힌 마지막 패치)를 두어, 한 항목만 새 세대로 구우면 그 항목만 이전
   패치를 읽지 않는다. 한 항목만 다시 굽는 것은 반영 스냅숏에서만 허용한다. 새 스냅숏은 모든 항목을
   다시 굽는다.
5. **묶음 형식 v1.**

   | 위치 | 크기 | 내용 |
   |---|---:|---|
   | 0 | 8 | 계약의 `magic` |
   | 8 | 2 | `format_version` (LE) |
   | 10 | 2 | 예약(0) |
   | 12 | 4 | 머리 JSON 길이 (LE) |
   | 16 | 4 | 색인 길이 (LE) |
   | 20 | — | 머리 JSON: 형식 버전, 레인, 항목, 세대, 패치, 법정동, Gold 표·스냅숏, 압축, 항목 수(문서·툼스톤), 색인 길이, 본문 길이, 본문 sha256 |
   | 뒤 | 28 × n | 색인: PNU 19자리, 본문 안 위치 u32, 길이 u32, 상태 u8(1 문서, 2 툼스톤) |
   | 뒤 | — | 본문: 문서마다 gzip 한 덩어리(mtime 0) |

   - Worker 는 머리를 범위 읽기 한 번(계약의 `head_read_bytes`)으로 읽고, 모자라면 한 번 더 읽는다. 머리는
     isolate 메모리와 엣지 캐시에 둔다. 묶음 키는 create-only 라 캐시가 낡지 않는다.
   - 쓰는 쪽과 읽는 쪽은 `by_pnu_pack.rs` 한 모듈에 있다. Worker 의 읽는 쪽은 발행기 시험이 쓰는 금본
     묶음(`foundation-building-gateway/test/fixtures/section-packs/`)으로 같은 바이트에 묶인다.
   - PMTiles 를 형식으로 쓰지 않은 이유: 키가 타일 id(z/x/y)라 PNU 문자열 키, 항목별 툼스톤 상태, 항목·세대
     머리를 담을 자리가 없다. 타일 Worker 에서는 범위 읽기와 "키가 불변이니 etag 가 바뀌면 거부" 규칙을 가져왔다.
6. **관문 (나)의 실측은 미리보기 Worker 로 한다(6절).**
   - 묶음은 운영 버킷에 새 세대로 create-only 로 굽고, manifest 는 아직 가리키지 않는다.
   - 미리보기 Worker 버전(바인딩 `FOUNDATION_PLATFORM_BUILDING_PACK_PREVIEW=true`, 운영 경로가 아님)이
     `?packs=g{n}` 로 그 세대를 서빙한다. 운영 경로는 manifest 가 그 세대를 가리킬 때만 이 질의에 답하고, 아니면 404 다.
   - 측정 명령은 표본 PNU 마다 운영 경로와 미리보기를 한 번씩, 번갈아 읽는다. 두 주소가 로컬·사설이면
     증거에 `local-simulation` 이라 적고, 그런 증거는 관문을 열지 못한다.
   - 첫 묶음 발행은 두 증거 파일이 모두 통과해야 한다. 발행기는 `passed` 를 믿지 않고 수치에서 판정을
     다시 낸다. 전수 비교 증거는 그것이 비교한 객체 상태가 지금 manifest 의 상태와 같아야 한다.
7. **측정(2026-10-04, 2세대 전량 굽기 요약 5,945,767건 + 공개 경로 표본).** 수치는 PR 본문에 있다.
   - 법정동 19,010개 × 항목 4 = 묶음 76,040개. 전량 굽기의 R2 쓰기는 객체 5,945,767회에서 76,042회(manifest
     와 이력 포함)로 줄어든다.
   - 머리+색인은 중앙값 5.2KB, 95분위 28.6KB, 최대 472KB 다. 270개(1.4%)는 첫 범위 읽기(64KiB)를 넘어 차가운
     읽기에서 한 번 더 읽는다.
   - 굽기 시간과 메모리는 운영 환경 파일을 읽어야 해서 아직 재지 않았다. 운영자가 `measure-building-section-packs.sh`
     로 전환 관문 전에 잰다.

## 개정 기록

- 2026-10-04: 건물 레인 구현에서 정한 것(압축과 합치기, v2 봉투 + `section_packs`, 건물 항목 넷, 패치 번호와
  `patch_floor`, 형식 v1, 미리보기 실측)을 위 Revision 절에 적었다. 결정 본문은 고치지 않았다.
