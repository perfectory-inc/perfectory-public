# 성능 병목 레지스터

perfectory의 **현재 성능 병목**의 정본이다. 무엇이 느리거나 막혀 있고, 측정값·근본원인·조치·상태가
무엇인가만 든다. 조치의 상세는 PR·ADR·runbook이 소유하고, 여기서는 링크만 건다 — 같은 내용을
복사하지 않는다.

이 문서는 축이 다른 두 문서와 겹치지 않는다: 출시 전 할 일은
[운영 준비 작업 목록](./production-readiness.md)이, 불변식과 그것을 재는 지표는
[기반 목표](./foundation-goals.md)가 소유한다. 여기 든 조치가 완료되면 그 줄은 지우고 결정은
ADR로, 실행 절차는 runbook으로 옮긴다.

## 상태 범례

| 기호 | 뜻 |
|---|---|
| 🟢 | 고치는 중 (PR 열림) |
| ⛔ | 사장 결정 대기 |
| 🟡 | 측정·설계가 더 필요 |
| 🔴 | 플랫폼 격차, 아직 미착수 |

판정 규칙: "느리다"는 측정으로만 주장한다. 측정 전 항목은 🟡로 두고 증거 칸에 "측정 필요"라고
적는다.

## 3. 플랫폼 성숙도 격차 (대기업 수준으로 가려면)

병목 하나하나가 아니라, 병목을 **빨리 찾고 다시 생기지 않게** 하는 바탕이다.

| # | 격차 | 왜 중요 | 조치 | 상태 |
|---|---|---|---|---|
| MAT-1 | **단계별 자동 계측 없음** (각 단계 시간·메모리 넘침) | 병목을 추측·수작업으로 찾아야 함 | 재빌드 단계별 시간·스필을 매 실행 기록 (추천 1순위) | 🔴 |
| MAT-2 | Spark **AQE(적응형 실행)** 켜짐 확인 안 됨 | 데이터 쏠림·파티션 크기를 Spark가 자동 처리 | 설정 확인·필요 시 켬 (추천 2순위) | 🟡 |
| MAT-3 | **속도 회귀 게이트** 없음 | 누가 코드로 느리게 만들어도 CI가 못 막음 | 작업 시간 예산을 CI로 고정 | 🟡 |

## 사장 결정 대기

- **CI-1 빌드 캐시**: 둘 중 하나를 고르면 풀린다.
  - (가) 저장소를 **비공개**로 → CI에서 비밀값 사용 가능 (간단)
  - (나) **공개-읽기 캐시 + ai-server만 쓰기** → 비밀값 없이 (더 복잡)

## 작업 순서 (현재 계획)

1. DP-1 (#841) CI 통과 → 배포 → ai-server에서 전/후 시간 실측 보고
2. MAT-1 (자동 계측) + MAT-2 (AQE 확인) — 작고, 앞으로 모든 속도 작업을 쉽게 만듦
3. DP-3 (공매 가동) — 단일-kind 강제 재빌드 경로 추가
4. CI-1 (빌드 캐시) — 사장 결정 후
5. 나머지(DP-2·CI-2·CI-3·MAT-3)는 위가 끝난 뒤 측정 결과를 보고 판단
