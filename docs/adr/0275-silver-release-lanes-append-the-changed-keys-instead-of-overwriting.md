# ADR 0275: 원천 판 Silver 레인은 표를 덮어쓰지 않고, 바뀐 키만 새 버전으로 쌓는다

- Status: Accepted
- Date: 2026-10-18 (사장 승인, 1단계 측정 뒤)
- Changes: [ADR-0169](./0169-silver-lanes-pick-their-source-release-from-the-ledger-and-refresh-themselves.md)
  §3 의 `iceberg_write_mode: overwrite`
- Builds on: [ADR-0267](./0267-a-versioned-table-declares-its-current-row-and-every-reader-takes-it-from-the-contract.md)
  (버전을 쌓는 표의 현재 행 규칙), [ADR-0180](./0180-panel-gold-recomputes-only-the-pnus-whose-inputs-changed.md)
  (Gold 는 빌드 열의 차이만 다시 만든다), [ADR-0237](./0237-lakehouse-snapshots-are-kept-30-days-12-month-ends-and-every-year-end.md)
  (스냅숏 30일, 월말 태그 12개, 연말 태그 영구)

## Context

hub.go.kr 건축물대장 세 레인과 VWorld 토지 레인 일곱은 판마다 전량 덤프를 받아 표 전체를 덮어쓴다
(`silver_refresh.spark.iceberg_write_mode: overwrite`). 2026-10-18 운영 실측(Trino 스냅숏 요약·시간 여행, 서버 저널,
읽기 전용)은 다음과 같다.

### 판 사이에 실제로 바뀌는 행

| 표 | 비교 | 추가 | 삭제 | 바뀜 | 같음 |
|---|---|---:|---:|---:|---:|
| `building_register_units` (1,985만) | 2026-08 판 → 2026-09 판, 키 `mgm_bldrgst_pk` | 0.44% | 0.03% | 7.6% | 92% |
| 위에서 PNU 만 바뀐 행 | (2026-07 행정구역 개편: 코드만 바뀜) | | | 7.55% | |
| 위에서 PNU 외 칸이 바뀐 행 | 동·호·층 | | | 0.02% | |
| `land_transfer_history` (1억 3,146만) | 0630 판 → 0930 판, 행 지문, PNU 5% 표본 | 18.3% | 11.1% | — | 81.6% |
| 같은 비교에서 개편 시도(29·46·12·28) 제외 | | 0.51% | 0.03% | — | 99.5% |

평상시 한 판의 변경은 **약 0.5%** 다. 개편처럼 코드가 바뀌는 달은 8–19% 다.

### 덮어쓰기가 치르는 값 (판 하나)

| 표 | 행 | 한 번 쓰는 바이트 | 실행 시간(저널) |
|---|---:|---:|---|
| `building_register_titles` | 806만 | 0.67 GB | 약 8분 |
| `building_register_units` | 1,985만 | 1.39 GB | 약 9분 |
| `building_register_unit_areas` | 1억 1,437만 | 8.9 GB | 약 75분(내보내기 20 + Spark 55) |
| `land_transfer_history` | 1억 3,146만 | 1.44 GB | 약 60–80분 |
| `land_use_plan` | 2억 4,758만 | 2.7 GB | — |
| 나머지 토지 넷 + 용도지역 코드 | | 1.2 GB | — |
| 합계 | | **약 16.6 GB** | |

- 보존 규칙(ADR-0237)은 30일 스냅숏, 월말 태그 12개, 연말 태그 영구다. 덮어쓴 판은 저마다 전체 사본이라
  표마다 **최대 13벌**(약 215 GB)이 R2 에 남는다. 해마다 연말 사본 한 벌(약 17 GB)이 영구로 늘어난다.
- 바뀐 0.5% 를 위해 매번 100% 를 쓰고, 그 100% 가 보존 기간 내내 남는다.
- 2026-10-10 의 표제부·호·호 면적 재적재는 같은 2026-09 판이었다. silver-refresh 레인으로 옮기면서 옛 경로의
  판 이름을 알아보지 못한 일회성 전환이고, 그 뒤로는 `already_loaded` 로 건너뛴다. 반복되는 낭비는 아니다.

### 시간은 아직 증명되지 않았다

바뀐 키를 찾으려면 새 판 전체를 내보내고 읽고 현재 행과 비교해야 한다. 덮어쓰기에서 줄어드는 것은 Parquet 쓰기와
커밋이다. 실행 시간이 얼마나 줄지는 재 보기 전에는 모른다(아래 1단계).

### 1단계 측정 결과 (2026-10-18, 운영 규모)

꺼진 일회성 작업 `silver_append_measure`(#702·#707·#713, 측정 뒤 #720 으로 지움)가 운영 Silver 를 읽기만 하고
scratch 네임스페이스에만 썼다. 표는 `land_transfer_history`, 앞 판은 0630, 새 판은 0930 이다.

| 단계 | 행 | 쓴 바이트 | 시간 |
|---|---:|---:|---:|
| 새 판 통째로 쓰기(덮어쓰기가 하는 일) | 131,464,796 | 1.44 GB | 약 3.5분 |
| 앞 판 복사(측정 준비) | 121,887,088 | 1.37 GB | 189초 |
| 비교: 행 지문 셔플 한 번 | 추가 24,127,886 · 삭제 14,550,178 | — | 319초 |
| 추가: 바뀐 행 + 삭제 표시 append | 38,678,064 | 1.02 GB | 2,015초 |
| **비교 후 추가 합계** | | **1.02 GB** | **약 39분** |

- 이 판 쌍은 2026-07 개편을 끼고 있다. 변경은 새 판의 18.35%, 앞 판의 11.94% 다. 5% 표본에서 개편 시도를 빼면
  추가 0.51%·삭제 0.03% 로 평상시 값과 같다.
- 비교 열은 레인마다 **선언**해야 한다. 처음 실행은 "모든 열에서 계보 열 빼기"로 지문을 만들었다. 그 목록에 판의
  기준일 `data_reference_date` 가 없어 모든 행이 바뀐 것으로 셌다. ADR-0180 의 `BUILD_COLUMNS` 처럼 내용 열을
  나열하고, 판마다 바뀌는 열은 넣지 않는다.
- 레인 실행의 60–80분은 대부분 Bronze 내보내기다. Silver 쓰기는 그중 약 3.5분이다.

**판단.** 비교 후 추가는 바뀐 행이 적어도 두 판을 다시 읽어 지문으로 고르므로 셔플이 남는다. 평상시 판도
20–30분 안팎으로 본다(추정). 이는 덮어쓰기의 3.5분보다 길어서 **시간 이득은 없다.** 이득은 쓰기 바이트와 보존
저장량이다. 평상시 판 하나에 1.44 GB 가 수십 MB 가 되고, 보존 사본은 표마다 최대 13벌에서 한 벌 + 변경분이 된다(10개
레인 합 약 215 GB → 30 GB 안팎, 추정). 대가는 Silver 독자 8곳의 이전이다(Spark 작업 7개의 읽기 경로, dbt 모델 2개,
간접 독자 2개는 같은 읽기 함수를 쓴다).

**승인.** 측정한 사람은 시간 이득이 없다는 이유로 덮어쓰기 유지를 권고했다. 사장은 측정을 보고 이 결정을 승인했다
(2026-10-18). 데이터는 덮어쓰지 않고 쌓는다는 원칙과, 판마다 전체 사본이 보존 기간 내내 남는 저장량이 이유다. 판마다
레인 시간이 약 20–40분 늘어나는 것은 이 결정의 대가로 받아들인다.

## Decision

1. **바뀐 키만 쌓는다.** 레인 계약에 두 가지를 적는다. 행의 업무 키(`row_key`)는 한 판 안에서 유일해야 하고, 레인마다
   실측해서 확정한다. 토지 이동 이력은 `(pnu, transfer_history_seq)` 이다(5% 표본 656만 행에서 유일). 비교할 내용 열
   (`content_columns`)은 판마다 바뀌는 열(판 기준일, 적재 id·시각)을 넣지 않는다(1단계에서 `data_reference_date` 가 모든
   행을 바뀐 것으로 만든 교훈). 새 판을 적재할 때는 현재 행과 키·내용 지문으로 비교한다.
   - 새 키·내용이 바뀐 키: 새 판의 행을 **append** 한다. `source_snapshot_id` 는 새 판이다.
   - 사라진 키: **삭제 표시 행**(키 + `row_state = removed` + 새 판)을 append 한다.
   - 같은 키·같은 내용: 쓰지 않는다.
   - 쓰기는 append 한 번이다. 있는 행을 고치거나 지우지 않는다. 판마다 그 판의 변경 전부가 한 스냅숏에 있다.
2. **현재 행은 ADR-0267 규칙으로 읽는다.** 계약에 `current_row_latest { key = row_key, newest_first = (판, ingested_at_utc) }`
   를 적는다. 키마다 가장 새 행을 고른 뒤, 그 행이 삭제 표시면 버린다. "최신을 고른 뒤 거른다" 는 0267 에 더하는 한
   단계다. 모든 독자는 `platform_contracts.current_rows` 하나로 읽는다.
   - Gold 생산자가 "한 판만 받는다" 고 검사하던 것(`assert_single_snapshot`)은 "현재 행이 여러 판에서 왔다" 를 허용한다.
     판의 완전성은 레인이 보증한다: 한 판의 변경 전부가 한 커밋이다.
3. **과거는 표 안에 남는다.** 어느 판의 상태든 "그 판 이하에서 키마다 최신" 으로 다시 만들 수 있다.
4. **옮기는 순서.** 작은 PR 로 나누고, 앞 단계에 기대는 PR 은 draft 로 둔다.
   1. 독자 8곳(Spark 작업 6개의 읽기 경로, dbt 모델 2개)을 먼저 현재 행 규칙으로 옮긴다. 레인이 아직 덮어쓰는 동안이라
      한 판에 키마다 행이 하나다. 그래서 현재 행 읽기 = 덮어쓴 표이고, 이 단계만으로도 안전하다. 독자마다 이 동등성을
      합성 데이터로 시험한다.
   2. 레인 하나(토지 이동 이력)를 "비교 후 바뀐 키만 쌓기 + 삭제 표시" 로 바꾼다. 계약이 바뀌므로 운영 표 모양 원장에
      대한 마이그레이션 시험(ADR-0259)을 함께 낸다.
   3. 그 레인에서 실제 판 하나가 통과한 뒤 나머지 레인을 하나씩 옮긴다. 레인마다 키를 실측하고 PR 하나다.
5. **전량 비교가 크면.** 변경이 전부에 가까워도(개편 달, 적재기 규칙 변경) 덮어쓰지 않는다. 같은 규칙으로 바뀐 키를 모두
   append 하고 사라진 키를 삭제 표시한다. 1단계 측정의 개편 판 쌍(행의 30% 변경)도 약 39분에 끝났다.

## Consequences

- 판마다 레인 시간이 늘어난다: Silver 쓰기 약 3.5분이 비교·추가 약 20–40분이 된다(1단계 측정, 평상시는 추정).
- 판마다 쓰는 바이트: 16.6 GB → 평상시 약 0.1–0.2 GB(0.5% + 삭제 표시).
- 보존: 13벌 전체 사본 → 현재 한 벌 + 판마다 0.5% 의 변경.
- 표 행 수는 판마다 약 0.5% 늘어난다(과거 버전이 표 안에 남는다). 압축(`replace`)은 그대로 돈다.
- 모든 Silver 독자가 `current_rows` 를 거쳐야 한다. Gold 생산자 셋·by-PNU·Trino 뷰가 해당한다. 이것이 이 변경의
  가장 큰 비용이고 위험이다. ADR-0267 의 기계적 차단(독자가 자기 창을 두지 못한다)을 이 표들로 넓힌다.
- ADR-0180 의 Gold 증분은 그대로 동작한다. 입력의 "현재 행" 차이만 본다.

## Rejected

- **`MERGE INTO`(copy-on-write) 로 현재 표를 고치기**: 0.5% 가 전국에 흩어져 있어 데이터 파일 대부분을 다시 쓴다. 쓰기
  이득이 거의 없고, 고쳐 쓰기라 덮어쓰지 않고 쌓는 규칙에 어긋난다.
- **merge-on-read 삭제 파일**: 쓰기는 작지만 행을 지우는 쓰기다. 굽기의 스냅숏 스캔이 delete 파일을 거부한다(ADR-0180).
- **SCD2 로 옛 행의 `valid_to_utc` 닫기**: ADR-0267 이 거절한 것과 같은 이유(쌓인 행을 고쳐 쓴다).
- **그대로 두기**: 비용이 보존 규칙 때문에 해마다 쌓인다. 측정 결과를 보고 사장님이 고를 수 있는 선택지다.
