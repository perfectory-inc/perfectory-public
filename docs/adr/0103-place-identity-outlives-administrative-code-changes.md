# ADR 0103: 장소의 정체성은 행정코드 변경보다 오래 산다

- Status: Accepted
- Date: 2026-09-12
- 관련: [ADR-0034 행정구역 코드는 자기 정밀도를 싣고 다닌다](./0034-an-administrative-code-carries-its-own-granularity.md), [ADR-0069 적재 정체성은 한 곳에서 정해진다](./0069-a-load-identity-is-decided-in-one-place.md), [ADR-0086 파이프라인 그래프는 모든 데이터셋을 명명한다](./0086-the-pipeline-graph-names-every-dataset.md), [ADR-0100 건물·층·호는 사전 구운 R2 객체로 서빙한다](./0100-buildings-floors-and-units-are-served-from-pre-baked-r2-objects.md)

## Context

행정구역은 계속 바뀐다. 세종 신설(2012), 청주·청원 통합(2014), 강원특별자치도(42→51, 2023),
전북특별자치도(45→52, 2024), 그리고 **광주+전남 → 전남광주통합특별시(2026-07-01)**. 앞으로도
통합·분리·개칭·재코딩은 계속 일어난다.

그런데 우리는 정부 코드를 **불변의 열쇠처럼** 쓰고 있다. `parcel_id`는
`sha256("perfectory.catalog.parcel.v1\0" + pnu)` 로 만들어지고 pnu 앞 5자리는 바뀌는 법정동
코드다(`foundation-shared-kernel/src/pnu.rs`). 즉 **정체성을 변하는 것 위에 세웠다.** 코드가
바뀌면 같은 땅인데 ID가 달라지고, 조인이 깨진다.

2026-09 실측으로 이 결함이 드러났다:

- 통합 **이전**(bronze `mart_djy_09` 202606)은 광주=**29**(563,834), 전남=**46**(507,307) —
  표준 법정동을 정상적으로 썼다.
- 통합 **이후**(silver vintage 202608)는 광주+전남이 **12** 하나로 합쳐졌다(1,069,836 ≈
  29+46). 정부 HUB 피드가 통합에 맞춰 옛 통합코드 12를 되살려 부여한 것이다.
- 우리 파이프라인은 소스의 `sigungu_cd` 를 검증 없이 pnu 앞자리로 **그대로 복사**한다. 그래서
  건물·호·가격은 12를, 지도(필지)는 아직 29/46을 쓴다. 두 코드가 안 맞아 광주+전남 건물은
  지도 필지에 **붙지 못하고 고아**가 된다.
- 이 사고를 **사람이 조인 실패로 우연히** 발견했다. 시스템은 아무 신호도 주지 않았다. 다음
  지역 변경에서 그대로 반복된다.

이건 잘 정립된 문제다: 참조데이터의 시간 이력(Slowly Changing Dimension / bitemporal)과
마스터 데이터 관리(MDM). 선행 사례로 Overture Maps **GERS**(릴리스 간 안정 128비트 ID +
Registry/Changelog/Bridge), **Who's on First**(`supersedes`/`superseded_by`, 레코드는 삭제
없이 대체만), Eurostat **NUTS** 버전 간 대응표, 영국 **ONS Code History Database**, Wikidata
시간 한정자(`replaces`/`start time`), 그리고 한국 **행정표준코드관리시스템(code.go.kr)** 이
법정동코드를 **생성일·말소일·후속코드 연계**까지 공개한다.

## Decision

지리 정체성을 코드에서 분리하고, 코드 변경을 시간 사전이 흡수한다. 다섯 기둥으로 세운다.
각 항은 시험 가능하게 적는다.

1. **안정 정체성은 변하는 코드에서 파생하지 않는다.** 모든 공간 대상(필지·건물·행정지역)은
   행정코드가 바뀌어도 변하지 않는 불변 내부 ID를 가진다. **`canonical_id`/`parcel_id` 를
   가변 코드가 든 pnu 문자열에서 해시하는 방식은 금지**하고, 한 번 부여한 뒤 코드 변경 시에도
   레지스트리의 승계 링크(3항)로 **동일 ID를 유지**한다. 시험: 같은 필지를 통합 전 pnu와 통합
   후 pnu로 각각 해석했을 때 **같은 내부 ID**가 나와야 한다.

2. **시간 사전(temporal registry)이 코드↔장소↔시점의 정본이다.** 행정표준코드(법정동코드
   전체자료: 생성일·말소일·후속코드 연계)를 정기 수집해 버전드 레지스트리에 적재한다. 각
   항목은 `(code, name, valid_from, valid_to, supersedes/superseded_by, provenance)` 를 싣는다.
   **코드→지역 사실을 소스코드에 하드코딩하지 않는다.** 시험: 레지스트리에 `29`·`46`·`12` 의
   유효기간과 12의 승계 관계가 데이터로 존재하고, 코드에는 그 매핑 상수가 없다.

3. **적재 입구의 해석기(resolver)가 유일한 코드 처리 지점이다.** 모든 소스 행의
   `(external_code, data_vintage)` 를 레지스트리로 해석해 내부 안정 ID로 바꾼다. pnu의 verbatim
   복사(`standard_pnu_from_hub_register_codes`)를 이 해석기를 거치도록 바꾼다(ADR-0069의
   "한 곳에서 정한다" 확장). 다운스트림은 전부 내부 ID로 조인한다. 시험: 소스가 12를 주든
   29/46을 주든 해석 결과 ID가 같고, 그 ID로 필지·건물·가격이 조인된다.

4. **해석 못 하는 것만 사람에게 — 스튜어드 검수 큐와 표시 정책.** 레지스트리로 해석 불가한
   코드(미등록·모호한 분리·소스 충돌)는 **버리지도 오조인하지도 않고 격리**한 뒤, 데이터가
   제안한 후보(예: pnu 꼬리 조인으로 도출한 크로스워크)와 함께 어드민 큐에 올린다. 스튜어드의
   결정은 **코드가 아니라 레지스트리 데이터(근거·작성자·일시 포함)** 로 저장된다. "전남광주
   통합특별시로 묶어 보일지" 같은 표시 그룹핑은 어드민 설정이지 코드가 아니다. 시험: 미등록
   코드를 심으면 격리되고 큐에 뜨며, 스튜어드 승인 후 재적재 시 자동 해석된다.

5. **표류 감지 가드.** 매 적재는 다음을 단언한다 — 배치의 모든 코드가 그 vintage 시점에
   레지스트리에서 유효하고, 두 소스가 같은 내부 ID를 서로 충돌하는 코드로 싣지 않는다.
   위반 시 격리 + 경보. **위협 모델(ADR-0001): 광주+전남(코드 12)이 지도(29/46)에 못 붙어
   사용자에게 통째로 안 보이는 채 발행되고, 조인 실패나 사용자 항의로만 뒤늦게 발견되는 그
   사고를 막는다.** 통과만 본 가드는 배신하므로(위반 주입 거부까지 시험), 코드 불일치를 심어
   가드가 실제로 거부하는지 확인한다.

6. **양시간(bitemporal) 보존.** 각 기록은 그 시점의 원본 코드를 유지하면서 안정 ID로도
   해석된다. 역사 데이터를 현재 코드로 덮지 않는다(append-only·무손실 원칙). 조회는 "특정
   시점 기준"이 가능하다. 시험: 통합 전 기준 조회는 29/46, 후 기준 조회는 통합 표현으로
   같은 대상을 답하고, 한 대상의 가격 이력이 통합 시점에서 끊기지 않는다.

## Consequences

- **광주 케이스가 이 구조에서 자동으로 풀린다.** 통합이 행정표준코드에 실려 있으므로 해석기가
  12↔29/46 을 자동 연결하고, 광주·전남 건물이 필지에 붙는다. 스튜어드는 "묶어 보일지"만
  결정한다. 다음에 어느 지역이 통합·분리돼도 같은 자동 경로, 엔지니어링 0.
- **사용자 체감**: 어느 지역·어느 시점에도 빈 구멍이 없고, 재코딩에도 값이 사라지거나 튀지
  않으며, 옛·신 주소 모두로 검색되고, 끊김 없는 시점 이력을 볼 수 있다(유일한 신규 기능).
- **비용과 이행**: 새 레지스트리 표 + 권위 사전 동기화 잡 + 해석기 + 어드민 검수 UI + 가드가
  필요하다. 기존 pnu-해시 ID로 적재된 실버·골드는 **일회성 재식별(re-identification) 패스**로
  내부 ID를 부여해야 한다(대규모). 기둥은 파도로 나눠 착수하되, 목표 아키텍처는 본 ADR로
  고정한다.
- **범위 밖**: 안정 ID의 정확한 앵커 정의(레지스트리 발급 ID vs pnu 꼬리 기반)와 재식별
  마이그레이션 절차, 스튜어드 UI 구현, 표시 정책 스키마는 후속 ADR/계획에서 정한다.
- **선행 사례 준수**: 본 결정은 Overture GERS·Who's on First·NUTS·ONS CHD·행정표준코드가 이미
  실물로 하는 것을 우리 필지·건물 도메인에 적용한 것이다.

## Revision (2026-09-12): 방향 정정 — 12가 현행, 29/46이 폐지

작성 당일, 권위기관(행정표준코드 `getStanReginCdList`, 우리 `DATA_GO_KR_SERVICE_KEY`로 실측)의
현행 시도 목록에 **`1200000000 전남광주통합특별시`** 가 있고 **`29`(광주)·`46`(전남)은
없다(폐지)**. 즉:

- **HUB 건물 데이터가 쓰는 12가 정부 현행 코드로 맞다.** 낡은 쪽은 오히려 **지적/지도(필지)의
  29/46**(원천이 아직 통합 전 코드).
- 따라서 해석기의 **정본(canonical) 목표는 "권위기관 현행 코드"**(현재 12)이고, 29/46은
  `superseded`로 잇는다. 초안이 함의하던 "12→29/46 정규화"는 **거꾸로였다** — 폐지 코드로
  되돌리는 것이므로 채택하지 않는다.
- 결정 6기둥(안정 ID·시간 사전·해석기·스튜어드·표류·양시간)은 그대로 유효하며, 사용자
  선택은 **(가) 별도 안정 식별자**: 원본 코드(29/46·12)를 **보존**한 채 각 장소에 안 변하는
  안정 ID를 부여하고, 옛·새 코드를 그 ID로 잇는다. 서빙 조인은 안정 ID로, **표시는 현행(12,
  전남광주통합특별시)**. 어떤 코드도 "덮어쓰기"하지 않는다.
