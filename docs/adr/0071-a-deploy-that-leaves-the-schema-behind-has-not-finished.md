# ADR 0071: 스키마를 두고 온 배포는 끝난 배포가 아니다

- Status: Accepted
- Date: 2026-09-01
- 관련: [ADR-0005 훅은 조언, CI가 권위](./0005-hooks-advisory-ci-authoritative.md), [ADR-0070 경계 원천은 필지의 용도도 면적도 나르지 않는다](./0070-the-boundary-source-carries-neither-use-nor-area.md), [ADR-0069 한 칸에 다섯 가지가 들어 있다](./0069-one-column-holds-five-kinds-of-thing.md)

## Context

2026-09-01, 배포 호스트의 런타임 상태를 처음 물어봤다.

```
저장소가 싣는 마이그레이션    33개
런타임에 적용된 것             4개   (전부 2026-07-19)
catalog.* 표                   전부 0행
foundation-api                 health=200,  GET /catalog/v1/complexes → []
foundation-platform-runtime:local   6주 전 빌드
foundation-migrate 컨테이너         6주 전 Exited(0), 그 뒤로 안 돎
```

**같은 날 배포를 세 번 했고 세 번 다 성공으로 보고했다.**

### 왜 배포가 이것을 못 옮기나

마이그레이션은 컴파일 시점에 바이너리 안으로 들어간다.

```rust
// services/foundation-api/src/bin/foundation-migrate.rs
static MIGRATOR: Migrator = sqlx::migrate!("../../migrations");
```

`foundation-release.sh` 가 하는 일은 소스 트리를 풀고 심볼릭 링크를 옮기는 것뿐이다. 마이그레이션
단계가 **글자 하나도 없다** — 확인했다. 그래서 디스크의 소스가 33개를 말해도, 그것을 적용할
바이너리는 7월에 알던 4개만 안다. 소스를 아무리 배포해도 스키마는 움직이지 않는다.

### 왜 아무도 몰랐나

**둘을 비교하는 것이 없었다.** 저장소도, CI도, 배포 스크립트도, 런타임도, 어느 쪽도 "지금 도는
것이 이 릴리스와 같은가"를 묻지 않는다. CI는 이 호스트에 닿을 수 없고(ADR-0005 가 CI를 권위로
둔 범위는 저장소이지 배포된 것이 아니다), 배포 스크립트는 자기가 옮긴 링크만 본다.

여섯 주 동안 아무 데서도 빨간불이 안 켜졌다. 그 사이에 이 저장소는 `catalog.parcel` 의 생산자가
없다는 것을 가장 큰 구조적 격차로 기록했는데(G1), **생산자를 만들었어도 그 스키마가 런타임에
없었다.** 오늘 root ADR-0070 이 연 두 칸도 런타임에는 아직 `NOT NULL` 이다.

## Decision

1. **배포는 자기가 남긴 스키마를 확인한다.** `foundation-release.sh install` 은 활성화한 릴리스가
   싣는 마이그레이션 버전 전부가 도는 데이터베이스에 있는지 확인하고, 없으면 실패한다. 릴리스는
   이미 설치·활성화된 뒤이므로 이것은 되돌리지 않는다 — **끝났다고 부르기를 거부할 뿐이다.**

2. **확인은 볼 수 없을 때 실패한다.** 닿지 않는 데이터베이스, 없는 컨테이너, 못 읽는 환경 파일,
   빈 원장 — 넷 다 "묻지 못했다"이고, 묻지 못한 것을 통과로 적는 것이 이 결함의 본체다.
   `assert-runtime-migrations.sh` 는 네 경우를 서로 다른 문장으로 구분해 말한다. 합쳐서 말하면
   멈춘 적 없는 컨테이너를 재시작하러 가게 된다.

3. **버전을 비교하고 내용은 비교하지 않는다.** `_sqlx_migrations.checksum` 은 적용된 바이트의
   SHA-384 인데, 이 저장소는 발행된 스냅숏이라 그 바이트와 다르다 — 2026-09-01 에 첫 두 개로
   확인했다. 내용 검사를 넣으면 드리프트와 무관한 이유로 빨간불이 켜진다. 검사는 자기가 무엇을
   보지 **않는지** 파일 안에 적어 둔다.

4. **적용할 방법이 배포 안에 있다.** `foundation-release.sh migrate` 가 현재 릴리스로 런타임
   이미지를 다시 빌드하고 마이그레이터를 돌린 뒤 (1)의 확인을 다시 한다. 다시 빌드하는 것이
   먼저인 이유는 (Context)에 있다 — 옛 이미지는 옛 마이그레이션만 안다. 빨간불에 대한 유일한
   답이 아무도 안 적어 둔 수동 복구인 상태를 남기지 않는다.

5. **가드가 (1)·(2)·(4)를 지킨다.** `a-deploy-verifies-the-schema-it-left` 는 install 갈래가
   확인에 닿는지, 확인이 "못 봤다"에 실패하는지, 적용 경로가 있는지를 본다. 파일 전체에 대한
   `grep` 이 아니라 **install 갈래 안에서** 찾는다 — 아무도 부르지 않는 `verify` 는 돌지 않는
   검사다.

## Consequences

**오늘부터 배포가 빨갛다.** 런타임이 29개 뒤에 있으므로 (1)이 즉시 실패한다. 그것이 이 결정의
목적이다 — 여섯 주 동안 초록이던 것이 사실은 빨간색이었다.

**첫 `migrate` 는 이미지를 다시 빌드한다.** 6주치 코드 변경이 들어가고, API 컨테이너가 재시작된다.
데이터베이스가 비어 있어 잃을 행은 없지만, 이것은 배포가 지금까지 한 적 없는 종류의 작업이다.

**CI 는 여전히 이것을 못 본다.** 이 확인은 배포 시점에만 돈다. CI 가 배포 호스트에 닿을 수 없기
때문이고, 그래서 자기 시험(`assert-runtime-migrations-self-test`)이 데이터베이스 없이 비교
로직을 돌린다 — 릴리스 디렉터리·compose 래퍼·`docker` 를 대신 세우고 검사 본체는 그대로 돌린다.
그렇게 하지 않으면 이 비교는 **자기가 잡으려는 사고가 날 때 말고는 한 번도 돌지 않는다.**

**이것은 마이그레이션만 본다.** 도는 이미지가 릴리스와 같은 커밋인지, 설정이 같은지는 아직
아무도 묻지 않는다. 같은 모양의 격차가 그 두 곳에 남아 있고, 이 ADR 은 그것을 닫지 않는다.

## 개정 각주 — 2026-09-01, 같은 날 저녁

위 문단이 남긴 둘 중 **설정 쪽은 그날 안에 닫혔다.** 결정을 적용하러 갔더니 곧바로 걸렸기
때문이다. `migrate` 가 이미지를 다시 빌드한 뒤 compose 보간에서 멈췄고, 환경 파일이
`FOUNDATION_RECOVERY_R2_*` 라는 옛 이름을 들고 있었다. 새 이름은
`FOUNDATION_PLATFORM_R2_POSTGRES_RECOVERY_*` 이고 키가 reader/writer 로 갈라져 있어 **여섯
개가 없었다.** compose 는 시도할 때마다 하나씩만 이름하므로 두 개짜리 구멍처럼 보였고, 파일
전체를 대조하고서야 여섯이었다. `assert-runtime-environment.sh` 가 그 대조를 한다 — compose
가 `${VAR:?}` 로 필수라고 선언한 것만 세고, **이름만 보고 값은 읽지 않는다.**

그 자리에서 두 가지가 더 드러났고 둘 다 같은 모양이었다.

**빈 데이터베이스에서는 이 스택을 세울 수 없었다.** `foundation-bootstrap` 이
`ALTER SCHEMA catalog` 과 `GRANT ... ON SCHEMA catalog` 을 하는데 `catalog` 을 만들지 않는다.
그것을 만드는 것은 마이그레이션 `20260719000001` 이고, compose 는 부트스트랩을 **먼저** 돌린다.
바로 옆 `serving_postgis` 는 `CREATE SCHEMA IF NOT EXISTS` 로 만들고 있었으니 대칭이 한 줄
깨져 있었을 뿐이다. 여섯 주 동안 안 보인 이유는 배포 호스트가 스키마를 이미 가진 덤프에서
복원된 것이어서다 — **한 번도 빈 데이터베이스에서 돌아본 적이 없는 순서였다.**
`bootstrap-creates-what-it-grants-on` 이 성질로 지킨다: ALTER 나 GRANT 가 이름한 스키마는
같은 파일의 CREATE 에 있어야 한다(`public` 은 Postgres 가 만드므로 예외로 명시).

**적용된 마이그레이션의 체크섬이 이 트리와 맞지 않았다.** `VersionMismatch(20260719000001)`.
(3)이 예상한 그대로다 — 발행 스냅숏의 바이트가 적용 당시와 다르다. 원장을 고쳐 검사를
통과시키는 선택지는 이 저장소가 하루 종일 반대해 온 것이므로, **데이터베이스를 이 트리로 다시
만들었다.** 업무 데이터는 설정 3행뿐이었고(전체 8,507행 중 8,500은 PostGIS 내장
`spatial_ref_sys`), 되돌릴 수 있도록 전체를 먼저 덤프했다. 그 뒤 33/33.

남은 것은 하나다. **도는 이미지가 릴리스와 같은 커밋인지는 여전히 아무도 묻지 않는다.**
