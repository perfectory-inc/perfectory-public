# ADR 0054: 정적 릴리스 도구는 실행 파일 신원 계약 하나를 가진다

- Status: Accepted
- Date: 2026-08-24

## Context

정적 벡터 타일 발행은 `martin-cp`, `mbtiles`, `pmtiles` 실행 파일과 같은 도구를 담은 컨테이너를
함께 사용한다. 그러나 도구 이름, 버전, 다운로드 주소, 컨테이너 참조와 사전 검증 조건이 Rust,
셸, Compose, 테스트와 문서에 따로 적혀 있었다. 특히 한 배포 묶음에 들어 있는 보조 도구가 배포
묶음의 주 도구와 독립된 릴리스 계보를 갖는데도 두 도구가 같은 버전이어야 한다고 검사했다. 공식
배포 묶음을 설치한 정상 실행도 이 잘못된 결합 때문에 발행 전에 거부되었다.

결함 유형은 **코드가 세상에 대한 사실을 주장하지만 그 사실을 실물과 대조한 적이 없는 상태**다.
이 저장소에서는 포인터 checksum 미대조, 존재하지 않는 운영 환경변수, 실제 타일을 읽지 못하는
decoder 계약에 이어 네 번째로 같은 유형이 드러났다. 검사 자체의 분기만 무력화하는 테스트는 검사의
전제가 현실에서 참임을 증명하지 못한다.

같은 종류의 결함을 막으려면 사람이 읽는 버전 문자열만 고정해서는 부족하다. 같은 배너를 출력하는
다른 빌드나 오염된 다운로드도 구별해야 하고, CI가 계약에 적힌 실제 실행 파일을 실행해야 한다.
반대로 해시만 검사하면 배포자가 공개한 도구의 의미상 버전 필드가 계약과 맞는지는 드러나지 않는다.

검토한 1차 자료는 각 프로젝트의 공식 GitHub release asset과 container registry manifest다.
패키지 관리자가 중간에서 다시 포장한 사본 대신 upstream 배포물을 사용하며, 저장소 규모에 맞지 않는
별도 artifact registry나 자체 updater는 만들지 않는다.

## Decision

1. [`static-release-toolchain.contract.json`](../../platforms/foundation-platform/config/static-release-toolchain.contract.json)이
   정적 릴리스 외부 도구의 유일한 사실 원장이다. 각 도구의 독립 버전, 버전 명령, 정확한 배너 조합,
   배포 묶음 관계와 호환 이유를 가진다. 지원 플랫폼별 upstream 전체 URL, archive SHA-256, archive
   member·설치 파일명·실행 파일 SHA-256, OCI repository·tag 파생 규칙·digest도 같은 계약에 둔다.
2. archive 해시는 내려받은 전송 단위가 upstream에서 검토한 바이트인지 증명한다. 실행 파일 해시는
   PATH에서 실제로 실행할 바이트가 그 배포 단위에서 나온 것인지 증명한다. 배너의 버전 필드는 그
   바이트가 주장하는 사람 대상 릴리스 의미를 증명한다. 세 검사는 대체 관계가 아니며 모두 통과해야
   한다.
3. Python 설치기는 지원 플랫폼, archive 해시, 필요한 member 전부와 실행 파일 해시를 먼저 검증한
   뒤에만 목적지로 승격한다. 다운로드와 외부 명령은 유한한 시간 제한을 가진다. 중간 실패는 부분
   실행 파일을 남기지 않는다. 목적지의 파일 집합과 해시가 이미 계약과 같으면 다운로드 없이 같은
   성공 결과를 반환하고, 다른 파일이 하나라도 있으면 덮어쓰지 않고 실패한다.
4. 발행기의 Rust 사전 검증은 빌드 시점에 계약을 포함하고 PATH에서 해석한 각 정확한 실행 파일을
   실행 전후로 해시한 뒤 정확한 배너를 비교한다. 검증기는 그 절대 경로를 typed toolchain으로 반환하고,
   실제 archive build의 모든 명령은 PATH를 다시 찾지 않고 그 경로만 실행하며 각 실행 전후 해시를 다시
   검사한다. 계약이 바뀌었는데 발행기 바이너리가 다시 빌드되지 않았다면 새 PATH 도구의 해시가 오래된
   내장 계약과 다르므로 닫힌 채 실패한다. 이것은 stale binary가 조용히 새 도구를 승인하지 못하게 하는
   의도된 배포 경계다.
5. CI는 계약 설치기로 Linux와 Windows 배포물을 각각 설치하고 그 디렉터리를 PATH 선두에 둔 뒤
   프로덕션과 같은 Rust 사전 검증 명령을 실행한다. 단위 테스트의 가짜 배너만으로 이 게이트를 대신하지
   않는다.
6. Compose와 proof 셸은 계약 투영기가 만든 digest-pinned 이미지 환경변수만 소비한다. repository guard는
   추적 파일 전체에서 계약 URL·해시·완성된 이미지 참조의 복제와 도구 옆의 새 버전 리터럴을 거부한다.

컨테이너 정책은 계약 이미지 변수를 일반 환경변수 예외로 취급하지 않는다. 셸 소비자는 추적된
투영기의 `image-env --shell` 결과를 정확히 한 번 평가한 뒤 사용하고 그 변수를 직접 재할당하지
않아야 한다. Compose 소비자는 추적된 단일 실행 소유자를 선언하며, 정책은 그 소유자가 같은
투영을 먼저 수행하고 해당 Compose 파일을 명시적으로 실행하는지 역추적한다. 따라서 계약 밖
다이제스트 복제를 금지하는 SSOT 가드와 고정되지 않은 이미지를 금지하는 컨테이너 가드는 같은
투영 경로를 증명하며, 단순히 이름이 같은 임의 환경변수에는 예외를 열지 않는다.

## Rejected alternatives

- 주 배포 도구 하나의 버전을 묶음 안의 모든 실행 파일에 적용하면 독립 릴리스 계보를 다시 결합한다.
- 배너의 부분 문자열만 확인하면 patch 차이, 긴 suffix와 다른 빌드를 승인한다.
- container tag만 고정하면 tag 이동을 막지 못하며 host 실행 파일의 신원을 증명하지 못한다.
- checksum을 셸과 CI에 복사하면 갱신이 원자적이지 않고 어떤 사본이 권위인지 다시 모호해진다.
- 자체 다운로드 서비스나 updater는 upstream release asset과 digest pin이 이미 제공하는 데이터 플레인을
  중복 구현한다.

## Consequences

도구 갱신은 계약 파일 한 곳의 독립 필드와 무결성 자료를 함께 검토하는 변경이 된다. 지원 플랫폼의
실제 배포물을 CI가 내려받으므로 네트워크와 빌드 시간이 늘지만, 발행 코드와 CI가 다른 도구를 검사하는
상태는 만들 수 없다. 새로운 플랫폼은 URL과 두 단계 해시가 없으면 표현할 수 없고, 오래된 바이너리는
새 도구를 자동 승인하지 않는다.

운영 문서에는 버전 숫자를 반복하지 않고 계약과 사전 검증 명령만 적는다. 공식 배포 구조가 바뀌면
계약 schema와 설치기 검증을 먼저 바꾸고, 무력화 실험과 실제 실행을 통과한 뒤 소비자를 승격한다.
