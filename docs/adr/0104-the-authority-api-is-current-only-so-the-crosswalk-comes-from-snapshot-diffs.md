# ADR 0104: 권위 API가 현행뿐이라 크로스워크는 스냅숏 차이에서 나온다

- Status: Accepted
- Date: 2026-09-13

## Context

ADR-0103 은 코드 변경을 시간 사전이 흡수하게 세웠고, 2항에서 "행정표준코드(법정동코드
**전체자료: 생성일·말소일·후속코드 연계**)를 정기 수집"한다고 적었다. #210 은 그 전제 위에
`derive_crosswalk_from_registry` 를 만들었다 — 한 적재분 안에 **생성 행과 말소 행이 둘 다**
있으면 같은 시군구명·같은 날짜로 1:1 매칭해 크로스워크를 뽑는다(광주 27쌍을 seed 없이 재현).

그런데 실제 권위 API 를 **직접 받아 확인**하니 그 전제가 그 API 에는 성립하지 않는다.
`getStanReginCdList`(data.go.kr, 우리 `DATA_GO_KR_SERVICE_KEY` 로 실측, 20,560행)의 한 행은
정확히 13필드이고 **날짜는 `adpt_de`(생성일) 하나뿐 — 말소일 필드가 없다.** 폐지된 코드는
현행 목록에서 **빠진다**(12(전남광주통합) 시군구 28개는 전부 `adpt_de=20260701` 로 들어와
있고, 옛 29(광주)·46(전남) 시군구는 **0개**). 즉 이 API 한 스냅숏에는 "말소 행"이 없어,
#210 의 단일-스냅숏 매칭으로는 크로스워크가 **하나도** 나오지 않는다.

말소일·폐지코드를 명시적으로 담은 관문은 따로 있다: `mois.go.kr` 의 KIKcd 전체파일
(`말소코드포함`). 그러나 그건 고정폭 텍스트(스펙이 HWP 문서)라 취약하고, 무엇보다 **운영에
필수가 아니다** — 아래처럼 깨끗한 API 스냅숏의 차이만으로 앞으로의 모든 변경을 흡수할 수
있기 때문이다.

## Decision

권위 REST API 는 **현행 코드 + 생성일만** 준다는 실측 사실을 정본으로 받아들이고,
크로스워크 도출을 두 메커니즘으로 나눈다. 둘 다 순수 커널로 두어 PySpark 없는 시험 레인이
그대로 검증한다.

1. **스냅숏 차이 도출(운영·전방).** `reference.legal_dong_code` 는 API 스냅숏을 append-only 로
   쌓는다(각 행: 현행 코드 + `created_date`=`adpt_de`, `abolished_date`는 항상 빈값 — API 가
   안 주므로). 크로스워크는 **연속한 두 스냅숏의 차이**에서 나온다:
   `derive_crosswalk_across_snapshots(prev_rows, curr_rows)` 가 이전 스냅숏에 있고 현재
   스냅숏에서 사라진 시군구 코드를 **말소**로, 현재 스냅숏에 새로 나타난(같은 `created_date`)
   코드를 **생성**으로 보고, 같은 **시군구명**으로 1:1 매칭되면 `현행(source) -> 폐지(canonical)`
   쌍을 낸다(valid_from=새 코드의 생성일). 이름이 안 맞거나(개명) 여럿이 하나로 몰리면(모호)
   내지 않고 스튜어드에게 남긴다(ADR-0103 ④). provenance 는 `derived:snapshot-diff:sigungu-
   name+date:{name}:{date}` 로, 스냅숏에 무관하게 안정적이라 재실행이 같은 쌍을 두 번 적재하지
   않는다.

2. **단일-스냅숏 도출(생성+말소를 한 파일이 다 담는 소스용).** 한 적재분에 생성 행과 말소 행이
   둘 다 있는 소스 — 체크인된 seed, 또는 선택적으로 KIKcd 전체파일 — 에는 #210 의
   `derive_crosswalk_from_registry`(시군구명+날짜 1:1)를 그대로 쓴다. 두 커널은 provenance
   접두사(`derived:registry:…` vs `derived:snapshot-diff:…`)가 달라 충돌하지 않고 감사된다.

3. **과거(수집 이전) 통합은 seed 가 부트스트랩한다.** 광주+전남(2026-07-01)은 우리가 스냅숏을
   쌓기 시작하기 전에 이미 통합됐다 — 이전 스냅숏이 없어 차이 도출이 불가하다. Wave 1 의
   체크인 seed(27쌍)가 그 부트스트랩이며 스튜어드가 확정한다. **수집 시작 이후의 모든 변경은
   메커니즘 1이 엔지니어링 0으로 흡수한다.**

4. **KIKcd 는 필수가 아니라 선택 보강이다.** 필요하면 `mois.go.kr`(승인된 provider) 의 KIKcd
   전체파일을 메커니즘 2로 들여 깊은 과거 말소 이력을 채울 수 있으나, 운영 전방 경로는
   메커니즘 1로 충분하므로 이 ADR 은 KIKcd 수집을 요구하지 않는다.

## Consequences

- ADR-0103 2항의 **수집·도출 방식만** 실측에 맞게 구체화한다. 6기둥(안정 ID·시간 사전·해석기·
   스튜어드·표류·양시간)은 그대로다. 정본 목표는 여전히 "권위기관 현행 코드"(현재 12).
- 앞으로 어느 지역이 통합·분리돼도, 우리가 이미 API 스냅숏을 쌓고 있는 한, 통합 전후 두
   스냅숏의 차이가 크로스워크를 **자동으로** 낸다. 취약한 고정폭 파싱도, 게시판 스크래핑도,
   엔지니어 개입도 없다.
- 비용: 스냅숏을 최소 두 번(변경을 사이에 두고) 갖고 있어야 그 변경을 차이로 볼 수 있다. 그
   래서 수집을 **지금부터 정기적으로** 돌려 스냅숏 history 를 쌓는 것이 이 자동화의 전제다.
- 한계: 한 스냅숏 주기 안에서 생성과 말소가 서로 다른 이름으로 일어나면(대규모 개편) 이름
   매칭이 모호로 떨어져 스튜어드로 간다 — 의도된 안전측 실패다(추측보다 격리).

## Revision 각주 대상

ADR-0103 에 이 ADR 을 가리키는 날짜 있는 개정 각주를 더한다(2항의 "말소일·후속코드" 전제는
`getStanReginCdList` 에는 실측상 성립하지 않으며, 도출은 본 ADR 의 스냅숏 차이로 한다).
