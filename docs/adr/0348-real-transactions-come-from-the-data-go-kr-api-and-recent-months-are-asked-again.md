# ADR 0348: 실거래가는 data.go.kr OpenAPI 로만 받고, 최근 달은 계약해제가 들어오는 동안 다시 묻는다

## Context

사장이 미수집 원천 전부의 수집을 승인했다(2026-10-30). 실거래가 12종(공장창고·토지·상업업무용·아파트 매매/전월세/
분양권·오피스텔 매매/전월세·연립다세대 매매/전월세·단독다가구 매매/전월세)은 카탈로그에서 `disabled_api_duplicate`
였다. 근거는 FP-ADR-0020: "`rt.molit.go.kr` 조건별 CSV export 가 기본 채널, data.go.kr API 는 그 중복". 그 결정을
실물로 대조했다.

| 사실 | 근거(2026-10-30 실측·확인) |
|---|---|
| `rt.molit.go.kr` 이용안내는 "기술적 수단(스크래핑, 캡처, 크롤러, 미러링 등 데이터 추출 프로그램 및 기타 자동화 수단)을 이용하여 본 사이트의 콘텐츠에 엑세스하는 행위" 를 금지하고, "데이터의 대량·반복적인 이용이 필요할 경우, 공공데이터포털(www.data.go.kr)에서 제공하는 국토교통부_실거래가 정보를 이용" 하라고 적는다 | `https://rt.molit.go.kr/pt/info/info.do` |
| FP-ADR-0020 의 export 경로(`plan-/execute-rt-molit-real-transaction-export*`, `ingest-rt-molit-real-transaction-export`)는 운영에서 한 번도 돌지 않았다 | 운영 `catalog.source_catalog` 에 `%real_transaction%` 원천 0, Bronze 객체 0 (읽기 전용 psql) |

| 신선도: 10-30 13:20 UTC 에 2026-10 을 물었을 때 계약일 최댓값은 공장창고 김포 28일·시흥 15일, 토지 김포 28일, 상업업무 시흥 23일. 이틀 전 계약까지 들어 있다 | API 실측 |
| 제공자는 과거 달을 **현재** 시군구 코드로 다시 묶어 준다. 화성시 `41590` 은 2025-01 에도 0건이고, 분구로 생긴 `41591`~`41597` 이 2025-01 거래를 준다 | API 실측(아파트 매매) |

즉 FP-ADR-0020 의 기본 채널은 제공자 약관이 자동 접근을 금지하는 경로였고, 그 약관이 대량·반복 이용자에게 가라고
하는 곳이 바로 "중복" 으로 꺼 둔 data.go.kr API 다. 벌크 파일은 없다. 그래서 "벌크 먼저" 원칙(수집 프로그램)의
벌크 자리는 비어 있고, API 가 이력 백필과 갱신을 모두 맡는다.

신선도 비교(같은 시군구·같은 달을 `rt.molit.go.kr` 조건별 자료제공과 API 에서 받아 행 수와 최신 계약일을 견줌)는
`rt.molit.go.kr` 쪽을 자동으로 받을 수 없으니 이 결정에서 재지 않았다. 사람이 브라우저로 한 번 내려받아 견주는
것은 약관 안이다(Consequences 의 사장 확인 1).

## Decision

1. **실거래가 12종의 유일한 자동 수집 채널은 data.go.kr 국토교통부_실거래가 정보 OpenAPI 다.** 연산은
   `operation_dataset_slug.rs` 의 12개(`getRTMSDataSvc*`), 원천 이름은 `datagokr__real_transaction_*`(ADR-0014)
   그대로다. `rt.molit.go.kr` 에 자동으로 접근하는 코드는 두지 않는다: FP-ADR-0020 의 export 계획·실행·적재 명령과
   그 모듈을 지운다(시험: 세 명령 이름을 `parse_command` 가 거부한다). provider id `rtmolitgokr`(ADR-0032 승인 목록)는
   이름 규칙의 일부라 남긴다.

2. **한 요청 = (연산, 시군구 5자리 `LAWD_CD`, 계약 달 `DEAL_YMD`, 페이지).** 수집의 단위는 (데이터셋, 시군구, 달)
   묶음이고, 그 묶음은 `totalCount` 까지 모든 페이지를 한 Bronze 객체에 담았을 때만 "완전" 하다. 시군구 목록은
   `reference.legal_dong_code_snapshot` 의 가장 새 스냅숏에서 `존재` 인 코드의 앞 5자리이고, 구가 있는 시(같은 앞
   4자리에 다른 코드가 있는 `…0`)는 그 구들로 묻는다. 제공자가 과거를 현재 코드로 다시 묶으므로(Context) 모든 달을
   현재 목록으로 묻는다. 목록에 **새로 든** 코드는 모든 달이 처음부터 다시 받을 것이 되고(백필), 목록에서 **빠진**
   코드는 받은 적 있는 달마다 한 번 더 물어(답은 비어 있다) Silver 가 그 묶음의 행을 내려놓게 한다(ADR-0349).

3. **다시 묻는 주기는 잰 해제 지연으로 정한다.** 계약 달의 나이(이번 KST 달 = 0)로:

   | 나이 | 다시 묻는 주기 | 이유 |
   |---|---|---|
   | 0–2 | 매일 | 신고 기한 30일 + 그 달 거래가 들어오는 중. 계약해제 31% 가 30일 안 |
   | 3–12 | 매주 | 해제의 p99 354일 |
   | 13–24 | 매달 | 해제 최댓값 442일 |
   | 25+ | 묻지 않는다(한 번 받은 뒤) | 그 뒤 바뀐 행은 2번의 코드 변경 때만 다시 받는다 |

   "이번 달과 앞의 2–3 달만" 은 해제의 57%(90일 안)만 잡는다. 주기·나이 경계는 소스 계약
   (`data-go-kr-rtms.contract.json` `refresh_tiers`)에 두고, 표본을 늘려 다시 재면 그 계약을 고친다.

4. **처음 받는 달(백필)은 다시 묻는 것보다 뒤, 우선순위 데이터셋 먼저, 새 달부터.** 순서: 나이 0–2 갱신 →
   빠진 코드의 마지막 질의 → 나이 3–12 → 13–24 → 백필. 같은 단계 안에서는 공장창고·토지·상업업무용이 먼저, 그다음
   나머지 아홉. 백필은 2006-01(매매)·2011-01(전월세)까지 내려간다(Context 의 첫 달). 운영자가 지켜볼 창은 필요 없다:
   백필도 3·5번의 상한 안에서 매시간 조금씩 간다.

5. **한 run 의 상한(ADR-0300 H).** 요청은 한 번에 하나, 계약의 `request_spacing_ms`(250ms, 초당 4) 간격이다:
   초당 한도 35 를 같은 키의 다른 수집과 나눈다. run 하나는 계약의 `per_run_call_limit`(3,000) 호출에서 멈춘다: 실측
   요청당 약 0.55초(간격 포함)라 약 28분이고, 작업 시간 한도 40분 안이다. 429 는 그 run 을 거기서 끝낸다(재시도
   루프 없음, 다음 run 이 잇는다). 다른 비정상 답(`000`·`03` 이 아닌 코드, HTTP 오류)은 run 의 실패다: 키·파라미터
   문제를 "거래 없음" 으로 읽으면 안 된다. 묶음 사이마다 이미 끝난 묶음을 Bronze 에 커밋하고 상태를 저장하므로(as it
   goes) 중간에 멈춘 run 은 마지막 묶음만 다시 묻는다.

6. **Bronze 는 덧붙이기만.** run 의 커밋마다 데이터셋 하나에 gzip JSON Lines 객체 하나, 줄 하나가 요청 하나(연산,
   키를 뺀 파라미터, HTTP 상태, 받은 본문 그대로)다(ADR-0280 §5, 온비드와 같은 모양). 같은 묶음을 다시 물은 답은 새
   객체가 되고, 옛 객체는 그대로다. 무엇이 바뀌었는지는 Silver 가 가린다(ADR-0349).

## Consequences

- `datagokr__real_transaction_*` 12 원천이 수집 원천이 된다. 카탈로그의 `disabled_api_duplicate` 는 `open_api_only`
  가 된다(수집기 PR). 범용 page-per-object 실행기(`execute-national-data-collection-async`)는 실거래에 계속 꺼 둔다:
  같은 사실을 두 길로 모으지 않는다(FP-ADR-0020 의 그 원칙은 유지).
- 양. 2025-09 한 달 전국 행 수(269 시군구의 `totalCount` 합, 실측, 오류 0):

  | 데이터셋 | 행/달 | 데이터셋 | 행/달 |
  |---|---:|---|---:|
  | 공장창고 | 988 | 아파트 전월세 | 95,786 |
  | 토지 | 30,098 | 오피스텔 전월세 | 21,993 |
  | 상업업무용 | 4,968 | 연립다세대 전월세 | 20,516 |
  | 아파트 매매 | 49,880 | 단독다가구 전월세 | 39,620 |
  | 분양권 | 3,145 | 오피스텔 매매 | 3,589 |
  | 연립다세대 매매 | 8,302 | 단독다가구 매매 | 3,669 |

  합계 약 28만 행/달. 이력(계산): 매매 약 10.5만/달 × 약 250달 + 전월세 약 17.8만/달 × 약 190달 ≈ 6천만 행.
  호출(계산): 269 × (매매 8종 × 약 250달 + 전월세 4종 × 약 190달) ≈ 74만 묶음 + 1,000행 넘는 묶음의 추가 페이지
  ≈ 82만 호출. 5번의 상한으로 약 12일.
- 비용(계산): API 는 무료다. Bronze 는 응답 JSON 약 600B/행(실측 바이트/행 456~665), gzip 약 1/6 → 약 0.1KB/행,
  6천만 행이면 약 6GB. Silver Parquet 를 더해도 10GB 안. R2 $0.015/GB·월 → 월 약 200원. 5만 원/월 문턱에 한참
  못 미친다.
- 사장 확인 1(선택, 약관 안): 같은 시군구·달(예: 시흥시 공장창고 2026-10)을 `rt.molit.go.kr` 조건별 자료제공에서
  손으로 한 번 내려받아 이 수집의 행 수·최신 계약일과 견주면 두 창구의 신선도 차이를 잰다. 자동 비교는 하지 않는다.
- 사장 확인 2(선택): 하루 한도 1,000,000/API 는 넉넉하지만 초당 35 는 키 하나에 묶인다. 수집기가 더 빨라야 하면
  data.go.kr 활용신청에서 트래픽 상향을 신청한다.
