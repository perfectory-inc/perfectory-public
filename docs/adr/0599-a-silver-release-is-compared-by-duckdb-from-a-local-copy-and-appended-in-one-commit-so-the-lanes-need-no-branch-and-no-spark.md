## Context

Silver 갱신 레인은 54 개다(손으로 쓴 계약 32 + HUB 계열 22, `silver_refresh/lane.rs`·`hub_lane_family.rs`). 53 개가 비교를 선언하고(적재 가지에 덮어쓰기 13: 표제부·전유부·토지 11, 덧붙이기 40), 1 개(공동주택가격)는 `main` 에 바로 덧붙인다. 모두 Spark 작업 둘로 돈다. 장부(`lakehouse-engine.contract.json`)의 4차 물결에 남은 가장 큰 덩어리다.

| 단계 | 지금 | 누가 |
|---|---|---|
| 내보내기 | 판의 Bronze 를 읽어 표의 열 모양으로 쓴다. 레인 종류마다 자리와 형식이 다르다(아래 표) | 발행기 (Rust) |
| 적재 | 그 파일을 읽어 행 검사를 하고 **적재 가지**(`load_…`)에 싣는다. 조각 레인은 묶음마다 한 커밋이고 여러 run 에 걸쳐 이어 싣는다(`LoadInProgress`) | Spark `silver_scalar_handoff_to_lakehouse.py` |
| 비교 | 적재 가지의 판과 `main` 의 현재 행을 키로 비교해, 바뀐 키의 행과 사라진 키의 삭제 표시를 묶음마다 **변경 가지**(`changes_…`)에 커밋한다. 여러 run 에 걸친다(`CompareInProgress`) | Spark `silver_release_compare.py` |
| 발행 | 변경 가지를 `main` 으로 한 번에 빨리 감고, 같은 커밋에서 판의 영구 기록(표 속성 `foundation.edition.<판>`)을 쓴다 | 발행기 `publish_branch` |

| 내보내기 종류 (`ExportKind`) | 판이 놓이는 자리 | 완료를 말하는 것 |
|---|---|---|
| `Unit` (전유부) | 실행 폴더의 로컬 Parquet | 없다 (적재 가지에 실렸는지로 안다) |
| `Title` (표제부) | 실행 폴더의 로컬 JSONL | 없다 (같다) |
| `UnitArea`·`HubParts` (전유공용면적, HUB 조각 레인) | R2 의 gzip JSONL 조각들 | R2 의 manifest (`status: complete`, 조각마다 행 수·바이트) |
| `Land` (VWorld 토지) | R2 의 gzip JSONL, Bronze 객체마다 하나 | 객체마다의 넘김 |

ADR-0560 §4 는 이 레인들을 Spark 에 남겼다. 발행기의 커밋은 `main` 에만 붙고(iceberg-rust 0.11.0 의 스냅숏 생성은 `MAIN_BRANCH` 만 가리킨다 — `transaction/snapshot.rs`), "가지로 커밋하는 길을 손으로 만들지 않는다"고 했으며, 비교 적재의 모양을 그때는 재지 않았다.

이번에 쟀다 (노트북, 운영 R2 읽기 전용, DuckDB 2 GB 한도·4 스레드 — 발행기 스테이지의 한도와 같다, 2026-11-20):

| 무엇 | 값 |
|---|---|
| 비교 대상 | `silver.land_use_plan` 의 가장 큰 묶음(시도 41). 표 전체 402,659,127 행(첫 판 247,584,668 + 둘째 판이 붙인 148,547,287 + 삭제 표시 6,527,172) |
| 묶음의 행 | 버전 87,483,827, 현재 행 47,121,580, 키 5,267,862 |
| 현재 행의 키별 지문 (R2 의 표를 읽으며) | 68.5~72.5 초, 임시 디스크 최대 7.0 GB |
| 로컬 Parquet 사본(370 MB, 4,712 만 행)의 키별 지문 | 2 초 |
| 바뀐 키·사라진 키 고르기 | 1 초 미만 |
| 합계 | 묶음 하나 약 85 초 |
| 같은 묶음의 Spark | 다른 표의 같은 시도에서 2,779 초를 쟀고(`silver.land_transfer_history`, 2026-11-03), 이 표는 약 31 분으로 추정돼 있다(`silver_refresh.rs`) |
| 하지 말아야 할 모양 | 현재 행을 열 19 개째로 순위 창에 통과시키면 350 초, 임시 디스크 22.6 GB (스테이지의 상한 32 GB 에 가깝다) |
| R2 의 조각을 DuckDB 가 바로 읽기 | 전유공용면적 202611 판(조각 115 개, 114,617,106 행, gzip 21.2 GB)의 조각 4 개(400 만 행, 730 MB)를 20 초에 읽었다 |

가지가 풀던 문제는 "Spark 가 판을 표에 실어야 읽을 수 있다"였다. DuckDB 는 판의 파일을 그 자리에서 읽는다.

## Decision

1. **적재 가지가 없다. 판은 먼저 레인 상태 폴더의 로컬 Parquet 사본이 된다.** 내보내기는 지금 그대로다(자리와 형식을 바꾸지 않는다). 그 뒤 DuckDB 가 판을 한 번 읽어 표의 열 모양·타입으로 로컬 Parquet 에 쓴다: 로컬 Parquet 은 그대로, 로컬 JSONL 과 R2 의 gzip JSONL 조각은 계약의 열 타입으로 읽는다(지금 Spark 의 `cast_handoff_frame` 과 같은 변환: 시각·날짜·숫자·16 진 이진). 조각 레인은 manifest 가 말하는 조각을 모두 읽고 행 수를 manifest 와 맞춘다. 비교의 모든 묶음은 이 사본을 읽는다(R2 의 조각을 묶음마다 다시 읽지 않는다).
   - 사본은 임시 이름으로 쓰고 끝나면 이름을 바꾼다. 그 옆에 완료 표지(판의 `identity`, 행 수, 파일 목록)를 같은 방식으로 쓴다. 표지가 없거나 다른 판의 것이면 폴더를 비우고 다시 만든다. 그래서 반쯤 쓴 사본은 완성된 것으로 읽히지 않는다.
   - run 의 첫 일은 지금처럼 `main` 의 커밋 기록을 읽는 것이다. 판이 이미 기록돼 있으면 폴더를 지우고 `unchanged` 로 끝낸다(커밋과 폴더 정리 사이에 죽은 run 은 여기서 정리된다). 남아 있던 스테이지 임시 폴더(`.duckdb-stage-*`)도 run 의 처음에 지운다.
   - 조각을 여러 run 에 걸쳐 가지에 이어 싣던 것(`LoadInProgress`)은 없어진다: 표에 싣지 않고 읽기만 하므로 이어 실을 것이 없다. `Land` 의 내보내기가 객체마다 여러 run 에 걸치는 것은 내보내기의 일이고 그대로다.

2. **커밋 전에 검사한다 — 가지 없는 write-audit-publish.** 두 Spark 작업이 하던 검사를 같은 뜻으로, 커밋 전에 한다. 하나라도 실패하면 커밋하지 않는다. 준비한 행은 커밋 전에는 어떤 스냅샷도 가리키지 않으므로(ADR-0560 §2·§4) 독자는 검사를 통과하지 못한 행을 볼 수 없다. 가지는 "쓰고, 검사하고, 발행한다"의 수단이었고, 여기서는 "준비하고, 검사하고, 한 번에 커밋한다"가 같은 보장을 준다.
   - 사본을 만들며: 넘김에 없는 열·읽히지 않는 타입, 열 이름과 순서, 필수 열의 null, 필수 문자열의 빈 값, 체크섬 형식, 정규화 상태의 값 범위(`proposal_required` 는 지금처럼 세기만 한다), 전유부의 건물 연결 근거, 기대 행 수(manifest·내보내기 요약), `source_snapshot_id` 가 비지 않았는지, 일반 토지 PNU 의 null 비율(계약이 선언한 표).
   - 비교 앞에서: 표의 계약이 비교를 허락하는지(행 키·삭제 열·`[판, ingested_at_utc]` 순서), 내용 열이 키·적재 열이 아닌지, 판이 하나의 판(edition)인지, 표가 이미 가진 판보다 오래되지 않았는지, 표에 이 run 의 시각 이후에 실린 행이 없는지, `main` 이 이 판의 객체 일부만 기록하고 있지 않은지.
   - 커밋 뒤: `main` 이 판의 객체를 모두 기록하는지(지금의 `confirm_recorded`).
   - 가지와 함께 없어지는 검사: 묶음 사이에 쪼개진 적재 식별자, 가지가 모든 객체를 기록하는지, 묶음마다 자기 커밋을 되읽어 행 수를 맞추는 것(커밋이 하나이고 그 행 수는 준비한 파일의 행 수다 — 커밋 요약의 붙인 행 수와 맞춘다). 바로 덧붙이는 레인의 재시도 시각 검사는 그 레인에 그대로 둔다.

3. **비교는 지금 규칙 그대로, 공용 부품 하나로, 묶음마다 한다.** 표의 행 키와 레인 계약의 내용 열로, 키마다 그 행들의 내용 지문의 다중집합을 비교한다(null 과 빈 문자열은 다르다; 키는 null 끼리도 같다). 붙일 행은 (a) 새 키이거나 다중집합이 다른 키의 판 행 전부, (b) 현재 행이 있는데 판에 없는 키마다 삭제 표시 하나다. 붙이는 모든 행에 판(edition)과 이 run 의 시각 하나를 찍는다(ADR-0328).
   - 이 비교는 발행기에 이미 한 벌 있다: 파일데이터 적재의 `data_go_kr_file_data_stage/changes.sql`(같은 `release_changes` 의 이식)이고, `gold_versions_commit.rs` 의 `diff` 가 키당 한 행인 경우다. 세 번째 사본을 만들지 않는다: 키·내용 열·찍을 값을 받는 비교 하나로 모으고 파일데이터 적재도 그것을 부른다. 현재 행은 계약의 `current_rows_sql_template()` 이 정하고(ADR-0564 §4), 그 부품이 **키·순서 열·지문만** 순위 창에 통과시킨다(위 표: 7 GB 대 22.6 GB) — 레인마다 기억할 규칙이 아니라 부품의 모양이다.
   - 삭제 표시는 사라진 키의 현재 행 가운데 하나로 만든다. 지금 Spark 는 `xxhash64` 순서의 첫 행을 고르는데 다른 엔진이 재현할 수 없다. 부품의 규칙은 하나다: 내용 열의 값 순서, 그다음 나머지 열의 값 순서로 첫 행(전체 순서라 동점이 없다). 표시의 뜻과 키·판·시각·삭제 열은 같고, 키에 현재 행이 여럿일 때 나머지 열의 값만 다를 수 있다. 그 열을 읽는 독자는 없다(`current_rows` 는 표시를 버리고, 변경 기록의 독자 `land_use_zone_area_by_tile` 은 살아 있는 행만 읽고 키로 지운다). 동등 판정은 이 열들을 따로 센다.
   - 묶음(`bucket_prefix_length`, `--bucket-scope release`)은 계약 그대로다. 묶음의 뜻은 이제 "커밋 단위"가 아니라 "한 번에 메모리·임시 디스크에 올리는 양"이다. `bucket_prefix_length` 가 0 인 레인(23 개 계약 줄: 표 전체가 한 묶음)은 옮길 때 그 표의 한 묶음을 재고(8 번), 스테이지의 임시 디스크 상한의 절반을 넘으면 접두 길이를 올린다.

4. **한 판은 한 커밋이고, 판의 영구 기록이 그 커밋에 함께 간다.** 묶음마다 바뀐 행을 스테이지 폴더(로컬)에 Parquet 으로 쓰고, 모든 묶음이 끝나고 2 번의 검사가 통과하면 그 파일 전부를 `append_at_head` 한 번으로 붙인다. 머리는 비교를 시작할 때 읽은 `main` 의 스냅숏이다.
   - 커밋 요약: 판의 객체 기록(`foundation.ingest-batch-objects` — 발행기에서는 `batch` 로 준다), 변경 기록(`changelog.change_record_options` 의 붙인 행 수·삭제 표시 수 — 지금은 묶음 커밋들에 나뉘어 있고 봉인 커밋은 0/0 이다; 이제 합계다), 판 기록(`foundation.edition`), 판의 버전(`foundation.compare-release-version`). 바뀐 것이 없는 판도 빈 커밋으로 기록한다(재실행 가드이자 판 기록이다 — 지금의 봉인 커밋, ADR-0318 §2).
   - **표 속성 `foundation.edition.<판>`**(ADR-0328 §3: 스냅숏 요약이 만료돼도 "이 판보다 오래된 판은 거부한다"가 남게 하는 기록)은 지금 `publish_branch` 만 쓴다. 추가 커밋과 **같은 트랜잭션**에 속성 갱신을 넣는다(iceberg-rust 의 트랜잭션은 동작 여럿을 한 커밋으로 낸다). 이것은 ADR-0560 이 "하지 않은 것"에 적은 조합이라, 첫 레인의 PR 이 시험 카탈로그에서 증명한다. 증명되지 않으면 판으로 순서를 매기는 레인은 옮기지 않는다.
   - `main` 이 그 사이 움직였으면 커밋이 거부된다(`HeadMoved`). 그 run 은 실패로 끝나고, 다음 run 이 남아 있는 사본으로 다시 비교한다. 커밋 응답을 잃은 경우는 ADR-0564 §3 의 규칙 그대로다(다음 run 이 머리의 기록을 읽어 안다).
   - 파일 크기: 커밋은 파일 하나를 통째로 메모리에 읽고(`lakehouse_data_commit.rs`), 파일 하나는 한 파티션이어야 한다. 묶음의 바뀐 행은 파티션마다, 256 MB 를 넘지 않게 나눠 쓴다.

5. **준비 파일의 자리와 버려진 run.** 준비 파일은 커밋 명령이 시작되기 전까지 로컬에만 있다. 커밋은 파일을 표의 `data/` 에 올린 뒤 커밋하므로, 그 둘 사이에서 거부되거나 죽으면 올린 객체가 남는다. 두 가지로 막는다.
   - 올리는 이름은 판과 묶음과 순번으로 정해진다(run 시각이 들어가지 않는다). 같은 판을 다시 비교한 run 은 같은 이름을 덮어쓰고 그 객체를 커밋이 가리킨다.
   - 올리기 전에 올릴 객체 키의 목록을 레인 상태 폴더에 적는다. run 의 처음에, 그 목록의 판이 `main` 에 기록돼 있지 않으면 목록의 객체를 지우고 목록을 비운다(다른 판으로 넘어간 버려진 run 의 고아). 커밋이 `HeadMoved` 로 거부된 run 은 끝나기 전에 같은 일을 한다.
   - 크기: 둘째 판만큼 바뀌는 판(1 억 5,507 만 행)이면 약 1.2 GB 다(측정한 370 MB / 4,712 만 행의 비율로 추정).

6. **여러 run 에 걸친 비교(마감·이어하기)는 옮긴 레인에서 쓰지 않는다. 지우는 것은 재고 나서다.** 지금의 마감(`--deadline-utc`, `CompareInProgress`)은 비교가 유닛의 150 분에 안 들어가서 생겼다. 옮긴 레인의 run 은 사본 만들기·비교·커밋을 한 run 에 한다. 유닛의 시간 제한은 그대로이고, 넘으면 그 run 은 실패다(조용히 다음 날로 넘기지 않는다): 다음 run 은 완료 표지가 있으면 사본을 다시 만들지 않고 비교부터 한다. 레인을 옮기는 PR 은 그 레인의 첫 운영 run 의 시간(사본·비교·커밋)을 적는다. 어느 레인이든 유닛 제한의 절반(75 분)을 넘으면 그 레인은 Spark 에 남기고 이 항을 다시 연다(묶음의 준비 파일을 run 사이에 남겨 이어 하는 길). 마감 코드는 마지막 레인이 옮겨진 뒤에 지운다.

7. **기하 허용 오차**(`silver.land_use_zone_area` 한 레인: 체크섬만 다르고 양쪽에 한 행씩인 키는 두 도형의 꼭짓점이 모두 0.1 m 안이면 바뀌지 않은 것)는 마지막에 옮기고 따로 판정한다. 등식을 새로 만들지 않는다: 이미 고정해 싣는 DuckDB `spatial` 확장으로 두 도형의 종류·부분 수·고리 수·꼭짓점 수가 같은지 보고, 꼭짓점을 순서대로 짝지어 `spatial` 의 거리 함수로 잰다(JTS `equalsExact` 의 뜻: 같은 구조, 같은 순서, 꼭짓점마다 허용 오차 안). 지금 Python 은 위도·경도를 111,320 m 로 곱해 재므로 경계의 키 몇 개가 달라질 수 있다. 그 레인의 운영 판(2026-11-05 에 98% 가 허용 오차 안이던 판)으로 `tolerated_keys` 를 대조해 판정하고, 다르면 그 수와 예를 적는다. 판정 전까지 그 레인은 Spark 에 남는다(장부의 비교 줄이 그 레인 하나 때문에 열려 있다).

8. **옮기는 순서, 엔진을 말하는 줄, 통과 기준.** 레인 계약의 실행 블록에 `engine` 한 줄(`spark`|`duckdb`, 없으면 `spark`)을 둔다. HUB 계열은 계열 파일의 `defaults` 와 레인 줄에 둔다(한 run 이 레인마다 그 줄을 읽으므로 한 run 안에 두 엔진이 섞여도 된다). `spark` 블록은 마지막 PR 까지 남는다. 레인을 `spark` 로 되돌릴 때는 그 레인의 상태 폴더를 비운다(되돌리는 PR 이 한다). `duckdb` 레인은 run 의 처음에 그 레인의 적재 가지·변경 가지가 남아 있으면 지운다(그 판은 새 길로 처음부터 비교한다). **`engine` 줄과 `spark` 블록은 마지막 PR 에서 지운다** — 영구 스위치가 아니다.
   - PR ① 공용 비교 부품, 사본 만들기, 4 번의 한 트랜잭션, 5 번의 정리, 그리고 레인 하나(`Land` 종류, 묶음 2 자리: `silver.land_use_plan`). 통과 기준: (가) 운영의 지난 판(20261109)을 그 판 전의 `main` 스냅숏과 그 판의 넘김으로 다시 비교해 Spark 가 붙인 148,547,287 행·삭제 표시 6,527,172 건과 같은 키·같은 행(삭제 표시의 키 아닌 열은 따로 센다); 그 스냅숏이 만료됐으면 남아 있는 가장 이른 스냅숏과 그 뒤의 판으로 한다. (나) 호스트에서 표 전체 run 의 시간, 임시 디스크 최대, 커밋 시간, 준비 파일 크기. (다) 유지보수 커밋(합치기·만료)과 겹친 커밋이 거부되고 다음 run 이 끝내는지(ADR-0560 §6 이 첫 표에 남긴 확인).
   - PR ② 나머지 비교 레인. 종류마다 하나씩(`Unit`, `Title`, `UnitArea`, `HubParts`) (가)의 판정을 하고, 나머지는 첫 운영 run 의 요약(붙인 행·삭제 표시·시간)을 적는다. 폭이 가장 넓은 `silver.building_register_unit_areas`(판 하나 gzip 21.2 GB)는 (나)를 다시 잰다.
   - PR ③ 바로 덧붙이는 레인(검사 뒤 한 번의 추가 커밋, #1547 의 모양), 기하 레인(7 번), 두 Spark 파일의 삭제, 장부의 두 줄을 `moved` 로, `engine` 줄·`spark` 블록·가지 이름·낡은 가지 치우기·빨리 감기·마감 코드의 삭제. 통과 기준: 저장소에 두 Spark 작업을 부르는 곳이 없고, 옮긴 표에 `main` 말고 참조가 없다.

## 독자에게 바뀌는 것

| 무엇 | 전 | 후 |
|---|---|---|
| `main` 의 행 | 바뀐 키의 행 + 삭제 표시 | 같다 (삭제 표시의 키 아닌 열은 3 번) |
| 판이 실렸는지 | `main` 의 커밋 요약의 객체 기록 | 같다 |
| 판의 영구 기록 (`foundation.edition.<판>`) | 빨리 감기 커밋이 쓴다 | 추가 커밋이 같은 트랜잭션에서 쓴다 |
| 판 하나의 커밋 수 | 묶음마다 하나 + 봉인, 빨리 감기로 한꺼번에 보인다 | 하나 |
| 변경 기록의 수(붙인 행·삭제 표시) | 묶음 커밋마다 | 한 커밋에 합계 |
| 묶음 이름을 적은 요약(`foundation.compare-bucket`, `foundation.compare-release`) | 있다 | 없다. 읽는 곳은 비교 작업 자신뿐이었다 |
| `foundation.compare-release-version` | 봉인 커밋에 | 그 한 커밋에 (읽는 곳: `changelog.py`) |
| 변경 기록을 읽는 독자(`changelog.changes_between`) | 걸음(커밋)마다의 행을 모은다 | 걸음이 하나다. 같은 행이다 |
| 가지 | 판마다 둘이 생겼다 지워진다 | 없다 |

## Consequences

- Spark 풀의 자리를 가장 오래 쓰던 레인들이 풀을 떠난다. 한 묶음의 비교가 수십 분에서 분 단위가 된다(측정은 묶음 하나, 노트북).
- 판의 로컬 사본과 준비 파일이 커밋까지 레인의 상태 폴더(호스트 SSD)에 남는다. 가장 큰 사본의 크기는 재지 않았다(전유공용면적 한 판이 gzip JSONL 로 21.2 GB 다. Parquet 사본은 그보다 작을 것으로 보지만 추정이다).
- R2 의 조각을 판마다 한 번 읽는다(지금은 Spark 가 한 번 읽는다 — 같다). 가지에 실린 판의 사본이 표에 생기지 않으므로 표의 크기와 만료할 스냅숏이 준다.
- `main` 이 비교 중에 움직이면 그 run 의 비교는 버려진다. 레인마다 쓰는 작업이 하나라(작업 계약과 유닛) 드물지만 유지보수 커밋과는 겹칠 수 있다(8 번 (다)).
- 옮기는 동안 `engine` 줄과 두 길이 함께 있다. 마지막 PR 이 지운다.

## 하지 않은 것, 확인하지 못한 것

- 측정은 "판 = 현재 행"(바뀐 키 0)으로 했다. 바뀐 키가 많은 판의 쓰기 시간과 준비 파일 크기는 재지 않았다(크기는 추정).
- 호스트에서의 시간. 노트북은 가정 회선으로 R2 를 읽었다. 호스트는 다른 작업과 디스크·CPU 를 나눈다.
- 표 전체(묶음 여럿)를 한 run 에 돈 적이 없다. 폭이 넓은 표(전유공용면적)와 `bucket_prefix_length` 0 인 표의 한 묶음도 재지 않았다. 6 번과 8 번이 옮기기 전에 재게 한다.
- 추가와 표 속성 갱신을 한 트랜잭션에 묶는 것(4 번). 첫 PR 이 증명한다.
- 판의 로컬 사본을 만드는 시간(조각 115 개를 읽고 Parquet 으로 쓰는 것). 조각 4 개 읽기 20 초만 쟀다.
- `spatial` 로 잰 허용 오차와 지금 Python 의 답의 차이(7 번의 판정이 본다).
- 운영 표에 대한 큰 추가 커밋(파일 여럿, GB 단위)의 시간. ADR-0560 이 남긴 미확인이고 첫 레인이 잰다.
- 설계 검토: EGM 검토자 넷(설계·코드 대조·구현 준비·범위)이 초안을 한 번 검토했다. 차단 6·주요 13·경미 11 가운데 이 문서에서 고친 것: 레인 수(34 가 아니라 54, 바로 덧붙이는 레인은 3 이 아니라 1), 판이 로컬 Parquet 인 것은 한 종류뿐이라는 사실(1 번을 종류별 규칙과 로컬 사본으로 다시 썼다), 판의 영구 기록(4 번), 커밋 전 업로드와 고아(5 번), 완료 표지와 폴더 비우기의 충돌(1 번), `engine` 줄의 모양과 되돌리기(8 번), 있는 비교 부품의 재사용과 삭제 표시 규칙 하나(3 번), 마감을 지우는 근거의 부족(6 번을 "재고 나서"로 바꿨다), 검사 목록의 빠진 것들(2 번), 봉인의 0/0 수(4 번), 파일 크기(4 번), 남은 가지(8 번), 죽은 run 의 정리(1 번), 통과 기준(8 번), iceberg-rust 의 인용 위치. 남긴 것: `bucket_prefix_length` 0 인 표들의 크기(세지 않았다 — 옮기는 PR 이 잰다), 빈 판(0 행)의 처리(지금 Spark 의 답을 옮기는 PR 이 확인해 같게 한다).

## 기각한 대안

- **가지 커밋을 발행기에 만든다**(iceberg-rust 의 `TableUpdate` 로 가지 참조를 직접 옮긴다). 판을 표에 싣지 않아도 읽을 수 있으므로 가지가 풀던 문제가 없다. 만들면 가지 수명·낡은 가지 치우기·빨리 감기가 그대로 남는다.
- **R2 의 조각을 묶음마다 바로 읽는다**(로컬 사본 없이). 묶음 수만큼 21 GB 를 다시 읽는다.
- **준비 파일을 처음부터 표의 위치에 쓴다.** 비교가 끝나기 전의 객체가 표 위치에 쌓인다. 로컬에 두면 남을 수 있는 것은 커밋 명령이 올린 것뿐이고 5 번이 그것을 치운다.
- **묶음마다 커밋한다.** 가지가 없으면 반쪽 판이 독자에게 보인다.
- **완료 표지 없이, 커밋이 기록되지 않았으면 언제나 다시 내보낸다.** 거부된 커밋마다 내보내기(전유부는 ZIP 셋을 다시 읽는다)를 되풀이한다.
- **기하 등식을 Rust 로 직접 쓴다**(`geo` 로 WKB 를 읽고 꼭짓점을 돈다). `geo` 는 WKB 를 읽지 않아 읽기부터 새로 써야 한다. `spatial` 은 이미 실려 있다.
- **Spark 를 남기고 계산만 옮긴다**(ADR-0559 §4 의 첫 단계). 세션이 남아 장부에서 빠지지 않고, 풀의 자리도 그대로 쓴다.
