# ADR 0618: 타일 굽기는 접두로 나뉜 Dagster 자산과, 그것을 합쳐 관문을 지나 승격하는 자산들이다 — run 나누기와 디스크에 둔 진행 상태를 옮기지 않는다

- Status: Proposed (여섯째 초안. EGM 검토 한 번, 자동화 스파이크 둘, ADR-0616·0615 와의 합동 검토 세 번(W82c)을 반영했다. "열린 질문" 1 은 §11, 2 는 §9, 3 은 §10 이 답했다(W86d))
- Date: 2026-11-25
- Builds on: ADR-0616 초안(작업은 Dagster 자산이고 AWS ECS 에서 돈다; 그 §7 의 걸음 A6 "굽기·서빙" 이 이 문서의 몫이다),
  ADR-0615 초안(입력은 관측 자산, 표는 시도 파티션 자산, 조각의 상태는 Dagster 의 것), ADR-0613(발행기 안의 합치기, #1685),
  [ADR-0316](./0316-parcel-boundaries-are-partitioned-by-edition-and-range-ordered-by-pnu.md)(접두별 타일 파일 캐시)
- 대신하게 될 것(구현 PR 이 표시한다): ADR-0493(run 예산과 미루기), ADR-0576(합치기 run), ADR-0611 의 작업 디스크 규칙과 폴더 치우기

이 문서는 설계다. 코드도 AWS 자원도 만들지 않는다. 사장 결정(2026-11-24): AWS 가 전제이고, ai-server 의 작업 층은 고치지 않는다.

## 사장에게

- 전국 필지 지도 굽기는 지금 꺼져 있다(#1683). 지도는 지금 것을 그대로 보여 주고, 새 기준(2026년 9월)은 AWS 에서 처음 나간다.
- AWS 에서는 시도마다 따로 굽고(여러 개를 동시에), 다 되면 한 번에 합쳐 검사하고 내보낸다. 얻는 것: 예약 시각 사이를 기다리지 않는다, 한 시도가
  실패해도 나머지는 끝난다, 서버 한 대에 맞추느라 만든 우리 장치(나눠 돌기·디스크에 적는 진행 기록·디스크 검사)를 옮기지 않고 지운다.
- 직원의 지도 편집은 지금처럼 바뀐 타일만 덧붙인다. 편집마다 전국을 다시 합치면 한 달에 R2 로 올리는 양이 약 492 GiB 늘어난다(§11, 계산).
- 아는 숫자: 전국을 통째로 구우면 169 분·디스크 43.7 GB, 시도별로 구우면 디스크 27 GB 이하, 시도 16 개를 하나로 합치는 데 약 4 분(메모리 180 MiB). 모르는 숫자: 돈, 시도 하나에 걸리는 시간.
- **지금 정할 것: 이 설계대로 코드 준비를 시작해도 되는가.** 돈은 쓰지 않는다. AWS 자원은 항목별 금액을 본 뒤에만 만든다(§8).

## 낱말

- **유닛**: 타일로 내보내는 지도 한 벌(`parcels`, `zoning` …). systemd 유닛은 "서버 유닛" 이라 쓴다.
- **접두**: 피처 id 의 앞 글자(필지: PNU 앞 두 자리 = 시도, 구역: 레이어 코드 네 자리). 굽기를 나누는 단위다.
- **시도의 수**(ADR-0615 와 같은 문장): 살아 있는 시도 코드는 16 개다(11, 12, 26, 27, 28, 30, 31, 36, 41, 43, 44, 47, 48, 50, 51, 52). 없어진 코드는 넷이다(42→51, 45→52, 29·46→12; ADR-0095·0103). 2026-11-25 에 운영에서 센 것: 서빙 필지(`gold.parcel_boundary_served`)에는 그 16 개가 있고 29·46 은 없다. `silver.land_ownership` 에는 17 개가 있다 — 12 가 없고 옛 코드 29(2,679,133 행)·46(15,308,318 행)이 그대로다. 그 표가 법정동 코드 변경을 아직 따라가지 않았다는 뜻인지(사장의 규칙 2026-10-31: 모든 데이터가 코드 변경을 따른다), 읽는 쪽이 `views.changed_codes` 로 따라가는 설계인지는 이 문서가 정하지 않는다: 그 레인의 주인이 답할 열린 항목이다. 파티션 키의 수는 표마다 그 표가 가진 코드의 수이고, 이 결정들은 그 수에 기대지 않는다.
- **타일 파일**: 접두 하나를 구운 PMTiles 파일. **합친 파일**: 그것들을 하나로 만든 것. **에디션**: 필지 원천의 기준 시점(202609).
- **인계물**: Spark 가 서빙 Gold 에서 뽑아 굽기에 넘기는 전국 파일(25 GB). **승격**: 합친 파일을 서빙 릴리스로 바꾸는 카탈로그 쓰기.
- **객체 저장소**: 지금 타일을 올리는 R2. AWS 로 가도 R2 다(ADR-0616).

### 연습이 서빙 표를 덮어썼다 (2026-11-20, 코드와 유닛 저널을 읽음)

`gold.parcel_boundary_served` 는 **2026-11-20T17:27Z 부터 다음 서빙 빌드까지 에디션 202609 를 든다.** 서빙 에디션은 202606 이고(원천 계약의
`served_edition`, 작업의 로그도 그렇게 말한다), 다른 Gold 표는 모두 202606 이다. 그래서 이 표를 다른 Gold 표와 잇는 읽기는 광주·전남을 잃는다

까닭은 핀이 아니라 연습이다. `parcel-tile-bake.sh` 는 서빙 에디션에 할 일이 없고 준비 판정이 더 새 에디션을 "연습 대기" 로 적으면 예약된 Gold

되돌리지 않는다(코디네이터 결정 2026-11-25: 사용자가 없고, 다음 연습은 202609 를 202609 로 다시 쓸 뿐이다). Spark 작업도 고치지 않는다.

### 읽은 것 — 주장마다 어느 판에서 확인했나

운영의 핀은 `dagster` 1.13.27, `dagster-aws` 0.29.27 이다.

| 주장 | 확인한 곳 |
|---|---|
| `AllPartitionMapping`: 파티션 없는 하류가 상류의 모든 파티션에 의존한다 | 문서(1.13.8·master, context7) + **1.13.27 스파이크**(정적·동적) |
| `eager()` 는 상류 파티션이 하나라도 구체화되지 않았으면 하류를 요청하지 않는다 | **1.13.27 스파이크**(정적·동적) |
| 상류가 도는 중이면 기다린다. 줄에 선 run(`QUEUED`)도 도는 중이다 | **1.13.27 소스**(아래) |
| 구체화는 데이터 버전이 같아도 하류의 `eager` 를 일으킨다 | **1.13.27 스파이크**(이 문서와 ADR-0615 의 (b)-C) |
| 막는 검사가 통과하지 못하면 그 스텝이 실패하고, 같은 run 의 하류는 돌지 않고, `RetryPolicy` 는 다시 돌리지 않고, 구체화는 적힌다 | **1.13.27 스파이크**(둘째) |
| 선언형 자동화가 만든 run 의 태그는 그 센서의 `run_tags` 이고, 실행기는 `ecs/cpu`·`ecs/memory`·`ecs/ephemeral_storage`·`ecs/task_overrides` 를 읽는다 | ADR-0616 이 1.13.27·`dagster-aws` 0.29.27 의 소스에서 확인했다(그 §2-8·2-9). 이 문서는 다시 보지 않았다 |
| **확인하지 않은 것** | 위 모두가 데몬이 도는 Dagster 에서도 같은가. `eager()` 또는 (`execution_failed()` 이고 cron 틱이 지남) 항(§4)이 이 모양에서 어떻게 도는가. ECS 위에서의 무엇이든 |

- ADR-0615 초안의 스파이크: "바뀐 파티션만" 은 **입력이 `observable_source_asset`(파티션별 데이터 버전), 하류가 진짜 `@asset`** 일 때만 된다.
  op 가 관측 사건을 적는 방식은 `eager` 를 한 번도 움직이지 않았다. 그 문서의 보고 규칙: 새로 쓴 것이 없는 파티션은 구체화가 아니라 **통과한 자산
  검사**로 알리고(하류가 움직이지 않는다), 표에는 이미 지어져 있는데 Dagster 가 모르는 파티션만 구체화로 다시 알린다. 타일의 접두는 그 규칙의
  둘째 예외다(ADR-0616 §6): 늘 구체화한다(§2).
- ADR-0616 초안: 도구가 다른 일은 코드 위치가 다르다 — `tiles` 코드 위치(발행기 + GDAL + tippecanoe)의 run 태스크가 굽는다. 둘째 태스크
  (`PipesECSClient`)는 쓰지 않는다(§2-2). 크기는 자산의 태그가 아니라 **크기 등급**이다: 등급마다 자동화 센서 하나가 `run_tags` 로 싣고, 한 run 은
  한 등급의 자산만 품는다(§2-9). 자산의 몸이 run 의 파티션 키를 읽어 일에 넘긴다(§3). 풀은 남의 한계에만 쓴다(§5). 표준 Pipes 클라이언트는 일이
  끝난 뒤에 결과를 돌려주므로 실패한 run 의 사건에 기대지 않는다(§3). 재시도의 표는 §4 에 하나, 단가와 금액은 §10 에 하나다.

### 스파이크 (2026-11-24, 노트북의 임시 venv, `dagster==1.13.27`, `DagsterInstance.ephemeral()`, 데몬 없음; 운영에 닿지 않음)

자산 넷을 §2 의 모양으로 선언하고(접두 16 개) `evaluate_automation_conditions` 를 틱마다 불렀다. 요청된 run 은 스크립트가 돌렸다.
첫째 스파이크(2026-11-24)는 정적 파티션, 둘째(2026-11-25)는 결정대로 **동적 파티션**(`DynamicPartitionsDefinition(name="sido")`)이다.
아래 표의 줄은 둘에서 같았다.

| 한 일 | 요청된 것 |
|---|---|
| 기준 틱 뒤 첫 관측(16 접두) | `partitions` 16 개 모두, 한 틱에. `merged` 0 |
| 16 개 중 5 개만 구운 뒤 | `merged` 0 (문서대로: 상류가 하나라도 없으면 요청하지 않는다) |
| 16 개 모두 구운 뒤 | `merged` 1 과 `release` 1 이 **같은 틱에** (한 run 에 함께 든다) |
| 그 뒤 두 틱 | 0, 0 |
| 접두 셋의 버전이 바뀐 관측 | `partitions` 그 셋만 |
| 그 셋을 하나씩 굽고 그때마다 틱(나머지는 **아직 돌지 않은** 상태) | `merged` 가 **세 번** |
| 같은 버전을 다시 관측 | 0 |
| 버전이 같은 접두를 손으로 다시 구움 | `merged` 1 (문서대로: 구체화는 버전을 보지 않는다) |

둘째 스파이크가 더 본 것(동적 파티션, `merged` 에 막는 검사 하나, `merged` 와 `release` 를 한 run 으로):

| 한 일 | 본 것 |
|---|---|
| 막는 검사가 통과하지 못한 run | `merged` 스텝이 실패(`DagsterAssetCheckFailedError`), `release` 는 돌지 않음("Dependencies for step release failed"), run 실패. `merged` 의 구체화는 적혔다 |
| 그 뒤 세 틱 | `merged` 0, `release` 0 — 거부된 뒤에 `release` 만 따로 요청되지 않았다 |
| `merged` 에 `RetryPolicy(max_retries=2)` 를 걸고 같은 일 | `merged` 는 **한 번** 돌았다(막는 검사의 실패는 재시도되지 않는다) |
| 접두 하나를 다시 굽고 검사가 통과 | `merged` 1 과 `release` 1 이 같은 틱에, 한 run 에서 둘 다 돌았다 |
| 동적 파티션에 키 하나를 더함 | 관측 전에는 0. 관측 뒤 `partitions` 그 키만. 구운 뒤 `merged` 1·`release` 1 |

기준 틱 없이 첫 관측을 하면 아무것도 요청되지 않았다(`eager` 의 "새로" 는 앞 틱과 견준다). 레인을 켤 때가 그 경우다(ADR-0616 §4) — §4 가 고른다.

**읽은 소스(1.13.27 `_utils/caching_instance_queryer.py` 205~225 행).** 자산이 "도는 중" 인 것은 계획된 구체화의 run 이 `STARTING`·`STARTED`·
`CANCELING`·`SUSPENDED` 또는 **`QUEUED`** 일 때다. 그러니 데몬이 한 틱에 요청한 접두 run 들은 줄에 서는 순간부터 "도는 중" 이고, `merged` 는 그것들이
모두 끝날 때까지 기다린다. 위의 "세 번" 은 스크립트가 나머지 run 을 줄에 세우지 않아서 나온 것이다 — **한 관측의 변경은 `merged` 한 번, 여러 관측에
걸친 변경은 관측마다 한 번**으로 읽는다. 실패한 접두 run 은 "도는 중" 도 "갱신" 도 아니다: 나머지가 끝나면 `merged` 가 요청되고, §2 의 버전 확인이
그것을 거부한다. 데몬이 도는 Dagster 에서 같은지, 재시도와 실패가 섞일 때 어떤지는 보지 않았다.

## Decision

### 1. 범위

정하는 것: 접두로 나뉘는 유닛의 **전체 굽기**(입력 → 접두별 타일 파일 → 합친 파일 → 관문 → 승격). 필지가 첫 대상이다.

편집이 지도에 닿는 길(패치 세대와 그것이 쓰는 피처 색인)은 §11 이 정하고, 접두 하나의 입력은 §10 이 정한다.

정하지 않는 것: 통째로 굽는 유닛(산업단지·행정경계), 구역 굽기 유닛이 함께 하는 `gold.land_use_zone_area_by_tile` 유지, 구역의 이행. 구역은
패치가 평소의 길이고 §11 의 모양이 맞지만, 구역의 인계물을 쓰는 것이 Spark 라(§10) 그 생산자가 발행기로 옮겨진 뒤에 옮긴다.

### 2. 자산 넷 (편집의 패치는 다섯째, §11)

| 자산 | 파티션 | 언제 | 하는 일 | 내는 것 |
|---|---|---|---|---|
| `tiles/<unit>/inputs` (관측 자산) | 접두 | 레인의 cron(ADR-0616 §4) | 접두마다 "그 접두의 굽기 입력의 버전" 과 그것을 읽은 서빙 Gold 스냅숏을 낸다 | 파티션별 데이터 버전 |
| `tiles/<unit>/partitions` | 접두 | `eager` | 그 접두를 그 스냅숏에서 굽는다 → 타일 파일과 곁 파일을 객체 저장소에 create-only 로 쓴다 | 타일 파일 하나 |
| `tiles/<unit>/merged` | 없음 (`AllPartitionMapping`) | `eager` | 모든 접두가 지금의 입력 버전인지 확인한다 → 받는다 → 합친다(ADR-0613) → 합친 파일을 create-only 로 올린다 → 관문 | 합친 파일, 관문 결과(막는 자산 검사) |
| `tiles/<unit>/release` | 없음 | `eager` | 검사를 지난 합친 파일을 승격한다(카탈로그 쓰기) | 서빙 릴리스 |

- **입력의 버전.** 필지는 서빙 Gold 의 머리가 시도마다 지닌 상태(`foundation.partition-state`)에서 읽는다. 그 표의 **버전**은 시도로 놓이지
  않은 입력(`silver.parcel_boundaries` 는 판본 안에서 pnu 순서일 뿐이다)이 움직이면 모든 시도에서 같이 움직인다(ADR-0615 결정 2-1; 그 결정 3 의
  ADR 전까지). 버전을 쓰면 입력이 움직일 때마다 모든 접두가 요청되고, 아끼는 것은 내용 해시 캐시뿐이다(§3: 입력은 읽고, GDAL·tippecanoe 는 돌지
  않는다). 그래서 타일의 입력 버전은 그 시도의 **(현재 행 수, `digest_sum`)** 이다: `digest_sum` 은 그 시도의 현재 행의 `row_digest` 앞 15 자리
  16 진수의 합(표 지문의 합을 그 시도로 좁힌 것)이라, 그 시도의 행이 더해지거나 바뀌거나 지워질 때만 움직이고 바뀐 키 없이 버전만 오를 때는
  움직이지 않는다(W97b 의 답, 2026-11-25). 그 상태는 **그 시도를 마지막으로 통째로 지은 빌드**의 것이다 — 편집의 접기가 커밋한 바뀐 키는
  기본판의 입력이 아니라 패치의 입력이다(§11). 한계 둘:
  - **아직 서빙 필지 경계에는 없다.** 오늘 main(#1692)의 상태 표는 시도마다 버전과 현재 행 수만 들고, 내용 지문은 표 전체의 것이다. `digest_sum`
    은 W97b 의 로컬 커밋에 있고(#1704 다음 드라이버 PR), 시도마다 커밋하는 표(`KindBuild.per_sido_commits`; 오늘은 토지소유뿐)에만 생긴다. 서빙
    필지 경계는 아직 제 드라이버로 표 전체를 한 번에 커밋한다. 그 표가 공통 드라이버로 옮겨지는 것이 `inputs` 의 선행이다(§7 걸음 1). 상태 표가
    생기기 전에 붙은 시도는 그 시도가 다음에 통째로 지어질 때까지 값이 없다 — 값이 없는 시도는 버전을 쓴다(늘 요청된다).
  - 정렬된 집합의 해시가 아니라 다이제스트 앞자리의 합이다. 충돌은 굽기가 이미 믿는 표 지문만큼 드물다.
  굽기의 인자와 도구 버전은 자산의 `code_version`(이미지 digest, ADR-0616 §4)이다.
- **파티션 정의.** 필지는 ADR-0615 의 `DynamicPartitionsDefinition(name="sido")` 를 같이 쓴다(키는 더하기만). 자산의 몸이 run 의 파티션 키를
  읽어 발행기의 "접두 하나 굽기" 명령에 인자로 넘긴다(ADR-0616 §3; 발행기는 Pipes 컨텍스트를 스스로 풀지 않는다). 행이 없는 접두는 빈 타일 파일이
  아니라 "행 없음" 을 적은 곁 파일로 구체화한다 — 구체화가 없으면 `eager` 가 하류를 끝내 요청하지 않는다. `merged` 는 그 스냅숏에 행이 있는
  접두만 합친다(없어진 시도의 옛 타일 파일을 합치면 id 관문이 영원히 거부한다).
- **한 스냅숏.** 릴리스는 서빙 Gold 스냅숏 하나를 적는다. 지금은 `join-next.json` 이 그것을 고정한다. 여기서는 곁 파일마다 스냅숏과 입력 버전을
  적고, `merged` 가 시작할 때 `inputs` 와 같은 물음으로 지금의 버전을 다시 읽어 **모든 접두의 곁 파일이 그 버전인지** 확인한다. 하나라도 뒤처졌으면
  (다시 굽기가 실패한 접두) 합치지 않고, 막는 검사 "모든 접두가 지금 버전" 을 통과 아님으로 알린다 — 관문의 거부와 같은 길이다(아래).
  `eager` 는 "구체화된 적 있음" 만 보므로 이 확인은 우리 것이다(§6).
- **곁 파일**(타일 파일 옆, 같은 이름): id 관문이 쓰는 서빙 id 해시, 행 수, 열 목록, `edits_through_change_seq`, 스냅숏, 입력 버전. 지금 관문은
  이것들을 작업 디스크의 색인과 인계물에서 읽는다 — 하류 태스크에는 그 디스크가 없다.
- **`merged` 와 `release` 를 가른다.** 관문·승격이 실패해도 8 GiB 를 다시 합치지 않는다(지금 `joined/` 가 하는 일).
- **`release` 를 막는 것은 둘이다.** (가) `merged` 와 `release` 는 **같은 크기 등급**이다(§4). 한 run 은 한 등급의 자산만 품으므로(ADR-0616 §2-9)
  등급이 다르면 둘은 다른 run 이 되고 막는 검사가 `release` 에 닿지 않는다. 같은 등급이면 같은 틱에 요청돼 한 run 에 들고, 막는 검사가 통과하지
  못하면 그 run 의 `release` 는 돌지 않는다(둘째 스파이크). (나) `release` 는 승격하기 전에 **합친 파일 곁의 관문 증거를 스스로 읽고**, 그 파일의
  증거가 통과가 아니면 승격하지 않는다. 운영자가 `release` 만 따로 돌리거나 run 이 갈리는 경우에도 듣는다 — (가)는 Dagster 의 것이고 (나)는 우리
  것이다(§6). 치르는 값: `release` 만 다시 돌 때(승격의 실패 뒤) 카탈로그 쓰기 한 번이 합치기 등급의 태스크에서 돈다.
- **같은 타일 파일들로 이미 합친 파일이 있으면 다시 합치지 않는다.** 합친 파일의 이름은 타일 파일 이름들의 해시다. 버전이 같은 접두를 다시 구우면
  `merged` 가 또 요청되므로(스파이크), 그때는 있는 파일을 그대로 쓰고 관문만 다시 본다. 승격은 풀 1 이다: 같은 유닛의
  승격 둘이 겹치면 안 된다. 그 풀은 "기계가 작아서" 가 아니라 카탈로그의 한 줄을 지키는 것이다(ADR-0616 §5 의 구분).
- **관문의 결과가 사는 곳.** 표준 Pipes 클라이언트는 일이 끝난 뒤에 결과를 돌려주고, 0 이 아닌 종료에는 예외를 낸다 — 실패한 일의 사건에 기대지
  않는다(ADR-0616 §3). 그래서 관문이 **거부한 것은 일의 실패가 아니다**: 발행기는 검사 결과(통과 아님)를 Pipes 로 알리고 **0 으로 끝난다**.
  그 뒤는 Dagster 가 한다(둘째 스파이크): 막는 검사가 통과가 아니므로 `merged` 스텝과 그 run 이 **실패로 적히고**, `release` 는 돌지 않고,
  `RetryPolicy` 는 그 스텝을 다시 돌리지 않고, 뒤의 틱은 둘 중 어느 것도 다시 요청하지 않는다. 다시 도는 것은 접두 하나가 다시 구워질 때다.
  run 재시도는 죽은 run 에만 걸리므로(ADR-0616 §2-7) 이 run 은 다시 돌지 않는다. 관문의 증거 파일은 합친 파일 곁의 객체 저장소에 쓴다. 일이 죽은
  경우(0 이 아닌 종료)는 검사 결과가 없고 run 이 실패한다 — 그때 `release` 가 돌지 않는 것은 상류의 실패 때문이다.
- **빌드 기록(카탈로그의 굽기 행)** 은 `release` 만 쓴다. 접두 태스크가 죽어도 열린 행이 남지 않는다.

### 3. 진행 상태의 자리

| 지금 | 여기서 |
|---|---|
| 어느 접두가 됐나: `join-next.json`, 미룬다는 줄 | Dagster 의 파티션 상태 |
| 캐시: 디스크의 `<unit>-partitions/…`, 하드 링크 | 객체 저장소의 `tiles/<unit>/partitions/<접두>/<해시>.pmtiles`, 조건부 쓰기 |
| 합친 파일의 캐시: `joined/<해시>.pmtiles` | `merged` 가 올린 파일(이름은 타일 파일 이름들의 해시 그대로) |
| 동등성 관문의 증거 파일: 작업 폴더 | 객체 저장소 |

**해시가 하는 일을 정확히.** 타일 파일의 이름은 그 접두의 모든 입력 줄과 굽기 입력(도구 이미지 문자열, 인자, 카탈로그에서 읽는 레이어 설정)의
해시다(`partition_archive`). 그래서 이름을 알려면 입력을 이미 읽어야 한다 — 캐시가 아끼는 것은 GDAL 과 tippecanoe 다. 입력을 읽지도 않게 하는 것은
`inputs` 의 버전이다(바뀌지 않은 접두는 요청되지 않는다). 이미지를 하나로 합치면 그 문자열이 바뀌므로 **AWS 의 첫 굽기는 모든 접두를 다시 굽는다.**

### 4. 태스크

- **run 태스크가 굽는다(ADR-0616 §2-1 의 기본 길).** run 태스크가 쓰는 이미지에 발행기·GDAL·tippecanoe 를 넣고 레지스트리에 올린다(버전은 지금의
  계약). 발행기는 `docker run` 을 조립하지 않고 실행 파일을 부른다. 접두마다 태스크는 하나다.
  첫 초안들은 `PipesECSClient` 로 굽기 이미지의 태스크를 따로 띄웠다. 합동 검토가 둘을 짚었다: `ecs/cpu`·`ecs/memory`·`ecs/ephemeral_storage` 는
  **run 태스크**의 크기라 디스크가 필요한 둘째 태스크에 닿지 않고, 접두마다 아무 일도 않는 run 태스크가 하나씩 곁에 선다(굽기 한 번에 16 개, 값을
  매긴 적 없음). 한 이미지로 하면 태그가 그대로 듣고 둘째 태스크가 없다. ADR-0616 §2-2 가 정했다: **타일만의 코드 위치**(발행기 + GDAL +
  tippecanoe)를 둔다. Dagster 의 ECS 실행기는 run 을 그 작업이 속한 코드 위치의 이미지로 띄우므로, 다른 자산의 이미지는 커지지 않는다.
- 디스크는 태스크의 임시 저장소이고 **크기는 등급으로 적는다**(ADR-0616 §2-9: 등급마다 자동화 센서 하나가 그 등급의 자산을 고르고, 센서의
  `run_tags` 가 `ecs/cpu`·`ecs/memory`·`ecs/ephemeral_storage` 와 태스크 역할을 싣는다). 접두 굽기가 한 등급, `merged` 와 `release` 가 함께 다른
  한 등급이다(§2 의 (가)). `inputs` 관측은 가장 작은 등급이다(ADR-0616 §4). 기본값에
  기대지 않는다. 하류는 타일 파일 8.2 GiB 와 합친 파일 8.2 GiB 를 함께
  든다. 디스크가 모자라면 그 태스크가 실패한다 — 여유 검사와 폴더 치우기는 없다.
- **죽은 run 의 남은 파일이 다음 run 을 막는 종류는 여기서 생기지 않는다.** ai-server 에서 2026-11-23~24 에 시간 한도로 죽은 넘겨받기
  판정 run 넷(서빙 필지 경계 하나, 건축 인허가 셋)이 `runs/<run>/verdict/` 아래에 DuckDB 단계 34.37 GB 를 남겼다. 치우기
  (`duckdb-stage-orphans.sh`)는 run 폴더의 맨 위 단계만 보므로 그것을 지우지 못했고, 서빙 필지 경계의 그림자 빌드가 11-24 13:26Z 부터 SSD
  예약(32.2 GB + 단계 34.4 GB)에서 매번 거부했다(W86d 가 저널과 run 로그에서 읽음). AWS 에서는 run 의 임시 디스크가 태스크와 함께 사라지므로
  그런 파일이 남을 자리가 없다. 그래서 치우기와 그 시험은 옮기지 않는다. ai-server 의 것은 고치지 않고, 그 표의 판정은 AWS 에서 돈다
  (코디네이터 결정 2026-11-24).
- 메모리는 태스크의 크기다. 넘으면 태스크가 죽고 run 이 실패한다. 그래서 빌드 기록을 `release` 만 쓴다(§2).
- 접두들은 동시에 돈다. 동시에 몇 개인지는 돈의 위(ADR-0616 §5: 계정의 vCPU 할당량과 줄의 한도)가 정한다.
- **재시도**는 ADR-0616 §4 의 표 하나이고, 여기에 다시 적지 않는다. 그 표의 줄을 이 자산들에 대면:
  - `partitions` 의 조건은 `eager()` 만이 아니라 **`eager()` 또는 (`execution_failed()` 이고 레인의 cron 틱이 지남)** 이다. `eager()` 만으로는
    재시도를 다 쓴 접두가 입력의 버전이 바뀔 때까지 FAILED 로 남고, 그동안 `merged` 는 "모든 접두가 지금 버전" 에서 계속 거부한다.
  - `merged` 와 `release` 에는 그 항을 **넣지 않는다.** 넣으면 관문이 거부한 합친 파일을 cron 틱마다 다시 받아(8.2 GiB) 같은 답을 낸다. 일시
    오류로 재시도를 다 쓴 `merged`·`release` 는 run 실패의 알림(ADR-0616 §6)을 받은 운영자가 Dagster 에서 다시 돌리거나, 다음 접두 굽기가 일으킨다.
  - 관문의 거부는 그 표의 마지막 줄이다. 그 줄의 "실패가 아니다" 는 **일**의 것이다: Dagster 는 그 run 을 실패로 적는다(§2).
- **레인을 처음 켤 때**(ADR-0616 §4 가 레인마다 고르라고 한 것): **켜는 PR 이 모든 접두의 백필을 한 번 낸다.** 조건에 "없으면" 항을 더하지 않는다.
  AWS 의 첫 굽기는 어차피 모든 접두를 굽고(§3), 한 번 하는 일을 조건에 영구히 남기지 않는다. 백필이 끝나면 `merged` 와 `release` 는 `eager` 가
  요청한다(스파이크: 접두가 모두 구체화된 틱에 둘이 요청됐다).

### 6. 남는 우리 것 (Dagster 가 하지 않는 일)

| 남는 것 | 왜 Dagster 의 것이 아닌가 |
|---|---|
| 접두의 입력 읽기와 타일 파일 이름 해시(ADR-0316) | 무엇이 "같은 입력" 인지는 굽기의 뜻이다 |
| tippecanoe·GDAL 인자 | 지도의 모양 |
| 합치기(ADR-0613) | PMTiles 와 MVT 의 일 |

| `release` 가 합친 파일의 관문 증거를 스스로 읽는 것(§2) | 막는 검사는 같은 run 안에서만 하류를 막는다 |

릴리스가 레이크하우스 굽기가 아닐 때만 돈다), 타일 바이트 예산, 헤더·줌 확인, tippecanoe 버전 확인, 인계물 무결성 확인, 스크립트의 대조·짝맞춤 관문.

### 8. 비용 — 양은 여기, 금액은 ADR-0616 §10

단가와 금액은 ADR-0616 §10 에만 있다(단가 표 하나, 타일 줄의 금액). 이 문서는 양만 가진다 — 아래는 필지의 전체 굽기 한 번이다.

| 항목 | 양 | 근거 |
|---|---|---|
| 접두 태스크의 시간 합 | 약 217 분 | **가정.** 잰 것은 전국 통째 169 분(GDAL 60 + tippecanoe 109, z16, 호스트가 바쁠 때). z17 은 tippecanoe 가 44 % 더 든다는 ADR-0493 의 인천 표본을 곱했다(60 + 109 × 1.44). 접두로 나눠도 합은 같다고 가정 |
| 접두 태스크의 크기(run 태스크 하나, §4) | 4 vCPU, 메모리 8~16 GB | **가정.** 잰 것은 tippecanoe 최고 5.42 GiB(전국 통째, 상한 8g). vCPU 는 재지 않았다 |
| 그래서 한 번에 | 약 14.5 vCPU·시간, 29~58 GB·시간 | 위 둘의 곱(가정의 곱) |
| 접두 태스크의 임시 저장소 | 30 GB | **잰 값의 위쪽 한계.** 접두별로 굽는 run 전체의 디스크 최고가 25.0~27.3 GB(ADR-0611). 접두 하나는 그보다 작다 |
| `merged` 태스크 | 임시 저장소 30 GB(타일 파일 8.2 GiB + 합친 파일 8.2 GiB + 여유). 합치기 250 초, 메모리 RSS 최고 180 MiB | 잰 값(걸음 0). 받기(R2 → 태스크 8.1 GiB)와 올리기, 관문의 시간은 재지 않았다. 메모리는 접두 굽기보다 작은 등급이면 된다 — 디스크만 크다 |
| `inputs` 관측 | 하루 횟수 × 짧은 태스크 하나 | **없음.** 레인의 cron 이 정한다 |
| 객체 저장소 | 한 벌 16.4 GiB(타일 파일 + 합친 파일). 옛 벌을 얼마나 두는지는 정하지 않았다 | 잰 값 |
| AWS → R2 로 올리는 바이트 | 전체 굽기 한 번에 최대 16.4 GiB | 잰 값. 받는 쪽(R2 → AWS 8.2 GiB)은 양만 적는다 |
| 접두별 입력 읽기 | **없음** | 길은 §10(그 시도의 파티션만 읽는다)이고 재지 않았다. 그 길이 지우는 것은 전국 인계물을 읽고 나누는 약 40 분이다 |
| 패치 태스크(§11) | **없음** | 이웃만 굽는다(차이의 이웃은 z14 타일 `MAX_FOLD_TILES` = 512 개 아래, 넘으면 내보내지 않는다). 시간·메모리·바이트를 재지 않았다 |
| 접두마다의 피처 색인(§11) | 한 벌 약 1.6 GB(피처마다 40 바이트 × 4 천만), 접두마다 그 몫 | ADR-0323 §1 의 크기. 굽기가 이미 모든 행을 흘리므로 따로 읽지 않는다 |
| 타일 태스크의 공인 IPv4 | 태스크 시간의 합과 같다(약 217 분 + `merged`) | 위 가정에서 나온 값 |
| `tiles` 코드 위치의 이미지 보관 | **없음** | 이미지를 짓지 않았다 |
| 옛 세대의 객체 저장소 보관 | **없음** | 몇 벌을 두는지 정하지 않았다(한 벌 16.4 GiB) |
| 로그 | 재지 않았다 | — |
| 한 달의 굽기 횟수 | 전체 굽기는 통째 빌드마다 — 평월에는 에디션의 한 번. 편집은 전체 굽기를 늘리지 않고 패치 하나씩이다(§11) | — |

**아직 비어 있는 줄**(ADR-0616 §10 이 값 없는 줄로 적은 것과 같다): `merged` 태스크의 받기·올리기·관문 시간, 한 달의 굽기 횟수,
`inputs` 관측의 횟수, 접두별 입력 읽기, 패치 태스크, 타일 태스크의 공인 IPv4, `tiles` 이미지의 보관, 옛 세대의 보관. 편집은 패치이므로(§11)
편집의 횟수가 `merged` 와 송신의 양을 곱하지 않는다 — 그 길을 버린 까닭이 이 줄이다(편집 묶음마다 합치면 하루 두 번에 한 달 약 492 GiB 를 더
올린다, 계산).

### 9. 연습은 아무것도 커밋하지 않는다

- **연습은 짓고(staged), 굽고, 관문을 모두 지나고, 멈춘다.** 발행기는 Iceberg 에 커밋하기 전에 지은 행을 Parquet 파일로 내려놓는다. 연습에서는
  그 파일이 "쓰기" 다: 접두 굽기는 그 파일을 읽고, `merged` 의 관문이 모두 돈다. 카탈로그에도 Gold 표에도 아무것도 쓰지 않는다 — Gold 를 읽는
  쪽이 볼 수 있는 것이 없다. 둘째 표도, 표 안의 표시도, 브랜치도 없다.
- **승격은 평소의 서빙 빌드다.** 원장이 그 에디션을 서빙으로 올리면 서빙 레인이 그것을 짓고 커밋하고, §2 의 자산들이 굽는다. 행이 연습과 같은
  접두는 타일 파일의 이름(내용 해시, §3)이 같으므로 **연습이 구운 타일 파일을 그대로 쓴다.**
- **Dagster 에서의 자리.** 연습은 자산이 아니라 **job** 이다(에디션이 run 의 설정). §2 의 자산은 서빙 에디션의 상태만 든다 — 후보 에디션을
  파티션 키에 넣지 않고 후보용 자산 벌도 두지 않는다. 연습이 남기는 것은 run 의 결과와 객체 저장소의 관문 증거, 캐시에 든 타일 파일이다.
  누가 언제 시작하는가(지금은 준비 판정이 7 일마다)는 구현 PR 이 ADR-0616 §4 의 표에서 고른다.
- **왜 Iceberg 브랜치가 아닌가.** 후보를 표의 브랜치에 쓰고 승격 때 `main` 을 옮기는 것이 Iceberg 의 기본 길(write-audit-publish)이고 처음 고른
  답이었다. `main` 을 옮기는 것은 이미 우리 것으로 운영에 있다(`IcebergRestCatalog::publish_branch`), Spark 는 브랜치에 쓴다. 그런데 AWS 로 가는
  레인의 커밋은 `iceberg` 크레이트이고, 최신인 0.11.0 의 추가는 `main` 에만 쓴다(`transaction/snapshot.rs` 가 `SetSnapshotRef main` 을 박는다).
  스냅숏과 매니페스트 목록을 손으로 짓는 것은 재발명이라 하지 않는다. **다시 볼 때**: apache/iceberg-rust #3150(브랜치·태그를 다루는 트랜잭션
  동작)과 #3691(이름으로 브랜치 읽기)이 릴리스에 들면, 내려놓은 파일을 브랜치로 바꿀 수 있다 — 모양은 그대로다.
- **코드가 되는 때.** 서빙 필지 경계가 공통 드라이버로 옮겨질 때다(§7 걸음 1). 그때까지 ai-server 의 연습은 지금처럼 서빙 표에 쓴다.

### 10. 접두 하나의 입력 — 발행기의 DuckDB 가 서빙 Gold 의 그 시도만 읽는다 (열린 질문 3 의 답)

- **읽는 표.** 서빙 필지 경계의 전환 PR(Spark 작업을 끄고 서빙 표를 `gold.parcel_boundary_served_versions` 로 바꾸는 PR, ADR-0564) 뒤의
  서빙 표다. 그 표는 `truncate(2, pnu)` 로 나뉘고 `pnu` 로 정렬된다(`infra/lakehouse/contracts/industrial_complex_lakehouse_contracts.json`).
  시도 하나가 표의 파티션 하나다.
- **읽는 길.** 접두 굽기 명령이 `inputs` 가 적은 스냅숏에서(`AT (VERSION => …)`) 계약의 현재 행 SQL(`LakehouseTableContract::current_rows_sql`,
  ADR-0564 §4)에 그 시도의 키 범위(`(pnu >= '41' AND pnu < '42')`, 서빙 빌드와 넘겨받기 판정이 쓰는 `sido_range`)를 걸어 발행기의 DuckDB 로
  읽는다. 둘 다 이미 있다 — 새 SQL 을 쓰지 않는다. `sido_range` 는 지금 `foundation-outbox-publisher` 안에만 있으므로 두 크레이트가 함께 쓰는
  자리로 옮긴다(베끼지 않는다).
- **내는 것.** 지금 `prepare_handoff` 가 인계물에서 만드는 것과 같다: 피처마다 id·속성·WKB 한 줄의 GDAL 입력, 서빙 id 해시, 행 수, 그리고
  §11 의 피처 색인. DuckDB 가 파일로 흘려 쓴다(`COPY … TO`) — 시도 하나의 행을 메모리에 모으지 않는다. 한 시도를 더 잘게 읽어야 한다면 그 나누기는
  공통 드라이버의 것이다(레인이 제 고리를 두지 않는다).
- **지우는 것.** 전체 굽기 쪽의 인계물(전국 25 GB)과 그것을 접두 CSV 로 나누는 약 40 분(Context 의 잰 값). 타일의 입력은 서빙 Gold 하나다 —
  패치도 인계물이 아니라 같은 표를 읽는다(§11).
- **구역은 아직이다.** 구역에는 서빙 Gold 가 없고, 인계물은 Spark(`land_use_zone_area_tile_handoff.py`)가 `silver.land_use_zone_area` 에서 쓴다.
  같은 길(접두의 범위를 건 DuckDB 읽기)이 맞는지는 그 표의 나눔을 보지 않아 모른다. §1 대로 범위 밖이다.
- **확인한 판.** 계약·`current_rows_sql`·`sido_range`·서빙 빌드의 시도별 읽기는 main `f15b94171`, 지금의 읽기(`prepare_handoff`)는 같은 판의
  `lakehouse_tile_bake.rs`. 접두 하나를 읽는 시간은 재지 않았다(§8).

### 11. 편집은 패치 세대다 — 편집마다 전국을 합치지 않는다 (열린 질문 1 의 답)

- **길.** 직원 편집이 지도에 닿는 길은 지금처럼 ADR-0323 의 패치다: 승격된 합친 파일(기본판) 위에 누적 패치 하나, 가변인 것은 manifest 하나,
  Worker 는 그대로다. 접두를 다시 굽고 전국을 다시 합치는 것은 기본판을 새로 할 때뿐이다.
- **왜 — 다시 합치는 길의 양(계산).** 편집 한 묶음을 기본판으로 내면 묶음마다 (가) 그 시도를 통째로 굽고(가장 큰 시도 약 1,600 초, ADR-0493 의
  계산), (나) 전국을 합치고(250 초, 걸음 0), (다) 합친 파일 8.2 GiB 를 R2 로 올린다. 지금의 굽기 일정(하루 두 번, `parcel-tile-bake` 의
  `45 8,20 * * *`)대로 묶음이 날마다 둘이면 (다) 만 한 달 약 492 GiB 다 — Bronze 평월 송신(90 GB, ADR-0616 §10)의 다섯 배가 넘는다(위쪽 한계).
  그리고 새 기본판은 타일 URL(`/{unit}-{base_release_id}/…`)을 바꾸므로 엣지의 모든 타일이 식는다. 패치는 바뀐 타일만 식힌다(ADR-0323 §6).
- **남의 길.** Mapbox MTS 의 incremental updates 는 만든·바꾼·지운 피처만 다시 처리하고, 데이터의 15 % 넘게 바뀌면 전체 갱신이 나을 수 있다고
  적는다([문서](https://docs.mapbox.com/mapbox-tiling-service/guides/incremental-updates/)). OSM 의 타일 서버는 diff 를 들이면서 만료된 타일의
  목록(osm2pgsql 의 `--expire-tiles`, imposm 이 diff 폴더에 쓰는 `.tiles`)을 내고 그 타일만 다시 그린다(mod_tile 의 `render_expired`). 5 % 문턱과
  MTS 의 15 % 의 비교는 ADR-0323 §8 에 있다.
- **자산 다섯째: `tiles/<unit>/patch`**(파티션 없음, `eager`, 접두 굽기보다 작은 등급 — 크기는 재지 않았다). 입력은 **지도가 보이는 스냅숏
  (manifest 의 `gold_snapshot`)부터 서빙 표의 머리까지 바뀐 키**다. 접기 run 하나가 넘긴 몫이 아니다 — 그래서 놓친 접기나 겹친 접기가 패치의
  사슬을 끊지 않고, 다음 run 이 스스로 따라잡는다. 표는 덧붙이기만 하므로(`version_seq`) 두 스냅숏 사이의 차이는 그 표에서 읽힌다. 바뀐 키의 옛
  상자는 아래의 색인에서, 새 상자는 새 행의 WKB 에서 나온다. 이웃을 고르는 것은 지금 접기가 쓰는 함수(`parcel_boundary_served_stage` 의
  `neighbourhood_tiles`, 상한 `MAX_FOLD_TILES` = z14 타일 512 개)다 — 그 함수와 상한은 Gold 를 떠나 이 자산의 것이 된다(W97c 가 서빙 필지
  경계를 공통 드라이버로 옮기며 접기의 부분 인계물과 종료 3 을 지운다, 2026-11-25). 차이의 이웃이 상한을 넘으면 패치는 아래의 5 % 와 같이
  내보내지 않는다. 그 뒤는 지금의 패치 길 그대로다(ADR-0323 §2~7: 이웃을 같은 GDAL·tippecanoe 로 굽고, 더러운 타일만 가져오고, 앞 세대와 합쳐
  누적 패치를 만들고, 관문, create-only 업로드, manifest CAS). 접기는 서빙 표에 커밋할 뿐 타일에 넘기는 것이 없다 — ADR-0375 §2 의 부분
  인계물은 걸음 5 에서 Superseded 로 적는다.
- **`release` 와 같은 풀을 쓴다.** 둘 다 manifest 를 옮긴다. CAS 가 진 쪽을 거부하지만, 진 쪽은 이웃을 다시 구워야 한다.
- **기본판의 입력과 패치의 입력을 가른다.** 접기도 서빙 표에 바뀐 키를 커밋하므로 그 시도의 (현재 행 수, `digest_sum`)이 움직인다. 그것을
  그대로 `inputs` 의 버전으로 쓰면 편집마다 접두를 다시 굽고 전국을 합친다 — 위에서 버린 길이다. 그래서 `inputs` 의 버전은 그 시도를 **마지막으로
  통째로 지은 빌드**의 상태다(§2). 통째 빌드는 필지 Silver 의 핀이나 에디션이 움직인 빌드이고, 원장만 움직인 빌드는 부분이다(공통 드라이버의
  규칙, W97c). 통째 빌드는 모든 편집을 적용하므로 새 기본판은 그때까지의 편집을 품고, `release` 는 새 기본판의 manifest 를 패치 없이 연다
  (ADR-0323 §5). 빌드가 통째였는지는 공통 드라이버가 커밋마다 스냅숏 요약에 적는 `foundation.build-scope`(`full`|`partial`)에서 읽는다 —
  `inputs` 는 시도마다 그 값이 `full` 인 가장 새 커밋의 상태를 쓴다.
- **새 기본판이 오는 중이면 패치는 기다린다.** 서빙 중인 기본판의 스냅숏이 마지막 통째 빌드의 것이 아니면(접두들이 굽히는 중) 패치는 아무것도
  내보내지 않고 끝난다. 그 차이는 새 기본판이 품는다. 새 `release` 가 구체화되면 `eager` 가 패치를 다시 요청한다.
- **피처 색인은 작업 디스크를 떠난다.** 패치는 서빙 중인 판의 피처 색인(피처마다 id 해시·내용 해시·상자, 전국 1.6 GB, ADR-0323 §1)으로 바뀐
  id 의 옛 상자를 찾고, 이웃의 나머지 행이 그 판이 구워진 행과 같은지 본다 — 다르면 패치하지 않는다(ADR-0375 §2 의 확인 그대로). 그 색인을 접두
  굽기가 접두마다 타일 파일 곁에 쓴다(이미 모든 행을 한 번 흘린다, 이름은 타일 파일과 같은 해시). 패치는 바뀐 키와 이웃이 든 접두의 색인만
  받는다(R2 → AWS 읽기는 무료, ADR-0616 §1). 패치가 만든 다음 색인은 그 패치 세대 곁에 접두마다 create-only 로 쓰고, 패치 세대의 곁 파일이
  접두마다 어느 색인인지 적는다. manifest 의 모양과 Worker 는 바뀌지 않는다.
- **누적 패치가 기본판 타일의 5 % 를 넘으면**(ADR-0323 §8) 그 패치는 내보내지 않고 막는 검사가 통과하지 않는다 — 관문의 거부와 같은 길이다(§2).
  지도는 다음 통째 빌드(다음 에디션)까지 앞 세대에 머문다. 에디션이 달마다 기본판을 새로 하므로 문턱을 넘을 때 통째 빌드를 스스로 시작하는
  장치는 두지 않는다.
- **구현 PR 이 잰 뒤 고르는 것.** 이웃의 행을 고를 때의 상자: 닿는 시도의 행마다 DuckDB 가 WKB 에서 셈하는가, 서빙 표가 상자 열을 싣는가(지금
  접기는 Silver 의 `bbox_*` 열을 쓴다). 앞의 것을 먼저 잰다.
- **구역.** 구역은 패치가 평소의 길이고 같은 모양(`tiles/zoning/patch`)이 맞는다. 구역의 이행은 §1 대로 그 인계물의 생산자가 발행기로 옮겨진 뒤다.
- **확인한 판.** 접기의 길(`parcel_boundary_served_build.rs` 의 `…_FOLD=1`, `plan`, `MAX_FOLD_TILES` = 512)·패치의 길
  (`lakehouse_tile_patch_run.rs`·`lakehouse_tile_patch_partial.rs`)·굽기 일정(`definitions/parcel-tile-bake.definition.json`)은 main `f15b94171`.
  MTS 의 문서는 2026-11-25 에 읽었다. osm2pgsql·imposm 은 그 프로젝트의 문서와 메일링 목록의 글에서 읽었고 판을 고정하지 않았다.

## 열린 질문

1. **패치 경로와 편집 접기의 자리 — §11 이 답했다.** 편집은 패치 세대의 자산이고 전국을 다시 합치지 않는다. 피처 색인은 접두마다 객체 저장소에
   있다. 남은 것은 구현 PR 이 잰 뒤 고르는 이웃의 상자뿐이다.
2. **연습 굽기 — §9 가 답했다.** 연습은 아무것도 커밋하지 않는 job 이다. 남은 것은 누가 언제 시작하는가뿐이다(구현 PR).
3. **접두 하나의 입력을 누가 읽나 — §10 이 답했다.** 발행기의 DuckDB 가 서빙 표의 그 시도 파티션만 읽는다. 구역의 입력은 §1 대로 범위 밖이다.
4. **`merged` 가 몇 번 도는가 — 데몬에서.** 스파이크(정적·동적)와 소스로는 "한 관측에 한 번" 이다. 데몬이 도는 Dagster 에서, 접두 run 이
   실패·재시도될 때도 그런지는 보지 않았다. 여러 번이면 `merged` 를 `on_cron` 으로 한다.
5. **임시 저장소와 메모리의 크기.** 가장 큰 시도의 굽기가 쓰는 디스크와 메모리를 따로 잰 적이 없고, 잰 값은 z16 의 것이다.
6. **첫 굽기 뒤의 동등성 관문.** 지금 릴리스가 레이크하우스 굽기가 되면 이 관문은 돌지 않는다. 그 뒤로 남기는가.
7. **멱등 키.** 지금은 호스트의 run 폴더 이름에서 나온다. Dagster 의 run id 에서 뽑는다 — 다시 시도한 run 이 같은 키를 갖는지 확인한다.
8. **입력의 버전으로 쓸 지문 — 답을 받았다(§2).** 남은 것은 선행이다: 서빙 필지 경계가 시도마다 커밋하는 공통 드라이버로 옮겨져 상태 표에
   `digest_sum` 을 싣는 것.

## Consequences

- 얻는 것: 예약 사이를 기다리지 않는다. 한 접두의 실패가 다른 접두를 막지 않는다. 캐시가 객체 저장소에 있어 어디서 돌든 다시 쓴다.
- 잃는 것·새로 생기는 것: 접두마다 태스크 시작 비용이 든다(지금은 run 하나가 여러 접두). 곁 파일이라는 새 계약이 생긴다. "모든 접두가 지금
  버전인가" 확인은 우리 코드로 남는다. 기본판의 입력(통째 빌드의 상태)과 패치의 입력(두 스냅숏 사이의 차이)을 가르는 규칙도 우리 코드다(§11).
  피처 색인이 접두마다 객체 저장소에 쌓인다(한 벌 약 1.6 GB). AWS 의 첫 굽기는 캐시를 쓰지 못한다(§3).
- 우리 코드가 얼마나 주는지는 구현 PR 이 센다(여기서 세지 않았다).

## 기각한 대안

- **지금의 모양을 그대로 AWS 로 옮긴다.** 나누기와 디스크에 둔 상태는 서버 한 대의 한도 때문에 생겼다. 옮기면 그 한도가 없는 곳에 그 장치만 남는다.
- **전국을 한 태스크에서 통째로 굽는다.** 잰 값이 있다(169 분, 43.7 GB, z16). 한 시도가 바뀌어도 전국을 다시 굽고, 실패하면 처음부터다.
- **연습의 후보 에디션을 서빙 표에 쓴다(지금).** 2026-11-20 에 서빙 표가 다른 Gold 표와 다른 에디션이 됐다(Context).
- **후보를 둘째 표에, 또는 표 안의 표시로.** 읽는 쪽마다 어느 것이 서빙인지 알아야 한다. 커밋하지 않으면 그 물음이 없다(§9).
- **이미 맞는 접두는 관측만 낸다(이 문서의 첫 초안).** ADR-0615 의 스파이크에서 run 이 적은 관측은 `eager` 를 움직이지 않았다. 관측만 있는 접두는
  "구체화된 적 없음" 으로 남아 하류가 끝내 요청되지 않는다. 그래서 입력을 관측 자산으로 두고 접두는 늘 구체화한다.
- **합치기·관문·승격을 자산 하나에.** 관문이나 승격이 실패하면 8 GiB 를 다시 합친다. ADR-0576 이 `joined/` 를 둔 까닭과 같다.
- **접두마다 관문을 둔다.** id 관문은 "서빙 필지 전부, 그것만" 을 본다 — 전국의 물음이다.
- **편집 묶음마다 그 시도를 다시 굽고 전국을 합친다.** 패치가 없어지고 길이 하나가 된다. 그 대신 묶음마다 8.2 GiB 를 올리고(하루 두 번이면 한 달
  약 492 GiB, 계산) 엣지의 모든 타일이 식는다(§11).
- **패치의 입력을 접기 run 이 넘긴 부분 인계물로 둔다(지금).** 접기 하나를 놓치거나 둘이 겹치면 패치의 사슬이 끊긴다. 두 스냅숏 사이의 차이는
  어느 run 이 쓴 것과도 상관없이 같다(§11).
- **피처 색인을 없애고 접기의 상자만 쓴다.** 옛 상자는 표의 옛 판에서 셀 수 있다. 그러나 "이웃의 나머지 행이 기본판이 구워진 행과 같다" 는
  확인(ADR-0375 §2)이 기본판 쪽의 기록 없이는 사라진다. 색인은 굽기가 이미 흘리는 행에서 나오므로 남긴다.
- **피처 색인을 전국 한 파일로 객체 저장소에.** 패치마다 1.6 GB 를 받는다. 접두마다 두면 바뀐 키와 이웃이 든 접두만 받는다.
