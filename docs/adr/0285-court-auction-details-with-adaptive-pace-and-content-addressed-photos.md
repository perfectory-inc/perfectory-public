# ADR 0285: 법원경매 상세는 적응형 속도로 받고, 사진은 내용 해시 객체로 둔다

- Status: Proposed
- Date: 2026-10-20
- Amends: [ADR-0281](./0281-court-auction-is-collected-openly-politely-and-stops-when-refused.md) §2 (속도), §3 (429·503 의 멈춤)
- Relates to: [ADR-0280](./0280-public-sale-court-auction-and-factory-registration-are-foundation-parcel-sources.md) (소유), ADR-0284 (머리글, PR #802 검토 중)

## Context

사장 결정(2026-10-20): 법원경매는 목록 두 개만이 아니라 사이트가 내주는 상세 전부를 받는다. 사진도 받는다(해시로 중복을 없앤 별도 객체, 첫해 약 7–20만 원 승인, 매주 실제 비용 보고). 속도는 빨라야 하지만 안전해야 한다. 프록시 없이, 처음엔 보수적으로 시작해 응답이 깨끗한 동안 단계적으로 올리고, 느려지거나 거절 신호가 보이면 바로 줄인다. 차단을 피하는 수단(위장, 지문 흉내, 우회 풀이기, IP·프록시·User-Agent 돌리기)은 어떤 것도 쓰지 않는다. 막히면 멈추고 보고한다.

확인한 사실:

- 2026-10-20 01:02–02:20 KST 목록 수집: `perfectory-foundation-court-auction/1` User-Agent, 1,377요청, 거절 없음. 진행 사건 19,647건, 물건 25,845건.
- 03:12 KST: 같은 서버에서 라이브러리 기본 User-Agent(`Python-urllib/3.x`)로 보낸 요청 2건(robots.txt, 사건 상세)이 둘 다 웹 방화벽 차단 화면(HTTP 200, HTML)을 받았다.
- 04:06 KST: 같은 서버에서 01:02 의 User-Agent 로 목록 1쪽을 1건 요청: HTTP 200, JSON, `ipcheck: true`, 50행. IP 는 막히지 않았다.
- 옛 수집기 코드(읽기 전용)가 부르던 상세 엔드포인트는 사건 6종(사건 상세, 문건·송달, 기일, 현황조사서, 현황조사 부동산 표시, 감정평가 요약)과 물건 상세 1종이다. 물건 상세 응답에 사진이 base64 로 들어 있다(물건당 20–35장, 10–20MB). 감정평가서 PDF·매각물건명세서 원문을 내주는 엔드포인트는 찾지 못했다. 옛 수집기는 브라우저 위장과 주거용 프록시 500개, 동시 64개 이상으로 돌았다. 그 방식은 옮기지 않는다.

## Decision

1. **범위.** 계약 `courtauction-go-kr.contract.json` 의 `detail.endpoints` 가 받는 엔드포인트의 하나뿐인 목록이다. 사건마다 6종, 물건마다 1종이다. 문서 원문은 엔드포인트가 확인될 때까지 범위 밖이다.
2. **적응형 속도(AIMD).** 연결 하나(HTTP/2, keep-alive)에 동시 요청 `rate_control.max_in_flight` 개까지. 시작 속도는 `floor_requests_per_second`(3초 간격과 같다)다. 깨끗한 응답이 `increase_after_clean_responses` 개 이어지면 `increase_step_requests_per_second` 만큼 올리고, `ceiling_requests_per_second` 를 넘지 않는다. 응답 시간 p95 가 그 밤의 기준값의 `slowdown_latency_ratio` 배를 넘거나 네트워크 오류가 나면 즉시 `decrease_factor` 를 곱해 줄인다(바닥 아래로는 내려가지 않는다). 값은 계약에 있고, 코드는 계약을 넘을 수 없다.
3. **멈춤.**
   - 429, 503, `Retry-After`: 그 밤의 수집을 즉시 끝낸다. 다음 밤은 바닥 속도로 다시 시작한다(ADR-0281 §3 을 이 세 신호에 한해 고친다).
   - 403, 방화벽 차단 화면, JSON 자리의 HTML, `ipcheck=false`, robots.txt 자리의 HTML: 즉시 멈추고 `refused` 로 기록하며, 사람이 원인을 확인하고 지울 때까지 다시 시작하지 않는다(ADR-0281 그대로).
   - 어떤 경우에도 다시 시도하거나 다른 길로 돌아가지 않는다.
4. **시간과 예산.** 새벽 01:00–06:00 KST(그대로). 밤마다 `night_budget_requests` 를 넘지 않는다.
5. **증분·이어받기.** 받을 순서는 새 사건, 목록이 바뀐 사건, 가장 오래 갱신되지 않은 사건 순이다. 무엇을 언제 받았는지는 Bronze 원장이 답한다. 따로 상태 파일을 두지 않는다. 예산이 끝나면 다음 밤이 이어 받는다.
6. **사진은 내용 해시 객체.** 물건 상세의 `picFile`(base64)을 풀어 SHA-256 으로 이름 붙인 객체(`photo_object_prefix` 아래, 한 번만 쓴다)로 둔다. 같은 해시는 다시 쓰지 않는다. Bronze 의 응답에는 `picFile` 자리에 해시와 바이트 수를 남긴다. 사진 바이트를 base64 로 다시 감싸면 원래 응답이 그대로 나오므로 원문은 잃지 않는다.
7. **측정.** 밤마다 원장에 요청 수, 달성한 초당 요청, 응답 시간 p50·p95, 줄인 횟수, 멈춘 이유를 남긴다. 매주 R2 사용량으로 실제 월 비용을 보고한다.
8. 프록시, IP·세션·User-Agent 돌리기, 브라우저·지문 흉내, stealth fetcher, 차단 풀이기는 계속 금지다. 수집기 코드의 금지 이름 검사가 그대로 지킨다.

## Consequences

- 백필(약 18만 3천 요청)은 평균 1 요청/초면 약 10밤, 상한 2 요청/초면 약 5밤이다. 실제 속도는 사이트 응답이 정한다.
- 사진 저장은 첫 백필 약 200–390GB(월 3–6달러)이고, 새 물건이 하루 300–700건이면 하루 3–8GB 늘어 첫해 합계 약 15–40만 원일 수 있다. 승인액을 넘으면 사장에게 먼저 알린다.
- 03:12 KST 의 차단은 이름 없는 프로그램 User-Agent 에서 났고, 04:06 KST 에 이름 있는 User-Agent 는 통과했다. User-Agent 결정(ADR-0284)은 이 사실을 보고 따로 정한다.
