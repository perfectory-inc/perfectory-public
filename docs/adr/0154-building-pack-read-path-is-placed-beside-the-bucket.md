# ADR 0154: 건물 게이트웨이는 버킷 옆에서 돌고, 묶음은 isolate 메모리에만, 답은 PNU 마다 엣지에 둔다

- Status: Accepted
- Date: 2026-10-06
- Amends: [ADR-0151](./0151-building-packs-serve-each-document-whole.md) 결정 2(PNU 마다의 엣지 응답 캐시는 묶음 경로에서
  쓰지 않는다)·결정 3(묶음 사본은 isolate 메모리와 엣지 캐시, 범위 읽기는 `onlyIf.etagMatches`)

## Context

2026-10-05 의 1,000-PNU 표본(ai-server, 동시 8, gzip)에서 묶음 경로는 객체 경로보다 차가운 p50 +441ms·p95 +561ms,
따뜻한 p50 +169ms 였고 503 이 한 건 있었다(계약 한도: p50·p95 +50ms, p99 +150ms). Workers 분석의 wall p50 은 운영 162ms,
미리보기 606ms, 미리보기 CPU p99 11ms(한도 5ms). 2026-10-06 같은 방식으로 원인을 쟀다(표본마다 처음 읽는 1,000 PNU,
운영 코드 사본 Worker 와 미리보기를 같은 배치로, 차가운 읽기 뒤 따뜻한 읽기, `Server-Timing`, Workers 분석).

1. **따뜻한 읽기**: 객체 경로는 PNU 마다 엣지 사본을 두고, 묶음 경로는 묶음 사본에서 다시 범위 읽기를 했다(R2 왕복 하나).
2. **R2 왕복 비용은 Worker 가 어디서 도느냐가 정한다.** 이 존의 한국 트래픽은 LAX 로 들어오고 버킷은 APAC 이다. 한 번
   읽힌 객체의 R2 읽기: LAX 실행 ~190ms, Tokyo(`aws:ap-northeast-1`) ~40ms, Seoul(`aws:ap-northeast-2`) ~70ms,
   Singapore(`aws:ap-southeast-1`) ~120ms. 배치는 Smart Placement 도 쟀다: 미리보기는 NRT 로, 운영 사본은 LAX 에 남겨
   두 경로가 다른 곳에서 돌았다(같은 배치 비교가 안 된다).
3. **R2 의 계층 읽기 캐시**([How R2 works](https://developers.cloudflare.com/r2/how-r2-works/)): 한 번도 안 읽힌 객체의 첫
   읽기는 느리다(LAX 실행 420–540ms, Tokyo 100–300ms). 관문 표본의 객체는 관문 (나)가 전날 이미 읽어 R2 에서 따뜻했고
   묶음은 처음 읽혔다. 같은 PNU 라도 두 경로의 R2 온도가 달라, 차가운 비교의 차이 대부분이 경로가 아니라 온도였다.
   온도를 맞추면(같은 배치 Tokyo): 둘 다 R2 에서 따뜻 +22/+10/−144ms, 둘 다 처음 −10/+136/+317ms(p50/p95/p99).
4. **묶음 크기**(documents g1, 19,010 묶음, 4.95GB): p50 112KiB, p90 488KiB, p95 981KiB, 최대 14.2MiB. 계약의
   `whole_pack_max_bytes`(256KiB) 근거는 4항목 묶음의 측정(문서 읽기 62.3% 한 번)이었고, documents 묶음에서는 문서의
   **40.6%** 만 한 번에 읽힌다(512KiB 55.4%, 1MiB 67.5%). 큰 묶음은 머리 + 범위로 R2 를 두 번 다녀온다. 그러나 비용은
   전송량이 아니다: 같은 배치에서 큰 묶음의 처음 읽기가 작은 것보다 빠르기도 했고(Tokyo, 처음 읽기 512KiB 이하 274ms, 2–4MiB
   81ms), 차이는 R2 호출의 **수**와 첫 읽기의 온도다.
5. **CPU**(Workers 분석, 차가운 읽기 구간): 묶음을 엣지 캐시에 쓰기 p99 8.2ms → 안 쓰기 5.7ms. 머리만 쓰기 6.5ms(작은
   묶음까지 범위 읽기가 됐다). 큰 묶음 범위 읽기의 `onlyIf.etagMatches` 8.4ms → 없이 6.7ms(각 약 590건). 첫 GET 을 흘려
   읽고 끊는 대신 범위로 한 번에 읽어도 같았다(8.6ms). 한 번에 읽는 작은 묶음만 읽으면 p99 5.1ms(1,093건). 따뜻한 읽기를
   엣지 사본의 스트림으로 흘려보내면 오히려 늘었다(p50 0.93 → 1.21ms).
6. **503**: 시도 하나가 기한(`r2_deadline_ms` 6s)을 다 쓸 수 있었다. 그 한 건은 클라이언트에서 6.44s(기한 + 클라이언트 경로),
   1MiB 묶음이었다. 재시도가 시작될 틈이 없었다.

## Decision

1. **PNU 마다의 엣지 답 사본을 둔다.** 한 번 답한 문서의 gzip 덩어리를 묶음 계획의 지문(`plan.fingerprint`, 세대·패치
   포함) 아래 합성 주소에 `immutable` 로 둔다. 다시 읽으면 캐시 조회 하나로 답한다(객체 경로의 PNU 캐시와 같은 일). 툼스톤과
   부재는 두지 않는다. 새 세대나 패치는 지문이 달라 옛 사본을 쓰지 않는다.
2. **묶음은 isolate 메모리(LRU)에만 둔다. 엣지 캐시에는 쓰지도 찾지도 않는다.** 버킷 옆에서는 한 번 읽힌 묶음의 R2 읽기가
   엣지 조회만큼 싸고, 사본 쓰기가 나머지 읽기보다 CPU 를 더 썼다. 사람이 다시 읽는 것은 자기 PNU 이고 그것은 결정 1 이다.
3. **범위 읽기는 조건을 보내지 않고, 답의 `etag` 를 머리의 것과 비교한다.** 키가 create-only 라 조건은 아무것도 가르지
   않으면서 CPU 를 썼다. 다른 태그의 바이트는 여전히 합치지 않는다(받은 뒤 거부).
4. **R2 시도마다 상한을 둔다**: 계약 `read_path.r2_attempt_timeout_ms`(2,000ms, 측정한 시도의 최대 1.4s 위). 넘긴 시도는
   버리고 기한 안에서 다시 묻는다.
5. **두 Worker 를 버킷 옆에 둔다**: 계약 `building_by_pnu_gateway.placement`(`{"region": "aws:ap-northeast-1"}`)를
   `wrangler.jsonc` 의 운영과 미리보기 둘 다에 투영한다. 관문은 같은 배치에서 두 경로를 비교한다. 배치는 올린 버전에
   붙는다(2026-10-06, 버리는 Worker 를 배치 없는 버전과 이 배치의 버전으로 50/50 나누자 답이 둘로 갈렸다). 그래서 운영의
   배치 변경은 카나리아의 코드 단계가 다른 변경처럼 올리고 내린다. Smart Placement 는 쓰지 않는다: 두 경로를 다른 곳에
   두었고 엣지 답 사본을 두 곳으로 나눴다.

## Consequences

- 같은 배치(Tokyo)·같은 R2 온도에서 묶음 경로는 계약 한도 안이다: 최종 코드, 처음 읽는 1,000 PNU, 차가운
  633/842/1347ms 대 운영 사본 600/958/1463ms(+33/−116/−116), 따뜻한 552/709/1165 대 554/750/1308. 503 은 측정한 모든
  실행(약 2만 읽기)에서 0 이다.
- **운영 객체 경로도 배치의 값을 치른다**: 엣지 사본 적중이 LAX → Tokyo 를 다녀와 따뜻한 p50 이 444 → 553ms 가 된다(차가운
  것은 623 → 595ms). Workers Cache(Worker 앞의 캐시, 사용자 쪽 하위 계층이 Worker 와 배치보다 먼저 답한다,
  [Workers Cache](https://developers.cloudflare.com/workers/cache/))가 그 값을 없앨 후보지만 키에 버전이 들고 만료가
  `Cache-Control` 이라, manifest 지문으로 즉시 바뀌는 지금의 엣지 사본과 의미가 달라 별도 결정이다.
- **CPU p99 5ms 는 아직이다.** 최종 코드의 차가운 읽기 p99 6.4ms(운영 사본 3.2ms), 따뜻한 3.3–3.8ms(운영 1.4–2.5ms). 큰
  묶음(R2 두 번)이 p99 를 만든다. 한 번에 읽는 묶음만이면 5.1ms 였다. 다음 단계는 묶음 크기 상한(큰 법정동을 PNU 앞자리로
  나눠 모든 묶음을 한 번에 읽기)이고, 그것은 발행기·manifest·Worker 의 형식 변경과 전체 재굽기(약 3만 묶음, R2 Class A)라
  소유자 승인 뒤 별도 ADR 이다. 관문의 한도는 바꾸지 않는다.
- **관문 (나)의 차가운 비교는 R2 온도가 같아야 공정하다.** 같은 표본을 여러 번 재면 객체 쪽만 R2 에서 따뜻해진다. 실서비스
  에서는 반대로 묶음이 따뜻하다(법정동 하나를 누가 읽으면 그 묶음 전체가 따뜻해진다, 객체는 PNU 마다). 관문 탐침이 두 쪽을
  먼저 같은 온도로 만드는 단계는 후속 작업이다.
- 미리보기와 운영 코드 사본의 실측 배포는 이 결정의 측정을 위해서만 했다(운영 Worker·manifest·R2 쓰기 없음). 버린 Worker 는
  지웠다.
