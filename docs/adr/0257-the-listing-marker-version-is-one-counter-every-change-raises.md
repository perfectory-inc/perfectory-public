# ADR 0257: 매물 마커 버전은 모든 변경이 올리는 카운터 하나다

- Status: Accepted
- Date: 2026-10-16
- Amends: GZ-ADR-0038 (매물 마커 서빙 인덱스·필터 마스크의 `projection_version` 뜻)

## Context

웹 지도는 매물 마커 소스에 서버의 `projection_version`을 싣는다. 카운트 API가 그 값을 주고, 델타·툼스톤 API는
`base_version`보다 큰 행만 돌려준다. 마스크 API는 `base_version`이 지금 값과 다르면 409로 거절한다.

그 값은 `listing_marker_projection` 행 버전의 `max()`였다. 행 버전은 매물마다 1부터 센다. 그래서 두 경우를 놓친다.

- 새 매물은 버전 1로 들어온다. 최댓값이 오르지 않아 지도가 새 매물을 모르고, `base_version` 이후 델타에도 없다.
- 최고 버전 매물을 내리면 그 행이 공개 집합에서 빠진다. 최댓값이 오히려 내려간다.

## Decision

1. **버전은 단일 행 카운터 하나다.** 표 `listing_marker_state(version)`에 행이 하나 있다. 마커 투영을 바꾸는
   트랜잭션은 같은 트랜잭션에서 `update listing_marker_state set version = version + 1 returning version`을 하고,
   그 값을 투영 행·델타 로그·툼스톤 로그에 찍는다. 쓰는 곳은 둘이다.
   - 매물 저장 뒤 동기화와 수동 upsert(`marker_projection.rs`): 실제로 바뀐 행이 있을 때만 올린다.
   - Foundation 앵커 가져오기(`foundation_anchor.rs`): 가져온 PNU에 공개 매물이 있으면 한 번 올린다.
2. **읽는 쪽은 그 행을 읽는다.** 카운트와 마스크의 `projection_version`은 `listing_marker_state.version`이다.
   델타·툼스톤은 찍힌 행 버전을 `base_version`과 비교한다(그대로).
3. **마이그레이션은 지금까지 낸 어떤 값보다 크게 시작한다.** 투영·델타·툼스톤의 최댓값으로 채운다. 클라이언트가
   들고 있는 옛 `base_version`으로도 이후 변경을 모두 받는다.

### 왜 동시 쓰기에서도 맞는가

행 잠금은 커밋까지 간다. N-1을 받은 트랜잭션이 커밋하기 전에는 다른 트랜잭션이 N을 받을 수 없다. 그래서 커밋
순서가 버전 순서와 같다. 읽는 쪽이 N을 보면 N 이하의 변경은 이미 모두 커밋되어 보인다. "N 이후" 델타가 N-1을
놓칠 수 없다.

### 버린 안

- **`max(projection_version)`** — 지금 방식. 새 매물·내린 매물을 놓친다(위 Context).
- **Postgres 시퀀스(`nextval`)** — 트랜잭션 밖에서 값을 준다. N-1을 받은 트랜잭션이 N보다 늦게 커밋할 수 있다.
  읽는 쪽이 N을 본 뒤 N-1이 커밋되면, "N 이후" 델타가 N-1을 영영 놓친다. 막으려면 커밋된 최소 미완 값을
  따로 추적해야 한다. 우리 규모에서는 그 장치보다 행 잠금 하나가 단순하다.
- **커밋 시각·`xmin`** — 시각은 순서를 보장하지 않고, `xmin`은 랩어라운드와 스냅숏 해석이 필요하다.

## Consequences

- 마커를 바꾸는 쓰기는 이 행에서 줄을 선다. 매물 저장 속도로는 문제가 없다. 앵커 가져오기는 커밋까지 행을 쥐니,
  그동안 매물 저장이 기다린다.
- 카운트 버전은 이제 필터별이 아니라 전역이다. 필터 밖 매물이 바뀌어도 지도는 다시 받는다. 값이 놓치는 것보다 낫다.
- 매물 행을 직접 지우면(외래키 cascade) 카운터가 오르지 않는다. 운영 코드에 그런 경로는 없다. 생기면 같은 갱신을
  거쳐야 한다.
- 테스트의 `truncate_all`은 카운터를 0으로 되돌린다. 운영에서 카운터는 내려가지 않는다.
