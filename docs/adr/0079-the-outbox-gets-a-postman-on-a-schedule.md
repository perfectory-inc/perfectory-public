# ADR 0079: outbox 는 시간표 위의 우체부를 갖는다

- Status: Accepted
- Date: 2026-09-04

## Context

첫 실경보(2026-09-03, 알림 관 개통 직후)가 가리킨 것: `catalog.outbox_event` 에 발행
담당자가 존재한 적이 없었다 — published 0, 적재가 낳은 이벤트 1,442건(이후 수집분 포함
1,612건)이 무기한 대기. 실물 조사 결과 전송로의 현재 상태는 이렇다:

- 발행기(`publish-outbox-once`)는 이미 있다: 틱당 50건, 이벤트를 **R2 객체로 실체화**
  (claim-check)하고 fan-out 으로 통지한다.
- fan-out 실측: Kafka 비활성, 웹훅 미설정 → **LoggingBroadcaster**. 즉 구독자는 현재 0
  이고, 공짱은 이벤트가 아니라 앵커 아티팩트 파일을 당겨간다(pull).
- 2026-09-04 수동 완주로 1,612건 전량 발행 확인(원장 pending 0).

## Decision

1. **상주 데몬이 아니라 시간표다.** `foundation-outbox-publish.timer` 가 30분마다
   `publish-outbox-once` 를 돌린다. 근거는 실측 볼륨 — 이벤트는 적재·수집 때만 뭉텅이로
   생기고(일 단위), 틱당 50건이면 30분 주기로 하루 2,400건을 소화한다. 상주는 실구독자
   (Kafka/웹훅)가 생기는 결정에서 재검토한다.
2. **발행의 뜻을 선언한다**: "구성된 전송로로 넘겼다". 현재 전송로는 R2 이벤트 객체
   실체화 + 로그 통지이며, 이 상태는 숨김이 아니라 이 문서의 선언이다. 구독자 0 인
   방송을 멈추지 않는 이유: 원장(published_at)이 진실이 되고, 이벤트 객체가 미래
   구독자의 재생 원천이 된다.
3. **설치는 릴리스의 `timers` 동사가 소유한다** (ADR-0077 의 전례). 유닛·스크립트는
   릴리스 안에 살고, 배포가 시간표를 함께 나른다.
4. **실패는 슬랙이 안다.** 스크립트는 실패 시 `#alerts` 로 외치고, 기존
   `FoundationPlatformOutboxOldestPendingStale` 경보는 시간표가 죽었을 때의 이중
   안전망으로 그대로 둔다.

## Consequences

- 적재·수집이 낳는 이벤트는 최대 30분 안에 발행된다. 4시간 경보는 정상 상태에서 다시
  울리지 않는다.
- 구독자 없는 발행이라는 사실이 문서화됐다 — "이벤트를 누가 들어야 하는가"(Kafka 도입,
  공짱 push 전환 여부)는 명명된 다음 결정이다.
- 우체부 셋(백업·훑기·발행)이 같은 관례(EnvironmentFile·강화 옵션·timers 동사) 아래
  모인다.
