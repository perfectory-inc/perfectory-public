# ADR 0330: 공매 회차는 미디어가 다 들어갈 때까지 상세를 다시 받고, 열린 회차부터 받는다

## Context

2026-10-29 실측(Trino `r2.silver`, 각 회차의 최신 판):

| 무엇 | 수 |
| --- | --- |
| 목록에 살아 있는 회차(물건관리번호·공매조건번호) | 72,188 (물건 24,332) |
| 그중 입찰 마감이 지나지 않은 회차 | 51,333 (물건 8,997; PNU 있는 회차 39,318 · PNU 5,278) |
| 사진이 Silver 에 있는 회차 | 622 (0.86%) · PNU 77 |
| 열리고 PNU 있는 회차 중 사진 있는 것 | 287 / 39,318 (0.73%) |
| 서빙 문서(v2) 4,613 중 사진 있는 PNU | 약 5 |

원인은 셋이다.

1. **"받음" 표시가 미디어와 따로 놀았다.** 수집기는 물건상세를 받으면 그 회차를 `state.detailed` 에 넣었다.
   미디어는 같은 run 의 상세 줄 전체 URL 을 정렬해 run 당 50장만 받았다. 회차당 사진·감정평가서는 4~5개라 50건의
   상세 중 몇 건만 사진이 들어가고, 나머지는 '받음'으로 남아 **다시는 사진을 받지 않았다.** 수집은 매시 성공이었고 아무도
   몰랐다.
2. **처리량.** 물건상세 run 당 50건 = 하루 1,200 회차. 열린 회차만 51,333 → 한 바퀴 43일.
3. **순서.** 밀린 회차를 키(물건관리번호) 순으로 받았다. 내일 마감인 회차도 석 달 뒤 회차와 같은 줄에 섰다.

측정한 그 밖의 사실:

- **목록 행은 자주 바뀌지만 사진과는 무관하다.** 10-26~29 바뀐 판 20,793 중 상태코드 13,038·유찰횟수 9,574 는
  회차 상태(목록에서 이미 Silver 로 간다). 제공자의 수정일시(`mdfcnDt`)가 바뀐 것은 1,836(하루 ~525).
- **새 회차는 하루 ~1,300, 새 물건은 ~200**(10-20~28 평균). 물건당 회차 ~5.7(앞 회차가 미리 올라온다).
- **미디어 URL 은 회차를 넘어 같다.** 10-29 03:07 run: 다운로드 상한 50 으로 50 회차(물건 7)에 사진 행 155 — 한 번 받은
  URL 이 같은 물건의 다른 회차 응답에도 그대로 나온다. 그러니 URL 로 기억하면 다시 받지 않아도 된다.
- **용량.** 사진 평균 213KB·물건당 3.3장, 감정평가서 평균 6.5MB·물건당 1.4개 → 물건당 ~9.8MB(93% 가 감정평가서).
- **API 한도.** data.go.kr 게이트웨이 `X-RateLimit-Limit` 100,000/일/API(운영계정, 2026-10-19 실측), 같은 키에 다른
  사용자가 있어 계약은 1/5 인 20,000 만 쓴다(`daily_call_limit_per_api`). 초당 한도는 공시가 없어 요청 간격 0.5s 를 유지한다.
  사진은 API 가 아니라 KAMCO 웹(`www.onbid.co.kr`)에서 받는다.

## Decision

1. **회차는 미디어가 다 들어가야 완료다.** `state.details` 는 상세를 받고 그 미디어 URL 이 전부 저장됐거나 영구
   제외(형식 불명·`max_file_bytes` 초과·4xx)된 회차만 담는다. 상한·시간·타임아웃·5xx 로 덜 받힌 회차는 표시하지 않고,
   다음 run 이 상세를 다시 받는다(상세 1콜은 싸고, 링크도 새로 받는다). 옛 `detailed` 는 읽지 않는다 — 사진을 놓친
   회차가 섞여 있으므로 한 번 다시 받는다.
2. **받을 순서와 '바뀜'.** 아직 완료가 아닌 회차, 그다음 제공자가 바꾼 회차를 받는다. 각각 **입찰 마감이 지나지 않은 것
   먼저, 마감 이른 순**(마감 모름은 뒤), 같으면 키 순. '바뀜' 은 목록 행의 계약 `item_detail.refresh_on_list_fields`
   (`mdfcnDt`) 값 다이제스트가 완료 때와 다른 것이다 — ADR-0180 §1 의 "읽는 열이 다른 행" 을 그대로 쓴 것으로, 상세가
   목록에서 얻는 것은 없으니 제공자의 수정 표시가 그 열이다. 상태·유찰 변화로는 다시 받지 않는다. 목록 전수 때의 마감·다이제스트는
   `state.listed` 에 둔다.
3. **처리량은 실측 한도 안에서, 시간으로 묶는다.**
   - 상세 `per_run_limit` 50 → **600**(0.5s 간격 ≈ 6분, 하루 14,400 ≤ 20,000).
   - 미디어는 회차 단위로 받는다. 한 회차의 URL 을 `media.concurrency`(6)개씩 동시에 받고, **`run_time_budget_seconds`
     (600)가 지났거나 남은 다운로드 상한이 그 회차를 다 담지 못하면 새 회차를 시작하지 않는다** — 반쯤 받힌 회차가 없고,
     벽시계 최악은 600s + 한 회차(≤ ceil(URL/6)×20s). 모든 시도(실패 포함)가 상한을 깎는다(2026-10-26 사고).
     `per_run_limit` 50 → 3,000, `daily_download_limit` 500 → 20,000.
   - 한 run 최악: 목록 ~2분 + 입찰결과 백로그 ≤1,000×~0.7s ≈ 12분 + 상세 ~7분 + 미디어 ≤11분 + 커밋 ~1분 ≈ 33분 <
     작업 한도 40분.
   - **이미 저장한 URL 은 다시 받지 않는다.** `state.media` 가 URL → (sha256·형식·크기·물건)을 열린 물건의 것만 기억한다
     (물건이 목록에서 빠지면 지운다). 제공자가 바꾼 회차(§2 refresh)만 기억을 건너뛰고 다시 받아 확인한다 — 같은 바이트면
     내용주소라 새로 쓰지 않는다(ADR-0298). 사진이 감정평가서보다 먼저다.
4. **커버리지를 지표로 남기고 떨어지면 알린다.** 수집기가 run 마다 `/var/lib/foundation-jobs/metrics/onbid-item-detail.prom`
   에 입찰이 끝나지 않은 회차 수·완료 회차 수·그중 사진 있는 회차 수·비율을 쓴다(쓰고 rename). 디렉터리는
   `jobs.v1.json` `state_directories`(수집 작업의 `state_paths`)이고, node-exporter 가 배포의 textfile 옆에서 함께 읽는다.
   규칙 `FoundationOnbidDetailCoverageRegressed`(하루 최고치보다 5%p 넘게 3시간)·`FoundationOnbidDetailCoverageStale`
   (3시간 무갱신). ADR-0001: 이 경보가 막는 사고는 2026-10-28 의 것 — 수집이 매시 성공인데 사진이 0.86% 에서 멈춰 있던 일.
5. **서빙 주기는 바꾸지 않는다.** 새 사진은 hourly Silver → `gold_public_auction_rebuild`(매일 21:35, 전량 143초·4,713행·
   0.001GB) → 자기 bake(ADR-0303, 45초·303MB 세대)로 화면에 간다. 사진만 더 자주 내보낼 이유가 없다: 사진은 그것이 붙은
   회차보다 먼저 화면에 갈 수 없고, 회차 자체(새 회차·상태)가 하루 한 번 Gold 로 간다(일일 반영 지시, ADR-0077). 4회/일로
   올리면 Spark 3슬롯 × 2.4분 × 3 ≈ 하루 7분이 더 들 뿐이지만, 바꿀 것은 사진이 아니라 공매 레인 전체의 신선도이므로 그
   결정은 따로 한다. 백필(아래 4일) 동안 화면 커버리지는 하루 한 계단씩 오른다.

## Consequences

- **커버리지(전망).** 상세 하루 14,400 − 새 회차 ~1,300 − 바뀐 회차 ~525 ≈ 순 12,600/일. 열린 회차 51,333 은 **약 4일**,
  목록 전체 72,188 은 약 6일에 한 바퀴. 이후 새 회차는 다음 run(최대 1시간, 목록 전수는 3시간마다)에 상세·사진이 들어가고,
  화면에는 다음 Gold(21:35)에 간다. 미디어는 물건 단위로 한 번: 백필 중 하루 ~2,500 물건 × URL 4.7 ≈ 11,800 다운로드
  (≤ 20,000), ~25GB/일, run 당 ~1GB(10분 → ~1.7MB/s). KAMCO 가 더 느리면 시간 상한이 끊고 백필이 늘어질 뿐 run 은 안전하며,
  지표에 그대로 보인다.
- **비용.** data.go.kr 무료. R2 Standard $0.015/GB-월(10GB 무료), ₩1,400/$:
  - 열린 물건 8,997 ≈ 88GB → 월 약 ₩1,600. 목록 전체 24,332 ≈ 239GB → 월 약 ₩4,800.
  - 증가: 새 물건 ~200/일 × 9.8MB ≈ 59GB/월 → 매달 월 ₩1,240 씩 늘어 1년 뒤 월 약 ₩20,000(append-only, 내용주소는
    지우지 않는다). 그중 93% 가 감정평가서 PDF 이다 — 사진만이면 1/14.
  - Class A(PUT) 약 11.5만 건 ≈ $0.5 1회, 이후 월 ~$0.13. egress 0.
- **상태 파일.** `state.media` 는 열린 물건의 URL ~11만 개(수십 MB JSON)를 쥔다. 매 run 한 번 쓰고 rename 한다.
- **확인하지 못한 것.** KAMCO 다운로드 속도·연결 한도(동시 6), 제공자가 `mdfcnDt` 없이 사진을 바꾸는 경우(그러면 다음 수정
  표시까지 옛 사진). 첫 배포 뒤 run.log 의 `onbid-media-summary-json`(`reused`·`downloaded`·`time_budget_reached`)과 지표로 잰다.
- **관찰(이 ADR 범위 밖).** 10-28 21:38 `gold_public_auction_rebuild` 의 출력 이벤트(asset event 3912)가
  `by_pnu_public_auction_bake` 를 시작하지 않았다(참조는 20:52 부터 있음, 큐 행·run 없음). bake 는 10:45 대체 일정으로만
  돈다 — Gold 뒤 화면 반영이 ~13시간 늦다. 별도로 고친다.
- 시험: `data_go_kr_onbid_collect/tests.rs`(완료 전 재요청·`mdfcnDt` 로만 refresh·순서·다이제스트·커버리지·메모 정리·옛 상태
  호환), `onbid_media.rs`(회차 단위 정착·메모 재사용·4xx 영구 제외·503 재시도·상한에서 회차 경계 정지·refresh 재확인).

개정 각주(2026-10-29): 상세와 완료의 단위는 [ADR-0339](./0339-a-public-auction-item-is-detailed-once-for-all-its-rounds.md)가
회차에서 물건(`cltrMngNo`)으로 바꿨다 — 미디어는 물건의 것이라 상세를 물건마다 한 번 받고 그 물건의 모든 회차가 쓴다.
§1·§2·§3(미디어 하루 상한)과 Consequences 의 "약 4일"은 그 ADR 이 고친다.
