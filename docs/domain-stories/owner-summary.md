# 사장 요약 — 서버 작업을 "명세 하나 + 러너 하나"로

## 결론

- 10-15 ~ 10-17 사고 대부분은 **작업에 대한 같은 사실이 여러 곳에 따로 적혀 있어서** 났습니다.
- 그래서 **작업마다 명세 한 줄**에 모두 적고, 나머지(systemd 유닛·폴더·sudoers·Airflow)는 거기서 **만들어 냅니다**.
- 모든 작업은 **러너 프로그램 하나**(`foundation-job-run`, Rust)가 돌립니다. 결과와 종료 코드는 러너만 정합니다.
- **배포는 돌던 작업을 기다리지 않습니다.** 돌던 작업은 자기 릴리스로 끝까지 돌고, 새 실행만 새 릴리스를 씁니다.
- 결정 문서: [ADR-0270](../adr/0270-server-jobs-come-from-one-spec-and-run-through-one-runner.md). 이야기 그림: [도메인 스토리](./README.md).
- **정하실 것은 두 가지**입니다(맨 아래).

## 옮기는 단계와 "끝났다"의 기준

시간 추정은 측정 전이라 적지 않습니다. 단계마다 작은 PR 여러 개입니다.

| 단계 | 하는 일 | 끝났다의 기준(잴 수 있는 것) |
|---|---|---|
| 0 | 이 문서 | 사장 결정 |
| 1 | 명세 v2 + 생성기(`cargo xtask jobs`) | 작업 유닛의 `TimeoutStartSec`·`ReadWritePaths` 를 손으로 쓴 곳 0개. 생성물을 손으로 고치면 CI 실패(심어서 확인) |
| 2 | 러너를 작업 2개에 | 가벼운 1개·무거운 1개가 러너로 7일 연속 돌고, 결과 줄과 종료 코드가 다른 실행 0건 |
| 3 | 무거운 대기열 | `takes_turns` 칸 0개, "미뤄진 작업" 기록 0건, 빌드가 대기열로 자리를 얻음 |
| 4 | 배포가 기다리지 않음 | 무거운 작업이 도는 중에 나간 배포 10번 연속: 멈춘 DAG 0, 죽은 작업 0, 로그에 "작업 끝 기다림" 0 |
| 5 | 나머지 작업 옮기기 | 유닛이 부르는 `scripts/ops` 셸 0개 |
| 6 | 지도·알림 | 일부러 실패시킨 훈련에서 Slack 알림 1개, 지도에 기다린 시간과 돈 시간이 따로 보임 |
| 7 | 셸 정책 | 대상이 "러너·xtask"인 셸 0개, 100줄 넘는 새 셸을 CI 가 거부(심어서 확인) |
