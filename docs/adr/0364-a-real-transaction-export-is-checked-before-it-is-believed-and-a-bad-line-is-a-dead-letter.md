# ADR 0364: 실거래 내보내기는 믿기 전에 확인하고, 나쁜 줄은 거부 줄로 남긴 채 나머지를 싣는다

- Status: Accepted
- Date: 2026-10-30
- Amends: [ADR-0348](./0348-real-transactions-come-from-the-rt-molit-bulk-export-and-recent-months-are-pulled-again.md)
  §2 (세션 하나에 동시 3건), [ADR-0349](./0349-a-real-transaction-row-is-named-by-its-content-and-a-cancellation-is-a-new-version.md)
  §3 (내보내기 전체를 그대로 싣는다)

## Context

2026-10-30 운영 Silver 적재(`rt_molit_real_transaction_silver`)가 매시간 같은 줄에서 죽었다. 오류는
`ValueError: line 13197 has 14 cells for a 20-column header` 였고, Silver 커밋은 하나도 내려앉지 않았다.

| 사실 | 근거(읽기 전용) |
|---|---|
| 오피스텔 전월세 2026-10 의 개수 확인은 13,180행이다. 머리말 16줄을 더하면 13,196줄에서 끝나야 한다 | Bronze 원장 `logical_record_count` |
| 그 Bronze 객체는 3,080,140 B 다. 같은 달을 손으로 다시 받은 것은 2,402,504 B, 13,196줄이고 문제가 없다 | `catalog.bronze_object`, 재다운로드 |
| 13,197번째 줄부터 14칸 줄(토지 내보내기의 모양)이 붙어 있다 | 오류 메시지 |
| 아파트 매매 2026-08·09·10, 오피스텔 전월세 2026-09·10 을 다시 받았다. 모두 `NO` 가 1..N 이고, 칸 수가 맞고, 줄 끝은 CR/LF 뿐이다 | 재다운로드 |

원인은 수집기에 있다. 한 세션에 내려받기 3건을 동시에 돌렸다(ADR-0348 §2). 제공자는 검색 조건을 세션에 둔다.
그래서 한 내보내기의 응답에 다른 내보내기의 줄이 섞였다. 파서는 그것을 처음 보고 멈췄을 뿐이다.

한 원천의 줄 하나가 레인 전체를 멈추게 하는 것도 그대로 둘 수 없다. 저장소의 기존 격리 방식도 찾았다.
- `silver.parcel_number_change_history` 의 `quarantine_reason`: 같은 표 안에 사유 열을 둔다.
- 실거래 행에는 그 방식을 쓸 수 없다. 나쁜 줄은 칸이 맞지 않아 행 이름(내용 해시)을 만들 수 없기 때문이다.

## Decision

1. **내보내기 하나는 세션 하나다.** 수집기는 내보내기마다, 다시 물을 때마다 새 세션을 연다. 동시 3건은 그대로 두고,
   서로 다른 세션에서 돈다.
2. **수집기는 믿기 전에 확인한다**(`export_problem`). 확인하는 것은 세 가지다.
   - 머리말의 `계약일자` 가 요청한 달이다.
   - 데이터 줄 수가 개수 확인과 같다.
   - `NO` 가 1..N 으로 이어진다.

   하나라도 아니면 새 세션에서 다시 묻는다(재시도 횟수는 계약). 끝내 맞지 않으면 Bronze 에 쓰지 않는다. 그 달은
   다음 run 이 다시 묻는다. 그 run 은 받은 것을 다 쓴 뒤 실패로 끝나 경보를 낸다.
3. **Silver 는 줄 단위로 거부하고 나머지를 싣는다.**
   - 읽는 방식: 머리줄부터 텍스트를 한 번에 CSV 로 읽는다. `str.splitlines` 는 쓰지 않는다. CR/LF 만 줄 끝이고,
     따옴표 안의 줄바꿈은 한 줄로 남는다.
   - 거부하는 줄은 세 가지다. 칸 수가 머리줄과 다른 줄, `NO` 가 이 내보내기의 차례를 잇지 않는 줄(다른 내보내기의
     줄), `계약년월` 이 내보내기의 달 밖인 줄이다.
   - 통째로 거부하는 내보내기는 머리줄이 없거나 머리말이 다른 달을 말하는 것이다. 이때 줄 번호 0 으로 하나를 남긴다.
   - 거부한 줄은 새 표 `silver.real_transaction_rejected` 에 남는다. 열은 Bronze 객체 키, 줄 번호, 원문, 사유다.
   - 나머지 줄은 평소처럼 실린다.
4. **문턱은 계약에 있다**(`silver_load.max_rejected_share`, 0.1%).
   - 한 내보내기에서 거부가 이 비율을 넘거나 통째로 거부되면, 적재는 모든 것을 실은 뒤 실패로 끝난다(경보).
   - 거부 수는 적재 요약(`rejected`, `rejected_share`, `rejected_reasons`)에 남는다.
   - 실린 객체는 기록되므로 다음 run 이 같은 객체로 다시 멈추지 않는다.

## Consequences

- 이미 Bronze 에 있는 섞인 객체(2026-10-30 의 것)는 이 적재가 처리한다. 자기 줄은 싣고, 붙은 줄은 거부 줄로 남긴다.
  최근 3개월은 매일 다시 받으므로, 다음 깨끗한 내보내기가 같은 달의 새 판이 된다.
- 동시 3건은 세션이 나뉘므로 그대로 둔다. 확인(2번)이 다시 섞인 응답을 Bronze 에 들이지 않는다.
- 사장이 정한 안전장치(429·5xx 재시도, 분명한 거절이면 멈춤)는 그대로다.
