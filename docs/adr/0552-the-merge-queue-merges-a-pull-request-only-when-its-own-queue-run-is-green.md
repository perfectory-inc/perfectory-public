# ADR 0552: 머지 큐는 자기 큐 실행이 초록인 PR 만 병합한다

- Status: Accepted
- Date: 2026-11-12
- Amends: [ADR-0211](./0211-the-merge-queue-merges-a-batch-whose-head-is-green.md) 1항(`HEADGREEN`),
  [ADR-0313](./0313-merge-queue-and-pull-requests-verify-only-what-changed-and-main-does-not-repeat-the-queue.md)의
  "큐 실행의 비교 기준은 main 끝"이라는 전제
- Keeps: [ADR-0421](./0421-a-run-that-failed-only-because-its-runner-did-is-re-run-once-and-the-merge-queue-keeps-building-two.md) 3항(동시 빌드 2)

## Context

2026-11-11 하루 동안 main 이 두 번 깨졌고(#1268 뒤 `foundation-jobs`, #1302 뒤 공짱 사본 시험), 큐는 세 번 비워졌다.
"필수 검사를 통과한 것만 main 에 들어간다"는 전제를 실물로 다시 쟀다(2026-11-12, `gh api`, 읽기 전용).

### 측정 1 — 큐 실행은 앞 항목과 비교한다

`merge_group.base_sha` 는 main 끝이 아니라 **큐에서 바로 앞 항목의 커밋**이다. 첫 항목만 main 끝과 비교한다.

| 큐 실행 | 만들어진 때 | 그때 main 끝 | 실행이 쓴 `CHANGE_SCOPE_BASE` |
|---|---|---|---|
| #1331 (`pr-1331-391ce804`) | 00:22:43Z | `391ce804` | `391ce804` (main 끝) |
| #1332 (`pr-1332-25c8e040`, run 43126832566) | 00:22:43Z | `391ce804` | `25c8e040` (#1331 의 큐 커밋, 아직 main 아님) |

ADR-0313 은 "큐의 머리는 기준에 앞선 모든 변경을 더한 것이므로 비교가 main 에 없는 모든 변경을 담는다"고 적었다.
둘째 항목부터는 사실이 아니다. 큐 실행은 **자기 PR 의 변경만** 검증한다.

### 측정 2 — 그래서 `HEADGREEN` 에서는 필수 검사가 빨간 PR 이 병합됐다

`HEADGREEN` 은 묶음의 머리 커밋만 초록이면 묶음 전체를 병합한다. 머리의 실행은 머리 PR 의 변경만 봤으므로,
앞 항목의 빨강을 다시 확인한 적이 없다. 큐에서 필수 워크플로가 실패한 커밋 가운데 main 의 조상인 것을 셌다
(실패한 `merge_group` 실행 198개의 `head_sha` 를 `git merge-base --is-ancestor` 로 대조).

| 날짜 | PR | 큐에서 실패한 필수 검사 | 실패한 실행 | 결과 |
|---|---|---|---|---|
| 11-10 18:58Z | #1243 | `required/repository` | 42880599967 | 병합됨 |
| 11-11 04:30Z | #1281 | `required/foundation` | 42959624602 | 병합됨 |
| 11-11 04:30Z | #1255 | `required/foundation` | 42959626739 | 병합됨 |
| 11-11 04:52Z | #1278 | `required/foundation` | 42961989303 | 병합됨 |
| 11-11 16:16Z | #1307 | `required/foundation` 외 4개 | 43056744164 | 병합됨 |

11-11 04:30~05:47Z 의 세 건은 #1268 이 깨뜨린 `foundation-jobs` 시험에 걸려 실패했다. 뒤따른 #1271 은 자기 변경이
그 크레이트에 닿지 않아 초록이었고, 큐는 넷을 함께 병합했다. main 은 고치는 #1293 이 병합된 07:16Z 까지 2시간 46분 깨져 있었다.

### 측정 3 — 처리량을 막는 것은 러너 칸이고, 큐 실행의 절반 이상이 버려진다

| 지표 (2026-11-11) | 값 |
|---|---:|
| 24시간 병합 | 55건(시간당 2.3), 병합 없는 시간 7개 |
| PR 열림 → 병합 | 중앙값 6.3시간, p90 13.7시간 |
| 열림 → 첫 큐 투입 | 중앙값 1.6시간 |
| 첫 큐 투입 → 병합 | 중앙값 2.8시간, p90 8.9시간 |
| 큐 실행 한 번(Foundation CI 성공) | 중앙값 32.5분, p90 53.8분 |
| 큐 실행 수 ÷ 병합 수 (07:16Z~00:45Z, 17.5시간) | 100 ÷ 37 = **2.7** |
| 큐에서 손으로 뺀 횟수 / 검사 실패로 빠진 횟수 | 17 / 4 |
| 바쁜 3시간(21~24Z) 러너 사용 | 20칸 중 평균 16.5칸, 그중 `merge_group` 12.6칸 |
| 같은 3시간 큐 커밋 하나의 작업 시간 | 중앙값 88 작업·분, p90 142 |

큐 체류가 병합 시간의 가장 큰 몫이다. 그런데 동시 빌드를 2 에서 올려도 처리량은 늘지 않는다. 바쁜 시간에는 표준
러너 20칸이 이미 차 있고, 큐가 그 대부분을 쓴다(ADR-0421 3항의 계산을 작업·분으로 다시 확인). 늘릴 수 있는 것은
**버려지는 실행**이다. 병합 하나에 큐 실행 2.7번이 들었다. 큐를 비우고 다시 넣은 것(3번), 깨진 main 위에서 연달아
실패한 항목, 그 뒤 항목의 재빌드가 그만큼이다.

## Decision

1. **`grouping_strategy` 는 `ALLGREEN` 이다.** `tools/github/main-ruleset.json` 의 `merge_queue` 에서 이 한 값만 바꾼다.
   큐에 든 PR 은 자기 큐 실행(앞 항목들 위에 자기 변경을 얹은 커밋)이 필수 검사를 통과해야 병합된다.
   - 큐 실행이 자기 변경만 검증하는 것(측정 1)은 그대로 둔다. 모든 항목이 자기 실행을 통과해야 하면, 변경마다
     정확히 한 번, 앞선 변경들 위에서 검증된다. GitHub 문서가 정의하는 `ALLGREEN`("묶음의 모든 커밋이 필수 검사를
     통과해야 한다")이 이것이다.
   - 기준을 main 끝으로 되돌리는 방법은 쓰지 않는다. 둘째 항목이 첫 항목의 검사를 다시 돌리게 되어, 러너가 막힌
     큐에서 같은 검사를 두 번 한다.
2. **가드는 `ALLGREEN` 만 받는다.** `scripts/guard/public-github-policy.sh` 가 다른 전략을 거부한다.
   실패가 막는 사고: 측정 2 의 다섯 건, 곧 필수 검사가 빨간 PR 이 뒤 항목의 초록에 실려 main 에 들어가는 일이다.
3. **동시 빌드 2, 묶음 5, 최소 1, 대기 5분, 응답 제한 120분은 그대로다.** 측정 3 이 ADR-0421 3항을 다시 확인한다.
   러너 동시 상한이 바뀌면(ADR-0420 의 결정) 같은 표를 다시 재고 올린다.
4. **처리량은 버려지는 실행을 줄여 올린다.** 큐를 비우지 않고 앞에 세우는 길(ADR-0553), main 이 깨진 것을 바로
   알리는 길, 범위 구멍을 닫는 일이 뒤따른다. 이 ADR 이 닫는 것은 그 가운데 "깨진 main 위에서 항목이 계속 병합되는" 고리다.

## 적용

정본이 바뀌어도 GitHub 쪽 규칙은 저절로 바뀌지 않는다. ADR-0211 의 절차로 한 번 적용하고 다시 읽는다.

```bash
id="$(gh api repos/perfectory-inc/perfectory-public/rulesets \
  --jq '.[] | select(.name == "perfectory-public-main") | .id')"
gh api --method PUT "repos/perfectory-inc/perfectory-public/rulesets/$id" \
  --input tools/github/main-ruleset.json
gh api "repos/perfectory-inc/perfectory-public/rulesets/$id" \
  --jq '.rules[] | select(.type == "merge_queue") | .parameters.grouping_strategy'
```

## Consequences

- 필수 검사가 빨간 PR 은 뒤 항목이 초록이어도 병합되지 않고 큐에서 빠진다. main 의 모든 커밋이 자기 큐 실행을 통과한
  트리다(이전에는 묶음의 끝만).
- main 이 이미 깨져 있으면 그 검사에 닿는 PR 은 전부 큐에서 빠진다. 전에는 닿지 않는 PR 뒤에 실려 들어갔다. 고치는
  PR 이 먼저 들어가야 하므로 ADR-0553 의 앞자리 길이 함께 필요하다.
- 러너 때문에만 실패한 큐 실행도 그 항목을 뺀다(전에는 뒤 항목이 초록이면 넘어갔다). ADR-0421 대로 keeper 가 초록인
  PR 을 다시 넣는다. 11-11 의 큐 검사 실패 제거는 24시간에 4건이었다.
- 처리량 숫자는 이 변경만으로는 오르지 않는다. 병합당 큐 실행 2.7 이 줄어드는지는 적용 뒤 같은 방법으로 다시 잰다.

## Rejected alternatives

- **`HEADGREEN` 유지, 큐 실행의 비교 기준을 main 끝으로**: 안전하지만 큐의 둘째 항목부터 앞 항목의 검사를 다시
  돌린다. 큐 커밋 하나가 중앙값 88 작업·분인데 러너가 이미 찬 시간대에 그 일을 겹쳐 한다.
- **동시 빌드 5**: 큐 깊이는 빨리 줄어 보이지만 바쁜 시간에는 20칸을 큐가 전부 차지해 PR 실행이 멈춘다. 실패 하나가
  버리는 뒤 항목 실행도 1개에서 4개로 는다.
