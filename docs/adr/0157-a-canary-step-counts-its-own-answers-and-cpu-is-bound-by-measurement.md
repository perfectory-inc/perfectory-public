# ADR 0157: 카나리아 단계는 도달을 자기 답으로 세고, CPU 한도는 측정에서 정한다

- Status: Accepted
- Date: 2026-10-06
- Amends: [ADR-0151](./0151-building-packs-serve-each-document-whole.md) Revision 의 카나리아 판정(새 버전 요청 수를
  Workers 분석에서 센다)과 계약 `worker_cpu_p99_max_ms`(5ms), [ADR-0154](./0154-building-pack-read-path-is-placed-beside-the-bucket.md)
  Consequences 의 "관문의 한도는 바꾸지 않는다"

## Context

2026-10-06 07:31–07:57Z 운영 건물 게이트웨이의 코드 단계(묶음 경로 꺼짐, 새 버전 `48dcff88`, 옛 버전 `155fe19c`)가
1% 단계에서 자동으로 되돌려졌다. 판정 JSON:

| 항목 | 새 버전 | 옛 버전 |
|---|---:|---:|
| 고정 읽기 보냄/답함(200·gzip) | 300 / 300 | 300 / 300 |
| Workers 분석 `sum { requests }` (판정 시점) | **137** | 296 |
| CPU p50 / p99 | 3.04 / 5.67ms | 1.75 / 3.70ms |
| wall p50 | 93ms (Tokyo 배치) | 192ms (LAX) |
| 운영 주소 응답 | 200 × 601 | |

위반은 둘이었다. 둘 다 새 버전의 결함이 아니라 판정의 결함이다.

1. **도달을 분석으로 셌다.** `workersInvocationsAdaptive` 는 표본추출되고 늦게 들어온다. 같은 구간을 07:25–08:00Z 로
   다시 물으니(2026-10-06 08:0xZ) 새 버전 304, 평균 `sampleInterval` 1.20(분 단위로 1.27·1.10), 옛 버전 298·1.01
   이었다. 300 을 보내 304 를 세었으니 `sum { requests }` 는 이미 표본 간격으로 확대된 추정치다(다시 곱하면 두 번 센다).
   137 은 표본 손실이 아니라 **지연**이다: 판정의 10분 대기가 끝났을 때 새 버전(배치된 버전) 행의 절반이 아직 안
   들어왔다. 분석이 늦으면 도달하지 않은 것으로 읽혀 건강한 버전이 되돌려진다.
2. **CPU 한도 5ms 가 경로 자체보다 낮았다.** 5ms 는 LAX 의 객체 경로(p50 1.95ms)에서 정한 값이다. Tokyo 배치에서 같은
   객체 경로가 p99 5.67ms, 미리보기의 묶음 경로가 p99 6.4ms(ADR-0154)다. 계정은 Workers Paid 라 10ms 차단이 없고
   요청당 한도는 우리 `cpu_limit_ms`(50ms)다. 그대로 두면 어떤 버전도 배치된 채로는 통과하지 못한다.

**새 코드의 CPU p50 이 두 배가 된 이유**(측정, 같은 구간 Workers 분석): 분포 전체가 일정하게 약 1.1ms 밀렸다(p25
1.55 → 2.64, p50 1.76 → 2.93, p75 2.25 → 3.26, p90 2.59 → 3.79ms). 일하는 양은 같다: 운영 manifest 에 `section_packs`
블록이 없고 패치도 없어(R2 에서 읽음, 459바이트) 두 버전이 같은 객체 경로를 돈다. 하위 요청 0, 응답 크기 중앙값 1,827B
로 같다. 버전 메타데이터(Cloudflare API)의 차이는 배치(`aws:ap-northeast-1`)와 `limits.cpu_ms` 50 뿐이고(번들에는
묶음 코드가 더 있지만 객체 경로에서는 불리지 않는다). 요청마다의 일정한 덧셈이라 꼬리(콜드 isolate)가 아니고, 남은
차이는 배치(NRT 의 실행)다. 같은 코드를 배치 없이 올려 비교하는 것은 배포라 이 결정에서는 하지 않았다. 코드에서 고칠 값싼
대상은 찾지 못했다.

## Decision

1. **각 답은 자기를 만든 Worker 버전을 이름한다.** 계약 `building_by_pnu_gateway.version_header`
   (`Foundation-Worker-Version`)에 Cloudflare 버전 메타데이터 바인딩(`version_metadata_binding`)의 id 를 적는다. 모든
   답(200·304·404·503, 묶음·객체·엣지 사본)에 나가는 순간 붙이고, 버전 사이에 공유되는 엣지 사본에는 넣지 않는다.
   `wrangler.jsonc` 는 계약에서 생성하며, 바인딩은 상속되지 않아 미리보기에도 따로 둔다. 버전 id 는 비밀이 아니다(고정
   헤더 `Cloudflare-Workers-Version-Overrides` 가 같은 id 를 받는다).
2. **도달은 고정 읽기의 답으로 센다.** 새 버전에 고정한 읽기 중 그 버전 id 를 단 답의 수가
   `canary.min_requests_per_step` 이상이어야 한다. 다른 버전이나 이름 없는 답은 세지 않는다(고정이 무시되면 도달 0).
3. **분석은 CPU·차단(`exceededResources`)·오류에만 쓰고, 그 답의 일정 비율을 셌어야 한다**: Workers 분석의 새 버전
   호출 수 ÷ 새 버전이 직접 답한 수 ≥ `canary.analytics_min_coverage`(0.3). 최소 개수가 아니라 비율이다. 0.3 은 위의
   137/300(0.46)을 받아들이고, 엉뚱한 버전·구간을 물어 거의 아무것도 못 센 답은 거부한다. 분석 질의는
   `avg { sampleInterval }` 도 읽어 보고서(`sample_interval_max`)에 남긴다. 요청 수는 이미 확대된 값이라 다시 곱하지 않는다.
4. **CPU 한도는 둘이다.** 절대 `worker_cpu_p99_max_ms` 10ms(측정한 건강한 경로 최대 6.4ms 위로 약 1.5배, `cpu_limit_ms`
   의 1/5)와, 카나리아 단계에서 옛 버전 p99 대비 증가 `worker_cpu_p99_max_increase_ms` 4ms(배치 이동의 +1.97ms 를 받고,
   싼 경로에 옛 p99 하나를 더 얹는 변경은 막는다). 둘 다 계약에 근거와 함께 둔다. 관문 (나)(미리보기 탐침)에는 옛 버전이
   없어 절대 한도만 적용된다.
5. 묶음 크기 상한(TODO, 큰 법정동 나누기)은 그대로 미룬다. 이 결정은 그 일을 대신하지 않는다.

## Consequences

- 2026-10-06 의 코드 단계는 이 판정이면 통과다(도달 300, 분석 137/300 = 0.46, CPU 5.67ms ≤ 10, 증가 1.97 ≤ 4).
  시험이 그 분석 답(표본 간격 1.2, 137 건)을 심어 판정 전체(`check`)를 돌리고, 같은 답에 다른 버전 id 의 답이면 거부되는
  것을 본다.
- 새 버전이 헤더를 내지 않으면(이 결정 이전 코드) 도달 0 으로 거부된다. 따라서 이 변경을 처음 올리는 코드 단계는 새
  버전이 헤더를 내는 코드여야 한다(이 릴리스 자체가 그렇다). 옛 버전은 헤더가 없어도 된다.
- 분석의 10분 대기는 그대로다(95% 를 세면 일찍 끝난다). 늦은 분석은 이제 판정을 막지 않고 CPU 의 표본 수만 줄인다.
- 운영 쓰기·배포는 하지 않았다. 측정은 Cloudflare GraphQL·버전 API·R2 manifest 읽기뿐이다.

## Rejected

- **분석 요청 수에 표본 간격을 곱한다**: `sum { requests }` 가 이미 추정치라(304 ≈ 300) 두 번 센다.
- **분석 대기를 늘린다**: 지연의 상한을 모른다. 도달은 우리가 직접 본 답으로 알 수 있다.
- **절대 한도만 올린다**: 버전 사이 회귀를 못 본다. 증가 한도가 그 일을 한다.
- **`cf-version-metadata` 같은 이름 없는 헤더**: 어느 Worker 가 붙였는지 계약에 없다. 이름은 계약이 정한다.
