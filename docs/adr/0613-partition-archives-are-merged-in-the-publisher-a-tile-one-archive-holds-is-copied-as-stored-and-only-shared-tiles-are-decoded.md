# ADR 0613: 시도 판은 발행기 안에서 합친다 — 한 판만 가진 타일은 저장된 바이트 그대로 옮기고, 여러 판이 가진 타일만 풀어 합친다 (tile-join 을 뗀다)

- Status: Accepted
- Date: 2026-11-24
- Amends: [ADR-0576](./0576-the-parcel-tile-join-runs-alone-and-its-joined-archive-is-cached.md) 결정 2 의 "tile-join 만 돌린다"(도구),
  [ADR-0316](./0316-parcel-boundaries-are-partitioned-by-edition-and-range-ordered-by-pnu.md) 의 "tile-join 으로 합친다"
- Builds on: ADR-0576 결과 절("그때 다음 단계는 … Rust 합치기다"), [ADR-0611](./0611-a-tile-bake-sizes-its-work-disk-from-measurement-and-removes-what-its-earlier-runs-left-and-spark-tmp-ages-out.md)(작업 디스크)

## 사장에게: 세 줄

- 2026년 9월 기준 전국 필지 지도가 아직 나가지 못했다. 시도별로 만든 지도 파일 16 개를 하나로 합치는 마지막 단계가 11-19 부터 11-23 까지
  여섯 번 시간 안에 끝나지 못했다.
- 합치는 외부 도구를 떼고 우리 프로그램이 직접 합친다. 대부분의 지도 조각은 열어 보지 않고 그대로 옮기고, 시도 경계에 걸친 조각만 합친다.
- 결과가 예전 도구와 같은지는 작은 시험 지도에서만 확인했다(조각 21 개, 차이 0). 전국 지도에서 실제로 끝나는지와 몇 분 걸리는지는 첫 운영 실행이 잰다.

## 낱말

- **시도 판**: 시도 하나의 필지를 구운 PMTiles 파일(`parcels-partitions/<시도>/<해시>.pmtiles`). **합친 파일**: 그것들을 하나로 만든 유닛의 파일.
  필지 원천의 판(202609)은 "에디션" 이라 쓴다.
- **발행기**: 굽기·업로드·승격을 하는 우리 실행 파일(`foundation-outbox-publisher`). **승격**: 합친 파일을 서빙 릴리스로 바꾸는 일.
- **타일**: 지도 조각 하나(줌·가로·세로). **run**: 굽기 유닛의 한 번 실행.

## Context

합치기는 한 번도 끝나지 않았다(운영 저널, 읽기 전용).

| 날 (UTC) | 합치기에 준 시간 | 끝 |
|---|---|---|
| 11-19 05:26 | 3,060 초 넘게(51 분, 유닛의 남은 시간) | 유닛 시간제한(115 분) |
| 11-20 03:52 | 3,600 초(60 분, 도구 1회 상한) | `tile-join exceeded its time bound` (#1541 이 6,300 초로) |
| 11-21 02:13 | 6,300 초(105 분) | 같은 오류 |
| 11-23 08:32, 13:14, 15:26 | 6,300 초씩 세 번 | 같은 오류. 사이에 #1661 이 옛 작업 폴더 43 GB 를 치웠다 |

시도 판 16 개는 합해 8.2 GiB 다(2026-11-24 `du`, `/data/foundation-platform/tile-bake/bake/parcels-partitions`, 판마다 0.05~1.39 GB; ADR-0576 의
"약 8.7 GB" 와 같은 파일이다). `/data` 는 HDD 다.

**tile-join 이 하는 일(tippecanoe 2.79.0 소스, ADR-0576 이 읽었다).** 타일을 잇지 않는다. 모든 판의 모든 타일을 풀고(`tile-join.cpp` 196 행
`tile.decode`) 다시 묶어 sqlite 에 쓴 뒤 PMTiles 로 옮긴다(1825 행). 8.2 GiB 를 전부 풀고, 임시 sqlite 를 쓰고, 다시 읽어 옮긴다. HDD 에서 이
단계가 디스크에 묶인다는 것은 소스에서 읽은 추정이다 — 어디서 시간이 가는지는 재지 않았다.

**그런데 겹치는 타일은 적다.** 시도 판은 PNU 앞 두 자리로 나뉜다. 한 타일을 두 판이 함께 가지는 곳은 시도 경계와 낮은 줌뿐이다. 나머지는 한
판만 가진다. 그 타일은 풀 까닭이 없다.

**읽은 것(`pmtiles` 크레이트 0.28.1, stadiamaps/pmtiles-rs, 2026-11-13 릴리스, 소스).**

- 읽기: `PmTilesReader::new_with_path`(동기, 런타임 불필요), `entries()` 가 디렉터리 항목을 낸다(`iter` 기능; 루트 다음 리프 순서다.
  타일 id 순서는 크레이트의 약속이 아니므로 합치기가 스스로 확인하고, 어긋나면 거부한다).
  0.28.1 이 구역 오프셋과 항목(`Header::data_offset`, `DirEntry::offset/length/run_length`)을 읽을 수 있게 했다(CHANGELOG #189).
- 쓰기: `PmTilesWriter::precompressed(Compression::Gzip)` — 문서가 "이미 압축된 타일을 다른 판에서 옮길 때 쓴다" 고 적는다.
  `dedup_by_key` 는 해시하지 않고 호출자가 준 키로 같은 내용을 한 번만 저장한다. 스트림 작성기는 임시 파일 없이 앞에서 뒤로 쓰고,
  디렉터리(루트·리프)와 헤더를 끝에 채운다(`write` 기능).
- 이 저장소의 `pmtiles_feature_ids.rs` 머리말은 "크레이트가 항목 순회를 내놓지 않는다" 고 적었다. 0.28.1 에서는 내놓는다. 그 머리말은 이
  PR 이 고쳤다.

## Decision

1. **합치기는 발행기 안의 `pmtiles_merge::merge_archives` 다.** 판들의 디렉터리를 타일 id 순으로 함께 걷고(k-way merge), 출력을 앞에서 뒤로
   한 번 쓴다. tile-join 컨테이너는 부르지 않는다.
2. **한 판만 가진 타일은 그 판이 저장한 바이트 그대로 옮긴다.** 풀지 않고, 다시 압축하지 않는다.
3. **여러 판이 가진 타일만 풀어 합친다.** MVT 로 읽어 이름이 같은 레이어의 피처를 한 레이어에 모으고 키·값 색인만 다시 매긴다. 도형은 바이트
   그대로다(읽지 않는다). 레이어는 처음 나온 순서, 피처는 판을 준 순서다. 같은 id 의 피처를 지우지 않는다(판은 id 접두로 나뉘어 겹치지 않는다).
   레이어의 extent(없으면 4096)나 version 이 판마다 다르면 거부한다(판을 같은 설정으로 굽지 않았다는 뜻이다. tile-join 은 extent 를 맞춰 다시
   쓰지만 여기서는 하지 않는다).
4. **PMTiles 읽기·쓰기는 `pmtiles` 크레이트다.** 디렉터리·헤더·리프 나누기를 다시 쓰지 않는다. MVT 는 `prost` 다(이미 쓰는 것).
5. **판이 한 번만 저장한 내용은 출력도 한 번만 저장한다.** 판의 디렉터리에서 여러 항목이 가리키는 오프셋을 먼저 찾아 그 내용에만 키를 준다.
   다른 타일은 해시하지 않고 기억하지 않는다. 서로 다른 판이 우연히 같은 바이트를 가진 타일과 합쳐진 타일은 한 번으로 줄이지 않는다 — 합친
   파일이 tile-join 의 것보다 조금 클 수 있다.
6. **메타데이터는 합친다.** 첫 판의 것을 바탕으로 한다(`name`·`description`·`generator` 는 첫 판의 것이고 판을 준 순서에 달렸다).
   `vector_layers` 는 모든 판의 합집합이다(줌 범위는 넓히고 필드는 합친다; 같은 필드의 형이 다르면 먼저 나온 것). 헤더의 줌·경계는 모든 판의
   범위, 중심은 경계의 가운데, 중심 줌은 첫 판의 것이다. tippecanoe 의 `antimeridian_adjusted_bounds` 는 합친 경계로 다시 쓴다. 한 판의 굽기만
   말하던 `tilestats`·`strategies`·`generator_options` 는 뺀다(읽는 곳이 없고, 한 시도의 수가 전국의 이름으로 남는다).
7. **시간 상한은 그대로 지킨다.** 합치기는 주어진 마감을 4,096 타일마다 보고 넘으면 오류로 끝난다. 마감은 두 가지다: 합치기만 하는 run 은
   계약의 `tile_join_run_budget_seconds`(`join_ahead`), 굽기에 이어 합치는 run 과 구역은 도구 1회 상한 `TOOL_TIMEOUT_SECONDS`(설정의
   `tool_timeout`). 마감은 타일 사이에서만 본다 — 판 16 개의 디렉터리를 여는 일과 끝의 디렉터리 쓰기는 그 밖이고, 한 번 시작한 합치기는 밖에서
   끊지 못한다(유닛의 시간제한이 마지막 줄이다).
   **실패하면 아무것도 남기지 않는다.** gzip MVT 가 아닌 판, 타일 id 순서가 어긋난 항목, 512 MiB 를 넘는 타일(저장된 크기든 푼 크기든), 키나 값을
   가리키지 못하는 태그, 빈 판 목록은 거부한다. 쓰다 만 `work/unit.pmtiles` 는 run 의 작업 폴더와 함께 지워지고, 합친 파일의 create-only
   이름(`joined/<해시>.pmtiles`)은 끝까지 쓰고 `fsync` 한 뒤에만 생긴다(ADR-0576 결정 2 그대로).
8. **ADR-0576 의 run 나누기(합치기 run → 승격 run)는 이 PR 에서 그대로다.** 합치기 시간을 모르고, 6,300 초는 작업의 115 분 한도에서 나온
   값이며, 이름을 바꾸면 계약·작업 정의·스크립트·시험이 함께 움직인다. 끝 조건: 첫 운영 실행들의 저널에서 (핸드오프 읽기 + 합치기 `seconds=` +
   관문·업로드)가 작업 한도 6,900 초의 90 % 아래면 한 run 으로 접고 `tile_join_run_budget_seconds` 를 지운다. 나누기가 남으면 같은 후속 PR 이
   계약의 키와 `remaining=tile-join` 을 "합치기" 의 이름으로 바꾼다. 그때까지 그 이름들은 "합치기 단계" 를 뜻한다.

## 같다는 증거

| 무엇 | 어떻게 | 결과 |
|---|---|---|
| tile-join 과 같은 타일 | 운영과 같은 tippecanoe 이미지(2.79.0)로 합성 사각형 두 판을 굽고 tile-join 으로 합친 기준 파일(`tests/fixtures/tile-join`). 시험 `the_merge_of_two_baked_partitions_is_what_tile_join_writes` 가 두 판을 합쳐 기준과 타일마다 피처의 모음(레이어·extent·version·id·종류·도형 바이트·속성)을 견준다 | 기준 파일끼리는 작성 중 Python 으로 견줬다: 타일 21 개(두 판이 함께 가진 것 8 개), 차이 0. Rust 시험의 판정은 이 PR 의 CI 다(로컬에서 컴파일하지 못했다) |
| tile-join 이 한 판만 가진 타일에 한 일 | 같은 시험이 압축을 푼 바이트를 원본과 견준다 | 작성 중 확인으로는 13 개 모두 바이트가 같다. 시험의 판정은 CI |
| 관문이 읽을 수 있는가 | 같은 시험이 합친 파일을 굽기의 자기 리더(`pmtiles_feature_ids::Archive`: id 관문·바이트 예산·패치 경로가 쓰는 것)로 걸어 같은 타일을 읽는다 | CI |
| 운영 에디션 | 합친 파일은 승격 전에 지금의 관문을 그대로 지난다: 최대 줌 id 관문(서빙 필지 id 전부·그것만), 첫 판 동등성 관문(계약의 줌마다 표본 타일) | 첫 운영 실행이 낸다 |

**이 증거가 보지 않는 것.**

- 순서: 레이어 안의 피처 순서(그리는 순서), 레이어 순서, 태그 순서. 헤더는 줌과 `vector_layers` 만 견준다(경계·중심·`name` 은 견주지 않는다).
- 기준 파일의 조건 밖: 판 3 개 이상이 만나는 타일(운영은 16 판; 합성 판 3 개의 시험은 있고 tile-join 과 견준 것은 아니다), 리프 디렉터리(21 타일은
  루트에 든다), tippecanoe 가 쓴 반복·공유 항목(크레이트가 쓴 합성 판으로만 시험한다), 운영의 줌과 디테일(기준은 z10~14·`--full-detail` 없음,
  운영은 z17·detail 13), 큰 타일, 구역 굽기의 옵션.
- 최대 줌 id 관문은 최대 줌만 읽는다. 합쳐지는 타일은 시도 경계와 낮은 줌에 많다. 낮은 줌은 동등성 관문의 표본이 본다.
- 운영 시도 판 둘을 실제 tile-join 과 견주지 않았다. 서버에서 판정용 빌드를 따로 만들지 않는다는 규칙 때문이고, 운영의 두 관문이 그 자리다.

## Consequences

- 디스크 쓰기는 출력 한 번(약 8.2 GiB)이다. sqlite 임시 파일이 없다. 읽기는 판마다 앞에서 뒤로다.
- 메모리: 모든 판의 디렉터리 항목과 출력의 항목(항목마다 24 바이트), 판을 여는 동안 그 판의 오프셋 집합, 판마다 타일 하나, 합치는 타일 하나의
  푼 조각들과 다시 묶은 것. 타일 내용의 해시 표는 없다. 수십 MB 로 본다(계산이고 잰 값이 아니다).
- 합쳐진 타일은 발행기가 gzip 으로 다시 압축한다. tippecanoe 와 바이트는 다를 수 있고 내용은 같다.
- MVT 명세가 이름 붙이지 않은 필드(확장 16 번 이상을 포함해, 타일·레이어·피처 어느 수준이든)는 합쳐진 타일에서 남지 않는다. tippecanoe 는 쓰지
  않는다. 그대로 옮긴 타일에는 영향이 없다.
- 이 저장소가 직접 쓴 PMTiles 읽기·쓰기(`pmtiles_feature_ids.rs` 의 `Archive`, `pmtiles_write.rs`)는 패치 경로와 관문이 아직 쓴다. 크레이트로
  옮기는 것은 다음 일이다(이 PR 은 합치기만 바꾼다).
- 구역(zoning)의 판도 같은 길로 합쳐진다. 구역은 레이어 코드로 나뉘어 거의 모든 타일을 여러 판이 가진다. 그 타일은 모두 풀어 합치고 다시
  압축한다(tile-join 이 하던 일과 같은 양이고 sqlite 가 빠진다). 한 스레드로 돌고 상한은 도구 1회 상한이다. 다시 압축한 타일의 크기는
  tippecanoe 의 것과 조금 다를 수 있어, 타일 바이트 예산 관문의 경계에 있던 타일은 판정이 바뀔 수 있다.
- **되돌리기.** 이 PR 을 되돌리면 tile-join 길로 돌아간다(핀 이미지에 tile-join 이 그대로 있다). 합친 파일의 이름은 시도 판의 이름만으로
  정해지므로, 잘못 합쳐진 `parcels-partitions/joined/<해시>.pmtiles` 가 있으면 다음 run 이 그것을 다시 쓴다 — 되돌릴 때 그 파일을 지운다.

## 구분

| 것 | 종류 |
|---|---|
| `pmtiles` 크레이트의 읽기·스트림 쓰기·키로 중복 저장 막기 | 기본 기능(오픈소스) |
| `prost` 로 MVT 읽기·쓰기 | 기본 기능(오픈소스) |
| `pmtiles_merge` (타일 id 순 함께 걷기, 레이어 합치기) | 운영 — 계속 남는다 |
| 합치기 run 과 승격 run 의 나누기(ADR-0576), `tile_join_run_budget_seconds` | 임시 — 합치기 시간을 잰 뒤 지울 후보 |
| `tests/fixtures/tile-join` 의 `joined.pmtiles` | 넘겨받기의 증거, 동결 — tile-join 은 더 돌지 않는다. 핀이 바뀌면 두 판만 다시 굽는다 |

## 확인하지 못한 것

- 전국 16 판을 합치는 시간과 메모리. 계산으로는 8.2 GiB 를 한 번 읽고 한 번 쓰는 일이고, 첫 운영 실행의 `lakehouse-tile-bake-joined … seconds=`
  줄이 측정이다. HDD 에서 16 판을 번갈아 읽는 속도는 그때 처음 안다.
- 전국에서 여러 판이 가진 타일의 수. 같은 줄의 `merged=` 가 낸다.
- 구역을 합치는 시간. 구역의 첫 `seconds=` 줄이 측정이다.
- 이 PR 의 Rust 코드는 로컬에서 컴파일하지 못했다(노트북 여유 메모리). CI 가 첫 컴파일이고 시험의 첫 실행이다.

## 기각한 대안

- **시간 상한을 더 올린다.** 여섯 번 실패했고 끝까지 걸리는 시간을 모른다. ADR-0576 의 결과 절은 115 분 안에 안 끝나면 다음 단계가 Rust
  합치기라고 적었고, 계약의 `tile_join_run_budget_seconds_reason` 은 그것이 더 큰 상한이 아니라고 적었다.
- **tile-join 의 작업 폴더를 NVMe 로 옮긴다.** 디스크는 빨라지지만 모든 타일을 풀고 sqlite 를 거치는 일은 그대로다. 재지 않았다. 풀 까닭이 없는
  타일을 푸는 것이 원인이라 고르지 않았다.
- **직접 쓴 PMTiles 작성기(`pmtiles_write.rs`)를 쓴다.** 패치 한 세대(타일 몇 퍼센트)를 위해 쓴 것으로 모든 타일을 메모리에 받는다. 오픈소스에
  스트림 작성기가 있다.
- **합치지 않고 시도 판 16 개를 그대로 서빙한다.** 타일 관문이 줌·좌표로 판을 골라야 하고, 경계 타일은 두 판을 받아 클라이언트가 합쳐야 한다.
  서빙 계약(유닛 하나에 판 하나)이 바뀐다. 이 결정의 범위가 아니다.
