# ADR 0275: 원천 판 Silver 레인은 표를 덮어쓰지 않고, 바뀐 키만 새 버전으로 쌓는다 (제안)

## Context

hub.go.kr 건축물대장 세 레인과 VWorld 토지 레인 일곱은 판마다 전량 덤프를 받아 표 전체를 덮어쓴다
(`silver_refresh.spark.iceberg_write_mode: overwrite`). 2026-10-18 운영 실측(Trino 스냅숏 요약·시간 여행, 서버 저널,
읽기 전용)은 다음과 같다.

### 판 사이에 실제로 바뀌는 행

| 표 | 비교 | 추가 | 삭제 | 바뀜 | 같음 |
|---|---|---:|---:|---:|---:|
| `building_register_units` (1,985만) | 2026-08 판 → 2026-09 판, 키 `mgm_bldrgst_pk` | 0.44% | 0.03% | 7.6% | 92% |
| 위에서 PNU 만 바뀐 행 | (2026-07 행정구역 개편: 코드만 바뀜) | | | 7.55% | |
| 위에서 PNU 외 칸이 바뀐 행 | 동·호·층 | | | 0.02% | |
| `land_transfer_history` (1억 3,146만) | 0630 판 → 0930 판, 행 지문, PNU 5% 표본 | 18.3% | 11.1% | — | 81.6% |
| 같은 비교에서 개편 시도(29·46·12·28) 제외 | | 0.51% | 0.03% | — | 99.5% |

평상시 한 판의 변경은 **약 0.5%** 다. 개편처럼 코드가 바뀌는 달은 8–19% 다.

### 덮어쓰기가 치르는 값 (판 하나)

| 표 | 행 | 한 번 쓰는 바이트 | 실행 시간(저널) |
|---|---:|---:|---|
| `building_register_titles` | 806만 | 0.67 GB | 약 8분 |
| `building_register_units` | 1,985만 | 1.39 GB | 약 9분 |
| `building_register_unit_areas` | 1억 1,437만 | 8.9 GB | 약 75분(내보내기 20 + Spark 55) |
| `land_transfer_history` | 1억 3,146만 | 1.44 GB | 약 60–80분 |
| `land_use_plan` | 2억 4,758만 | 2.7 GB | — |
| 나머지 토지 넷 + 용도지역 코드 | | 1.2 GB | — |
| 합계 | | **약 16.6 GB** | |

- 보존 규칙(ADR-0237)은 30일 스냅숏, 월말 태그 12개, 연말 태그 영구다. 덮어쓴 판은 저마다 전체 사본이라
  표마다 **최대 13벌**(약 215 GB)이 R2 에 남는다. 해마다 연말 사본 한 벌(약 17 GB)이 영구로 늘어난다.
- 바뀐 0.5% 를 위해 매번 100% 를 쓰고, 그 100% 가 보존 기간 내내 남는다.
- 2026-10-10 의 표제부·호·호 면적 재적재는 같은 2026-09 판이었다. silver-refresh 레인으로 옮기면서 옛 경로의
  판 이름을 알아보지 못한 일회성 전환이고, 그 뒤로는 `already_loaded` 로 건너뛴다. 반복되는 낭비는 아니다.

### 시간은 아직 증명되지 않았다

바뀐 키를 찾으려면 새 판 전체를 내보내고 읽고 현재 행과 비교해야 한다. 덮어쓰기에서 줄어드는 것은 Parquet 쓰기와
커밋이다. 실행 시간이 얼마나 줄지는 재 보기 전에는 모른다(아래 1단계).

## Decision (제안)

1. **바뀐 키만 쌓는다.** 레인 계약에 행의 업무 키(`row_key`)를 적는다. 예: 호 `mgm_bldrgst_pk`. 키를 확정하는 일이
   1단계에 들어간다. 새 판을 적재할 때는 현재 행과 비교한다(ADR-0180 §1 처럼 빌드가 읽는 열의 지문).
   - 새 키·내용이 바뀐 키: 새 판의 행을 **append** 한다. `source_snapshot_id` 는 새 판이다.
   - 사라진 키: **삭제 표시 행**(키 + `row_state = removed` + 새 판)을 append 한다.
   - 같은 키·같은 내용: 쓰지 않는다.
   - 쓰기는 append 한 번이다. 행을 고치거나 지우지 않는다(덮어쓰지 않고 쌓는다). 판마다 그 판의 변경 전부가 한 스냅숏에
     있다.
2. **현재 행은 ADR-0267 규칙으로 읽는다.** 계약 `current_row_latest { key = row_key, newest_first = (판, ingested_at_utc) }`
   로 키마다 가장 새 행을 고른 뒤, 그 행이 삭제 표시면 버린다. 이렇게 "최신을 고른 뒤 거른다"는 0267 에 없는 한 단계라
   함께 더한다. 모든 독자는 `platform_contracts.current_rows` 하나로 읽는다.
   - 하나의 판만 받는다는 Gold 생산자의 검사(`assert_single_snapshot`)는 "현재 행이 여러 판에서 왔다"를 허용하도록
     바뀐다. 판의 완전성은 레인이 보증한다: 한 판의 변경 전부가 한 커밋이다.
3. **과거는 표 안에 남는다.** 어느 판의 상태든 "그 판 이하에서 키마다 최신" 으로 다시 만들 수 있다. 월말 태그는 더 이상
   전체 사본이 아니라 그 달까지의 변경 묶음을 가리킨다.
4. **전량으로 돌아갈 때.** 변경이 계약의 비율(예: 30%)을 넘으면 표를 새로 쓴다. 개편 달이나 적재기 규칙이 바뀐 때가
   그렇다. 새로 쓸 때도 덮어쓰지 않는다: 새 판 전체를 append 하고, 그 판에 없는 키는 삭제 표시 행으로 append 한다.
5. **단계.**
   - 1단계(측정 스파이크): 가장 큰 `land_transfer_history` 하나에서 키를 확정하고, 운영 규모 사본으로 "비교 + 변경 append"
     시간을 덮어쓰기와 나란히 잰다.
   - 2단계: 시간이 같거나 줄면 이 ADR 을 Accepted 로 하고 레인별 PR 로 옮긴다.
   - 시간이 늘면 바이트·보존 이득만으로 갈지 사장님이 정한다.

## Consequences (승인되면)

- 판마다 쓰는 바이트: 16.6 GB → 평상시 약 0.1–0.2 GB(0.5% + 삭제 표시).
- 보존: 13벌 전체 사본 → 현재 한 벌 + 판마다 0.5% 의 변경.
- 표 행 수는 판마다 약 0.5% 늘어난다(과거 버전이 표 안에 남는다). 압축(`replace`)은 그대로 돈다.
- 모든 Silver 독자가 `current_rows` 를 거쳐야 한다. Gold 생산자 셋·by-PNU·Trino 뷰가 해당한다. 이것이 이 변경의
  가장 큰 비용이고 위험이다. ADR-0267 의 기계적 차단(독자가 자기 창을 두지 못한다)을 이 표들로 넓힌다.
- ADR-0180 의 Gold 증분은 그대로 동작한다. 입력의 "현재 행" 차이만 본다.

## Rejected

- **`MERGE INTO`(copy-on-write) 로 현재 표를 고치기**: 0.5% 가 전국에 흩어져 있어 데이터 파일 대부분을 다시 쓴다. 쓰기
  이득이 거의 없고, 고쳐 쓰기라 덮어쓰지 않고 쌓는 규칙에 어긋난다.
- **merge-on-read 삭제 파일**: 쓰기는 작지만 행을 지우는 쓰기다. 굽기의 스냅숏 스캔이 delete 파일을 거부한다(ADR-0180).
- **SCD2 로 옛 행의 `valid_to_utc` 닫기**: ADR-0267 이 거절한 것과 같은 이유(쌓인 행을 고쳐 쓴다).
- **그대로 두기**: 비용이 보존 규칙 때문에 해마다 쌓인다. 측정 결과를 보고 사장님이 고를 수 있는 선택지다.
