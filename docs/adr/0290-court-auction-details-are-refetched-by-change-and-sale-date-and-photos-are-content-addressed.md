# ADR 0290: 법원경매 상세는 바뀐 것과 매각기일에 맞춰 다시 받고, 사진은 내용 해시로 한 번만 저장하며, PNU 는 코드로 조립한다

- Status: Accepted
- Date: 2026-10-21
- Builds on: ADR-0289(접속·세션·속도·SSOT), [ADR-0286](./0286-every-table-contract-declares-how-its-rows-are-versioned.md)(행 버전), [ADR-0288](./0288-every-parcel-source-converges-on-one-place-identity.md)(place-identity 해석기), [FP-ADR-0016](../../platforms/foundation-platform/docs/adr/0016-bronze-commit-protocol.md)(Bronze 쓰기 관문)
- Amends: ADR-0288 §2 — 경매는 주소 이름이 아니라 **코드**로 해석기에 들어간다
- Replaces the draft: ADR-0285(#804)와 그 계약 초안(#805) — 번호를 쓰지 않고 닫는다

## Context

2026-10-21 시제품의 전체 수집(ADR-0289 Context)을 열어 확인한 것:

1. **상세 API 6종의 요청 모양이 실물로 확인됐다.** 사건상세(`/pgj/pgj15A/selectAuctnCsSrchRslt.on`), 문건·송달(`selectDlvrOfdocDtsDtl.on`), 현황조사(`/pgj/pgj15B/selectCurstExmnRletIndctLst.on`), 감정평가(`selectAeeWevlInfo.on`), 물건상세(`/pgj/pgj15B/selectAuctnCsSrchRslt.on`), 매각결과 검색. 사건 30,067건 × 4종 = 120,224 요청 중 2건만 실패했고, 물건상세 39,296건은 전부 받았다.
2. **목록은 날짜를 보내야 전체가 온다.** `bidBgngYmd`/`bidEndYmd` 를 비우면 서버가 기본 기간만 준다. 2026-10-21 실물 대조: 물건 검색 4조합의 `totalCnt` 합이 날짜 없이 63,005, 앞뒤 365일이면 108,306(+71.9%)이다. 지금 main 은 날짜를 보내지 않는다. 매각결과 검색은 `statNum` 이 있든 없든 `totalCnt` 가 같았다(7,552).
3. **물건상세 응답의 99.5% 는 사진이다.** `csPicLst[].picFile` 에 base64 로 실려 응답이 1.5~5MB 다. 사진 없이 받는 API 는 없다. 사진을 빼면 물건당 약 19KB 다.
4. **경매 데이터에는 PNU 를 조립할 코드가 있다.** 물건상세의 매각대상(`gdsDspslObjctLst[]`) 49,383개 중 48,669개(98.6%)가 법정동코드 10자리(`rprsAdongSdCd`·`SggCd`·`EmdCd`·`RiCd`)와 지번(`rprsLtnoAddr`)을 가진다. `pnuNoCtt`(19자리 PNU)는 19.6% 에만 있고 17자리 불량값도 있다. 둘 다 있는 4,915건 중 668건이 다른데, 보이는 예는 모두 **옛 시군구 코드**다(11540↔11545, 11300↔11305). 조립이 안 되는 1.4% 는 지번 칸이 문장이다("800-23외 6필지", "…도시개발구역5블록"). 목록 행에도 `srchHjguRdCd`(10자리)+`srchHjguLotno` 가 있다(58.5%). 지금 main 은 이 코드를 두고 행정구역 **이름**으로 주소를 맞춘다(PNU 86.5%).
5. **경매는 일정이 정해진 절차다.** 목록 행이 매각기일(`maeGiil`)과 진행 상태(`jinstatCd`)를 가진다. 내용이 바뀌는 때는 대개 기일 전후와 상태가 바뀔 때다.

시제품의 증분은 "이미 받은 key 는 건너뜀" 하나다. 다시 돌려도 기일 변경·유찰·매각결과가 반영되지 않는다.

## Decision

1. **받는 범위.** 목록 2종(물건 검색 4조합 + 매각결과 2조합, 날짜 앞뒤 계약 일수), 사건상세 4종(사건상세·문건송달·현황조사·감정평가), 물건상세(사진 포함). 목록 한 바퀴의 쪽 수는 서버 `totalCnt` 와 같아야 완료로 친다.

2. **변경 감지.** 목록은 매번 전체를 받는다(약 8분). 행마다 계약이 정한 칸들로 내용 해시를 만들고, 직전 해시와 비교해 **새로 생긴 행·바뀐 행**만 상세 대기열에 넣는다. 목록에서 사라진 행은 Silver 에 삭제 표지를 단다(완전한 한 바퀴일 때만).

3. **매각기일에 맞춘 재수집.** 사건마다 상태를 둔다: 신건 → 기일 대기 → 기일 경과 → 종국. 상태와 매각기일로 다음 수집 시각을 정한다 — 기일 전날, 기일 다음 날(결과), 상태가 바뀐 날. 종국된 사건은 다시 받지 않는다. 어느 상태에서 어느 엔드포인트를 며칠 간격으로 받는지는 계약의 **재수집 정책 표**가 정한다. 예: 감정평가·현황조사는 처음 한 번, 사건상세·문건송달은 기일 전후, 물건상세는 목록 행이 바뀌었을 때만.

4. **우선순위 대기열.** 상세 요청은 foundation Postgres 의 대기열 표에 쌓인다. 순서는 신건 → 기일 임박 → 일반 갱신이다. 실행이 끊겨도 표에서 이어서 처리한다. 대기열에 넣는 일과 꺼내 받는 일은 같은 key 로 한 번만 처리된다(같은 key 가 두 번 들어가도 한 번 받는다).

5. **실패 장부.** 막힘이 아닌 오류로 끝내 못 받은 key 는 장부에 이유·시각·횟수와 함께 남고, 다음 실행이 먼저 다시 받는다. 장부의 건수는 지표로 내보낸다.

6. **주간 전체 대조.** 계약의 주기(지금 7일)마다 진행 중인 사건 전체의 사건상세를 한 번 받아 해시를 대조한다. §2·§3 이 놓친 변경을 잡기 위한 것이다. 대조에서 바뀐 것이 나오면 그 수를 지표로 내보낸다 — 0 이 아니면 재수집 정책이 무언가를 놓치고 있다는 신호다.

7. **사진은 내용 해시로 한 번만 저장한다.**
   - 받자마자 `picFile` 의 base64 를 디코딩해 원본 이미지 바이트로 바꾸고, 앞부분 바이트(매직 넘버)로 형식을 판정한다.
   - 이름은 계약의 사진 접두어 아래 `sha256/<해시>.<확장자>` 다. 이미 있으면 올리지 않는다. 같은 사진은 몇 번 받아도 한 번만 저장된다. FP-ADR-0016 관문으로 쓴다.
   - Bronze 의 물건상세 응답은 원본 그대로 두되 `picFile` 값만 `sha256:<해시>` 참조로 바꾼다. 응답과 사진 객체를 합치면 원래 응답을 바이트 그대로 되살릴 수 있다. base64 를 Bronze 에 그대로 쌓지 않는다(33% 크고, 다시 받을 때마다 같은 사진이 또 쌓인다).
   - Silver 사진 표: 사건·물건·순번·사진 제목(`picTitlNm`)·해시·크기·형식·처음 본 시각.
   - 화면용 썸네일·WebP 는 이 원본에서 따로 만든다. 원본은 바꾸지 않는다. 이 일은 이 ADR 밖이다.
   - **읽을 때 검증:** 사진 객체를 읽는 쪽은 해시를 다시 계산해 이름과 대조할 수 있다. 이름이 곧 체크섬이다.

8. **PNU 는 코드로 조립하고, 해석기는 하나다.**
   - 매각대상마다 법정동코드 10자리 + 산 여부 1자리 + 본번 4자리 + 부번 4자리로 PNU 를 조립한다. 칸 이름은 계약에 적는다.
   - 조립한 PNU 는 온비드와 같은 형식 검사(계약의 `pnu` 규칙, Rust `Pnu::parse` 와 같은 규칙)를 거쳐 **ADR-0288 의 place-identity 해석기**에 코드로 들어간다. 해석기가 옛 법정동코드를 현재 코드로 옮기고 현재 필지만 남긴다.
   - `pnuNoCtt` 는 대조값이다. 조립값과 해석 후 결과가 다르면 그 수를 지표로 내보낸다.
   - 원본 코드·지번·`pnuNoCtt` 는 `*_raw` 칸에 남는다. 조립이 안 되는 행(지번이 문장)은 `pnu` 를 비우고 해석기의 스튜어드 큐로 간다(ADR-0288 §4). 주소 이름 매칭은 경매에서 쓰지 않는다.
   - **시험:** `courtauction_go_kr.py` 가 `address_pnu` 의 주소 해석을 부르지 않는다.

9. **Silver 표와 행 버전.** 상세마다 Silver 표를 둔다(사건·문건송달·현황조사·감정평가·물건·매각대상·사진). 표마다 ADR-0286 의 행 버전 규칙을 계약에 선언하고, 내용이 바뀐 행만 새 버전으로 붙인다. 그래서 "언제 무엇이 바뀌었나" 가 Silver 에서 읽힌다.

10. **SSOT.** 아래 값은 모두 `courtauction-go-kr.contract.json` 한 곳에만 있다.
    - 엔드포인트별 요청 모양
    - 변경 감지 해시에 넣는 칸
    - 재수집 정책 표
    - 대조 주기
    - 사진 접두어와 형식 판정 목록
    - PNU 조립 칸
    - Silver 표 이름

    수집 일정은 작업 등록부 한 곳에만 있다. 수집기, Silver 적재, 시험은 이 두 파일을 읽는다. Silver 표 모양은 지금처럼 표 계약(`industrial_complex_lakehouse_contracts.json`)이 정본이다.

## Consequences

- 평소 상세 수집은 바뀐 수백~수천 건이다. 처음 한 번만 전체(약 16만 요청, 시제품 실측 약 65분)를 받는다.
- 사진 저장량은 물건 약 4만 건 × 사진 여러 장 × 1.5~5MB 응답 기준으로 첫 수집이 수십 GB 대다. 정확한 값은 첫 수집에서 잰다. 같은 사진은 다시 쌓이지 않는다.
- 경매 PNU 는 이름 매칭(86.5%)에서 코드 조립(물건상세 98.6%, 해석기 통과 후 값은 첫 적재에서 잰다)으로 바뀐다. 조립이 안 되는 1.4% 는 스튜어드 큐로 간다.
- 기존 Silver 두 표(`silver.court_auction_item`, `silver.court_auction_sale_result`)의 PNU 는 §8 로 다시 해석한다(ADR-0288 §7 의 전수 재해석에 포함).
- 구현 순서: ① 목록 날짜 범위 수정 → ② 접속 스파이크(ADR-0289 §1) → ③ 계약 확장 → ④ 수집기(세션 풀·속도 조절·대기열·장부) → ⑤ 사진 → ⑥ Silver 표·PNU → ⑦ 작업 켜기.

## Rejected

- **이미 받은 key 는 건너뛰기(시제품):** 기일 변경·매각결과가 반영되지 않는다.
- **매일 상세 전체 다시 받기:** 하루 약 16만 요청에 사진 수십 GB 를 매일 다시 받는다. 바뀐 것은 그중 일부다.
- **사진을 base64 그대로 Bronze 에 두기:** 33% 크고, 재수집마다 같은 사진이 다시 쌓이고, 화면에 바로 쓸 수 없다.
- **사진을 버리기(시제품):** 물건 사진은 경매 정보의 일부다. 다시 받으려면 물건상세 전체를 다시 받아야 한다.
- **주소 이름으로 PNU 찾기(지금 main):** 같은 행에 코드가 있는데 이름을 맞추면 표기 차이로 놓친다(86.5%).
