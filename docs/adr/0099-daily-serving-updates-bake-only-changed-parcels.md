# ADR 0099: 매일의 서빙 갱신은 바뀐 필지만 굽는다

- Status: Accepted
- Date: 2026-09-10

## Context

ADR-0096 의 by-PNU 서빙 실증에서 굽기 비용을 전부 실측했다. 배치 호스트에서 R2 로 객체
하나를 쓰는 데 ~0.29초(왕복 지연 지배), 동시성은 R2 의 파티션별 429 스로틀이 막고(정렬
순서 32 동시에서 사망), 순서 분산·적응형 재시도·범위 재개를 갖춘 뒤에도 전국 39,861,511
객체의 전량 굽기는 병렬 차선으로 **시간 단위**다. 이 비용을 매일 낼 수는 없다.

한편 gold.parcel_panel 은 매일 전체를 다시 계산해 **통째로 덮어쓴다**(단일 스냅숏 게이트가
요구하는 모양이다). 그래서 Iceberg 의 스냅숏 증분 읽기는 "무엇이 바뀌었나"에 답하지
못한다 — 덮어쓰기 사이의 증분은 전부다. 바뀐 행을 알려면 내용 기준의 비교가 필요하다.

문서는 이미 순수 함수다: 같은 gold 행(계보 제외)은 같은 서빙 JSON 바이트를 낳는다
(ADR-0096, create-only 재사용이 이 성질 위에 서 있다).

## Decision

1. **gold.parcel_panel 에 `row_digest` 칼럼을 더한다.** 값은 서빙 문서에 들어가는 내용
   칼럼들(pnu·kind·area_m2·각 섹션 JSON·land_right_total)만의 결정적 SHA-256 이다.
   스냅숏 계보 칼럼(source_snapshot_id·published_at_utc)은 지문에 넣지 않는다 — 계보가
   바뀌어도 내용이 같으면 다시 구울 필요가 없다는 것이 이 ADR 의 요점이다.
2. **변경 집합은 지문 비교로 얻는다.** Spark 잡(`parcel_panel_delta`)이 현재 스냅숏과
   직전 스냅숏(또는 명시된 기준 스냅숏)을 pnu 로 조인해 지문이 다르거나 한쪽에만 있는
   PNU 목록을 산출한다. 신규·변경 PNU 는 allowlist 파일로, 삭제 PNU 는 별도 목록으로
   내린다(현 세대 안에서 객체 삭제는 하지 않는다 — 세대 교체가 삭제를 흡수한다).
3. **델타 굽기는 기존 명령의 조합이다.** `export-parcel-by-pnu-serving` 에 변경 PNU
   allowlist + `ALLOW_OVERWRITE=true`(같은 세대 제자리 갱신, ADR-0096 의 델타 재굽기
   경로) → `publish-parcel-by-pnu-serving-manifest` 재발행(`ALLOW_REPOINT=true`).
   객체 캐시가 immutable 이 아니라 1시간 유계인 이유가 바로 이 경로다.
4. **전량 굽기는 예외 절차로 남는다**: 문서 스키마가 바뀌는 날만 새 세대로 전량을 굽고
   포인터를 넘긴다. 그 실행 편의를 위한 원격(저장소 근접) 굽기 타깃은 후속 결정으로
   다룬다 — 이 ADR 은 "매일"의 모양만 못박는다.
5. 델타 잡의 산출(변경·신규·삭제 수)은 스파크 요약 표준(`spark_run_summary.v1`)으로
   남기고, 변경 수가 전체의 절반을 넘으면 잡이 사유를 말하며 거부한다 — 지문 로직
   오류가 전량 재굽기로 위장하는 사고를 막는 안전선이다.

## Consequences

- 매일의 서빙 갱신이 분 단위가 된다: 변경 수천~수만 건 × ~0.3초 ÷ 동시 64+.
- gold 계약에 칼럼이 하나 늘고(`row_digest`), 그 값의 정의는 굽기 문서와 같은 칼럼
  집합에 묶인다 — 문서에 칼럼을 더하는 변경은 지문 정의도 같이 움직여야 하며, 이는
  전량 재굽기(새 세대)를 뜻한다. 그때 4번 절차가 발동한다.
- 직전 스냅숏이 없거나(최초) 기준 스냅숏이 명시되지 않으면 델타 잡은 거부한다 —
  "비교 대상 없음"을 "변경 없음"으로 읽는 확인은 만들지 않는다.
