# ADR 0416: 법원경매·등록공장의 이미 쌓인 행도 법정동 코드 변경을 따라간다 — 바뀐 코드 아래만 다시 잇는다

- Status: Accepted
- Date: 2026-11-05
- Builds on: ADR-0280 §4(주소로 PNU), ADR-0318(바뀐 키만 쌓는다), ADR-0328(덧붙인 행이 옛 행을 앞선다),
  ADR-0329 §3(`views.changed_codes`), ADR-0401(data.go.kr 파일 적재가 같은 따라가기를 갖는다), ADR-0403(시도 접두어는 법정동 표에서)

## Context

사장 규칙(2026-10-31)은 "모든 데이터는 법정동 코드 변경을 따라간다, 적재 때 한 번 풀고 멈추지 않는다" 다. 두 적재는 이 규칙을
지키지 못했다.

- **법원경매**(`courtauction_go_kr.py`)는 밤마다 검색에 나온 물건만 다시 푼다. 매각이 끝나 검색에서 빠진 물건은 처음 풀린 PNU 로 남는다.
- **등록공장**(`data_go_kr_registered_factory.py`)은 판 전체를 한 번 쌓는다. 공급자는 1년에 한 번쯤 판을 낸다. 다음 판이 오기
  전까지 1년 동안 그 사이의 코드 변경이 닿지 않는다.

**측정 (2026-11-04, 운영 Trino 읽기 전용, ADR-0403).** 2026-07-01 광주·전남 통합(29·46 → 12) 뒤 넉 달 동안 두 표의 광주·전남 행이 이랬다.

| | 행 | 연결 |
|---|---:|---:|
| 법원경매 물건 | 4,774 | 3 |
| 등록공장 | 13,214 | 10,801 (지번 0) |

ADR-0403 의 해석기 수정은 다음 적재부터만 듣는다. 이미 쌓인 행을 다시 잇는 단위가 없었다.

### 실사례

- **차원 변경은 영향받은 사실만 다시 잇는다.** Kimball 의 늦게 오는 차원(late-arriving dimension)과 Delta Lake·Iceberg 의 MERGE
  기반 재매핑은 바뀐 차원 키에 걸린 사실 행만 다시 쓴다. 전체를 다시 적재하지 않는다.
- **무엇을 반영했는지 기록한다.** Kafka Connect 의 오프셋과 Debezium 의 소스 위치처럼, 표가 어디까지 따라갔는지를 표 자신의
  커밋 기록에 둔다. 그래야 실패한 실행을 다음 실행이 이어 받는다.

## Decision

1. **따라가기는 모듈 하나다**(`infra/lakehouse/spark/jobs/code_change_follow.py`). ADR-0401 의 data.go.kr 파일 적재가 만든
   방식을 그대로 일반화했다.
   - 표는 링크를 만든 변경 표의 스냅숏을 커밋 기록 `follow:reference.legal_dong_code_change@<스냅숏>@<UTC>` 로 남긴다.
   - 다음 실행에서 변경 표가 움직였으면, 두 스냅숏 사이 `views.changed_codes` 가 이름 대는 코드의 PNU 접두어 아래 현재 행과
     PNU 가 없는 행만 고른다.
   - 고른 행의 원래 값은 그대로 두고 링크만 다시 만든다. 연결이 바뀐 행만 덧붙인다(append-only).
   - 기록이 없는 표는 처음 한 번 현재 행 전부를 다시 잇는다. 앞 스냅숏이 만료된 경우도 같다. 이것은 선언된 예외다(아래 비용).
2. **법원경매.** 두 표(물건·매각결과)의 다시 이은 행은 따라가기의 기록과 그 시각을 `source_record_id`·`source_snapshot_id` 로 갖는다.
   그래서 현재 행 규칙(`source_snapshot_id` 가 가장 새 것)에서 옛 행을 앞선다(ADR-0328). 표 계약은 바꾸지 않는다.
3. **등록공장.** 이 표는 판(Editions) 표다. 읽는 쪽은 (기준일, 적재 시각) 순으로 가장 새 판 하나를 통째로 읽고, 같은 기준일을
   다시 적재하면 앞 적재를 앞선다(ADR-0286 §3, ADR-0328). 그래서 따라가기는 연결이 바뀐 줄이 하나라도 있을 때 그 판을 한 번 더
   덧붙인다. 모든 줄을 이번 실행 시각으로 싣되, 바뀐 줄은 새 링크로, 나머지는 그대로 싣는다. 바뀐 줄이 없으면 따라가기 기록만
   남긴다. 표 계약은 바꾸지 않는다. 판 하나(약 22만 행)를 다시 싣는 것은 판 표의 단위가 판이기 때문이고, 코드 변경이 이 판에 닿을
   때만 일어난다(선언된 예외). 지금 이 표를 읽는 소비자는 없다(그래프 `contract_only`).
4. **같은 실행 안에서 한다.** 새 작업·새 스위치는 없다. 두 적재의 `load` 가 객체를 다 쌓은 뒤 따라가기를 한 번 하고, 요약 줄에
   `follow`(등록공장)·`follows`(법원경매)로 `checked`·`appended` 를 센다.

## Consequences

- **고친 뒤(계산, ADR-0403 의 측정).** 첫 따라가기가 현재 행 전부를 새 해석기로 다시 잇는다. 그러면 광주·전남 법원경매는
  **3 → 4,761**, 등록공장은 **10,801 → 11,630 이상**이 된다.
- **비용(계산).** 첫 따라가기는 법원경매 현재 행 약 4만 4천 행과 등록공장 한 판 약 22만 행을 드라이버로 모아 다시 푼다. 한 판을
  적재하는 일과 같은 크기이고, 각 작업의 단위 시간(90분) 안에 든다. 그 뒤로는 바뀐 코드 아래의 행만 다시 풀고, 법원경매는 그 행만,
  등록공장은 바뀐 줄이 있을 때만 판을 덧붙인다. 광주·전남 통합 같은 큰
  변경도 수천 행이다. 저장은 바뀐 행만 덧붙이므로 수 MB 이하, R2 월 1원 아래다.
- data.go.kr 파일 적재(ADR-0401, #1038)는 같은 일을 자기 안에 갖고 있다. 그 PR 이 main 에 들어오면 이 모듈을 쓰도록 바꾼다.
