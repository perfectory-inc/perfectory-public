# ADR 0615: DuckDB 로 옮긴 Gold 레인은 시도로 나뉜 Dagster 자산이고, 시도마다의 상태는 Dagster 의 것이다

- Status: Accepted
  - 정해진 것: 결정 1(파티션은 시도), 2-3~2-8(짓기·커밋·표가 참 — 발행기의 코드가 이 PR 에 있다), 4, 7(드라이버의 API).
  - 방향만 정해졌고 도는 데몬에서 확인한 뒤에 짜는 것: 결정 2-1·2-2(입력 관찰과 `eager`), 결정 6 의 PR 3 부터. "확인하지 못한 것"이 그 목록이다.
    (저장소의 가드는 코드가 인용하는 ADR 이 Proposed 인 것을 거부한다. 그래서 정해진 것과 아닌 것을 여기서 가른다.)
- Date: 2026-11-24
- 고치는 곳: [ADR-0564](./0564-a-gold-of-row-versions-is-born-as-its-own-versions-table-beside-the-replaced-one-and-its-current-row-rule-is-rendered-once-in-the-contract-artifact.md)
  결정 3(전국 한 커밋)과 넷째 개정(이어 짓기), ADR-0333 §1(시도 파티션은 "레인이 Dagster 로 옮기면")의 실행.
  ADR-0333 §2(그래프 노드의 `partitions {dimension, keys_from}` 와 명령의 `--partition <key>`)와는 다르게 간다: 키는 노드에 적지 않고 입력
  관찰이 더하며(결정 1-2), 짓기는 키를 인자가 아니라 환경 변수로 받고 없으면 낡은 시도를 모두 올린다(결정 2).
- 짝: ADR-0616(Dagster 가 일을 직접 시작한다, W82c). 이 문서의 "파티션", "파트가 알리는 방법", "파트를 시작시키는 것"은 0616 이 그대로 쓴다.

## 사장에게: 세 줄

- 지금은 "얼마나 한 번에 싣고, 어디까지 했고, 실패하면 어디서 잇는가"를 레인마다 우리 코드가 정한다. 2026-11-23 에 그림자 넷이 그래서 멈췄다.
- 앞으로 **상태를 가진 단위는 시도 하나, Dagster 의 파티션**이다. 어느 시도를 지을지, 실패한 시도만 다시 돌리기, 한꺼번에 몇 개 돌릴지는 Dagster 의 기본 기능이 한다.
- 우리 코드는 둘만 한다: 시도마다의 "입력 버전"을 데이터로 내고, 한 시도를 메모리 안에서(시군구씩, 바뀐 필지만) 짓고 붙인다. 참은 표다:
  실패한 실행이 어디까지 했는지는 표가 말하고 우리는 기록하지 않는다.

## Context

**11-23 에 멈춘 것.** 그림자 넷이 같은 까닭(시도나 전국을 한 문장으로)으로 멈췄다: 토지소유 OOM 4/4, 필지 패널 OOM 1/1, 실거래 열린 파일 9/9,
인허가 판정 시간 초과. 메모리는 #1676(`kind_versions_stage::build_in_parts`, 시군구 조각)이 공통 빌드에서 막았다. 남은 것은 **상태**다.

**지금 상태를 가진 것(main `ec446d36`, 코드를 읽음).**

| 우리 코드 | 하는 일 | 어디 |
|---|---|---|
| 이어 짓기 | 지문마다 상태 디렉터리, 끝난 묶음 파일, 25 분 멈춤, `partial` 결과 | `gold_versions_resume.rs`, `gold-versions-build.sh` |
| 레인 기록 | "이 커밋은 지역마다 무엇에서 지어졌나" | 실거래 레인(`real_transaction_versions_stage`) |
| 시도 루프 | 무엇을 지을지 정하는 `for sido` | `kind_versions_build` 와 자체 드라이버 4(주변·호 공시가격·서빙 경계·실거래) |
| 판정 기록 | 머리마다 판정했는지, 다음 표는 무엇인지(`last_judged`) | `gold_takeover_check.py` 의 `takeover-verdict.json` |

Dagster 쪽은 작업마다 job 하나이고(`run_jobs.py`), 그 op 가 유닛을 한 번 시작하며, 유닛은 전국을 한 Iceberg 커밋으로 붙이고 파티션 없는
materialization 하나를 알린다. Dagster 는 시도를 모른다.

**읽은 것(Dagster 1.13 문서와 1.13.27 소스; 우리 핀은 `dagster==1.13.27`).**

- 파티션: `StaticPartitionsDefinition`, `DynamicPartitionsDefinition`(자산마다 10 만 개 이하 권장).
  <https://dagster.io/docs/api/dagster/partitions>
- 한 조각의 사건: `AssetMaterialization(asset_key, partition=...)`, `AssetObservation(..., partition=...)`.
  <https://dagster.io/docs/guides/build/assets/metadata-and-tags/asset-observations>
- 백필: 기본은 파티션마다 run 하나, `BackfillPolicy.single_run()` 은 고른 파티션을 한 run 에("실패하면 모두 다시").
  <https://dagster.io/docs/examples/best-practices/partition-backfill-strategies>
- 선언적 자동화: `AutomationCondition.eager()` 는 static·dynamic 파티션에서 모든 파티션을 본다. 상류가 **관찰**되면 데이터 버전이 바뀐 때만
  갱신으로 치고, **materialize** 되면 버전과 상관없이 갱신으로 친다. <https://dagster.io/docs/guides/automate/declarative-automation>
- 동시 실행: 풀과 태그 한도는 run 에 건다. 파티션 하나가 run 하나면 지금의 `duckdb` 풀(ADR-0605)이 곧 파티션 한도다.

**스파이크 둘(2026-11-24, 노트북의 임시 venv, `dagster==1.13.27`, `DagsterInstance.ephemeral()`; 운영에 닿지 않음).**

(a) `BackfillPolicy.single_run()` 과 떨어진 키.

| 물은 것 | 결과 |
|---|---|
| 7 개 키 전부 | run 1 개, 구간 `11..48` |
| `{11, 41, 47}` | run 2 개: `11..11`, `41..47` — **이어진 구간마다 run 하나**(정의의 키 순서에서) |
| 구간 `11..41` 의 run 이 `28` 에서 실패(시도마다 `AssetMaterialization(partition=)` 을 알리던 중) | `11·26·27` = MATERIALIZED, `28·41` = FAILED, 나머지 = 없음 |
| 뒤이은 `28..41` run | 성공, `28·41` = MATERIALIZED |

소스: `dagster/_core/definitions/automation_tick_evaluation_context.py` `_build_run_requests_with_backfill_policy` 가
`partition_subset.get_partition_key_ranges()` 의 구간마다 run 요청 하나를 만든다. 그래서 떨어진 키를 한 run 에 넣는 길은 없다(우리가 만들지 않는다).

(b) 파티션마다의 데이터 버전이 `eager` 를 파티션마다 움직이는가. 상류 = 레인의 입력, 하류 = 판 표 자산(시도 파티션, `eager`).

| 상류를 알리는 방법 | 결과 |
|---|---|
| A. `@observable_source_asset(partitions_def=...)` 가 `DataVersionsByPartition` 을 돌려줌(Dagster 가 관찰을 돌린다) | 처음: 넷 모두 요청. 같은 버전 다시 관찰: 0. `41` 만 바뀜: `[41]`. `11·47` 바뀜: `[11, 47]`. static·dynamic 둘 다 같다 |
| B. op 가 `AssetObservation(partition=, tags={"dagster/data_version"})` 를 적음 | 한 번도 요청하지 않음 |
| C. op 가 `AssetMaterialization(partition=)` 을 적음 | 매번 넷 모두 요청(문서대로: materialize 는 버전을 보지 않는다) |

그래서 기본 기능만으로 "바뀐 시도만"이 되려면 **입력은 `observable_source_asset`, 판 표는 진짜 `@asset`** 이어야 한다. op 가 사건을 적는
모양으로는 되지 않는다(지금의 `run_jobs.py` 는 op 가 파티션도 데이터 버전도 없는 `AssetMaterialization` 과 검사 결과만 적는다).

**입력이 시도로 놓여 있는가(2026-11-24, 운영 카탈로그의 `SHOW CREATE TABLE`, 메타데이터만).** 종류 레인이 읽는 Silver 가운데 시도로 나뉜 것은
`silver.unit_official_price`(`sido`) 하나다.

| 입력 | 파티션 | 정렬 | 시도로 놓였나 |
|---|---|---|---|
| `silver.land_ownership`(토지소유) | 없음 | 없음 | 아니다 |
| `silver.parcel_boundaries`(모든 레인) | `source_snapshot_id` | `pnu` | 판본 안에서 파일이 pnu 순서다(파일 min/max 로 걸러진다) |
| `silver.building_register_titles`·`units` | 없음 | 없음 | 아니다 |
| HUB 표(`building_permit_*`, `building_register_master`·`sub_parcel` …) | `vintage` | 없음 | 아니다 |
| `silver.land_characteristic`·`land_use_plan`·`land_forest_ledger`(패널) | 없음 | 없음 | 아니다 |
| `silver.registered_factory`, `silver.onbid_*` | 없음 | 없음 | 아니다 |

그러니 지금은 입력이 조금만 움직여도 17 시도의 버전이 모두 움직이고, 시도마다 읽으면 표를 17 번 훑는다(W95b 가 잰 것: 2,155 키를 짓는 데 308 초,
17 시도를 모두 읽어서). "바뀐 시도만"이 얼마나 듣는가는 이 배치가 정한다.

## Decision

### 1. 파티션은 시도다

1. 상태·재시도·백필의 단위는 **시도(PNU 앞 2자)** 다. ADR-0333 §1 의 키이고, 판 표의 Iceberg 파티션이다. 시군구(약 250)는 드라이버 안의 메모리
   조각(#1676)이고 밖에서 보이지 않는다.
2. PNU 로 나뉘는 모든 Gold 레인이 **`DynamicPartitionsDefinition(name="sido")` 하나**를 같이 쓴다. **키는 더해지기만 한다.** 입력 관찰(결정 2-1)이
   돌려주기 전에 `instance.add_dynamic_partitions` 로 제 목록의 새 키를 더한다(센서가 아니다; `build_add_request` 는 센서의 API 라 쓰지 않는다).
   목록은 **입력에 있는 시도와 표의 머리가 아직 든 시도의 합**이다(지금 드라이버의 `head_sidos`): 폐지된 코드의 시도도 파티션으로 지어져
   지우는 표시를 받는다. 키를 자동으로 지우지 않는다: 지우면 그 행을 지울 run 이 없어지고, 한 레인의 관찰은 다른 레인이 그 키를 쓰는지 모른다.
   지우는 것은 모든 레인의 그 시도 현재 행이 0 이 된 뒤 운영자의 일이다(시도 코드가 바뀐 것은 두 번뿐이다: 42→51, 45→52).
   static 목록은 새 코드마다 PR 이 필요해서 고르지 않았다. 스파이크 (b)-A 는 dynamic 에서도 같았다.
3. **코드 변경으로 이어진 두 시도(42 와 51)는 한 커밋으로 짓는다.** 채움 검사가 옮겨 간 행을 한 diff 안에서만 맞추기 때문이다
   (`gold_versions_commit` 의 구역 손실 막이). 한 시도를 받은 짓기는 변경표가 그 시도와 잇는 시도를 같이 짓고 둘 다 알린다. 다른 run 이 나머지를
   받으면 결정 2-5 의 "표가 참"으로 알리기만 한다.
4. PNU 로 나뉘지 않는 표는 까닭을 선언한다: 스튜어드 큐 = `unit`(둘), 발행 ID = `(unit, scope)`, 산업단지 목록(1,442 행) = 파티션 없음.
   실거래는 이 ADR 밖이다: "잇는 시군구 묶음"이 시도를 넘는지 W81f 와 정한 뒤 따로 적는다(파티션의 뜻을 둘로 만들지 않는다).

### 2. 바뀐 파트가 파티션 키가 되는 길

**목표는 AWS 다(사장 결정 2026-11-24; ADR-0616 이 AWS 를 전제로 다시 쓰인다).** 거기서는 Dagster 가 파티션 하나(또는 구간)를 일 하나로 직접
시작하고(ECS 태스크), run 의 파티션 키가 일에 닿는다. 그래서 아래 1·2 의 "입력 관찰 + 파티션마다의 `eager`"(스파이크 (b)-A)가 본길이다.

**짓기는 키를 받으면 그 시도만, 받지 않으면 낡은 시도를 모두 올린다**(`FOUNDATION_PLATFORM_GOLD_VERSIONS_PARTITIONS`, 쉼표로 이은 시도 — 자산의
몸이 run 의 `partition_keys` 를 넣는다; Dagster 가 구간을 키로 풀어 주므로 짓기는 dynamic 파티션의 순서를 몰라도 된다). 표가 참이므로(아래 4·5)
짓기는 어느 쪽이든 원하는 버전을 스스로 셈하고, 머리의 상태가 다른 시도만 짓고, 같은 시도는 건너뛴다. 키 없이 도는 길은 파티션을 하나씩 시작할
수 없는 곳(지금의 유닛 시작)에서의 길이고, ai-server 의 시작 층은 이 ADR 때문에 고치지 않는다.

1. **입력 관찰.** 레인마다 `@observable_source_asset(partitions_def=sido)` 하나가 `DataVersionsByPartition` 을 돌려준다. 값은 공통 드라이버의
   `plan-gold-versions <lane>` 이 낸 한 줄의 JSON(`{"partitions": {"11": "<버전>", ...}}`)이다. `plan` 은 상태를 갖지 않고, 레이크하우스 열쇠가
   있는 일(ADR-0616 이 정하는 태스크)에서 돈다 — Dagster 데몬에는 열쇠가 없다.
   **버전(시도) = hash(짓기가 그 시도에 쓸 입력 핀 전부, 코드 버전, 서빙 판본, 시각 칸).** 핀은 드라이버가 지금 정하는 그대로다
   (`gold_versions_commit::planned_inputs`): 그림자는 옛 표 빌드 태그가 적은 핀이고(입력의 머리가 아니다 — 그래서 Silver 가 붙어도 그림자의
   버전은 옛 표가 다시 지어질 때만 움직인다), `pins_from` 이 있는 종류는 그 표의 핀이다. 시각에 달린 종류(공매: `as_of_dependent`)는 관찰의
   시각 칸(레인의 cron 한 칸)이 버전에 들어 매 칸 모든 파티션이 요청된다 — 지금 "매 실행 전량"과 같다. 시도로 놓이지 않은 입력의 핀은 표의
   스냅숏이라 17 시도의 버전이 같이 움직인다(지금의 `whole_table_inputs` 를 데이터로 말한 것).
2. **Dagster 가 정한다.** 판 표는 `@asset(partitions_def=sido, automation_condition=AutomationCondition.eager(), deps=[입력 관찰])` 이다.
   스파이크 (b)-A 대로 버전이 바뀐 시도만 요청된다. 우리 센서는 없다. 관찰을 언제 돌리는가는 ADR-0616 의 것이다(레인의 cron).
3. **짓기.** 자산의 몸은 받은 키·구간으로 일을 시작한다(결정 5). 드라이버는 시도마다: 시군구씩 짓고, **파티션 안에서는 지금처럼 바뀐 PNU 만**
   짓고(`changed_pnus`: 그 시도의 옛 핀과 새 핀 — ADR-0564 결정 3-2 의 부분 처리는 파티션 안에 그대로 남는다), 머리와 diff 하고, 그 시도의
   Iceberg 추가 커밋 하나를 하고, `report_asset_materialization(partition, data_version)` 과 그 시도의 검사를 알린다. 바뀐 키가 0 인 시도는 materialization 을 알리지
   않는다: 행이 붙지 않았으므로 하류가 움직일 까닭이 없다. 그 시도가 이 버전에서 읽혔고 바뀐 것이 없다는 것은 통과한 자산 검사로
   알리고(ADR-0616 §6), 머리의 상태 표는 그 시도의 버전을 올린다. 표가 이미 그 버전인 시도(앞 run 이 붙이고 죽었거나 운영자가 다시 돌린 것)도 observation 이 아니라
   **materialization** 으로 알린다(`found_current: true`): Dagster 는 그 시도를 모른다. materialization 은 데이터 버전이 같아도 하류의 `eager` 를
   움직인다(스파이크 (b)-C). 받아들인다: 이 일은 실패한 run 뒤와 운영자의 재실행에서만 일어나고, 하류도 표가 참이라 그 run 은 할 일 없이 끝난다.
4. **커밋은 시도마다이고, 표의 머리 하나가 모든 시도의 상태를 든다**(ADR-0564 결정 3 을 고친다).
   - `version_seq` 는 지금처럼 **표의 커밋 번호**다: 커밋할 때 `main` 의 머리에서 읽어 1 을 더한다. 굽기의 변경 집합
     (`gold_versions_change_set`: `version_seq > V`)이 그대로 맞는다.
   - 커밋마다 **시도별 상태 표**(시도 → 핀·코드 버전·판본·버전·현재 행 수·지문)를 요약에 통째로 이어 적는다. 그래서 가장 새 커밋 하나가 모든
     시도의 `Base` 다: 30 일 동안 움직이지 않은 시도의 기준도 만료에 잃지 않는다.
   - `foundation.current-records` 와 지문은 지금처럼 **표 전체의 값**이다(이어 더한 합). 굽기의 `max_delta_fraction`, 줄어든 행 하한,
     `after_digests` 가 읽는 것이 바뀌지 않는다.
   - ADR-0564 결정 3-4 의 한계(줄어든 행의 하한, 바뀐 키의 비율)는 커밋마다, **그 시도의 행 수**로 본다(머리의 상태 표가 적은 값). 한계를 넘긴 시도는 붙지 않고 run 이
     실패한다; 앞서 붙은 시도는 선다.
   - 묶음 신원(`run_id`)에 **파티션 키와 그 버전**이 든다. 지금의 신원(표·핀·코드·판본)으로는 한 run 의 둘째 시도가 "이미 붙음"이 된다.
   - 입력 핀 태그는 상태 표를 따른다: 입력마다 상태 표가 드는 가장 오래된 핀이 태그로 남는다.
   - 한 표에 두 run 이 같이 붙으면 Iceberg 의 낙관적 커밋이 하나를 거절하고, 거절된 쪽이 머리를 다시 읽어(번호·상태 표) 다시 붙인다. 레인마다의
     풀은 두지 않는다. 풀은 ADR-0616 의 것이다(기계 크기의 풀은 없어지고, 카탈로그 커밋이 부딪는 곳에만 둔다).
5. **여러 시도를 한꺼번에.** 자산은 `BackfillPolicy.single_run()` 을 선언한다. 처음 짓기와 코드 버전 이동(17 개 모두)은 run 하나·입력 한 번
   읽기이고(스파이크 (a): 구간 하나), 떨어진 키는 이어진 구간마다 run 하나다.
   **실패한 run 이 이미 알린 시도를 Dagster 가 적는다고 기대하지 않는다.** 기본 Pipes 클라이언트는 일이 끝난 뒤에 결과를 돌려주고 실패하면
   돌려주지 않는다(1.13.27 `dagster_docker/pipes.py`; 지금의 `systemd_pipes` 도 끝난 뒤에 넘긴다; ADR-0616 은 그 클라이언트를 고쳐 쓰지 않는다).
   그래서 **표가 참이다**: 짓기는 시도마다 머리의 상태 표가 적은 버전을 보고, 받은 버전과 같으면 짓지 않고 materialization 만 다시 알린다.
   다음 run 은 붙은 시도를 다시 짓지 않고 Dagster 의 파티션 상태는 표에서 다시 선다. 우리 쪽에 실행의 기록은 없다.
6. **다시 하기와 시간.** 누가 다시 하는가는 ADR-0616 의 표 하나가 정한다(태스크가 죽으면 run 재시도, 일이 실패하면 짧은 op 재시도, 긴 물러남은
   다음 cron 칸). 이 ADR 이 더하는 것은 하나다: 다시 하는 run 은 5 대로 붙은 시도를 건너뛴다. 재시도를 다 쓴 파티션은 FAILED 로 남는다.
   run 의 시간·메모리 한도는 ADR-0616 의 태스크 크기이고, 시도를 차례로 짓는 run 에서도 메모리는 한 시도(안에서는 한 시군구)의 값이다.
7. **읽는 쪽.** by-PNU 굽기는 상태 표의 판본과 코드 버전이 모든 시도에서 같은 머리만 핀한다(표에서 읽는다; Dagster 의 백필 상태를 읽지 않는다).
8. **그림자와 판정.** 판정받는 머리는 "모든 시도가 같은 그림자 핀을 적은 머리"다. `takeover_equal` 은 그런 머리마다 한 번, 마지막 시도가 붙은
   뒤에 돈다(선언한 시도의 행 견주기와 전국 집계). 자산의 몸이 Dagster 의 검사 이력에서 마지막 판정의 `candidate_snapshot` 을 읽어 지금 머리와
   다르면 그 run 에 판정을 시킨다 — `takeover-verdict.json` 을 대신한다.

### 3. 입력을 시도로 놓는 것은 따로 정한다

시도로 놓이지 않은 입력은 전국 표로 센다(결정 2-1). 그래서 이 ADR 만으로는 입력이 움직이면 17 파티션이 모두 요청되고, 파티션마다 바뀐 PNU 만
짓는다 — 짓는 양은 지금과 같고, 얻는 것은 상태·재시도·백필이다. Silver 표의 파티션 명세에 시도를 더해 "움직인 시도만 요청"을 얻는 것은 다른
결정이다(Silver 의 배치, R2 Data Catalog 의 명세 진화, DuckDB 의 걸러 읽기, 옛 명세 파일이 남는 동안의 지문, 합치기가 스냅숏을 움직이는 것을
먼저 재야 한다). 그 ADR 의 번호는 코디네이터에게 받는다. 위 Context 의 표가 그 출발점이다.

**일을 시작하는 층에 기대는 것**(ADR-0616). 셋이다.

1. run 의 파티션 키가 일의 환경에 닿는다(위의 환경 변수 하나; 없으면 낡은 시도 모두).
2. 일의 Pipes 줄(`report_asset_materialization`·`report_asset_check`)이 **파티션과 데이터 버전을 지닌 채** 사건이 된다.
3. 일의 종료 상태가 run 의 성패다.

기대지 **않는** 것: 실패한 run 의 사건이 남는 것(결정 2-5: 기본 Pipes 클라이언트는 일이 끝난 뒤에만 결과를 돌려준다 — 표가 참이다).
ai-server 의 지금 층(`run_jobs.py`·`systemd_pipes.py`·`start-scheduled-job.sh`)은 AWS 가 대신하므로 이 설계를 위해 고치지 않는다.

**어디에 선언하나.** 작업 정의에 `partitioned_by: sido` 가 있으면 생성기가 그 작업의 출력을 `partitioned_assets.py` 의 `@asset` 과 입력 관찰로
만든다. 그 노드는 `observe_assets` 의 `AssetSpec` 에서, 그 작업은 `run_jobs` 의 job 과 `decide` 의 센서에서 빠진다: 시작시키는 것은 `eager` 하나다.
`job_specs`·선언 생성물·파이프라인 지도·메모리 가드는 같은 정의에서 읽으므로 새 칸 하나를 안다. 자산의 몸이 일을 어떻게 시작하는가는 ADR-0616 의 것이다.

### 7. 공통 드라이버의 API (한 쪽)

모든 Gold 판 레인은 드라이버 하나(`kind_versions_build::run`)와 단계의 trait 하나(`KindVersionsStage`)를 쓴다. 낱말은 둘이다: **파티션 = 시도**(커밋·상태·
Dagster 의 키), **파트 = 시군구**(한 번에 메모리에 드는 양; 밖에서 보이지 않는다). 레인은 SQL 과 아래의 선언만 준다. 스풀·나눔·루프·이어 짓기·검사 알림을
레인이 갖지 않는다.

**드라이버가 하는 일(순서).**

1. 계획: 핀·코드·판본 → 원하는 버전. 머리의 상태 표와 견줘 지을 시도를 고른다(결정 2).
2. 읽기: 입력마다 한 번 스풀(`<이름>/sido=<시도>/`). **기준 쪽(옛 핀)은 움직인 입력만 읽는다.** 필지 핀과 판본이 기준과 같으면
   `served_old` 는 `served` 다(두 번째 4 천만 행 읽기 없음).
3. 바뀐 키: **한 번, 스풀에서.** 움직인 행 묶음의 새 스풀과 기준 스풀을 파트 파일끼리 견준다(같은 multiset 이면 그 파트에 대상이 없다). 결과는
   전국의 `targets(pnu)` 다. 단계가 `changed_pnus` 를 따로 갖지 않는다(기본 규칙: 행 묶음의 열 전부의 multiset 차이 + 서빙 필지의 차이). 다른 규칙이
   필요한 단계만 `changed_keys_sql` 을 준다.
4. 시도마다, **대상이 있는 파트만**: 싣고(파트와 그 파트가 읽는 다른 파트), 짓고(`build_in_parts`), 머리의 현재 행을 **대상이 있는 시군구의
   글자 범위**(`pnu >= 'ddddd' AND pnu < 'ddddd'+1`)로 읽어 diff 하고, 검사하고, 그 시도를 커밋한다. 대상이 없는 시도·파트는 싣지도 읽지도 않는다.
5. 알림: 시도마다 `report_asset_check`(검사)와 `report_asset_materialization`(커밋 뒤), 요약에 단계별 밀리초(`spool`·`targets`·`load`·`build`·
   `diff`·`checks`·`stage`·`commit`).

**trait 에서 바뀌는 것.**

| 무엇 | 모양 | 기본값 | 누가 쓰나 |
|---|---|---|---|
| 다른 열쇠로 드는 행·파트 밖에서 읽는 행 | `fn part_tables(&self) -> Vec<&'static str>` — `load_more` 가 남긴 표 가운데 `part` 칸으로 파트를 말하는 것 | 빈 목록(표는 PNU 앞 5자로 가른다) | 실거래: 주소 코드로 드는 거래, 코드 짝·서빙 형태·계보가 잇는 시군구의 행 |
| 바뀐 키의 다른 규칙 | `fn changed_keys_sql(&self) -> Option<String>` | `None`(위 3 의 기본 규칙) | 부속지번·인허가가 필요하면 |
| 결과 검사 | `fn result_checks(&self) -> Vec<ResultCheck>` — `ResultCheck { name, sql, blocking }`; SQL 은 그 시도의 `built`·`appended`·`current_rows` 위에서 어긴 행 수를 낸다 | 빈 목록 | 레인의 도메인 거부 |
| 시도 통째로 짓기 | `fn whole_region_reason(&self) -> Option<&'static str>`(#1676) | `None` | 지금 없음 |
| 지워지는 것 | `changed_pnus`, 단계마다의 `_old` 싣기 | — | — |

단계는 다른 파트가 읽는 행을 **읽는 파트마다 한 번씩** 스풀한다(`spool_more`): `part` 칸에 그 파트를 적고 그 파트의 시도 아래에 둔다. 드라이버는
`part` 칸이 있는 표를 그 칸으로, 나머지를 PNU 앞 5자로 갈라 한 파트씩 보이고, 짓는 동안 `build_part(part)` 로 그 파트를 알린다. 단계는 **PNU 가
그 파트에 드는 문서만** 쓴다. 어기면 그 문서가 두 번 지어져 diff 가 거부한다(키가 두 번) — 드라이버가 따로 지우지 않아도 틀린 표는 붙지 않는다.
다른 시도의 행도 읽는 파트의 시도 아래에 스풀되므로 시도 하나를 싣는 것으로 끝난다. 파트는 그대로 시군구이고 파티션은 그대로 시도다:
실거래의 자체 스풀 배치·단위 묶음·예산 짜기·이어 짓기·자체 드라이버는 지운다.

**모든 레인이 받는 검사**(드라이버가 돌리고 알린다; 단계가 쓰지 않는다): 시도의 행 수와 키 수, 키마다 현재 행 하나(지금의 거부), 바뀐 문서가 스키마
레지스트리의 그 revision 을 지킴, ADR-0564 결정 3-4 의 두 한계. `blocking` 검사가 어기면 그 시도는 붙지 않는다. 검사는 커밋 **앞**에 돌고 Pipes 의
`report_asset_check`(파티션 = 시도)로 알린다. Spark 모듈·Trino 로 돌던 검사는 넘겨받기와 함께 사라지고 이것이 남는다.

**임시 공간의 상한은 레인마다 잰 값이다.** 지금은 모든 DuckDB 단계가 레인의 크기와 상관없이 32 GiB 를 선언한다(`max_temp_directory_size` 의 기본). 2026-11-24 에
ai-server 에서 토지소유와 발행 ID 의 그림자가 이 선언 때문에 시작도 못 했다(선언 32 GiB + 호스트 예약 30 GiB = 66.6 GB 가 필요했고 디스크에는
56~65 GB 가 비어 있었다). 드라이버는 요약에 스풀과 임시 공간의 최고값(`stage_bytes_peak`)을 적고, 레인의 선언은 그 잰 값에서 온다.
AWS 의 태스크 디스크도 그 값으로 잡는다(ADR-0616). 이 PR 들은 아직 그렇게 하지 않는다: 종류 레인의 요약에는 그 칸이 없다.

**Pipes 줄.** 발행기가 문서로 정해진 Pipes 메시지를 표준 출력에 한 줄씩 쓴다(작은 공통 모듈 하나: `report_asset_materialization`,
`report_asset_check`, 파티션과 데이터 버전을 실어). Dagster 의 Rust Pipes 구현을 쓰지 않는 까닭: 공식 클라이언트는 Python 뿐이다(확인할 것 — 있다면 그것을
쓴다).

**누가 무엇을 짜나**(구현은 하나, 차례대로 같은 가지 위에).

| 차례 | 무엇 | 누가 |
|---|---|---|
| 1 | 시도마다 커밋·상태 표·받은 키(이 PR), 그 위에 드라이버 루프의 4·5(대상 없는 파트 건너뛰기, 글자 범위, 단계별 시간, 검사 틀과 Pipes 줄) | W97b |
| 2 | 읽기 2 와 바뀐 키 3(움직인 입력만의 기준 스풀, 스풀에서 한 번 찾는 대상, `changed_pnus` 지우기), 부속지번·인허가 단계 | W95b |
| 3 | `spool_more`·`load_more`·`part_tables`·`changed_keys_sql` 로 실거래 단계를 옮기고 자체 스풀·묶음·이어 짓기를 지운다 | W81f |
| 4 | 공통 검사의 내용(스키마 revision, 행·키)과 레인의 `result_checks` | W96b |

## Consequences

- 전량 짓기 한 번이 커밋 17 개다. 상태 표가 머리에 있어 만료가 어느 시도의 기준도 지우지 않는다.
- 성공한 구간 run 은 시도마다 사건이 둘이다(일이 알린 것, run 끝의 것; 스파이크 (a) 에서 봄). 고치지 않는다.
- 결정 3 의 ADR 전에는 입력이 움직이면 17 파티션이 모두 돈다(파티션 안에서는 바뀐 PNU 만). 짓는 양은 지금과 같다.
- 한 표의 시도들이 서로 다른 입력 핀에 설 수 있다. 문서는 제 PNU 의 행만 읽으므로(#1676 에서 종류 단계 여덟을 확인) 맞는 표이고, 굽기와 판정은
  고른 머리만 본다(결정 2-7·2-8).

## 하지 않은 것, 확인하지 못한 것

- Dagster 쪽 코드가 없다. 스파이크는 프로세스 안의 임시 인스턴스였다: 데몬이 도는 운영 Dagster 에서 같은지는 PR 3 전에 본다.
- PR 1 의 발행기 코드는 노트북에서 컴파일하지 못했다(여유 메모리 2 GB): CI 가 판정한다. 상태 표와 버전은 단위 시험이 있고, 시도마다 붙이는
  길 자체는 레이크하우스가 있어야 돌아 운영의 토지소유 첫 빌드가 처음 쓴다.
- **`eager` 는 FAILED 파티션을 다시 요청하지 않는다**(스파이크 (c), 2026-11-24, 프로세스 안의 임시 인스턴스, `dagster==1.13.27`): 구간 `11..48` 의 run 이 `28` 에서
  죽은 뒤(`11·26·27` MATERIALIZED, `28·41·47·48` FAILED) 다음 칸도, 같은 버전을 다시 관찰한 뒤의 칸도 요청이 없었다. `28` 의 버전이 바뀌어야 `[28]` 이
  요청됐다. 그래서 실패한 파티션은 재시도(ADR-0616 의 표)나 조건의 한 가지(`execution_failed()` 를 레인의 cron 칸에 묶는 것 — 기본 연산자다)가
  다시 요청해야 한다. 어느 쪽인지는 PR 3 이 정한다.
- **처음 짓기는 `eager` 가 요청하지 않을 수 있다**(같은 스파이크): 자동화가 처음 평가되기 전에 관찰된 입력은 "새로 움직인 것"이 아니라서 첫 칸이 아무것도
  요청하지 않았다. 레인을 켤 때의 첫 짓기는 백필 한 번이거나 조건에 `missing` 을 더한다(PR 3).
- run 재시도가 구간 run 에 어떻게 드는지는 데몬이 있어야 보인다: 아직 읽지도 돌리지도 않았다(PR 3 전에 도는 데몬에서 정한다).
- `single_run` 과 `eager` 가 같이 있을 때 요청이 구간 run 으로 나가는지는 소스(`_build_run_requests_with_backfill_policy`)로만 보았다.
- 실거래, Silver, 입력을 시도로 놓는 것은 이 ADR 밖이다.

## 기각한 대안

- **30 줄짜리 센서로 버전을 견주기.** 스파이크 (b)-A 가 기본 기능으로 됨을 보였다.
- **지금처럼 op 가 사건을 적기.** (b)-B·C: 요청이 아예 없거나 매번 전부다.
- **파티션 = 시군구.** 250 개의 상태는 사람이 읽지 못하고, 표의 Iceberg 파티션과 어긋난다.
- **static 시도 목록.** 코드가 바뀔 때마다 PR 이다.
- **파티션마다 run 하나(기본 백필).** 시도로 놓이지 않은 입력을 17 번 읽는다.
- **시도마다의 `Base` 를 그 시도의 가장 새 커밋에서 읽기**(첫 초안). 만료가 기준을 지우고 번호가 겹친다.
- **기본 Pipes 클라이언트를 고쳐 실패한 run 의 사건을 살리기.** 우리 코드가 는다; 표가 참이면 필요 없다.
