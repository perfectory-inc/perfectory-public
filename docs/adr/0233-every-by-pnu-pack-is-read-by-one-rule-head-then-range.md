# ADR 0233: PNU 묶음은 크기와 레인에 상관없이 한 규칙으로 읽는다 — 머리, 그다음 문서 하나를 범위로

- Status: Accepted
- Date: 2026-10-14
- Supersedes: [ADR-0163](./0163-a-large-legal-dong-pack-is-split-into-parts-read-whole.md)(큰 법정동을 조각으로 나누고 조각 색인으로 찾는다),
  [ADR-0151](./0151-building-packs-serve-each-document-whole.md) 결정 2의 "gzip 을 받지 않는 클라이언트는 Worker 가 푼다"와
  결정 3 첫 항목(`whole_pack_max_bytes` 이하 묶음은 통째 읽는다)
- Amends: [ADR-0147](./0147-by-pnu-documents-are-served-from-section-packs.md) 읽기 경로(머리 + 범위를 큰 묶음만이 아니라 모든 묶음의 규칙으로)

## Context

2026-10-14 필지 특성 레인의 관문 (나)가 Worker CPU p99 10.678ms(한도 10ms)로 멈췄다. 속도(p95 −58ms)와 일치(불일치 0)는
통과했다. 같은 날 레인마다 미리보기를 자기 경로만으로 3,000건 차갑게 읽어 Workers 분석에서 따로 쟀다(레인별 창이 겹치지 않게).

| 레인 (미리보기, 차가운 읽기) | 읽기 방식 | CPU p50 | p90 | p99 | p999 |
|---|---|---|---|---|---|
| 필지 특성 | 조각 색인 + 통째 | 1.92ms | 3.32 | 25.27 | 53.9 |
| 공시지가 | 조각 색인 + 통째 | 1.80 | 3.13 | 21.05 | 52.6 |
| 용도지역 | 조각 색인 + 통째 | 2.00 | 3.23 | 11.61 | 52.5 |
| 필지 묶음(기준) | 조각 없음, 머리 + 범위 | 2.58 | 5.05 | 9.37 | 35.5 |

p50 은 같고 꼬리만 다르다. 실제 바이트로 V8 에서 단계마다 잰 값:

| 단계 | 언제 | 비용 | 무엇에 비례하나 |
|---|---|---|---|
| 조각 색인 `parts.json` 파싱 + 항목마다 정규식 (17,883 법정동, 270KB) | isolate 의 첫 읽기 | 20–45ms | 조각 난 법정동 수 |
| 같은 색인 sha256 (운영 manifest 경로) | isolate 의 첫 읽기 | 0.6–4ms | 색인 크기 |
| 통째 묶음 복사 + 머리 파싱 + 이진 탐색 (136KB) | 요청마다 | 0.06–0.2ms | 묶음 크기 |
| 운영 경로 manifest 파싱 (필지, 패치 법정동 16,000) | **요청마다** | 1.5–5.7ms | 패치 법정동 수 |
| gzip 을 받지 않는 클라이언트에게 Worker 가 풀기 | 그 요청마다 | 1MB 당 5.8ms | 문서 크기(건물 최대 11.5MB, 호 단가 1.5MB) |

꼬리는 조각 색인이다. 조각 레인은 법정동 수만큼 큰 객체를 isolate 마다 파싱한다. 그리고 읽기 규칙이 셋이었다:
256KiB 이하는 통째(0151), 그 위는 머리 + 범위(0147), 큰 법정동은 조각 + 조각 색인(0163). 규칙마다 요청 CPU 가
다른 데이터 크기에 비례했다. 새 종류 레인이 생길 때마다 숫자(조각 목표 크기 등)를 맞추는 것은 근본 해결이 아니다.

## Decision

1. **읽기 규칙은 하나다.** 모든 레인, 모든 크기의 묶음을: 머리(접두·머리 JSON·색인)를 isolate 메모리에서, 없으면 범위
   없는 GET 하나로 머리 끝까지만 읽고(나머지 본문은 취소) 머리 길이의 버퍼 하나에 한 번만 복사한다 → 색인을 이진
   탐색한다 → 문서 하나를 범위 읽기로 가져온다 → 저장된 gzip 덩어리를 그대로 낸다. 통째 읽기 분기는 없다.
2. **Worker 는 문서를 풀지 않는다.** gzip 을 받지 않는 클라이언트에게도 같은 덩어리와 같은 `ETag` 를 내고, 변환은
   런타임/엣지가 한다(Cloudflare 는 압축된 응답을 받지 않는 방문자에게 풀어 준다; Miniflare 의 workerd 도 같다).
   변환된 응답의 태그는 약해질 수 있고, Worker 는 태그를 약하게 비교한다.
3. **요청 하나의 CPU 는 데이터 크기에 비례하지 않는다.** 요청이 복사하는 바이트를 계약
   `by_pnu_section_packs.read_path.request_cpu_budget` 가 묶는다: 문서 gzip 덩어리 ≤ `document_max_bytes`(256KiB),
   묶음 머리 ≤ `pack_head_max_bytes`(1MiB). **묶음을 쓰는 곳은 `PackWriter` 하나이고, 그것이 넘는 문서와 머리를
   거부한다** — 기본 세대든 패치든, 어느 레인이든. 새 종류 레인은 굽는 순간 이 예산을 지키거나 멈춘다.
   2026-10-14 실측 최대: 문서 256,326B(건물), 머리 720,333B(필지 묶음, 약 25,700 항목).
4. **운영 경로는 manifest 를 isolate 마다 한 번만 파싱한다.** 엣지 사본에 R2 `etag` 를 붙여 두고, 같은 태그면
   파싱해 둔 계획을 쓴다. 신선도는 그대로 엣지 사본의 수명이다.
5. **기본 세대는 법정동을 조각으로 나누지 않는다.** 크기와 상관없이 법정동 하나가 묶음 하나다. 조각 색인을 쓰지 않는다.
6. **검증은 굽기와 발행 때 끝낸다.** Worker 는 manifest 가 가리키는 create-only 객체를 믿고, 머리의 형식·길이와
   범위 응답의 `etag` 만 본다.

## 전환 (조각과 `whole_pack_max_bytes` 의 은퇴)

조각 읽기는 새 규칙의 분기가 아니라 이미 조각으로 구운 세대를 읽기 위한 것으로만 남고, 그 세대가 없어지면 지운다.

1. 이 결정의 코드: 굽기는 조각을 만들지 않고, Worker 는 머리 + 범위로만 읽는다(조각 색인 조회는 조각 세대가 남은
   동안만 남는다). 조각 세대 위의 패치 굽기는 그 세대의 조각을 따른다.
2. 조각 세대(운영 용도지역 g1, 공시지가 g1, 미발행 특성·임야대장·토지이동이력·대지권 g1)를 조각 없이 다시 굽고
   관문을 거쳐 발행한다.
3. 운영 manifest 에 조각이 하나도 없으면 Worker·발행기의 조각 코드, 계약 `parts` 블록, `whole_pack_max_bytes`,
   manifest `section_packs` schema 4 를 지운다.

## Consequences

- 차가운 첫 요청은 R2 두 번(머리, 문서)이다. 통째 읽기보다 한 번 많다. 필지 묶음 레인이 이미 이 방식으로 서빙 중이며
  관문 (나)의 기준선이 바로 그것이므로(차가운 p50 461ms·p95 638ms, 2026-10-13), 종류 레인도 같은 수준이 된다. 관문이
  이 규칙을 통과하지 못하면 네 번째 분기를 더하지 않고 수치를 가지고 다시 결정한다.
- isolate 메모리 예산(`memory_budget_bytes` 32MiB)은 이제 머리만 담는다. 문서는 엣지의 PNU 응답 사본에 남는다.
- 건물 문서 최대가 예산의 98% 다. 그 레인에 더 큰 문서가 생기면 굽기가 멈춘다 — 의도된 동작이다. 그때는 문서 키를
  좁힌다(ADR-0204 처럼 접미 키).
- 조각 은퇴까지 특성·임야대장·토지이동이력·대지권 레인은 다시 구워야 한다(묶음 쓰기 수가 법정동 수로 준다).

## Revision (2026-10-14): 머리는 범위 읽기 한 번으로 받는다

결정 1의 규칙(머리 → 이진 탐색 → 문서 하나 범위 읽기)은 그대로다. 머리를 받는 방법만 바꾼다. 범위 없는 GET 의 본문을
덩어리로 받아 JavaScript 에서 복사하던 것을, 묶음 앞 256KiB 의 `Range` 헤더 읽기 한 번(런타임이 버퍼 하나로 넘긴다)으로
받고, 머리가 그보다 길면(표본 3%) 나머지를 범위 읽기 한 번 더로 받는다. 두 번째 읽기의 `etag` 가 다르면 거부한다.

- 측정(같은 시간대, 측정용 Worker, 요청별 `cpuTime`, 표본 약 2,600건씩): R2 머리 읽기 p90 5→3–4ms, 머리 200–500KB 의
  p50/p90 4–5/8–10 → 3/4–5ms, p99 10–23 → 4–12ms. 지연은 같다(Worker 총시간 p50 78–82ms).
- 변하지 않은 것: 가장 가벼운 경로(isolate 메모리의 머리 + 범위 읽기 1번)도 p99 6–7ms(최대 11)다. isolate 의 첫
  `_capabilities` 요청은 1ms, 첫 문서 요청은 5–9ms(요청의 1% 미만). 응답 엣지 사본 쓰기는 p50 을 약 1ms 올리지만 p99 는
  바꾸지 않는다.

## Revision (2026-10-15): 요청 경로의 첫 호출은 isolate 시작 때 치른다

규칙은 그대로다. isolate 가 시작될 때(전역 범위, 요청과 따로 재는 시작 CPU 한도) 요청 경로의 순수 단계를 한 번 돌린다:
레인·PNU 판정, 미리보기 계획, 키, 합성 묶음 두 칸의 머리 해석과 이진 탐색(적중·부재), CORS, `Server-Timing`, 응답
생성(`warmRequestPath`). 첫 R2·캐시 사용 같은 입출력은 전역 범위에서 할 수 없어 첫 요청에 남는다.

- 측정(같은 시간대, 측정용 Worker 두 개, 회차마다 새로 올려 새 isolate 약 600개씩, 요청별 `cpuTime`): isolate 첫 문서
  요청 p50/p90/p99 9/14/19 → 7/13/17ms, 평균 9.8 → 8.3ms(치환 검정 p<0.001), 10ms 이상 비율 49 → 39%. 따뜻한 요청은
  같다(p50/p99 3/8ms 양쪽).
- 계약의 p99 5ms 목표는 이것으로도 닿지 않는다: 따뜻한 요청의 p99 가 이미 8ms 이고, 첫 요청에 남은 몫은 입출력이다.
