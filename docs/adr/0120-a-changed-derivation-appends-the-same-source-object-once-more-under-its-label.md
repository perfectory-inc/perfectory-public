# ADR 0120: 파생 규칙이 바뀌면 같은 원천 객체를 그 규칙의 이름으로 한 번 더 쌓는다

- Status: Accepted
- Date: 2026-10-01
- Builds on: [ADR-0062](./0062-an-ingest-batch-records-itself-in-the-table-it-writes.md)(적재 기록은 그 커밋 안에),
  [ADR-0069](./0069-one-column-holds-five-kinds-of-thing.md)(적재 단위는 계약이 정한다),
  [ADR-0117](./0117-metadata-has-one-contract-per-dataset-and-one-place-to-look.md) §5(원본 글자 칸)

## Context

- 레이크하우스는 덮어쓰지 않고 쌓는다. 같은 원천 객체가 두 번 붙는 사고(2026-08-27, 필지 1,865,891건 세 벌)를 막으려고
  ADR-0062 는 "이 객체를 이미 붙였는가"를 Iceberg 스냅숏 요약에 남기고, 이미 붙인 객체는 건너뛴다.
- 2026-10-01 산업단지 원본 글자 칸(ADR-0117 §5)을 채우려고 8/18 과 **같은 원천 객체**(`30138-6.zip`)를 새 코드로 다시
  파생했다. 원본 글자 칸이 더해졌고 HTML 엔티티 580행이 바르게 풀렸다. 그런데 적재는 "이미 실음"으로 건너뛰었다.
  **파생 규칙이 바뀌었을 때 같은 객체를 다시 쌓을 정당한 길이 없었다.** 남은 길은 행을 고쳐 쓰거나(금지) 객체 이름을
  바꾸는 것(거짓 계보)뿐이었다.
- 같은 실행에서 두 번째 결함이 드러났다. 산업단지 표는 `source_record_id` 를 행마다 `{객체}#{단지코드}` 로 쓴다.
  적재 판단(ADR-0069)은 이를 객체 하나로 줄여 읽지만, 쓴 뒤 다시 읽는 확인은 원값 1,442개를 목록으로 만들다가
  상한 64를 넘겨 거절했다. 이 표의 적재 경로는 확인 단계에서 항상 실패하는 상태였다.

## Decision

1. **적재 식별자에 선택적인 파생 이름을 붙인다.** `append_batch_once(..., derivation=)` 에 이름이 주어지면 식별자는
   `{객체}@{이름}` 이다. 같은 객체는 이름마다 한 번 쌓이고, 같은 이름으로 다시 돌리면 여전히 건너뛴다. 이름이 없으면
   식별자는 지금과 똑같아서 기존 적재의 뜻은 하나도 바뀌지 않는다. 이름에는 `@` 와 `,` 를 쓸 수 없다.
2. **파생 이름은 사람이 다시 파생하는 실행에서만 준다.** 예: 계약에 칸이 늘었을 때. 이름은 무엇이 바뀌었는지를 말한다
   (`source-words-2026-10` 처럼). 정기 적재는 이름을 주지 않는다.
3. **새로 쌓인 판이 현재 판이다.** 같은 객체의 두 판은 `valid_from_utc` 가 같고 `ingested_at_utc` 로 갈린다. Silver 를 읽는
   쪽(Gold 투영 등)은 이미 키마다 최신 판을 고른다.
4. **쓴 뒤 다시 읽기는 이번 배치의 (`source_snapshot_id`, `ingested_at_utc`) 로 거른다.** 원값 목록을 만들지 않으므로 행마다
   값이 다른 표도 상한에 걸리지 않고, 다시 파생한 배치도 자기 행만 읽는다. 내보내기는 실행마다 하나의 `ingested_at_utc` 를
   찍는다.

## Consequences

- 산업단지 Silver 는 1,442행의 두 번째 판을 갖게 된다(8/18 판은 그대로 남는다). Gold·Postgres 는 새 판을 보인다.
- 다른 표가 같은 일을 겪으면 같은 이름 인자를 그 잡에 더한다. 지금은 산업단지 잡만 이 인자를 받는다.
- 시험: `tests/test_lakehouse_ingest.py` 의 `DerivationTest` 가 이름 없음=불변, 새 이름=한 번 더, 같은 이름=건너뜀을 고정한다.
