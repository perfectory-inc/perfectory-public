# ADR 0063: 검색을 못 좁히는 나누기는 파일만 쪼갠다

- Status: Accepted
- Date: 2026-08-28

## Context

`silver.parcel_boundaries` 를 `sigungu_code` 와 `bucket(256, pnu)` 로 나누고 있었다.
전국 필지 3,986만 행을 적재하던 중 실측했다.

```
행 5,610,755 · 1.71 GB · 파일 6,144개   →  파일 평균 0.28 MB
전량 적재 시 예상                        →  파일 43,649개 (평균은 같다)
```

Parquet 파일 하나의 통상 목표는 128–512 MB 다. 0.28 MB 는 그 하한의 1/460 이다. 파일이
작으면 읽는 쪽이 열어야 할 파일이 그만큼 많아지고, 파일마다 붙는 꼬리표(각주·통계·열
메타데이터)가 실제 데이터보다 커진다. 쓰는 쪽에서도 칸마다 Parquet 버퍼를 하나씩 잡으므로
같은 원인이 적재 중 힙 부족의 뿌리이기도 했다.

칸이 65,280개(255 시군구 × 256 버킷)라 칸당 610행이다.

**버킷이 아무것도 못 좁힌다.** PNU 19자리는 법정동코드 10자리로 시작하고, 그 앞 5자리가
시군구 코드다. 그래서 PNU 로 찾는 질의는 `sigungu_code` 칸 하나로 이미 좁혀진다. 그 안에서는
`sort_order` 가 `pnu` 로 잡혀 있어 Parquet 의 최소/최대 통계가 나머지를 건너뛴다. 버킷은 그
위에 아무 선택도 더하지 못하면서 칸 수만 256배로 만든다.

`bucket(256, pnu)` 는 이 저장소의 관용이다 (`silver.building_register_floors`,
`silver.complex_parcel_memberships` 도 쓴다). 관용을 따랐다는 것이 이 표에 맞는다는 근거는
아니었고, 아무도 칸당 행 수를 세어 보지 않았다.

## Decision

1. `silver.parcel_boundaries` 의 `partition_spec` 은 `["sigungu_code"]` 다. `pnu` 버킷을
   두지 않는다.

2. 나누기 항목은 **질의를 좁히는 것**만 넣는다. 이미 좁혀진 것을 다시 좁히는 항목은 칸 수를
   곱할 뿐이다. 나누기 항목을 더하거나 바꾸는 변경은 그 항목이 없을 때와 있을 때 읽어야 할
   칸이 어떻게 달라지는지를 근거로 적는다.

3. 나누기를 정할 때 **칸당 행 수를 계산해 남긴다.** 데이터셋 크기를 칸 수로 나눈 값이며,
   칸 하나가 파일 하나 아래로 내려가면 그 나누기는 과하다.

## Consequences

칸이 65,280개에서 255개로, 파일이 43,649개에서 255개로 줄고 파일 평균이 0.28 MB 에서 약
47 MB 가 된다. 47 MB 는 여전히 통상 목표의 아래쪽이지만 같은 자릿수이며, 더 굵게 하려면
시군구보다 넓게 묶어야 해서 질의가 좁히지 못한다.

**이미 적재된 561만 행은 버린다.** Iceberg 는 나누기 규칙을 진화시킬 수 있지만 기존 데이터는
옛 규칙을 그대로 지니므로, 표에 두 규칙이 섞이고 옛 부분은 여전히 43,649개 쪽 밀도로 남는다.
적재 33분 시점이라 다시 넣는 편이 싸다.

**같은 관용을 쓰는 다른 세 표는 손대지 않았다.** `silver.building_register_floors`(칸 16),
`silver.complex_parcel_memberships`(칸 65,280), `silver.building_register_units`(칸 32) 는
아직 실물이 없거나 규모가 달라, 칸당 행 수를 재기 전에는 결정 2·3 을 적용할 근거가 없다.
`silver.complex_parcel_memberships` 는 필지와 같은 규칙이므로 적재 전에 반드시 재야 한다.

**이 결정은 적재 속도를 목표로 하지 않는다.** 칸이 줄면 쓰기 중 동시에 여는 버퍼가 줄어
힙 여유가 생기지만, 그것은 부수 효과이고 판단 근거는 읽는 쪽의 파일 크기다.
