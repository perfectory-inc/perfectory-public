# ADR 0339: 공매 물건상세는 회차가 아니라 물건마다 한 번 받고, 그 미디어를 물건의 모든 회차가 쓴다

- Status: Accepted
- Date: 2026-10-29
- Amends: [ADR-0330](./0330-a-public-auction-round-is-detailed-until-its-media-landed-open-rounds-first.md)
  §1(완료 단위)·§2(순서·'바뀜')·§3(미디어 하루 상한)
- Builds on: [ADR-0296](./0296-public-auction-serves-full-info-and-shares-one-content-addressed-media-store.md) §5,
  [ADR-0298](./0298-content-addressed-media-is-a-write-once-store-not-a-per-object-bronze-ledger.md),
  [ADR-0312](./0312-gold-commits-record-their-changed-pnus-and-every-rebuild-is-partial-or-says-why.md) §2

## Context

ADR-0330 은 열린 **회차** 51,333 을 하나씩 물건상세(`getRlstDtlInf2`)로 받아 약 4일에 한 바퀴를 돈다고 했다. 그런데
사진·감정평가서는 회차가 아니라 **물건**(`cltrMngNo`)의 것이다. 2026-10-29 실측(Trino `r2.silver`, 읽기만):

| 무엇 | 결과 |
| --- | --- |
| 회차가 둘 이상인 물건의 사진 목록(해시·순서·제목) | 94 물건 중 **94 가 모든 회차에서 같다**, 다른 것 0 |
| 같은 비교, 감정평가서 | 13 중 **13 같다**, 0 다름 |
| 여러 run 에 걸쳐 받은 물건의 미디어 집합 | 13 물건 중 바뀐 것 0 |
| 열린 회차·물건(입찰 마감 전, 각 회차의 최신 판) | 50,363 회차 · **8,722 물건**(물건당 5.8 회차) |
| 회차가 둘 이상인 열린 물건 7,397 의 물건 사실(PNU·감정가·물건명·토지면적) | 7,397 모두 회차 사이에 같다 |
| 같은 물건들의 `mdfcnDt`(제공자 수정일시) | 6,512(88%) 가 모든 회차에서 같다, 885 는 다르다 |
| 하루 새 물건 / 새 회차 / 새 수정일시를 보인 기존 물건 (10-20~28) | ~200 / ~1,300 / ~150(최대 449) |

상세 응답 중 Silver 로 가는 것은 미디어뿐이다(`data_go_kr_onbid.py` `photo_rows_of`): 회차의 사실(상태·입찰가·마감)은
목록(`getRlstCltrList2`)에서 회차마다 이미 Silver `onbid_real_estate_item` 으로 간다. 그러니 상세 응답에 회차마다
다른 필드가 있더라도 아무도 읽지 않는다. 회차마다 상세를 받는 것은 같은 미디어 목록을 5.8 번 받는 일이다.

## Decision

1. **상세는 물건마다 한 번.** 수집기는 열린 회차를 물건으로 묶어, 물건마다 그 물건의 입찰 마감이 지나지 않은 회차
   중 마감이 가장 이른 회차(`pbctCdtnNo`)로 상세를 묻는다. 순서는 ADR-0330 §2 를 물건에 그대로 쓴다: 마감 전 회차가
   있는 물건 먼저, 아직 완료가 아닌 것이 바뀐 것보다 먼저, 마감 이른 순, 같으면 키 순. `item_detail.per_run_limit`
   (600)은 이제 물건 수다.
2. **완료는 물건 단위, 미디어가 다 들어간 뒤에만**(ADR-0330 §1 유지). `state.items` 가 물건 → (완료 때 그 물건 회차들이
   보인 목록 다이제스트 집합, 사진 수)를 쥔다. ADR-0330 의 회차 표시(`state.details`)는 다음 run 에 한 번 물건으로 접어
   넣고 더 쓰지 않는다 — 회차의 미디어가 곧 물건의 미디어임을 위에서 쟀다.
3. **다시 받는 때.** 물건의 어느 회차가 완료 때 그 물건이 보지 못한 `refresh_on_list_fields`(`mdfcnDt`) 다이제스트를
   보일 때만: 회차의 수정일시가 바뀌었거나(ADR-0330 의 규칙), 새 회차가 다른 회차들에 없던 수정일시를 들고 왔을
   때(새 회차의 미디어 신호가 바뀜). 이미 본 수정일시의 새 회차, 닫혀 목록에서 빠진 회차는 아무것도 묻지 않는다.
   목록 행에 따로 미디어 필드가 없으므로 수정일시가 그 신호다(ADR-0180 §1: 소비자가 읽는 열이 바뀐 행).
4. **물건의 미디어를 그 물건의 모든 회차에 붙인다, 복사하지 않고.** Silver `onbid_real_estate_item_photo` 는 한 번 받은
   대로 한 행씩 쌓고(append-only), 계약의 현재 행 키를 `(cltr_mng_no, sha256)` 으로 바꾼다 — `pbct_cdtn_no` 는 답한
   회차를 적는 출처일 뿐이다. 같은 run 의 두 줄(이 결정 전, 한 물건의 두 회차를 같은 run 에 받은 경우)은 뒤 줄이
   이긴다(`newest_first` 에 `source_line_number`). Gold(`onbid_public_auction_silver_to_gold.py`)는 미디어를
   `cltr_mng_no` 로 묶어(`photos_by_item`) 회차에 물건으로 조인하고, 부분 재빌드(ADR-0312 §2)는 미디어 행이 바뀐 물건의
   **모든 회차**를 건드린 것으로 센다. 서빙 문서 모양(회차마다 `photos`)은 바뀌지 않는다.
5. **ADR-0330 의 보장은 그대로.** run 당 상한(상세 600·다운로드 3,000)과 미디어 단계 시간 예산(600s), 반쯤 받힌
   물건 없음, 열린 것 먼저, 커버리지 지표(회차 단위: 회차는 그 물건이 완료면 완료)와 두 경보. 미디어 하루 상한
   `media.daily_download_limit` 은 20,000 → **45,000**: 물건 단위면 run 당 최대 600 × 4.7 ≈ 2,820 다운로드라, 열린
   물건 백필 ~41,000 이 하루 상한에 이틀로 쪼개지지 않게 한다(총량 ~88GB 는 ADR-0330 이 이미 잡은 것과 같다).
6. **API 하루 상한(1/5)은 그대로 둔다.** 2026-10-29 확인: 이 서버에서 `DATA_GO_KR_SERVICE_KEY` 를 받는 단위는
   `foundation-onbid-collect.service` 하나다(`config/runtime-secrets.contract.json`). 트리의 다른 data.go.kr 수집기는 다른
   API 를 부르고, data.go.kr 한도는 API 마다 따로라 공매 API 의 "다른 사용자"가 될 수 없다. 그러니 그 사용자는 이
   플랫폼 밖, 같은 data.go.kr 계정의 다른 앱이다(AWS 의 운영 공짱은 이 결정의 범위 밖이라 보지 않았다). 그 몫을 잴
   수 없으니 1/5 를 지킨다. 그래도 모자라지 않다: 가장 무거운 `item_detail` 이 백필 ~8,700 번 한 번, 이후 하루 ~350 이다.
   전용 키(별도 data.go.kr 계정)는 지금은 필요 없다 — 어느 API 든 하루 사용이 상한의 절반(10,000)을 넘게 될 때 사장
   단계로 한다(Consequences).

업계 방식과의 대응: 같은 내용을 여러 주소가 가리키면 대표 하나만 받고 나머지는 대표에 묶는 것은 웹 크롤러의 정규화
(canonicalization — Google 검색 크롤러가 중복 URL 묶음에서 대표 URL 만 크롤하는 방식)와 같다. 속성은 그것이 바뀌는
결(grain)에 둔다는 차원 모델링의 원칙(Kimball: 물건 차원 속성을 회차 사실 행마다 복제하지 않는다)대로, 미디어는 물건
결에 한 번 두고 회차는 조인으로 가리킨다. '바뀌었을 때만 다시 받기'는 HTTP 의 조건부 요청(RFC 9110 `Last-Modified`)을
제공자의 수정일시로 하는 것이다.

## Consequences

- **시간(계산).** 열린 물건 전체의 상세·미디어 완료까지:

  | | 전(ADR-0330, 회차) | 후(이 ADR, 물건) |
  | --- | --- | --- |
  | 받을 단위 | 열린 회차 50,363 | 열린 물건 8,722 |
  | 상세 백필 | 하루 14,400 − 새 회차 ~1,300 − 바뀐 회차 ~525 ≈ 순 12,600 → **약 4.0일** | 600/run → 15 run ≈ **약 15시간** |
  | 백필 뒤 하루 상세 | ~1,800(새 회차 + 바뀐 회차) | ~350(새 물건 ~200 + 새 수정일시 물건 ~150) |
  | 미디어 하루 상한 | 20,000 | 45,000(백필 ~41,000 이 하루 안) |

  상세 호출은 더 이상 병목이 아니다. 남는 상한은 KAMCO 다운로드 속도다: run 당 600 물건의 미디어는 ~5.9GB 라 10분
  예산 안에 다 받으려면 ~9.8MB/s 가 든다. 그보다 느리면 시간 예산이 새 물건을 멈추고, 받지 못한 물건은 다음 run 이
  다시 묻는다(상세 1콜, ADR-0330 §1 그대로). 그 경우 완료 시간 ≈ 88GB ÷ (KAMCO 속도 × 600s × 24). 첫 배포 뒤
  `onbid-media-summary-json` 의 `time_budget_reached` 와 커버리지 지표로 잰다.
  실측(ADR-0330 첫 run, 10-29 06:07, Silver): 600 회차가 물건 **80** 이었고 새 파일 279(≤0.49GB)가 시간 예산에 걸리지
  않고 들어갔다(run 전체 18분). 그러니 ADR-0330 의 실제 속도는 하루 ~1,900 물건, 열린 물건 전부 **약 4.5일**이고, KAMCO
  속도의 하한은 ~0.8MB/s 다. 미디어 바이트(~88GB)는 두 설계에서 같으므로, KAMCO 가 그 하한뿐이면 둘 다 ~7일이고 이 결정의
  이득은 상세 호출이다. 9.8MB/s 이상이면 ~15시간. 바이트의 93% 가 감정평가서라, 모든 물건의 사진을 감정평가서보다 먼저 받는
  것(사진 커버리지 ~하루)은 후속 결정으로 남긴다.
- **화면.** 물건이 완료되면 그 물건의 모든 회차가 같은 Gold 에서 사진을 갖는다(회차마다 기다리지 않는다). 서빙 주기는
  ADR-0330 §5 그대로.
- **비용.** data.go.kr 무료. R2 총량은 ADR-0330 의 열린 물건 ~88GB(월 ~₩1,600)와 같다 — 같은 파일을 더 빨리 받을 뿐.
  Class A 는 백필 하루 ~41,000 ≈ $0.2 한 번.
- **상태 파일.** `state.items` 는 물건 ~8,700 개, 회차 표시보다 작다. 옛 `details` 는 접어 넣은 뒤 쓰지 않는다.
- **Silver 현재 행 키 변경.** `silver.onbid_real_estate_item_photo` 의 계약 변경이라 배포의 lakehouse 마이그레이션이 이
  표를 바뀐 표로 센다(`release_changes.py`). 열 모양은 같다(운영 모양 원장 변화 없음).
- **사장 단계(지금은 필요 없음, 조건부).** 어느 공매 API 든 하루 사용이 10,000 을 넘게 되면, 공유를 끊는 길은 전용
  data.go.kr 계정이다. data.go.kr 인증키는 계정마다 하나이고 한도는 그 키의 API 마다 따로라서, "API 마다 전용 키"는
  계정을 따로 두는 것이다:
  1. 법인 명의로 data.go.kr 계정을 새로 만든다.
  2. 그 계정으로 온비드 API 5종(15157207 물건목록, 15157216 공고목록, 15157254 입찰결과, 15157247 물건상세, 15157222 공고
     입찰결과)을 활용신청한다.
  3. 운영계정 전환을 신청한다(활용사례 등록, 한도 100,000/일).
  4. 새 키를 `runtime_secrets.py set data-go-kr` 로 놓는다(런북 "처음 켜기" 1).
  그 뒤 이 플랫폼이 그 키의 유일한 사용자이므로 `daily_call_limit_per_api` 를 실제 한도 가까이 올리는 PR 을 낼 수 있다.
- **확인하지 못한 것.** 상세 응답 원문(Bronze)은 이 노트북·읽기 권한으로 열 수 없어, 회차마다 다른 필드가 실제로 있는지는
  응답이 아니라 '상세에서 Silver 로 가는 것은 미디어뿐'이라는 코드로 판단했다. 미디어가 같다는 실측은 미디어가 저장된
  물건 100(사진)·14(감정평가서)에 한한다. 공매 API 의 다른 사용자가 누구인지는 게이트웨이 `X-RateLimit-Remaining` 을
  기록하지 않아 재지 못했다. KAMCO 다운로드 속도.
- 시험: `data_go_kr_onbid_collect/tests.rs`(한 물건 한 상세·대표 회차·새 회차/바뀐 수정일시/닫힌 회차·회차 표시 접기·
  커버리지), `test_onbid_public_auction_gold.py`(물건 미디어가 모든 회차에·현재 행이 물건×해시 하나·미디어 변경이 물건의
  모든 회차 PNU 에 닿음).

개정 각주(2026-10-29): **사진 먼저.** Consequences 가 후속으로 남긴 '모든 물건의 사진을 감정평가서보다 먼저'를 정한다. 단위와
완료 규칙(§2: 물건은 미디어가 다 들어간 뒤에만 완료)은 그대로이고, 순서만 바뀐다.
(a) 미디어 단계는 run 의 상세 줄 전체의 **사진을 먼저**, 그다음 감정평가서를 받는다. 두 번 모두 같은 줄 순서(열린 것 먼저·마감
이른 순)이고, 한 줄의 한 종류는 상한·예산 안에 다 들어갈 때만 시작하며, 하나가 들어가지 못하면 그 뒤로는 아무것도 시작하지
않는다(`onbid_media.rs` `mirror_detail_lines`). (b) 사진은 다 들어갔고 감정평가서만 남은 물건은 `state.photos_landed` 에
그때의 목록 다이제스트와 함께 남고, §1 의 순서에서 **아직 사진이 없는 물건 뒤로** 간다(열린 것 먼저 다음의 둘째 키). 다이제스트가
바뀌면(새 사진일 수 있다) 다시 앞으로 온다. (b) 없이 (a) 만이면, 미완료 물건이 다음 run 에도 순서 맨 앞을 차지해 같은 600 물건이
감정평가서를 다 받을 때까지 다른 물건의 사진이 시작되지 않는다 — 사진 커버리지가 전과 같다.
Silver·Gold 는 바꿀 것이 없다(코드로 확인): 수집기는 완료 여부와 상관없이 저장된 파일마다 상세 줄에 `sha256` 을 적고, Silver
`photo_rows_of` 는 `sha256` 이 있는 항목을 모두 행으로 만들며, Gold `photos_by_item` 은 완료를 보지 않는다. 그러니 감정평가서를
기다리는 물건의 사진도 그 run 의 Silver 적재로 화면 쪽에 간다.

시간(계산). 열린 물건 8,722, 미디어 ~88GB 중 사진 7% ≈ 6.2GB·감정평가서 ≈ 81.8GB, run 은 매시 24회·미디어 예산 600s·상세
600 물건/run·다운로드 3,000/run. run 하나는 KAMCO 속도 × 600s 를 받는다. 600 물건의 사진은 ~1,980 장·~420MB 다.

| KAMCO 속도 | 전: 사진 전부 | 후: 사진 전부 | 감정평가서까지 전부(전·후 같음) |
| --- | --- | --- | --- |
| 0.8 MB/s(실측 하한, run 당 480MB) | ~183 run ≈ **7.6일**(물건이 통째로 들어가야 사진도 들어감) | 상세 15 run ≈ **15시간**(사진 420MB/run < 480MB) | ≈ 7.6일 |
