# ADR 0454: 필지의 경매 문서는 그 필지의 매각결과를 함께 싣는다

- Status: Accepted
- Date: 2026-11-09
- Builds on: ADR-0280(법원경매 수집), ADR-0353(경매 종류), ADR-0382(정본 해석기·코드 변경 따라가기), ADR-0336(스키마 레지스트리
  개정), ADR-0312 §2(바뀐 키만), ADR-0428(화면에 출처 줄 없음)

## Context

`silver.court_auction_sale_result`(법원경매정보 매각결과 검색, 매각가 포함)는 수집·적재가 돌지만 읽는 소비자가 없어, 정의에서 만든
표(`production-readiness` §10)의 "없음" 줄이었다. 산업 부동산 사용자에게 매각가는 그 필지와 이웃 필지가 실제로 얼마에 팔렸는지 —
감정가 대비 몇 % 에 낙찰됐는지 — 를 말한다.

**측정(운영 Trino 읽기 전용, 2026-11-09).** 10,120 행, 물건 키(법원·사건·물건번호·목록번호)가 행마다 다르다. 판은 하나(매각기일
2026-10-13..19). PNU 있는 행 9,817(97.0%), PNU 6,774 개, 한 PNU 최대 362(아파트 단지). 매각가 있는 행 2,062. 물건 표와 같은 키를
가진 결과 7,489.

같은 물건 키, 같은 출처, 같은 PNU 자리 정하기다. 따로 종류를 두면 화면이 같은 경매 물건을 두 구획에 나눠 보이고, 굽기·서빙 레인이
하나 더 든다.

### 실사례

- **진행과 결과를 한 물건 화면에.** 국내 경매 정보 서비스(법원경매정보 사이트 자신, 민간 경매 정보 서비스들)는 한 소재지의 진행 물건과
  지난 매각결과를 같은 화면의 두 목록으로 보인다. Zillow 의 집 화면도 "현재 매물" 과 "판매 이력" 을 한 문서에 둔다.
- **필드를 더하는 개정은 같은 major.** Confluent Schema Registry 의 `FULL_TRANSITIVE` 에서 선택 필드 추가는 앞뒤로 호환된다.

## Decision

1. **문서에 두 칸.** `parcel-court-auction` 문서의 `court_auction` 이 `sale_results`(그 필지에 놓인 매각결과의 현재 행, 매각기일이 늦은
   순, 최대 50)와 `sale_result_total`(전부의 수)을 갖는다. 값은 Silver 그대로(코드는 코드, 빈 값 null, 매각가 없는 결과도 null 로
   싣는다). 결과 몫은 문서 한도 256 KiB 가운데 64 KiB, 진행 물건이 나머지를 쓴다. 매각결과만 있고 진행 물건이 없는 필지도 문서가
   있다(`rounds` 빈 배열).
2. **자리 정하기는 물건과 하나.** 결과의 현재 행(계약의 `current_rows`)을 `onbid.placed` 로 놓는다 — 은퇴 필지는 계보를 따라가고, 갈 길
   없는 것은 `lineage_missing` 으로 세고 서빙 Gold 에 쓰지 않는다(ADR-0292).
3. **법정동 코드 변경을 따라간다(사장 규칙 10-31, ADR-0329 §3).** 결과의 PNU 는 짓기마다 정본 해석기의 쌍으로 현재 코드에
   옮긴다(`place_identity_resolver.carried_to_current`). 코드 변경 표가 바뀌면 바뀐 코드(`views.changed_codes`) 아래 물건과 결과가 닿는
   PNU 만 다시 짓는다. 적재 때 한 번 정하고 멈추지 않는다.
4. **부분 처리.** 결과 표는 물건 키로 비교한다(`changed_rows`, 양방향). 바뀐 결과의 키가 지금 놓인 PNU 와 지금 Gold 가 그 키를 싣고 있는
   PNU 둘 다 다시 짓는다. 부분 빌드의 입력 자르기도 그 PNU 에 놓인 물건·결과의 키로 두 표를 자른다. 결과 표는 통째 입력이 아니다.
5. **레지스트리 개정 1.3**(`parcel_court_auction_by_pnu/1/3.schema.json`, 개정 1.2 의 사진 칸 위, ADR-0384), `schema_version` 은 `.v1` 그대로. 웹 pact 가 결과 칸을
   읽는다(`pnpm gen:schemas`).
6. **화면.** 필지 패널 경매 칸에 진행 물건 다음 "매각결과 N건": 결과마다 사건번호·물건 이름, 소재지, 감정가·최저매각가·매각가, 매각기일,
   유찰 횟수. 라벨은 법원경매정보의 칸 이름, 0·빈칸은 보이지 않는다. 출처 줄은 화면에 없다(ADR-0428, 문서에는 남는다). 경매
   구분은 진행 물건이나 매각결과가 하나라도 있으면 보인다.

## Consequences

- §10 표에서 법원경매 매각결과 줄이 "없음 → 길 있음·꺼짐" 이 된다(정의에서 계산). 경매 Gold·굽기 작업이 첫 측정 빌드 뒤 켜지면(ADR-0435
  자동 승격) "화면" 이다.
- **비용(계산).** 빌드마다 1만 행 Silver 를 한 번 더 읽고 놓는다 — 초 단위. 문서는 결과 있는 필지 6,774 개가 늘고(경매 Gold 약 4만 →
  약 4.6만 행), 결과 하나가 JSON 약 500 바이트라 R2 는 수 MB, 월 1원 미만.
- 결과 판이 지금 하나다(10-13..19). 수집기가 결과 검색을 다시 돌면 새 판이 쌓이고, 바뀐 결과만 다시 짓는다.
- 상태 코드(`item_status_code`)는 코드로 싣고 화면은 읽지 않는다 — 원천 코드표가 수집되면 그 원본 말로 붙인다.
