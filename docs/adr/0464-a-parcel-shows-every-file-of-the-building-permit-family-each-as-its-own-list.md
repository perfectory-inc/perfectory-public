# ADR 0464: 필지 화면의 건축인허가는 같은 묶음의 다른 파일 여덟을 각자의 목록으로 함께 싣는다

- Status: Accepted
- Date: 2026-11-09
- Builds on: ADR-0402(건축HUB 나머지 파일 한 레인씩), ADR-0404(정기점검이력은 관리건축물대장PK 로 표제부에 읽을 때 잇는다),
  ADR-0451(건축인허가 종류), ADR-0452(같은 허가 키의 주차장), ADR-0329 §3(법정동 코드 변경을 따라간다), ADR-0312 §2(바뀐 키만),
  ADR-0336(스키마 레지스트리 개정)

## Context

**사고(2026-11-09, 화면 표 `production-readiness` §10).** ADR-0457(#1201)이 적재 작업을 켠 Silver 20 개가 "없음"이다 — Gold 도
by-PNU 길도 없어 행이 쌓여도 화면에 영원히 닿지 않는다. 그중 여덟이 건축HUB 건축인허가 묶음이다: 동별개요, 층별개요, 대지위치,
대수선, 가설건축물, 부설주차장, 공작물관리대장, 그리고 건축물 정기점검이력. ADR-0402·0404 는 이 표들을 "읽는 소비자(필지 by-PNU
패널)는 다음 PR" 로 미뤘다.

**측정(ADR-0402·0404, 2026-10 판).**

| 파일 | 행 | 행의 키 | PNU |
|---|---:|---|---|
| 동별개요 | 8,546,999 | 관리동별개요PK(고유) | 행마다 지번(97.9% 표준 PNU) |
| 층별개요 | 15,041,597 | 관리층별개요PK(고유) | 행마다 지번(97.2%) |
| 대지위치 | 13,639,544 | 관리대지위치관리번호(고유) | 행마다 지번(92.5%) — 허가 하나가 여러 필지에 걸친다 |
| 대수선 | 113,817 | 행 글자 SHA-256 | 행마다 지번(99.4%) |
| 가설건축물 | 2,308,148 | 행 글자 SHA-256 | 행마다 지번(96.9%) |
| 부설주차장 | 58,823 | 행 글자 SHA-256 | 행마다 지번(97.8%) |
| 공작물관리대장 | 559,438 | 행 글자 SHA-256 | 행마다 지번(98.3%) |
| 정기점검이력 | 64,328 | 행 글자 SHA-256 | 없음 — 표제부에 이어 94.7% |

다섯은 관리허가대장PK 로 기본개요의 허가에 붙지만, 대지위치·부설주차장은 **허가의 대표 지번이 아닌 다른 필지**를 말하고, 가설건축물·
공작물은 허가 없이 신고된 행도 있다. 허가 레코드 안에 넣으면(ADR-0452 의 주차장 방식) 그 필지에 허가가 없는 행이 사라진다.

### 실사례

- **한 대상의 여러 원천 목록은 읽기 모델의 형제 칸으로.** CQRS 읽기 모델은 원천마다의 행 목록을 문서의 칸 하나씩으로 편다. CoStar 의
  필지 화면도 허가(permits)·건물(buildings)·부지(site) 정보를 같은 필지 아래 각자의 표로 둔다. 키가 다른 원천을 억지로 한 레코드에
  합치지 않는다.
- **선택 필드 추가는 같은 major.** Confluent Schema Registry `FULL_TRANSITIVE` 에서 선택 필드 추가는 앞뒤로 호환된다(ADR-0452 와 같다).
- **조인 키는 읽을 때.** dbt·Iceberg 읽기 모델은 다른 표를 거친 연결(정기점검 → 표제부 → 필지)을 적재 때 박지 않고 빌드마다 다시
  계산한다. 표제부의 필지가 바뀌면 다음 빌드가 따라간다(ADR-0404 §2, 사장 규칙 2026-10-31).

## Decision

1. **파일 하나 = 목록 하나.** `parcel-building-permits` 문서의 `building_permits` 가 `records`(허가, 그대로) 옆에 여덟 칸을 갖는다:
   `building_outlines`·`floor_overviews`·`site_locations`·`major_repairs`·`temporary_buildings`·`annex_parkings`·`structures`·
   `regular_inspections`. 각 칸은 `{total, records}` — 그 필지의 행(행의 키마다 하나, 같은 행 되풀이는 하나), 원천 글자 그대로(빈 값
   null), 최대 50 건, 전체 건수. 행이 없으면 null. 어떤 칸을 싣는지는 생산자 `building_permit_silver_to_gold.DETAILS` 한 곳이 정한다
   (스키마·웹 pact 는 그것을 따른다). 키, 건물명·대지위치·특수지명(개인 이름, ADR-0402), 정기점검의 동명은 싣지 않는다.
2. **필지는 행 자신의 PNU.** 일곱 파일은 그 행의 PNU 에, 정기점검은 ADR-0404 §2 의 규칙으로 이은 표제부 하나의 PNU 에 싣는다
   (`inspection_pnus`, 매 실행 연결 수 `regular_inspection_linked` / `regular_inspection_rows`). 모든 PNU 는 기본개요와 같은
   `renumbered` 로 서빙 필지판의 코드로 읽는다(ADR-0329 §3) — 적재 때 고정하지 않는다. 허가가 없고 다른 파일의 행만 있는 필지도
   문서를 갖고 `building_permit_total` 은 0 이다.
3. **부분 처리.** 파일마다 고정한 Silver 와 지금 Silver 의 행이 다른 PNU(`changed_rows`, 양방향)만 다시 계산한다. 표제부가 바뀌면
   이어진 정기점검(고정한 표제부로 이은 것과 지금 표제부로 이은 것)이 다른 PNU 만 다시 계산한다. 입력 자르기는 PNU 로 한다.
   법정동 코드 변경 표가 바뀌면 전처럼 통째로 짓는다(ADR-0451).
4. **레지스트리 개정 1.3**(`parcel_building_permits_by_pnu/1/3.schema.json`), `schema_version` 은 `.v1` 그대로. 웹 pact 가 여덟 칸을
   읽는다(`pnpm gen:schemas`).
5. **화면.** 건축인허가 구획 안에 파일마다 묶음 하나: 제목은 원천의 파일 이름("동별개요 N건" 등), 레코드마다 이름 칸(주용도명·구조명
   등)은 굵게, 나머지는 원천의 칸 이름으로("용적률산정연면적 …㎡", "가설건축물존치만료일 …"). 0·빈칸은 보이지 않는다. 구획은 허가나
   다른 파일의 행이 하나라도 있으면 보인다.

## Consequences

- §10 표에서 여덟 줄이 "없음 → 길 있음·꺼짐" 이 된다(정의에서 계산: 화면 29/68 그대로, 길 있음·꺼짐 13 → 21, 없음 26 → 18).
  레인 작업이 켜지면(첫 전체 빌드를 잰 뒤, ADR-0386·0435) 기본개요와 함께 "화면" 이다. 이 PR 은 작업을 켜지 않는다: 전국 첫 빌드는
  ADR-0457 §1 의 계산 첫 실행 길로 켜지지 않는 큰 일이다.
- **비용(계산).** 전체 빌드 입력이 기본개요 653만 행에서 여덟 파일 4,033만 행과 표제부 현재 행 만큼 늘어난다. 기본개요 Silver 첫 판
  (653만 행)이 6 분이었으므로 읽기·창 함수·PNU 별 묶음에 수십 분이 더해질 것으로 본다 — 첫 전체 빌드의 측정이 단위의 150 분 안인지
  판정한다. 부분 빌드는 바뀐 PNU 만이라 판마다 수만 PNU 다(각 파일 9→10월 차이 수천~7만 행). Gold 문서는 칸마다 최대 50 건이라
  필지당 수 KB 를 넘지 않는다. R2·계산은 ai-server 라 추가 지출 0.
- 여덟 Silver 는 아직 카탈로그에 표가 없다(2026-11-09 21:00 UTC, 적재 대기). 레인이 그 표들을 필수 입력으로 읽으므로 표가 다 생길
  때까지 이 레인의 빌드는 시작하지 못한다 — 레인이 아직 꺼져 있어 지금 잃는 것은 없다.
- 정기점검 연결은 실측 규칙이다(ADR-0404). 연결 수를 매 실행 run 요약에 남기므로 제공자가 키 꼴을 바꾸면 그 비율이 떨어지는 것으로
  보인다.
