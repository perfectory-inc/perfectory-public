# ADR 0191: 릴리스는 적재 때 한 번 변경 기록이 되고, 모든 층은 변경만 읽는다

- Status: Proposed — 단계 ②(허브 덮어쓰기 레인 셋이 `changelog.py` 를 부른다)와 함께 병합될 때 Accepted
- Date: 2026-10-12
- Builds on: [ADR-0180](./0180-panel-gold-recomputes-only-the-pnus-whose-inputs-changed.md) (Gold 는 바뀐 PNU 만),
  ADR-0189 (PR #425, 병합 대기) (append 입력은 추가분이 변경 집합),
  [ADR-0183](./0183-a-release-loaded-in-batches-is-staged-on-a-branch-and-published-at-once.md) (브랜치 적재·공개 한 번),
  [ADR-0169](./0169-silver-lanes-pick-their-source-release-from-the-ledger-and-refresh-themselves.md) (Silver 레인),
  [ADR-0099](./0099-daily-serving-updates-bake-only-changed-parcels.md)·[ADR-0147](./0147-by-pnu-documents-are-served-from-section-packs.md) (굽기의 변경 집합)

## Context

원천은 대부분 통째 월간 릴리스다(hub.go.kr 등록부, VWorld 필지·용도지역·속성 CSV). 원천 쪽에 변경 로그가 없으니
"무엇이 바뀌었나" 는 어딘가에서 옛 판과 새 판을 견주어 만들어야 한다. 지금 그 비교가 일어나는 곳:

| 층 | 지금 하는 일 | 전량인 부분 |
|---|---|---|
| Silver 레인 | 판을 통째로 덮어쓰거나(표제부·호·호 면적·토지 7종) 판을 쌓는다(가격·전유부 다리) | 적재 자체(피할 수 없다: 원천이 통째다) |
| Gold (ADR-0180) | 입력마다 고정 판과 새 판을 **소비자가** 두 번 읽어 빌드 열 투영의 `exceptAll` | 두 판 전체 읽기 + 셔플. 1.14억 행 호 면적 릴리스에서 26분 중 20분 |
| Gold (ADR-0189) | append 사슬이면 추가분만 읽기 | 덮어쓰기 입력에는 해당 없음 |
| 굽기 | 두 Gold 판의 `pnu, row_digest` 바깥 조인 | 좁은 두 열이지만 표 전체 |

같은 Silver 판 쌍의 차이를 소비자마다(필지 패널, 건물 패널, 다음 소비자) 다시 계산하고, 비교할 옛 판을 남기려고
입력마다 태그로 한 판씩을 R2 에 붙잡는다(ADR-0180 §6). 덮어쓰기는 계보 열(`source_snapshot_id`,
`ingested_at_utc`, 행 id)을 모든 행에서 바꾸므로 Iceberg 의 증분·changelog 읽기로는 "전부 바뀜" 이다. Silver 스냅숏은
7일 뒤 만료되므로(`lakehouse-maintenance.contract.json`) 덮어쓴 판의 역사는 남지 않는다 — "덮어쓰지 않고 쌓는다"
원칙과도 어긋난다.

## Decision

1. **차이는 적재 때 한 번 계산해 변경 기록 표에 쌓는다.** Silver 표 `silver.<t>` 마다 쌓기만 하는
   `silver.<t>__changes` 를 둔다. 행 모양은 Silver 행 그대로에 세 열을 더한 것이다.
   - `_weight` (+1 / −1): 들어온 행 / 나간 행. 변경 기록은 **가중 다중집합(Z-set)** 이다. 수정은 −1(옛 행)과
     +1(새 행)의 쌍이다. 여러 판에 걸친 변경은 `(키, 지문)` 으로 묶어 가중치를 더하고 0 을 버리면 합성된다 —
     건너뛴 실행이 따라잡을 때 따로 쓸 논리가 없다.
   - `_from_snapshot_id`, `_to_snapshot_id`: 이 변경이 옮긴 Silver `main` 의 두 스냅숏.
   - 비교 단위는 `(change_key, row_fingerprint)` 의 다중집합 차이다. `change_key` 는 표마다 계약에 적고(건물
     `mgm_bldrgst_pk` 계열, 토지 `pnu`), `row_fingerprint` 는 **계약의 계보 열을 뺀 모든 열**과 그 NULL 표시의
     xxhash64 다. 같은 키 안에서만 비교하므로 바뀐 행이 같은 지문을 가질 확률은 행마다 2^-64 다.
     계보 열만 바뀐 행은 바뀐 것이 아니다. 내용 열 목록은 따로 적지 않고
     "스키마 − 계보 열" 로 계산한다(거울 목록 금지).
   - ADR-0180 이 Silver 해시를 기각한 이유("해시가 덮는 열 ≠ 빌드가 읽는 열이면 변경을 놓친다")는 지문이 **모든**
     내용 열을 덮으므로 생기지 않는다. 빌드가 읽지 않는 열의 변경은 Gold 에서 다시 계산되지만 `row_digest` 가 같아
     합쳐지지 않는다(거짓 양성은 비용, 놓침은 없다).
2. **지문은 Silver 열로 저장한다.** 덮어쓰는 Silver 표에 `row_fingerprint` 열을 더한다(계약 스키마 진화). 적재가
   새 행에 계산해 쓰므로, 차이의 개수 세기는 옛 판에서 `change_key, row_fingerprint` 두 열만 읽는다. 나간 행의 옛
   모습은 차이로 고른 키를 옛 판에 semi-join 해 가져오므로, 옛 판을 **모든 열로 한 번 더 훑는다**(필터는 조인 뒤라
   파일을 건너뛰지 못한다). ②의 "적재 시간 +15%" 는 이 훑기를 포함해 잰다.
3. **순서: 브랜치 → 변경 기록 → 공개.** 덮어쓰기 레인도 ADR-0183 브랜치에 적재한다(지금은 표제부·호·호 면적이
   `main` 에 한 번 쓴다). 브랜치 머리와 `main` 머리를 비교해 변경 기록을 `_from=main 머리, _to=브랜치 머리` 로
   쌓은 뒤 브랜치를 빨리감기로 공개한다. 빨리감기는 스냅숏 id 를 바꾸지 않으므로 `_to` 는 공개 뒤의 `main` 머리다.
   공개가 실패하면 변경 기록 행은 `main` 계보에 없는 스냅숏을 가리키는 고아이고, 아무도 읽지 않는다. 같은 판의
   재시도는 같은 `(from, to)` 를 다시 쓰지 않는다(적재 등록부 ADR-0069 의 identity 로 한 번만).
4. **소비 위치 = 이미 있는 판 기록.** 새 워터마크 저장소를 만들지 않는다. 소비자는 출력 커밋의 스냅숏 요약에 입력별
   Silver 스냅숏(`foundation.source-iceberg-snapshots`, ADR-0139)을 이미 남긴다. 출력과 같은 커밋이라 원자적이고,
   실패한 실행은 같은 판에서 다시 시작하며, 건너뛴 실행은 다음 실행의 범위가 넓어질 뿐이다(Kafka 소비자가 처리 결과와
   같은 트랜잭션에 offset 을 커밋하는 것과 같은 꼴).
   - 소비자는 고정 판 P 에서 새 판 N 까지 `main` 부모 사슬을 걷고, 각 걸음 `(from, to)` 에 변경 기록이 있으면 그
     행을 읽는다. 압축(`replace`)은 내용을 바꾸지 않으므로 빈 걸음이다. 한 걸음이라도 기록이 없으면 그 입력은
     ADR-0189(append 사슬) → ADR-0180(두 판 차이) 순으로 내려간다. 세 길의 결과는 같은 변경 집합이고, 시험이 이를
     단언한다.
   - 변경 기록으로 읽는 입력은 옛 판의 Silver 데이터가 필요 없다. 그 입력의 `foundation-gold-input-*` 태그
     (ADR-0180 §6)는 더 붙잡지 않는다.
   - 굽기는 지금처럼 Gold 의 `row_digest` 변경 집합을 읽는다(Gold 합치기가 이미 변경만 쓴다). Gold 합치기가 자기
     변경 PNU 를 `gold.<t>__changes` 에 함께 쌓는 일은 측정(아래) 뒤 판단한다.
5. **전량으로 남는 것(이유를 실행 요약에).**
   - 첫 적재·백필·계약의 `change_key` 변경·Silver 스키마 변경(지문 정의가 바뀐다): 변경 기록 대신 "전량" 표시
     한 행을 남기고, 소비자는 그 걸음에서 전량 빌드로 간다.
   - 빌드 코드 변경: Gold 생산자가 실행 요약에 자기 모듈 소스의 해시(`foundation.build-source-sha256`)를 남기고,
     머리 커밋의 값과 다르면 전량이다. 지금은 패리티 표본이 우연히 잡을 때만 전량이 된다(ADR-0180 Consequences).
   - 앵커 하나가 표 전체에 닿는 입력(`WHOLE_TABLE_INPUTS`, 예: 용도지역 코드표)과 `max_changed_key_fraction` 초과.
6. **정합성 관문.**
   - 적재 때: 변경 기록이 닫혀야 한다 — `count(옛 판) + Σ_weight = count(새 판)` 이고, 지문의 순서 무관 합
     (정확한 십진 합)도 같은 식을 만족해야 한다. 어긋나면 공개하지 않는다. 두 판을 다시 읽지 않는 산술 검사다.
   - Gold: 실행마다 패리티 표본(ADR-0180 §5) 그대로. 더해서 주기(계약 `full_reconciliation_days`, 첫 값 7)마다
     전량 빌드를 증분 결과 옆에 만들어 `row_digest` 다중집합을 비교하고, 다르면 전량 결과를 쓰고 경보한다.
   - 이 관문이 "아무 일도 안 일어남" 을 성공으로 읽지 않도록, 시험은 변경 기록에서 행 하나를 빼면 거부됨을 보인다.
7. **구현 위치.** 차이·합성·사슬 걷기·닫힘 검사는 `infra/lakehouse/spark/jobs/changelog.py` 하나다. Gold 의
   두 판 차이(`gold_incremental._fingerprinted`)는 ③에서 이 지문으로 옮겨 지문 계산이 한 곳에만 남는다.
8. **이주 순서와 목표(레인마다 따로 병합, 운영 첫 실행은 감독).**

   | 단계 | 범위 | 측정 (실행 로그 한 줄 `changelog-phase <단계> seconds= rows_read=`) | 목표 |
   |---|---|---|---|
   | ① | 순수 부품: Z-set 차이·합성·사슬 걷기·닫힘 검사 (pyspark 없는 unittest + Iceberg 런타임 레인) | — | 증분 = 전량 시험 |
   | ② | 허브 덮어쓰기 레인 셋(표제부·호·호 면적): 브랜치 적재 + `row_fingerprint` + 변경 기록 | 적재 추가 초 | 적재 시간 +15% 이내 |
   | ③ | 건물 Gold 가 변경 기록을 읽음 (ADR-0189 경로와 공존) | `affected` 단계 초·읽은 행 | 읽은 행 ≈ 변경 행, `affected` 2분 이내 (지금 호 면적 20분) |
   | ④ | 토지 레인 7종 + 필지 Gold | 같은 두 값 | 같은 목표 |
   | ⑤ | 주기 전량 대조 작업, 빌드 소스 해시 | 불일치 행 수 | 0 |
   | ⑥ | (측정 뒤) 굽기·Gold 변경 기록 | 굽기 delta 초 | — |

   기준값은 지금 운영 로그(ADR-0189 의 단계 줄)에서 다음 릴리스 전에 잡고, 각 단계 PR 은 같은 줄로 전후를 잰다.

## 검토한 실사례

| 사례 | 가져온 것 | 가져오지 않은 것 |
|---|---|---|
| Iceberg `create_changelog_view` / `IncrementalChangelogScan` | 출력 모양(변경 종류·커밋 스냅숏), `net_changes` 의 합성, carry-over 행 제거 | Silver 표에 직접 쓰기: 덮어쓰기와 계보 열 때문에 전부 바뀜이고, 7일 만료로 범위가 사라진다 |
| Delta Change Data Feed | 변경을 데이터와 따로, 커밋 단위로 쌓고 보존을 표 스냅숏과 분리 | Delta 로 옮기기(엔진 교체) |
| Materialize / Feldera (DBSP) | 변경 = 가중 다중집합(Z-set), 합성 = 가중치 합 | 상주 IVM 엔진 도입: 월간 갱신에 상태 저장 시스템 하나가 더 늘고 Spark·Rust 스택 밖이다 |
| dbt incremental | `is_incremental` / `--full-refresh` 두 길과 `unique_key` | `max(updated_at)` 워터마크: 원천 행에 믿을 시각이 없고 늦은 행을 놓친다 |
| Debezium CDC | 앞·뒤 모습, 소비 위치를 결과와 함께 커밋 | 로그 꼬리 읽기: 원천이 파일이라 꼬리가 없다 |

## 검토한 대안

- **Silver 를 키 기준 `MERGE` 로 바꿔 스냅숏 자체를 변경으로 만들기**: Iceberg 변경 읽기를 그대로 쓸 수 있지만,
  copy-on-write 는 흩어진 키에서 파일 대부분을 다시 쓰고, 변경 읽기가 다시 쓴 파일을 통째로 내보내 carry-over 제거를
  다시 해야 하며, 7일 만료로 역사가 남지 않는다. 행마다 계보 열이 갈려 건물 생산자의 단일 배치 가정(`assert_single_snapshot`)도 깨진다.
- **소비자별 차이 유지(현 상태)**: 같은 차이를 소비자 수만큼 계산하고 옛 판을 태그로 붙잡는다.
- **별도 워터마크 표**: 출력 커밋과 원자적이지 않다. 이미 있는 판 기록이 같은 일을 원자적으로 한다.
- **원천 쪽 증분 API**: 제공자가 통째 릴리스만 준다(현행 + 생성일).

## Consequences

- 덮어쓰는 Silver 표도 변경 기록으로 모든 판의 역사가 남는다(쌓기 원칙). 크기는 판 사이 변경량이다.
- Silver 에 `row_fingerprint` 열이 늘고, 덮어쓰기 레인 셋이 브랜치 적재로 바뀐다.
- 원천이 통째인 한 적재 때 차이 한 번(옛 판을 두 열로 한 번, 나간 행의 모습을 위해 모든 열로 한 번 읽기)은 피할 수 없다. 그 뒤 모든 층은 변경 크기에 비례한다.
- 변경 기록이 없거나 끊긴 범위는 지금 길(ADR-0189·0180)로 내려가므로 이주 중에도 정합성은 그대로다.
