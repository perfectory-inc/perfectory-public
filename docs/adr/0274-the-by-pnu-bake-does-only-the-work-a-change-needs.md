### 되돌리기 수단이 낡았다

ADR-0151 Revision 3·5 와 계약의 `fallback` 은 per-PNU 객체를 되돌리기 수단으로 남겼다: 서빙 바인딩이 `off` 인 Worker 버전으로
트래픽을 옮기거나 manifest 를 묶음 이전 판으로 되돌리면 Worker 가 객체에서 답한다(`findObject`), 그리고 모니터가 30일
깨끗할 때까지 객체를 둔다(`objects_kept_clean_days`). 그런데 묶음 굽기는 객체를 쓰지 않는다. parcel 은 10-16 22:49
묶음 세대 3 발행부터 객체가 서빙 문서와 다르다(그 뒤 매시간 모니터가 "객체와 차이 4"로 실패, #689 가 그 비교를 은퇴시켰다).
building 레인도 같은 굽기다. 지금 그 수단을 당기면 **묶음보다 오래된 문서를 오류 없이 서빙한다** — 장애보다 나쁜, 보이지
않는 오답이다. 오늘 운영 parcel Worker(100% 버전 `6be8f812`, 10-15)는 바인딩 `on` 이라 객체를 읽지 않는다.

묶음 쪽에는 이미 되돌리기가 있다: 대체된 묶음 세대와 그 세대를 이름한 manifest 기록은 다음 세대가 서빙된 지 7일 동안
남는다(ADR-0242, `superseded_generation_keep_days`). 패치는 그 기본 세대 아래에 남으므로, 나쁜 패치는 그 패치가 없던
manifest 로 되돌리면 된다. 7일이 지난 뒤의 되돌리기는 정본인 Gold 에서 다시 굽는 것이다.

`max_patches`(7) 개다(ADR-0141 §6).

## Decision (제안)

1. **같은 내용의 Gold 는 비교하지 않는다.** 생산자(`gold_incremental.build_or_merge`)는 커밋할 Gold 의 내용 지문
   — 모든 행 `row_digest` 의 순서 무관 합(SHA-256 앞 64비트의 2^64 모듈러 합)과 행 수 — 을 스냅숏 요약
   `foundation.content-fingerprint` 에 적는다. 직전 Gold 와 지문이 같으면 **커밋하지 않는다**(새 스냅숏이 없으면
   굽기는 "할 일 없음"이다). 굽기는 반영 스냅숏과 새 스냅숏의 지문이 같으면 비교 없이 reflect 한다. 지문이 없는
   옛 스냅숏은 지금처럼 비교한다. 10-17 에 아꼈을 시간: 비교 31분과 그 Gold 쓰기.
2. **누적 변경 문턱은 레인의 항목 수가 아니라 잰 손익분기에 둔다.** 한 항목 레인(오늘의 모든 레인)의
   `max_cumulative_change_ratio` 는 0.05 → **0.25**(잰 손익분기 29~52% 의 아래쪽보다 낮게). 패치 수 상한
   `max_patches`(7)·한 패치 상한 `max_delta_fraction`(0.5)·문서 스키마 변경 시 전량은 그대로다.
   계약 한 줄이고, 근거 표는 계약의 reason 으로 간다. 10-17 의 이동연혁은 패치(25~46분)가 됐을 것이다.
3. **같은 내용을 두 번 굽는 패널 레인은 웹이 종류 레인을 읽는 순간 굽기에서 뺀다.** 패널 레인의 굽기·발행은
   웹(#462, ADR-0193 §5)이 여섯 종류 레인을 읽기 시작한 뒤 은퇴한다. 그 전까지 패널 패치는 지금대로다(10-17:
   14분). 항목 단위 굽기를 섹션 묶음 안에서 다시 만들지 않는다 — 레인이 이미 그 단위다.
4. `section_packs/bake.rs` 의 "패치는 모든 항목을 쓴다"·"새 스냅숏은 모든 항목을 다시 굽는다" 규칙은 둔다.
   항목이 하나뿐인 지금은 비용이 없고, 여러 항목 레인이 다시 생기면 그때 항목별 지문(1.)으로 고친다.

5. **되돌리기 수단은 직전 묶음 세대다, 객체가 아니다.**
   - 되돌리기는 manifest 기록의 직전 판(직전 세대, 또는 문제 패치가 없던 판)으로 manifest 를 되돌리는 것이고,
     ADR-0242 의 7일이 그 창이다. 7일 뒤에는 Gold 에서 다시 굽는다. 런북의 되돌리기 절은 이 순서만 적는다.
   - parcel·building 레인을 계약에서 `pack_only: true` 로 선언한다(종류 레인·unit-price 와 같다). 그러면 Worker 는 어떤
     버전·바인딩·manifest 에서도 객체를 읽지 않고, 묶음이 없는 manifest 는 오답이 아니라 503 이다. `serving_binding`
     과 카나리의 `code`/`packs` 두 단계, 계약의 `fallback` 블록은 함께 은퇴한다(카나리는 묶음 판끼리 버전 비율로만 돈다).
   - **객체는 이 결정으로 지우지 않는다.** 서빙에서 빠진 날(`pack_only` 배포)부터 30일 그대로 둔다 — 그동안 어떤 경로도
     객체를 읽지 않음을 R2 읽기 지표로 확인할 시간이다. 그 뒤 삭제는 별도의 소유자 승인으로 한 번 한다(append-only 원칙,
     계약의 "owner decision"). 객체는 묶음보다 낡았으므로 다시 쓰일 일이 없다.

## 기각한 대안

| 대안 | 판정 |
|---|---|
| 문턱을 그대로 두고 개편 같은 일회성 변경은 수동 패치 | 기각. 사람이 판단해야 하는 일을 매번 만든다. 손익분기는 이미 쟀다. |
| 문턱을 없애고 패치 수 상한만 | 기각. 패치가 커지면 기본 세대가 낡은 채 저장소가 커지고, 레인 크기를 넘는 패치도 가능해진다. 0.5(`max_delta_fraction`)는 둔다. |
| 패널 문서를 섹션 묶음 여러 항목으로 나눔 | 기각. ADR-0151 이 Worker 의 요청별 합치기를 버린 이유가 그대로다. 종류 레인이 이미 나눠 놓았다. |
| 객체를 묶음 굽기마다 같이 갱신해 되돌리기 수단을 살림 | 기각. 굽기마다 바뀐 PNU 수만큼 PUT 이 늘고(전량이면 4천만, ADR-0193 이 금지한 비용), 지키려는 것은 이미 묶음 세대 7일이 준다. |
| 객체 경로를 남기되 모니터가 낡음을 알리게 함 | 기각. 당기면 안 되는 레버를 남기는 것이다. 낡은 문서보다 503 이 낫다(정본 Gold 에서 다시 구울 수 있다). |
| 비교를 Iceberg 스냅숏 요약의 added/deleted 수로 대신 | 기각. 전량 재생성은 같은 행도 전부 다시 쓰므로 수가 내용 변경을 말해 주지 않는다. |

## Consequences

- 10-17 같은 날이 156분에서 약 80~100분이 된다(비교 31분 절약, 이동연혁 73분 → 25~46분 패치).
- 패치가 커지면 다음 전량까지 기본 세대 위에 더 큰 패치가 얹힌다. 읽기 GET 상한(패치 7개)은 그대로다.
- 구현(승인 뒤 별도 PR): ① Gold 지문 기록·같은 지문 커밋 생략 + 굽기의 지문 비교(Python 생산자, Rust 굽기), 시험은
  같은 행의 재생성이 커밋하지 않음·지문이 다르면 비교함, ② 계약 비율 0.25 와 reason, ③ 패널 레인 은퇴는 #462
  병합 뒤 ADR-0193 의 순서대로, ④ parcel·building `pack_only: true` + `serving_binding`·`fallback`·카나리 두 단계 은퇴 +
  런북 되돌리기 절(시험: 묶음 없는 manifest 에 Worker 가 503, 객체를 읽지 않음), 30일 뒤 객체 삭제는 소유자 승인 별건.
