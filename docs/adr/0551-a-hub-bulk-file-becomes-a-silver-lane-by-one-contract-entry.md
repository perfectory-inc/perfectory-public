# ADR 0551: 건축HUB 대용량 파일은 계약 항목 하나로 Silver 레인이 된다 — 계열 레인, 주택인허가 15·건축인허가 7

- Status: Accepted
- Date: 2026-11-12
- Builds on: ADR-0092(HUB 레이아웃 계약과 스트리밍 엔진), ADR-0169(장부가 판을 고른다), ADR-0193(by-PNU 종류 표는 레인
  줄에서 파생), ADR-0318(바뀐 키만 쌓는다), ADR-0397(키 없는 행은 내용이 키), ADR-0402(같은 엔진, 레인 하나에 PR 하나),
  ADR-0415·0418(선언된 정의에서 작업·그래프 생성), ADR-0511(받은 파일은 모두 Silver 까지)
- Supersedes(부분): ADR-0402 §1·§2 의 "레인 하나에 PR 하나"와 레인마다 고치는 파일 목록 — 계열 레인에 한해서다.
  손으로 쓴 HUB 레인(표제부·전유부·기본개요 등 20개)은 그대로다

## Context

ADR-0511 은 주택인허가 16·건축인허가 나머지 7 을 Silver 로 잇기로 했다. ADR-0402 의 틀로 첫 레인(주택인허가 기본개요,
#1313)을 이으니 레인 하나가 **23 파일, 894 줄**이었다(측정: `gh pr view 1313`). 그중 엔진이 레인마다 다르게 하는 것은
없다: Rust 표 계약 102줄은 칸 이름을 문자열로 옮겨 적은 것이고, 내보내기 모듈 31줄·레인 목록(`Lane` 변형·`ALL`·id·계약·
`ExportKind`)·명령(`Command` 변형·분기·파서)·작업 정의 99줄은 모두 같은 틀에 이름만 바꾼 것이다. 표 계약 JSON 사본 177줄과
ODCS 158줄은 그 Rust 에서 생성된다.

더 나쁜 것은 **숫자**다. `Lane::ALL: [Self; 29]`, Python 시험의 레인 수(`["hub"] * 20`), 컴파일 시점 읽기 기준값
(`COMPILE_TIME_READ_BASELINE`)을 레인마다 하나씩 올린다. 두 레인 PR 은 git 충돌이 없어도 머지 큐에서 서로를 깬다
(#1313 위에 #1323 을 옮길 때 세 숫자를 31·31·170 으로 손으로 합쳤다). 22 개를 이 틀로 하면 22 번 줄을 서야 한다.
작업도 문제다: Silver 갱신은 템플릿 유닛 하나(`foundation-silver-refresh@.service`, 한도 150분 고정)라 레인 하나가 작업
하나이고, 각 작업이 spark 풀 3칸을 최대 160분 잡는다. 22 개를 더하면 풀 대기 상한 검사(`job_specs.pool_starvation`)에서
`parcel_tile_bake` 의 최악 대기가 16,150분으로 한도 14,400분(12시간 주기 × 20)을 넘는다(2026-11-12 계산).

**실측(2026-11-12, 운영 장부 최신 판 2026-10, R2 읽기 전용 키, 22 파일 끝까지).** 22 개 모두 `|` 구분·UTF-8·머리줄
없음·멤버 하나이고, 최신 판 ZIP 합 981,211,224 바이트다. 칸 수는 제공자 OpenAPI(주택인허가 HsPmsHubService data.go.kr
15136560, 건축인허가 ArchPmsHubService 15136267)의 해당 작업 항목 수와 20 개가 같고, 주택인허가 전유공용면적(25칸, 명세 24)과
관리공동형별개요(44칸, 명세 43, 사업주체명 없음)만 다르다. 대용량 파일의 칸 순서는 OpenAPI 명세 순서가 아니라 **PK 들 → 대지위치 →
(PK 와 특수지명 사이 항목: 건물명·행정동코드·대표여부) → 지번 다섯 → 특수지명·블록·로트 → 나머지는 명세 순서**다. 이 규칙은
이미 실측된 두 레이아웃(건축인허가 동별개요 ADR-0402, 주택인허가 기본개요 ADR-0511)을 그대로 재현하고, 22 개 파일의 칸마다
모양(시군구·법정동 5자리, 대지구분 1자리, 번·지 4자리, 날짜 8자리, 면적 소수, 생성일자 모든 행 8자리)과 맞는다. 맞지 않은
곳은 건축인허가 주택유형 칸 13·14(면적이 소수·세대수가 정수)와 주택인허가 대지위치 칸 1·2(대표여부 한 자리가 대지위치
앞)로, 모양대로 붙였다. 칸 수가 다른 두 파일은 모양이 확인한 칸(키·지번 다섯, 관리공동형별개요는 사용검사일까지)만 이름을
붙인다.

칸 수가 다른 줄은 6 개 파일에 있었다: 건축인허가 전유공용면적 20·호별전유공용면적 20·호별개요 4, 주택인허가 동별개요 24·
층별개요 52·호별개요 4 줄. 모두 **값 안의 줄바꿈**이 행을 자른 것이다: 앞뒤 줄을 이으면 정확히 그 파일의 칸 수다. 따옴표는
값 안의 글자(인치 표기 등)로만 있고, 칸 수가 다른 줄 중 `"…"` 인용으로 읽으면 맞는 줄은 0 이다. 지금 엔진은 그런 줄을 "칸 수가 다르다" 로 거부하고 세기만 하므로
그 행들은 Silver 에 오지 않는다.

### 실사례

- **선언형 커넥터.** Airbyte 의 Low-code CDK(`manifest.yaml`)와 Singer/Meltano 의 tap 설정은 스트림 하나를 YAML 항목
  하나(스키마·기본키·커서)로 선언하고, 엔진·스케줄·카탈로그는 그 항목에서 만든다. 새 스트림은 코드 변경이 아니다.
  dbt 의 `sources.yml` 도 같다: 원천 표 하나가 항목 하나이고, 테스트·문서·계보는 항목에서 생성된다.
- **스트림 여럿, 동기화 작업 하나.** Airbyte 의 연결(connection) 하나는 스트림 여러 개를 한 동기화 작업으로 돌리고,
  스트림마다 상태(커서)를 따로 남겨 끊긴 작업이 다음 동기화에서 잇는다. Fivetran 의 커넥터도 표마다 따로 일정을 잡지 않는다.
- **정본 하나에서 나머지를 생성.** Backstage 의 `catalog-info.yaml`, Dagster 의 asset factory(`@multi_asset` 를 설정 목록에서
  찍어 냄)는 목록을 손으로 세지 않는다. 이 저장소의 by-PNU 종류 표(ADR-0193)와 선언된 정의(ADR-0415)가 같은 구조다.
- **줄바꿈 낀 값.** RFC 4180 CSV 는 줄바꿈을 인용으로 감싸 허용하고, 인용 없는 파일을 읽는 도구(PostgreSQL `COPY`
  의 `text` 형식, Spark CSV `multiLine`)는 칸 수가 찰 때까지 다음 줄을 붙이는 방식을 쓴다. 칸 수가 정해진 고정 레이아웃에서
  "칸 수가 모자라면 다음 줄로 채운다" 가 그 규칙이다.

## Decision

1. **계열 파일.** `platforms/foundation-platform/infra/lakehouse/contracts/hub-lane-family-<계열>.v1.json`(지금
   `housing-permit`, `building-permit`)의 `lanes` 항목 하나가 Silver 레인 하나다. 항목은 ZIP 멤버, 칸 수, 키 규칙
   (`column`: 칸 0 이 모든 행에 채워지고 서로 다를 때 그 칸이 `mgmt_key`, 아니면 `sha256_of_row`), 비교 묶음 폭(행 300만
   넘으면 2), 이름 붙인 칸(`이름: [index, 뜻]`), 실측, 표 설명, 첫 실행 추정이다. 계열이 함께 쓰는 값(Spark 크기, 판 크기,
   작업 틀)은 파일의 `defaults` 다.
2. **나머지는 모두 파생한다. 레인을 세는 숫자나 목록은 없다.**
   - 이름: 항목 이름 `<id>` 가 레인·systemd 인스턴스, `hubgokr__<id 의 _>` 가 Bronze 원천, `silver.<id 의 _>` 가 표,
     `export-<id>-silver-handoff` 가 내보내기, `FOUNDATION_PLATFORM_<ID>` 가 환경 앞머리다.
   - Rust: `lakehouse-domain` `hub_lane_family` 가 표 계약(`mgmt_key`, 이름 붙인 칸을 파일 순서로, `pnu`·`raw_columns`·
     계보·`row_state`; `LatestPerKey` ADR-0328)과 원천 계약(손 레인의 `hub-*-source-objects.json` 과 같은 모양)을 짓는다.
     표는 `industrial_complex_lakehouse_contracts()` 에 들어가 Spark 산출물·ODCS 가 그대로 생성된다. Silver 갱신의
     `Lane::all()` 은 손 레인 목록(`HAND`, 개수 없는 슬라이스)과 계열 레인이고, 내보내기 명령은 계열 조회로 연결된다.
   - 작업·그래프: `scripts/catalog/declared_definitions.py` 가 항목마다 자산·엣지를, 계열 전체에 **작업 하나**
     (`silver_refresh_hub_lane_family`, `foundation-silver-refresh@hub-lane-family`)를 짓는다. 같은 이름의 정의 파일이
     있으면 거부한다. Dagster 자산 그룹(`observe_assets`)과 그래프 가드(`pipeline_graph.py`)도 계열 파일을 읽는다.
   - 실행: 계열 작업의 한 실행은 계열 레인을 이름순으로 하나씩 돈다. 판이 이미 표에 있는 레인은 장부와 표 기록만 읽고 수 초에
     끝난다. 실행의 마감(ADR-0391)에 걸린 레인이 실행을 끝내고 다음 실행이 거기서 잇는다(적재 묶음·비교 묶음은 커밋된 만큼
     남는다). 레인마다 `silver-refresh-lane …` 줄을, 마지막에 계열의 `silver-refresh-outcome lane=hub-lane-family` 줄을
     남기고, 한 레인이라도 바뀌면 `changed` 다. 그래서 풀은 계열이 한 번만 잡는다(위의 대기 상한이 그대로 든다).
   - 시험: 엔진 시험은 항목마다 합성 행(99999)을 만들어 변환하고 칸 배치·PNU·키를 확인한다. 레인마다 시험 파일을 쓰지 않는다.
3. **칸 배치 규칙과 근거.** 칸 뜻은 OpenAPI 항목명(낙타 표기를 밑줄 표기로, 지번 다섯은 `sigungu_cd`·`bjdong_cd`·
   `san_gubun`·`bonbeon`·`bubeon`)이고, 위의 대용량 순서 규칙으로 놓은 뒤 칸마다 실측 모양과 맞춘 결과를 `how_measured` 에
   적는다. 대지위치·건물명·특수지명·블록·로트·생성일자는 손 레인처럼 `raw_columns` 의 원래 index 로만 둔다(ADR-0402 §3).
4. **줄바꿈 낀 값은 잇는다.** 항목의 `broken_lines`(실측 행 수)가 있으면 엔진은 칸이 모자란 줄에 다음 줄을 `\n` 으로 붙여
   칸 수가 찰 때까지 잇는다. 넘치면 이은 줄 모두를 거부하고 센다. 행 번호는 첫 줄의 번호이고, 이은 줄 수는 매니페스트의
   `joined_lines` 다. 이 규칙은 손 레인에도 같은 `joins_broken_lines` 로 켤 수 있다.
5. **화면은 다음 단계.** Silver 표는 소비자가 서기 전까지 `contract_only` 다(그래프 규칙). 주택인허가는 ADR-0511 §2 대로
   건축인허가 by-PNU 레인의 문서에 실린다(#1314 가 기본개요부터).
6. **PNU 와 코드 변경.** 엔진이 HUB 코드로 PNU 를 짓고(ADR-0145), 합병·분할·법정동 변경은 소비자가 place-identity 해석기와
   `views.changed_codes`(ADR-0329 §3)로 따라간다. 적재 때 한 번 풀고 멈추지 않는다.

## Consequences

- 새 HUB 대용량 레인은 계열 파일의 항목 하나(약 25–45 줄)다. 다른 레인과 같은 파일을 고치지 않고(항목은 이름순이라 서로
  다른 곳에 들어간다), 숫자를 올리지 않는다. 생성되는 Spark 표 계약 산출물·ODCS 는 그대로 생성한다.
- 첫 적재는 계산으로 22 레인 합 13,720 초, 실행 하나가 마감까지 약 8,100 초라 두 번의 실행에 걸친다.
- 22 레인이 한 PR 로 들어온다(ADR-0402 §1 의 "한 PR 에 두 레인을 싣지 않는다" 는 계열 레인에 적용하지 않는다: 같은 규칙에서
  나온 항목이고, 시험이 항목마다 같다).
- 손 레인 20 개는 이 ADR 로 옮기지 않는다. 그중 특수한 것(부속지번의 두 번째 PNU, 정기점검의 `parcel_link`, 월별 에너지의
  이은 키)은 계열이 표현하지 않는다. 단순한 것은 같은 표 모양이라 옮길 수 있고, 옮길 때는 표 계약이 바이트까지 같은지
  산출물 시험이 확인한다.
- **비용(계산).** 22 개 Bronze 는 이미 받고 있다(최신 판 ZIP 합 0.98 GB). Silver 첫 적재는 판당 원문의 수분의 일인
  Parquet 이고 이후는 바뀐 키만 쌓는다. R2 $0.015/GB·월, 1,450원/$ 로 22 개 합쳐 월 100원 아래다. 계산은 ai-server Spark
  풀에서 돌고, 첫 실행 추정은 계열 작업의 `first_run` 이다(이웃 실측 기준 2.5 배).
