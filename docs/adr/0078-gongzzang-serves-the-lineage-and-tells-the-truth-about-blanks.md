# ADR 0078: 공짱은 계보를 서빙하고, 빈 칸을 거짓으로 채우지 않는다

- Status: Accepted
- Date: 2026-09-04

## Context

root ADR-0076 이 기반 플랫폼에 계보 API 를 열었다: 건물 자원, keyset 페이지의 호 목록,
그리고 "대장이 말하지 않은 값은 null" 이라는 읽기 계약. 공짱은 그 소비자인데 두 가지가
어긋나 있다.

1. **공짱의 소비 사슬이 옛 계약을 약속한다.** `foundation-platform-client` 의
   `CatalogBuildingResponse` 는 `purpose_code: String`·`floor_area_m2: f64`·
   `built_year: i32` 로 값을 강제하고, 리더는 `stories` 를 `u8` 로 좁히며, B2C 응답과
   화면(`b.total_area_m2.toLocaleString()`)까지 그 강제가 이어진다. 상류가 정직해진 지금,
   null 을 실은 첫 건물에서 이 사슬 전체가 역직렬화 오류로 끊긴다 — ADR-0076 이 기반
   쪽에서 고친 것과 똑같은 읽기 모델 지연이, 한 저장소 건너에 하나 더 있었다.
2. **호는 아무 데도 나오지 않는다.** 사용자가 "이 건물에 무슨 호실이 있는가"를 볼 경로가
   화면에도 B2C API 에도 없다 — 1,940만 연결이 서비스 관점에서는 아직 빈손이다.

## Decision

1. **소비 사슬이 상류의 null 을 따라간다.** 클라이언트 DTO 다섯 칸이 `Option` 이 되고,
   리더 레코드와 B2C 응답의 해당 칸도 부재를 싣는다. B2C 계약은 공짱 소유이므로 부재
   표기는 공짱의 기존 관례(`skip_serializing_if` — 키 생략)를 따르고, 화면은 빈 값을
   "-" 로 그린다 — 0 이나 지어낸 수로 채우지 않는다.
2. **`GET /api/buildings/:building_id/units` 를 연다.** 기존 `/api/buildings` 와 같은
   노출 등급(authenticated_user)·같은 리더 포트 패턴. 응답은
   `{ units: [...], next_cursor }` 이고 **커서는 불투명 통과다** — 공짱은 상류가 발급한
   커서를 해석·저장·조립하지 않고 그대로 되돌려 보낸다. 상류가 커서를 거부하면(400)
   그 거부를 그대로 400 으로 전달한다.
3. **정책 레지스트리가 경로의 정본이다.** 프록시·백엔드 정책 두 항목을
   `traffic-auth-policy-registry.v1.json` 에 더하고, TS 프록시 클라이언트는 생성기로만
   갱신한다 — 손으로 고친 생성물은 다음 생성이 지운다.
4. **화면은 건물 패널에서 호를 편다.** 건물 항목을 펼치면 첫 페이지를 부르고,
   `next_cursor` 가 있으면 "더 보기"가 다음 페이지를 잇는다. 한 건물이 호 5,372개를
   실측으로 가지므로, 전체를 한 번에 그리는 UI 는 만들지 않는다.

## Consequences

- 사용자가 처음으로 필지 → 건물 → 호 3층을 화면에서 본다. 인증 붙은 소비가 생기므로,
  ADR-0076 이 남긴 "인증 포함 E2E 증명" 부채가 실사용으로 닫힌다.
- 클라이언트 크레이트의 경계 테스트는 null 변형 픽스처를 얻는다 — 값이 강제로 남아
  있으면 테스트가 먼저 끊어진다.
- 호 레코드의 B2C 칸은 기반 응답의 부분집합으로 시작한다(동·호·층·면적·용도). 칸 추가는
  공짱 계약의 결정이지 기반 계약의 복사가 아니다.
